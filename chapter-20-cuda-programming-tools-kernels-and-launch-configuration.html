CUDA programming: tools, kernels, and launch configuration

Adding 1003 pairs of numbers with four blocks of 256 CUDA threads launches 1024 threads. Exactly 21 must avoid the array, and the host must wait for the result before inspecting or freeing its storage. A program can get the sum formula right while violating either condition. The running case turns this short addition into an explicit protocol: allocate valid objects, copy the required data, launch a bounded set of threads, detect errors, establish completion, validate every output and release the allocations.

Grounded in NPTEL High Performance Scientific Computing, IIT Bombay: W8L1, An Introduction to GPU Programming: Tools, Techniques, and CUDA, Part 1, and W8L2, Part 2. Lecture material: programming approaches, CUDA execution flow, function and variable qualifiers, vector types, launch dimensions and built-in variables, memory functions, atomics, synchronization, device queries, errors and compiler options. Research extensions: CUDA language and runtime documentation establish API semantics; installed CUDA 13.3 headers check names and types; NVIDIA's compiler manual separates host and device flags; AMD's HIP guide, Kokkos documentation and the SYCL specification qualify portability claims; tool documentation identifies suitable correctness and profiling checks. Original teaching constructions: the checked vector-add protocol, layout and storage-lifetime example, bounded midpoint-integration reduction, safe launch-error diagnostic, timing boundaries, ownership proofs and six worked exercises.

Objects, owners, and completion form the CUDA program

The host is the CPU side of the application; the device is the selected graphics processing unit, or GPU. CUDA is NVIDIA's parallel computing platform and programming model. A kernel is a device entry function launched over many logical threads. A block groups threads that can cooperate through block-local shared memory and synchronization, and a grid contains the blocks of one launch. These are software execution units; their indices do not permanently identify physical arithmetic processors.

Let \(n\) be the number of pairs to add. Host arrays \(a^{(H)},b^{(H)},c^{(H)}\) and device arrays \(a^{(G)},b^{(G)},c^{(G)}\) represent separate objects in the explicit-copy model. Superscripts identify their memory role. The desired output is \(c_i^{(H)}=a_i^{(H)}+b_i^{(H)}\) for indices \(0\le i\lt n\). An address stored in a host variable is not the array itself and is not evidence that a GPU can dereference the corresponding CPU allocation.

For a one-dimensional launch, let \(u\) be threads per block, \(g\) the block count, \(b\in\{0,\ldots,g-1\}\) a block index and \(r\in\{0,\ldots,u-1\}\) a thread's local index. The candidate array index is \(i=bu+r\). The launch creates \(p=gu\) logical threads, while useful work consists of \(n\) additions. These counts can differ. We choose \(g=\lceil n/u\rceil\) for positive \(n\), then guard accesses with \(i\lt n\). An empty problem skips the launch.

Each 32-bit single-precision floating-point (FP32) value occupies \(s=4\) bytes in the examples. An input allocation requires \(ns\) bytes. The verification version adds two sentinel values around the output, so its output allocation requires \((n+2)s\). A sentinel is a known value placed beside useful storage to detect some accidental writes outside that storage. It supplements the index proof and full payload check; two unchanged sentinels cannot prove that every possible invalid access was absent.

A stream is an ordered sequence of submitted CUDA work. These examples use one default stream, with no attempt to overlap separate streams. Required copies precede their consumers in that ordering. A kernel launch is asynchronous with respect to the host: submission can return before the kernel finishes. Completion must be established before the host consumes a device-produced result or considers the operation finished. A host wait is distinct from threads meeting at a device barrier. CUDA Runtime API, synchronization behavior.

Three timing intervals will be kept separate. A host interval around submission measures how long the CPU spends submitting work; it need not include completed device computation. CUDA events surrounding a kernel measure a device-timeline interval, denoted \(T_{\mathrm{dev}}\). A host steady-clock interval from before allocation to after copying results and freeing device storage is \(T_{\mathrm{alloc-free}}\). It includes a larger workflow. Neither can be called whole-application runtime if initialization, input generation or validation lies outside it.

The local execution target is an NVIDIA GeForce RTX 3050 Laptop GPU with 4 GB nominal memory, compute capability 8.6, under WSL 2. Compute capability identifies a CUDA hardware feature generation; it is different from toolkit version. The installed toolkit is CUDA 13.3. The programs compile for the visible device with -arch=native, bound allocations well below 500 MB and check all runtime calls and launch status. Every successful performance observation is conditional on the accompanying numerical validation.

Choose an expression of parallel work, then check its implementation W8L1 0:06

GPU programming approaches divide responsibility differently. Standard-language parallel algorithms can expose work through ordinary C++ interfaces and a suitable implementation. Directive-based models such as OpenACC and OpenMP annotate regions and data movement. Explicit kernel models express device functions and launches directly. Portable abstraction libraries and heterogeneous-language systems provide a common interface with multiple backends. Higher-level languages call GPU libraries or compile selected functions. These categories overlap: a Python library can ultimately launch CUDA kernels, and a C++ abstraction can select a CUDA backend.

The lecture's inventory names NVIDIA's compiler support for C++ and Fortran, OpenACC, OpenMP, CUDA, HIP, Alpaka, Kokkos, OpenCL, RAJA, SYCL, Python packages such as CuPy, cuDF, PyCUDA and Numba, and Julia's device packages. This is a map of interfaces, not a promise that every combination supports every GPU, language feature or numerical library. A standard syntax alone does not ensure that a particular compiler offloads it to the selected device.

Portability has several meanings. Source portability concerns whether source code can be built for another target. Binary portability concerns whether the same compiled artifact executes there. Performance portability concerns whether performance remains acceptable after changing targets. Supporting the first does not establish the other two. A mathematical algorithm can be portable while its explicit runtime calls and launch syntax require a backend or translation layer.

HIP belongs in this discussion rather than in an absolute AMD-only box. AMD's HIP porting guide describes testing converted code on an NVIDIA machine before building it for AMD. That is a concrete counterexample to interpreting the lecture's non-portable-kernel category as a universal restriction on HIP source. It does not imply that an arbitrary CUDA executable runs unchanged on AMD hardware. HIP porting guide, ROCm 6.4.1, Porting a CUDA Project.

Kokkos documents CUDA, HIP and SYCL execution spaces. SYCL 2020 defines a heterogeneous C++ model with implementation-dependent backends. These sources support checking a specific implementation and enabled backend rather than inferring device support from a label. They do not establish that every feature or vendor library has a portable equivalent. Kokkos execution spaces; SYCL 2020 revision 12, §§2–3.

For the running case, explicit CUDA makes ownership and completion visible: the host creates inputs, the runtime allocates device storage, the kernel owns disjoint outputs, and the host validates the completed result. An abstraction could automate portions of this protocol, but its underlying dependencies would remain. Learning the explicit form therefore helps diagnose a high-level application's transfers or synchronization without requiring every scientific application to be rewritten in low-level CUDA.

The explicit-copy protocol has a dependency at every transition W8L1 7:04

The execution flow starts with host allocation and input initialization. A C++ vector owns a host allocation and releases it when destroyed. Its data() member yields an address suitable for a copy operation while the vector remains valid. Creating a host vector named a does not allocate a device array. Likewise, copying a pointer variable copies only an address value; it does not transfer the array to which it points.

cudaMalloc obtains device storage and writes its address into a host pointer variable. The size argument counts bytes, so allocating n FP32 elements requires n * sizeof(float), not merely n. Newly allocated storage does not supply the scientific input values. The application initializes it by a host-to-device copy, a device kernel or another specified mechanism. cudaMemcpy takes destination first, then source, byte count and direction; cudaFree releases the device allocation. These names come from the runtime memory API. CUDA Runtime API, Memory Management.

For vector addition, the required chain is input initialization, input copies, kernel reads and writes, result copy, host validation. Each step depends on the previous producer of the data it consumes. An output need not normally be copied to the device first if the kernel overwrites every useful element. Our diagnostic version intentionally initializes the output and both guards before launching so it can detect missing writes and guard corruption. That extra transfer is part of its measured allocation-to-free workflow.

The host arrays must remain valid while a transfer uses them; device arrays must remain valid while kernels or transfers use them. Releasing an allocation and retaining its pointer leaves a stale address, not a valid object. Lifetime reasoning should establish completion explicitly rather than depend on an incidental wait that a particular allocation or deallocation routine may perform. The examples synchronize before reading results and before freeing storage used by their kernels.

Copy completion also needs an exact description. With pageable host memory, a host-to-device cudaMemcpy may return after staging data while the final device transfer is still pending. A device-to-host copy returns after its copy is complete. Stream ordering places our subsequent kernel after the required input copies. Thus the protocol is valid without the stronger, incorrect rule that every routine whose name lacks Async always blocks until every device activity is complete. Runtime API, synchronous memcpy cases.

The CUDA macro in the listings evaluates one API call, checks its cudaError_t return value against cudaSuccess, and prints the failing expression and diagnostic before terminating on an unexpected error. It does not turn asynchronous work into synchronous work. After a kernel launch, cudaGetLastError checks launch status, and a later checked completion operation detects failures reported while device work executes. The complete error model is developed after the synchronization example.

This structure resembles a resource protocol more than a translated scalar loop. Its correctness argument has three parts: valid storage, unique and in-bounds work ownership, and producer-before-consumer ordering. A numerical checksum alone tests none of these exhaustively. Conversely, passing API checks alone does not establish that the kernel computed the intended function. The examples combine API checks, explicit dependency reasoning and payload comparisons.

Function placement and storage lifetime are separate declarations W8L1 10:33

A CUDA execution qualifier describes where a function can execute. A function marked __global__ is a kernel entry point; the ordinary launches here originate on the host and execute on the selected device. It returns void, while results are written to storage supplied through parameters. A __device__ function is callable from device code and executes there. A __host__ function executes on the host; an ordinary unqualified C++ function has this host role. Combining __host__ __device__ permits compiling corresponding host and device implementations of the same source function. This does not make every library called inside it available in both environments.

A device function call is not a remote call from one GPU to another. The qualifier itself provides no cross-device execution protocol. Similarly, placing a host pointer in a kernel argument does not change the allocation it identifies. The function's execution space and each pointed-to object's accessibility must both be correct. NVIDIA's language-extension reference defines these execution-space annotations independently of the memory annotations. CUDA Programming Guide §5.4.1.

The same spelling __device__ also appears on variables, with a different role. A file-scope device variable resides in device global memory and persists across kernel invocations within the CUDA context's lifetime. A context holds device execution and resource state; it is more precise here than simply calling every device variable's lifetime the host application's lifetime. Separate devices have their own relevant instances. Host code accesses the symbol through the appropriate runtime operations rather than directly dereferencing an ordinary host variable with the same name.

A __constant__ variable supplies device-readable constant storage. The host can initialize it through a symbol copy when no concurrent kernel accesses that object. “Constant” therefore describes device-side access, not a claim that its value can never be changed by the host. A __shared__ array supplies separate block-local storage, visible to that block's threads and valid for that block's execution. It does not retain a previous block's scientific values for the next invocation, and sharing its address does not make it a grid-wide array.

A __managed__ variable can be accessed by host and device under Unified Memory's rules. Address accessibility does not remove ordering requirements: the host must not inspect a value while the kernel is updating it without an appropriate supported protocol. Our example writes the managed counter on the host before launching, increments it on the device, and reads it only after a checked device synchronization. It does not rely on concurrent CPU/GPU atomic access or claim that managed storage has no migration cost.

__restrict__ addresses a different issue: pointer aliasing. Aliasing means that pointers designate overlapping storage. A restricted pointer communicates an access promise that can permit the compiler to reuse loaded values or reorder operations. It neither allocates a new region nor checks that the promise is true. The vector-add program satisfies a simple sufficient condition by allocating independent input and output regions. A caller must not then replace an output pointer with an overlapping input merely because a particular test seemed to work. Read-only input relationships and the full language rules are subtler than “no other pointer may ever contain the same address.”

Scope, placement, lifetime and synchronization answer different questions. A block-local shared array can have several writers and still require a barrier before one thread reads their contributions. A long-lived global counter can race despite remaining allocated. A managed object can be accessible from both processors yet require a host wait. The declaration table supplies objects for the protocol; it does not supply the protocol itself.

Vector types group components; launch dimensions count threads W8L1 20:56

CUDA's built-in vector types group one through four scalar components. A float2 can represent a planar point's two coordinates, a float3 a three-dimensional position, and a float4 four color components such as red, green, blue and alpha. Components are named x, y, z and w where present. The helper make_float2 constructs a two-component value. These are C++ structures, not an assertion that each arithmetic expression automatically becomes a packed single-instruction, multiple-data (SIMD) instruction, which applies one instruction to multiple data lanes.

Layout has two relevant quantities. Size is the number of bytes occupied by an object, including any padding. Alignment constrains the addresses at which objects may begin. The installed CUDA types give float2 size/alignment 8/8 bytes, float3 12/4 and float4 16/16. In particular, three components do not imply a sixteen-byte object. The next program checks these properties instead of assuming that all vector types share one alignment rule.

Grouping coordinates improves representation when they belong together, but does not guarantee efficient memory transactions. If successive threads access successive float3 records but only their x members, requested addresses are twelve bytes apart. Three separate coordinate arrays instead give adjacent four-byte requests for the same field. If every operation needs every coordinate, a different tradeoff can apply. Coalescing concerns the addresses requested by a group of threads, not merely whether one thread's object has consecutive fields. Deeper layout optimization follows in the memory chapters.

dim3 serves another purpose. It stores three unsigned components used for launch dimensions. Missing constructor arguments default to one: dim3(5) is (5,1,1), not (5,0,0). The total represented count is the product of its dimensions. Thus (5,5) describes twenty-five positions, and (5,5,5) one hundred twenty-five. These are counts, not the largest valid indices; a dimension five has indices zero through four. The installed vector header and language reference agree on these defaults and layouts. CUDA Programming Guide §5.4.2, built-in types and variables.

The following complete example checks layout, omitted dimensions and storage lifetime. It launches one block of thirty-two threads twice, using the basic launch form sample<<<1,32>>>. Each thread puts its index plus one into a shared array, all threads reach the barrier, and thread zero sums the thirty-two entries and adds a constant bias of one half. The sum is \(1+\cdots+32=32\cdot33/2=528\), so each result should be 528.5. Only that single thread updates the counters, and the launches are ordered; this example does not require an atomic increment.

#include <cuda_runtime.h>
#include <cstdio>
#include <cstdlib>

#define CUDA(call) do { cudaError_t e = (call); if (e != cudaSuccess) { \
    std::fprintf(stderr, "%s: %s\n", #call, cudaGetErrorString(e)); \
    std::exit(1); } } while (0)

__device__ int device_calls;
__constant__ float bias;
__managed__ int managed_calls;

__host__ __device__ float component_sum(float2 p) { return p.x + p.y; }
__device__ float device_value(unsigned t)
{
    return component_sum(make_float2((float)t, 1.0f));
}

__global__ void sample(float *out, int pass)
{
    __shared__ float values[32];
    unsigned t = threadIdx.x;
    values[t] = device_value(t);
    __syncthreads();
    if (t == 0) {
        float sum = 0;
        for (unsigned j = 0; j < 32; ++j) sum += values[j];
        out[pass] = sum + bias;
        ++device_calls;
        ++managed_calls;
    }
}

int main()
{
    CUDA(cudaSetDevice(0));
    dim3 one(5), two(5,5), three(5,5,5);
    std::printf("float2 size=%zu align=%zu; float3 size=%zu align=%zu; "
                "float4 size=%zu align=%zu\n", sizeof(float2), alignof(float2),
                sizeof(float3), alignof(float3), sizeof(float4), alignof(float4));
    std::printf("dim3(5)=(%u,%u,%u); dim3(5,5)=(%u,%u,%u); "
                "dim3(5,5,5)=(%u,%u,%u)\n", one.x,one.y,one.z,two.x,two.y,two.z,
                three.x,three.y,three.z);
    if (sizeof(float2)!=8 || alignof(float2)!=8 || sizeof(float3)!=12 ||
        alignof(float3)!=4 || sizeof(float4)!=16 || alignof(float4)!=16 ||
        one.y!=1 || one.z!=1 || two.z!=1) return 2;
    int zero = 0;
    float half = 0.5f;
    CUDA(cudaMemcpyToSymbol(device_calls, &zero, sizeof(zero)));
    CUDA(cudaMemcpyToSymbol(bias, &half, sizeof(half)));
    managed_calls = 0;
    float *out;
    CUDA(cudaMalloc(&out, 2*sizeof(float)));
    for (int pass = 0; pass < 2; ++pass) {
        sample<<<1,32>>>(out, pass);
        CUDA(cudaGetLastError());
    }
    CUDA(cudaDeviceSynchronize());
    float result[2];
    int calls;
    CUDA(cudaMemcpy(result, out, sizeof(result), cudaMemcpyDeviceToHost));
    CUDA(cudaMemcpyFromSymbol(&calls, device_calls, sizeof(calls)));
    float expected = half;
    for (unsigned t = 0; t < 32; ++t)
        expected += component_sum(make_float2((float)t, 1.0f));
    if (result[0]!=expected || result[1]!=expected || calls!=2 || managed_calls!=2)
        return 3;
    std::printf("shared sums=%.1f,%.1f device_calls=%d managed_calls=%d checked=2\n",
                result[0],result[1],calls,managed_calls);
    CUDA(cudaFree(out));
    return 0;
}

The host/device helper is used in both execution spaces, while device_value is device-only. The host initializes the device and constant symbols through symbol-copy APIs. Shared entries are initialized afresh in each launch, while the global and managed counters persist and accumulate two calls. The host reads them after synchronization. All values in this small sum are exactly representable, making exact comparisons appropriate for this test. That justification will not apply to the general floating-point reduction later in the chapter.

A launch specifies a set of indices, not just a thread count W8L2 0:06

Inside a kernel, gridDim gives the grid's dimensions in blocks and blockDim the block's dimensions in threads. blockIdx identifies the current block and threadIdx the thread within that block. Counts and indices differ: for a one-dimensional block of 256 threads, blockDim.x is 256 while threadIdx.x ranges from zero through 255. The built-in objects are device-side values, not host variables to read before launching.

The form kernel<<<grid,block,shared_bytes,stream>>>(arguments) separates execution configuration from ordinary function parameters. The first two entries choose grid and block dimensions. The third specifies additional dynamic shared-memory bytes per block; it does not mean a single shared array for the whole grid. The fourth selects a stream. Omitting the last two uses zero dynamic shared bytes and the default stream. The function name and argument list must match the declared kernel; the lecture's launch slide accidentally uses kernel where its second declaration names myKernel.

In the vector-add source, \(i=bu+r\) becomes (size_t)blockIdx.x * blockDim.x + threadIdx.x. Conversion before multiplication prevents the product from first overflowing a narrower integer type. Bounds also depend on the input domain: our listed lengths are small enough for their byte counts and grid dimensions. General-purpose input handling would additionally reject lengths whose multiplication by element size overflows size_t.

For positive \(n\), the ceiling calculation can be written without forming \(n+u-1\):

\[ g=\left\lfloor\frac{n}{u}\right\rfloor+\mathbf 1_{n\bmod u\ne0}.\tag{20.1} \]

The indicator \(\mathbf 1\) is one when its condition holds and zero otherwise. Equation (20.1) avoids an unnecessary addition-overflow risk. For 1003 entries and 256 threads per block, quotient three and nonzero remainder give four blocks. Their candidate indices span zero through 1023. The guard rejects precisely indices 1003 through 1023.

Every useful index has a unique writer. Euclidean division gives \(b=\lfloor i/u\rfloor\) and \(r=i\bmod u\), so a useful index belongs to exactly one launched thread. Conversely, each thread that passes the guard has a valid input and output index. Independent input arrays are read-only and each output is written once. No block barrier is needed for this elementwise kernel because no thread consumes another thread's intermediate result.

A valid dimension component does not by itself prove a valid block. The product of the block's three dimensions must obey the total-thread limit, each component its own limit, and the grid components their grid limits. Resource use can impose additional kernel-specific restrictions. The program queries relevant device limits rather than importing the recording's illustrative count of streaming multiprocessors (SMs), the GPU hardware units that host resident thread blocks. Block dimensions also describe a software arrangement, not a permanent placement on a chosen SM.

Byte counts, copy directions, and timing boundaries belong in the interface W8L2 7:28

The comparison with C's malloc, memcpy, memset and free is useful provided their roles remain distinct. A CUDA allocation is not initialized by allocating it. A copy transfers bytes rather than converting element types. A byte count must match both the source's readable extent and destination's writable extent. The direction argument must describe the pointers actually supplied; exchanging source and destination does not merely reverse an abstract mathematical arrow.

cudaMemset fills bytes. Setting an integer array's bytes to one produces a repeated-byte bit pattern, not an array of integer ones. In a 32-bit integer this pattern is hexadecimal 01010101, or 16843009. A zero byte fill is useful for the IEEE binary floating-point zero used in the reduction accumulator. Other numerical initial values should be supplied by a typed initialization or a kernel. The distinction between a value and its byte representation is part of the memory API contract.

The next program uses host C++ vectors and three independent device allocations. For each positive length it copies inputs, initializes an output with two guards, launches a bounded kernel, waits on a recorded event, copies all outputs back and frees device allocations. It validates every useful result and both guards after the measured host interval. The chosen quarter- and half-integer inputs make their sums exactly representable, allowing exact checks here. The total device allocation is \((3n+2)s\), about 12 MiB at the largest tested length.

Three block sizes, 128, 256 and 512, are tested against empty, singleton, boundary-adjacent and nonmultiple lengths. With \(n=0\), the host skips allocation and launch rather than requesting a zero-block grid. The inactive field reports \(gu-n\), the number of launched threads rejected by the guard. The printed output is a sample run: both timing fields vary, so the execution contract checks successful exit after the program's own full validation. Its field named kernel_us is the event-to-event interval around submission of one kernel, including any intervening idle gaps, rather than isolated GPU busy time.

#include <cuda_runtime.h>
#include <chrono>
#include <cstdio>
#include <cstdlib>
#include <vector>

#define CUDA(call) do { cudaError_t e = (call); if (e != cudaSuccess) { \
    std::fprintf(stderr, "%s: %s\n", #call, cudaGetErrorString(e)); \
    std::exit(1); } } while (0)

__device__ float add_values(float a, float b) { return a + b; }
__host__ float reference_value(float a, float b) { return a + b; }

__global__ void vector_add(const float *__restrict__ a,
                           const float *__restrict__ b,
                           float *__restrict__ c, size_t n)
{
    size_t i = (size_t)blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) c[i] = add_values(a[i], b[i]);
}

int main()
{
    CUDA(cudaSetDevice(0));
    cudaDeviceProp prop;
    CUDA(cudaGetDeviceProperties(&prop, 0));
    std::printf("device=%s CC=%d.%d SMs=%d warp=%d max_threads=%d\n",
                prop.name, prop.major, prop.minor, prop.multiProcessorCount,
                prop.warpSize, prop.maxThreadsPerBlock);
    cudaEvent_t start, stop;
    CUDA(cudaEventCreate(&start)); CUDA(cudaEventCreate(&stop));
    for (unsigned threads : {128u, 256u, 512u}) {
        if (threads > (unsigned)prop.maxThreadsPerBlock ||
            threads > (unsigned)prop.maxThreadsDim[0]) return 2;
        for (size_t n : {size_t(0), size_t(1), size_t(255), size_t(256),
                         size_t(257), size_t(1003), size_t(1048573)}) {
            if (n == 0) {
                std::printf("n=0 threads=%u skipped: no zero-grid launch\n", threads);
                continue;
            }
            size_t blocks = n / threads + (n % threads != 0);
            if (blocks > (size_t)prop.maxGridSize[0]) return 3;
            std::vector<float> a(n), b(n), result(n+2, -65536.0f);
            for (size_t i = 0; i < n; ++i) {
                a[i] = (i % 1024) * 0.25f;
                b[i] = (i % 37) * 0.5f;
            }
            size_t bytes = n * sizeof(float);
            float *da, *db, *dc;
            auto t0 = std::chrono::steady_clock::now();
            CUDA(cudaMalloc(&da, bytes)); CUDA(cudaMalloc(&db, bytes));
            CUDA(cudaMalloc(&dc, (n+2)*sizeof(float)));
            CUDA(cudaMemcpy(da, a.data(), bytes, cudaMemcpyHostToDevice));
            CUDA(cudaMemcpy(db, b.data(), bytes, cudaMemcpyHostToDevice));
            CUDA(cudaMemcpy(dc, result.data(), (n+2)*sizeof(float), cudaMemcpyHostToDevice));
            CUDA(cudaEventRecord(start));
            vector_add<<<(unsigned)blocks, threads>>>(da, db, dc+1, n);
            CUDA(cudaGetLastError());
            CUDA(cudaEventRecord(stop)); CUDA(cudaEventSynchronize(stop));
            float milliseconds;
            CUDA(cudaEventElapsedTime(&milliseconds, start, stop));
            CUDA(cudaMemcpy(result.data(), dc, (n+2)*sizeof(float), cudaMemcpyDeviceToHost));
            CUDA(cudaFree(da)); CUDA(cudaFree(db)); CUDA(cudaFree(dc));
            auto t1 = std::chrono::steady_clock::now();
            for (size_t i = 0; i < n; ++i) {
                if (result[i+1] != reference_value(a[i], b[i])) {
                    std::fprintf(stderr, "payload mismatch at %zu\n", i); return 4;
                }
            }
            if (result.front() != -65536.0f || result.back() != -65536.0f) return 5;
            double workflow_us = std::chrono::duration<double, std::micro>(t1-t0).count();
            std::printf("n=%zu threads=%u blocks=%zu inactive=%zu kernel_us=%.3f "
                        "alloc_to_free_us=%.3f checked=%zu guards=2\n", n, threads,
                        blocks, blocks*threads-n, milliseconds*1000, workflow_us, n);
        }
    }
    CUDA(cudaEventDestroy(start)); CUDA(cudaEventDestroy(stop));
    return 0;
}

Atomicity protects an update; synchronization orders cooperating work W8L2 8:46

A read-modify-write update such as adding to one shared total consists conceptually of reading its old value, computing a new value and storing it. If two threads do this with ordinary accesses, both can read the same old total and overwrite one another's contributions. atomicAdd makes the update atomic at its specified scope: competing atomic updates to that word do not lose contributions through this interleaving. It returns the old value. An atomic operation protects that operation, not an arbitrary region of surrounding code.

The classic CUDA family includes arithmetic operations, exchange, compare-and-swap and bitwise AND, OR and XOR. atomicCAS conditionally replaces a value after comparing it with an expected value, returning the prior value. atomicInc and atomicDec have specified wrap/limit rules, rather than being unrestricted synonyms for adding or subtracting one. The displayed atomicFetchAdd-style names are not the classic CUDA intrinsics: atomicAdd already returns the old value. Newer atomic interfaces have their own spellings and contracts.

For the legacy unsuffixed operations used here, scope is the device and memory ordering is relaxed. Atomicity of the total does not publish unrelated ordinary stores to every observer or act as a block barrier. Nor does an atomic operation guarantee one update per clock or a prescribed thread order. Correctness of our final total comes from atomic updates followed by completed kernel execution, after which the host copies the result. CUDA Programming Guide §5.4.5.1, legacy atomics.

A barrier solves another problem. __syncthreads coordinates a block's participating threads and orders the relevant earlier memory accesses before they proceed. A shared-memory reduction needs this before a thread reads contributions written by other threads. The calls must satisfy uniform block participation requirements; placing a barrier in a branch reached by only some active threads is not a safe tail-handling method. Idle threads can instead contribute the additive identity zero and still participate. The supplied programs use this structure. Writing SIMT Kernels, shared-memory synchronization.

__syncwarp coordinates the lanes named by its mask under the warp API's participation rules; it does not coordinate unrelated warps or blocks. On the host, cudaDeviceSynchronize waits for preceding requested device work and reports failure if that work failed. cudaEventSynchronize waits for work captured by a recorded event. An event does not mean that all GPU threads gather at a new in-kernel rendezvous. Its position in the submitted work determines what completion it represents. Runtime API, device synchronization; event synchronization.

A bounded reduction makes these differences concrete. Define \(f(x)=4/(1+x^2)\), whose integral on the unit interval is \(\pi\). With \(n\) midpoint samples, spacing \(h=1/n\) and sample positions \(x_i=(i+1/2)h\), the approximation is

\[ \pi_n=h\sum_{i=0}^{n-1}f(x_i).\tag{20.2} \]

Here \(\pi_n\) denotes the quadrature result, not exact mathematical pi. In the program each logical thread first sums a disjoint sequence \(i=bu+r+qgu\), where \(q=0,1,\ldots\) until the index reaches \(n\). This grid-stride loop allows a bounded launch to cover more entries than its thread count. Every index has one quotient/remainder decomposition modulo \(gu\), so it belongs to exactly one thread.

Threads write local sums into a dynamic shared array with \(u\) entries. A power-of-two block size lets the reduction halve the active range repeatedly: first combine entries separated by \(u/2\), then by \(u/4\), down to one. A barrier follows each level, outside the conditional that selects adding threads. Induction shows that the surviving entries represent disjoint sums of twice as many original contributions at each level. Thread zero writes its block partial and atomically adds it to the global total. Only one atomic operation per block is needed, rather than one per sample.

Equation (20.2) also has a useful mathematical error bound. Direct differentiation gives \(f'(x)=-8x/(1+x^2)^2\) and \(f''(x)=8(3x^2-1)/(1+x^2)^3\). To bound its magnitude, put \(y=x^2\in[0,1]\). For \(y\le1/3\), \(1-3y\le1\le(1+y)^3\); otherwise \((1+y)^3-(3y-1)=2+3y^2+y^3\ge0\). Hence \(|f''(x)|\le8\). A midpoint cell of width \(h\) has absolute integration error at most \(8h^3/24\): the first-order term integrates to zero about the midpoint, and the second-order remainder is bounded by integrating \(8(x-x_i)^2/2\). Summing \(n\) cells gives

\[ |\pi_n-\pi|\le\frac{1}{3n^2}.\tag{20.3} \]

Equation (20.3) concerns exact-arithmetic quadrature, not every floating-point evaluation. The implementation uses 64-bit double-precision floating-point arithmetic (FP64) and separately checks each block partial against a long-double host reference, checks the atomic aggregate against that reference, and checks its analytic error against the truncation bound plus a selected floating-point allowance of \(5\times10^{-12}\). This is a test allowance for the listed cases, not a proved universal rounding bound. Different addition orders can change final bits even when all atomic updates are correct, so bitwise equality is inappropriate.

__global__ void pi_partials(size_t n, double *partials, double *total)
{
    extern __shared__ double sums[];
    unsigned t = threadIdx.x;
    size_t first = (size_t)blockIdx.x * blockDim.x + t;
    size_t stride = (size_t)gridDim.x * blockDim.x;
    double value = 0;
    for (size_t i = first; i < n; i += stride) {
        double x = ((double)i + 0.5) / (double)n;
        value += 4.0 / (1.0 + x*x);
    }
    sums[t] = value;
    __syncthreads();
    for (unsigned step = blockDim.x/2; step > 0; step /= 2) {
        if (t < step) sums[t] += sums[t+step];
        __syncthreads();
    }
    if (t == 0) {
        double part = sums[0] / (double)n;
        partials[blockIdx.x] = part;
        atomicAdd(total, part);
    }
}

Device queries establish limits; errors identify failed operations W8L2 16:36

Device queries replace guesses about an enabled GPU with inspectable capabilities. The runtime uses cudaGetDeviceProperties and cudaDeviceGetAttribute. For example, cudaDevAttrMaxThreadsPerBlock selects the maximum block thread count. The driver API instead uses cuDeviceGetAttribute with a CUdevice_attribute enumerator such as CU_DEVICE_ATTRIBUTE_MAX_THREADS_PER_BLOCK. These are different function, handle and enumeration families. Copying a driver enumerator into a runtime call is not a supported way to ask the same question. Runtime API, Device Management.

Properties are constraints, not performance predictions. A maximum thread count does not prove that a particular kernel can use that many threads after its register and shared-memory requirements are accounted for. An SM count does not tell how many blocks are simultaneously resident. A queried nominal clock does not measure a running kernel's frequency. The vector program uses limits to reject invalid dimensions, and measures its own operation rather than inferring runtime from those limits.

cudaError_t is an error-code type. Constants such as cudaErrorMemoryAllocation, cudaErrorInvalidValue and cudaErrorInvalidConfiguration are values returned by operations, not functions to call in order to test a hypothesis. Functions such as cudaGetErrorName and cudaGetErrorString turn a code into a diagnostic. The installed CUDA 13.3 runtime header contains cudaErrorMemoryAllocation; the slide's cudaErrorOutOfMemory is not its runtime enumerator. Some older entries in the table are retained as deprecated names rather than useful modern diagnoses.

Errors can become visible at different times. An invalid launch configuration can be rejected during submission; an execution fault can be reported at a later synchronization or other API call. cudaPeekAtLastError inspects the host thread's runtime error state without clearing it. cudaGetLastError returns that state and resets it to success. Clearing this bookkeeping does not repair an illegal access or make a failed execution valid. The API explicitly notes that these functions can report earlier asynchronous failures. Runtime API, Error Handling.

The next diagnostic first validates a legal one-thread launch, resets its output, then deliberately requests one more thread than the queried block limit. It recognizes only cudaErrorInvalidConfiguration or cudaErrorInvalidValue as the intended submission rejection, verifies inspection and clearing, and validates another legal launch afterward. The second result must come from new work because the output was reset. This is a bounded test of a recoverable submission error, not an experiment in invalid memory accesses, deadlocks or a watchdog timeout. The program treats every other error as a failure. On the captured RTX 3050 Laptop stack, runtime 13030, driver API 13010 and driver package 592.82, the oversized request returned cudaErrorInvalidValue. The initial test expecting only cudaErrorInvalidConfiguration failed and was corrected; no cause for the enum difference was isolated, and no identical enum is promised on every stack.

Compiler options select distinct stages and numerical contracts W8L2 21:07

A CUDA source contains host and device code, and nvcc coordinates their translation. Here -arch=native selects visible GPU targets, -std=c++17 selects the language dialect, and -O2 sets host optimization. Native targeting is useful for this machine's executable tests; it is not a distribution strategy for unknown future GPUs. A deeper account of intermediate representations and linking belongs to the compilation chapter.

The lecture's debug flag needs a case-sensitive correction: nvcc -g supplies host debug information; -G supplies device debug information and normally disables device optimization unless the relevant optimization option is requested. -lineinfo supports source-line correlation for profiling. The device assembler has its own optimization level, whose documented default is three. Thus nvcc -O3 being a host option does not mean device code otherwise receives no optimization.

--maxrregcount requests a register limit, subject to minimum requirements of the application binary interface (ABI), which defines compiled-code calling conventions; reducing the limit can move values from registers into thread-local memory, a process called spilling. --use_fast_math changes specified floating-point behaviors, including single-precision subnormal handling and division/square-root options. --fmad controls contraction of multiplication and addition; it is not a switch allocating a special physical unit to a function. Numerical validation must accompany changes. NVCC manual §§4.2.3, 4.2.7 and 4.2.9.

A register cap can increase the number of resident threads while making each thread perform more memory accesses. A faster approximate operation can reduce runtime while violating the application's error requirement. These are changes in a resource or numerical tradeoff, not an optimization ordering that guarantees improvement. The examples retain ordinary arithmetic settings and explicit validation before any such experiment. We make no general claim that omitting a target flag must cause compilation or execution failure.

Exercises

Exercise 1 (derive). For \(n=1003\), prove coverage and uniqueness for four one-dimensional blocks of 256 threads. Identify the owner of entry 1002 and count inactive threads. A programmer changes each block to dim3(32,8) while retaining the expression using only threadIdx.x and blockDim.x. Explain the error and derive a corrected flattening.

Solution

For every useful \(i\), Euclidean division by 256 gives a unique pair \(b=\lfloor i/256\rfloor\), \(r=i\bmod256\). Since \(i\le1002\), \(b\le3\), so that pair is launched. If two pairs produced the same index, subtracting their equations gives \(256(b-b')=r'-r\). The right side has magnitude below 256, forcing both sides to zero and proving uniqueness. Entry 1002 belongs to block three and thread 234 because \(3\cdot256+234=1002\). There are \(4\cdot256-1003=21\) inactive threads, all in the last block.

With a 32-by-8 block, the old expression becomes \(32b+\mathrm{threadIdx.x}\), independent of the y coordinate. Eight threads now address each candidate entry, and four blocks reach only indices zero through 127. Equal total thread count did not preserve the indexing function. Define the flattened local index as \(r=\mathrm{threadIdx.x}+32\,\mathrm{threadIdx.y}\), ranging uniquely from zero through 255, and then use \(i=256b+r\). The same bound guard and proof apply. The omitted z dimension is one, not zero. For an empty array, skip the launch rather than substituting a zero grid.

Exercise 2 (compute and interpret). For 1003 FP32 elements, compute the vector program's total device allocation, host-to-device bytes and device-to-host bytes, including guards and diagnostic output initialization. Can dividing all those transferred bytes by allocation-to-free time be interpreted as the GPU's local-memory bandwidth?

Solution

Each input has \(1003\times4=4012\) bytes. The output including two guards has \(1005\times4=4020\) bytes. Total device allocation is \(4012+4012+4020=12044\) bytes. The program copies both inputs and the initialized guarded output to the device, so host-to-device traffic is also 12044 bytes. It copies the whole guarded output back, adding 4020 bytes and giving 16064 transferred bytes in the two directions combined.

An unguarded production operation that overwrites all output values needs only two input copies and one output copy, totaling 12036 bytes. The demonstration intentionally does more work for validation. Dividing 16064 by the host interval would define a transfer-bytes-per-workflow-second quantity, but its denominator includes allocation, event handling, launch, waiting and deallocation. Its numerator describes transfers between host and device, not the kernel's requested traffic to local GPU memory. It therefore cannot be relabeled as local-memory or peak link bandwidth. A meaningful transfer measurement must name its direction, included operations, memory type and timing interval.

Exercise 3 (counterexample). A programmer claims that atomic addition makes a floating-point sum reproducible and exact. Start an FP32 total at \(2^{24}\), then atomically add one and \(-2^{24}\) from two different threads. Under nearest-even rounding, show two permitted final results. Does the example establish a data race?

Solution

If the addition of one occurs first, adjacent FP32 values at \(2^{24}\) are two units apart. The exact value \(2^{24}+1\) lies halfway between them and nearest-even rounding selects \(2^{24}\). Adding \(-2^{24}\) then gives zero. If the negative term occurs first, cancellation gives zero exactly, followed by one exactly. Both update orders are permitted, so final results can be zero or one even though the real-arithmetic answer is one.

Each update is atomic; no contribution is lost through a non-atomic read/store interleaving. The discrepancy is caused by finite-precision nonassociativity and unspecified order, not evidence of a data race between these atomic operations. Correct atomic access and reproducible arithmetic are separate requirements. A tolerance or a reproducible summation algorithm must be chosen for the scientific problem. The classic atomicAdd returns the old value, which also differs between the two orders; it does not promise a newly accumulated result or a predetermined position in the sequence.

Exercise 4 (diagnose an assumption). In the last block of the 1003-element example, a reduction writes a shared entry and calls __syncthreads only inside if (i < n). It then reduces all 256 shared entries. Diagnose the participation and initialization problems, and give a valid structure. Would a host cudaDeviceSynchronize after the launch repair the in-kernel protocol?

Solution

The last block has 235 useful threads and 21 padding threads. The branch does not supply a common block-wide barrier path for all active threads, and the 21 unused shared entries have not been assigned the identity element. Even if a particular execution happens to finish, the reduction has no valid proof that all consumed entries were initialized and ordered. An observed result or lack of a hang cannot repair those missing assumptions.

Every thread should first write its own entry: the contribution when its index is valid, and zero otherwise. All threads then execute a barrier. At each tree level only selected threads add, but every participating block thread executes the following barrier outside that selection. Each read then sees initialized contributions from the preceding level. The host device wait occurs after the kernel's internal work; it cannot retroactively order a shared-memory read before which a block barrier was needed. It supplies host/device completion, not an in-kernel communication phase. The faulty version should be diagnosed from its dependencies rather than run as a hang experiment.

Exercise 5 (design judgment). Consider one hundred dependent same-size GPU steps whose intermediate results are needed only by later device steps. Assume serialized costs of 60 microseconds for allocation/free, 80 for input transfer, 10 for one kernel and 40 for final output transfer. Compare rebuilding the complete workflow at every step with retaining arrays on the device. State the synchronization and numerical assumptions needed for the comparison.

Solution

Rebuilding at every step costs \(100(60+80+10+40)=19000\) microseconds. Keeping storage resident costs \(60+80+100\cdot10+40=1180\) microseconds, an idealized ratio \(19000/1180\approx16.10\). This is a model with hypothetical costs, not a measured speedup. It removes repeated setup and transfer rather than improving the kernel's arithmetic throughput.

The resident scheme must preserve producer-before-consumer ordering between steps, for example by placing their launches in one stream. Changing host pointer variables to designate old and new device allocations need not copy grid data. Storage must remain allocated until all users complete, and the host must wait before reading the final result. If a convergence check requires host inspection each step, that introduces intermediate completion and transfer costs excluded by the question. The kernels must also implement the same recurrence and precision; changing a math flag or updating a Jacobi grid in place could change the numerical algorithm and invalidate a timing comparison.

Exercise 6 (implementation and measurement). Design a bounded check for the pi kernel with 257 samples, sixteen blocks and 256 threads per block. Identify which block partials should be empty. Explain how to test numerical correctness, barrier structure, expected launch-error handling and timing scope without claiming that any one check proves all the others.

Solution

The grid has 4096 threads, so each of the 257 samples is visited once with no second grid-stride iteration. Block zero owns samples zero through 255, block one owns sample 256, and the remaining fourteen blocks have no samples. All threads in those empty blocks still write zero shared entries and execute the same reduction barriers. Their returned partials should be zero. The host reference's block owner formula \(\lfloor(i\bmod4096)/256\rfloor\) independently gives the same partition.

Compute a long-double reference for every block, compare each finite returned partial within the stated tolerance, compare the atomic total with the reference sum, and check analytic error against \(1/(3\cdot257^2)\) plus the floating-point allowance. This avoids demanding serial/GPU bitwise identity. Include the singleton and large cases and several grids to test empty groups and repeated grid-stride work. Inspect that every reduction level's barrier lies outside the adding-thread branch; passing payload checks alone is not an exhaustive synchronization analysis.

Separately, request one more thread than the queried block limit and require a specifically recognized dimension-rejection code, then clear it and validate a legal result after resetting the output, in addition to the baseline legal launch. The captured stack reports cudaErrorInvalidValue; the listing also recognizes cudaErrorInvalidConfiguration. A random crash or a different error must fail the test. For timing, use ordered events around the kernel and a host clock around the stated allocation-to-free workflow, retaining the different exclusions. Repeat serialized captures and report their range without treating it as a confidence interval. Full payload checks, expected-error handling, API checks and timing endpoints supply complementary evidence; a sanitizer or profiler would add its own specifically scoped evidence.
