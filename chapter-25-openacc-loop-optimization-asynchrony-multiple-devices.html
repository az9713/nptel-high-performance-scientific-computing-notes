OpenACC II: loop optimization, asynchrony, and multiple devices

A Jacobi sweep on a grid with 512 interior points per side updates 262,144 temperatures. Twenty sweeps perform 5,242,880 updates. The same mathematical work can be assigned by rows, flattened into one loop, or partitioned into tiles. A second choice is whether the host waits after each launch or enqueues independent work ahead of time. A third is which device owns each allocation. These choices affect different things: iteration ownership, completion order, and memory location. Confusing them can produce a fast wrong answer. The running case keeps two temperature arrays resident on one graphics processing unit (GPU), checks every output against a serial calculation, and treats timing as an observation about a specified execution.

Grounded in W9L6, OpenACC loop optimizations, W9L7, asynchronous behavior, and W9L8, multiple-device programming. Lecture material: loop correctness clauses, private variables, collapse and tiling, gang/worker/vector execution, device-specific tuning, asynchronous queues and waits, device routines, Mandelbrot image partitioning, and OpenACC-only, OpenMP, and MPI device ownership. Research extensions: the OpenACC 3.3 specification supplies the reference semantics; the specification catalogue and 3.4 document identify the newer published edition; the OpenACC consortium's loop and advanced-feature guides supply engineering interpretations; the GNU Compiler Collection (GCC) 13.3 nvptx documentation supplies its particular mapping; NVIDIA's compiler and CUDA guides supply vendor-specific compiler targeting and transfer boundaries. Original teaching constructions: the ownership proof, non-square tile arithmetic, resident Jacobi comparison, task-graph and pipeline derivations, bounded image and device-partition programs, and all six worked exercises. The examples are independently written. They are not reproductions of the lecture programs.

The objects of the chapter: iterations, storage, and completion

Let \(N\) denote the number of interior points along either side of a square grid. Include one fixed boundary layer on all sides, giving two arrays of \((N+2)^2\) doubles. A double occupies eight bytes in the checked implementation and uses binary64, also called FP64, floating-point arithmetic. Store the arrays in row-major order: the column index changes fastest. Set \(s=N+2\), and define \(\operatorname{IDX}(i,j)=is+j\). The interior index set is \(\mathcal J=\{(i,j):1\leq i,j\leq N\}\). The old iterate is \(u\), the new iterate is \(\mathrm{unew}\), and the two allocations do not overlap.

For the steady heat equation without a source, a Jacobi update writes the average of four neighboring old values. The top edge, at row zero, has value one except at the corners; the other edges and the initial interior have value zero. Both arrays carry the same fixed boundary values. The iteration therefore implements

\[ \mathrm{unew}_{i,j}=\tfrac14\left(u_{i-1,j}+u_{i+1,j}+u_{i,j-1}+u_{i,j+1}\right),\qquad (i,j)\in\mathcal J. \tag{25.1} \]

A sweep is the entire transformation in (25.1), not one cell update. Only after the sweep completes may the next sweep consume its results. Swapping the host pointer variables changes which allocation is called old; it does not move an array and does not finish outstanding device work. This distinction becomes central when synchronous launches are replaced with queues. The numerical dependency remains even when a host pointer assignment takes almost no time.

For an iteration \(a\), define its read set \(R_a\) and write set \(Z_a\) as the memory locations it reads and writes during that iteration. Two ordinary iterations can run without ordering when neither writes a location accessed by the other. In symbols, require \(Z_a\cap Z_b=\varnothing\), \(Z_a\cap R_b=\varnothing\), and \(R_a\cap Z_b=\varnothing\) for distinct \(a,b\). Shared reads are harmless. Reductions and atomic updates require their own semantics and are exceptions to this simple disjointness test.

Within one Jacobi sweep, every iteration writes one distinct location of unew and reads only u. The disjointness conditions follow from the two-array assumption. Across successive sweeps, they do not hold: the next sweep reads the allocation just written. Parallelizing all cells of one sweep is therefore legitimate, while executing two successive sweeps concurrently without an ordering edge is not. An in-place update also changes the argument, because one cell can then read a neighbor while that neighbor is being overwritten.

The execution model has a host thread running on a central processing unit (CPU) that submits work, one or more devices with separate allocations, and activity queues attached to devices. A task is a computation, transfer, or ordering operation. A dependency edge means that its destination must not use the source's result until that source has completed. The graph describes legal execution orders; it does not promise that two ready tasks physically overlap. The compiler, runtime, and hardware choose among legal schedules.

Keep three checks separate throughout. Mathematical validity asks whether the transformation preserves the intended discrete algorithm. Implementation correctness asks whether the actual program respects its memory and synchronization contracts. Performance asks how long that correct program takes in a particular environment. A checksum alone cannot answer all three: a race can occasionally produce the right checksum, and a faster twenty-sweep computation does not imply a faster solve to a prescribed tolerance.

Prove ownership before choosing a loop clause W9L6 1:44

The first tuning decision is whether a loop is safe to partition. The auto, independent, and seq clauses express different responsibilities. OpenACC 3.3, §2.9.5–2.9.7, p. 61, distinguishes compiler analysis, the programmer's independence assertion, and sequential execution. Under kernels, auto is the default for a loop construct without independent or seq. These are correctness contracts, not interchangeable performance hints.

Consider matrix multiplication, which introduces the issue before the Jacobi tuning. Let A, B, and C be non-overlapping \(N\)-by-\(N\) matrices. The desired output is \(C_{ij}=\sum_{k=0}^{N-1}A_{ik}B_{kj}\). Different pairs \((i,j)\) write different outputs and share only reads of A and B. But different k iterations contributing to the same pair all update one sum. The outer two loops and the innermost accumulation therefore have different dependency structures.

A reliable construction gives one logical owner to each output pair, initializes a scalar sum inside that owner's iteration, accumulates k sequentially, and writes C once. This is not a claim that a dot product cannot be parallelized. A reduction can split the k work and combine partial sums, provided it is explicitly expressed at the appropriate level. That alternative changes the addition order and can change floating-point rounding. The sequential inner loop supplies a transparent reference ownership scheme.

The reason initialization belongs inside the owning iteration is semantic. If sum is shared by several concurrent output owners, each owner can overwrite another's partial result. If sum is private but uninitialized, every owner has its own undefined starting value. Private storage solves an ownership problem; initialization solves a value problem. Neither substitutes for the other. A declaration such as double sum=0 inside the output loop makes both decisions visible to a reader.

Private also has an execution level. A temporary private to a gang can still be shared among that gang's workers or vector lanes. The OpenACC 3.3 loop-private rules in §2.9.10 describe this distinction. One cannot mechanically translate every occurrence of private as “one variable per CUDA thread.” CUDA is NVIDIA's accelerator programming platform; an OpenACC implementation may map its abstract levels differently. Place a temporary at the level that owns the value, then inspect the compiler's realization if resources or races remain unclear.

The related firstprivate clause gives each private instance an initial value from the corresponding host-side value. For example, each independent owner can start with the same supplied threshold without sharing a writable threshold variable. It differs from private, which supplies storage without copying that initial value. Neither clause copies a final private result back as an automatic reduction. A private pointer value also does not, by itself, allocate or copy the array it points to; pointed-to storage needs an appropriate data mapping.

A useful counterexample is a prefix recurrence, \(x_i=x_{i-1}+a_i\). Even with a private loop index, iteration i reads an output from iteration i−1. Adding independent does not manufacture disjoint read and write sets. A compiler may accept that assertion and produce an invalid result, or diagnose a limitation, but acceptance is not a proof of independence. A parallel prefix algorithm must reorganize the dependency graph; it is a different construction from putting a directive on the original recurrence.

The following complete program tests output ownership for a 17-by-17 matrix product. Inputs are small nonnegative integers represented exactly as doubles. The largest possible dot product is at most \(17\cdot4\cdot6=408\), so all products and partial sums fit exactly in binary64. Exact elementwise comparison is justified for this test, rather than chosen because a tolerance happened to pass. Its effects are allocation-free local array computations and one printed line; an accelerator witness returns failure if the compute region did not execute on an NVIDIA device.

#include <stdio.h>
#include <stdlib.h>
#include <openacc.h>
int main(void) {
  enum { N=17, M=N*N };
  double a[M], b[M], c[M], ref[M];
  for(int i=0;i<N;i++) for(int j=0;j<N;j++) {
    a[i*N+j]=(i+j)%5; b[i*N+j]=(2*i+j)%7;
    c[i*N+j]=ref[i*N+j]=0;
  }
  for(int i=0;i<N;i++) for(int j=0;j<N;j++)
    for(int k=0;k<N;k++) ref[i*N+j]+=a[i*N+k]*b[k*N+j];
  int gpu=0;
  #pragma acc serial copyout(gpu)
  { gpu=acc_on_device(acc_device_nvidia); }
  if(!gpu) return 2;
  #pragma acc parallel loop collapse(2) copyin(a[0:M],b[0:M]) copyout(c[0:M])
  for(int i=0;i<N;i++) for(int j=0;j<N;j++) {
    double sum=0;
    #pragma acc loop seq
    for(int k=0;k<N;k++) sum+=a[i*N+k]*b[k*N+j];
    c[i*N+j]=sum;
  }
  int errors=0; long checksum=0;
  for(int i=0;i<M;i++) { errors+=(c[i]!=ref[i]); checksum+=(long)c[i]; }
  printf("nvidia_execution=%d matmul_errors=%d checksum=%ld\n",gpu,errors,checksum);
  return errors?1:0;
}

Zero mismatches checks every matrix entry, while the checksum is an additional compact record of this particular input. The example proves neither numerical accuracy for ill-conditioned downstream calculations nor efficiency of the sequential dot product. It isolates ownership so later scheduling changes have a known starting point. For general real-valued matrices, use a justified error criterion rather than importing this exact-integer comparison.

The final device-type slide in W9L6 visibly shows collapse(3) around the i, j, and k loops of an accumulating matrix product. As written, multiple collapsed iterations update the same c[i][j] without a displayed reduction or atomic operation. That snippet does not satisfy the independence contract. The corrected construction above collapses only i and j and keeps one accumulation per owner. This is a limitation of the displayed snippet, established from the frame and the read/write argument; it is not a claim about unverified spoken wording.

Collapse exposes work; tiling changes its organization W9L6 8:20

For a rectangular loop with rows \(0\leq i\lt n_i\) and columns \(0\leq j\lt n_j\), define a flattened index \(q=in_j+j\). Its inverse is \(i=\lfloor q/n_j\rfloor\), \(j=q\bmod n_j\). Division with remainder guarantees uniqueness, and \(0\leq q\lt n_in_j\) covers every pair. Thus collapse can expose \(n_in_j\) independent iterations to the implementation instead of exposing only the outer loop's \(n_i\) iterations. The bijection says nothing by itself about which processor executes a pair.

For Jacobi's one-based interior, use \(q=(i-1)N+(j-1)\). With \(N=4\), q runs from zero through fifteen and the pair sequence begins (1,1), (1,2), (1,3), (1,4), (2,1). This is a conceptual enumeration, not a guarantee that runtime execution follows that order. The purpose of proving the bijection is to check that no interior cell is omitted or assigned twice. Boundary cells remain outside the iteration domain.

Collapse is attractive when the outer trip count is small relative to the available parallel resources. A grid with four rows and 1,024 columns has only four outer-loop iterations but 4,096 cell updates. Flattening makes it possible to partition the entire domain more finely. It does not create new mathematical work. Nor does it automatically improve locality: the original row-major inner traversal was already contiguous, and a compiler's actual distribution may preserve or alter how neighboring logical iterations are grouped.

The consortium loop-optimization guide treats collapse as a way to expose parallelism when individual loop dimensions are insufficient. For the running Jacobi case, the practical question is whether flattened scheduling improves use of the machine enough to offset its indexing and mapping costs. There is no need to infer an answer from the word collapse. Compare complete correct variants and retain the observed scope.

Tiling decomposes each index into a tile coordinate and an element coordinate. For row tile size \(t_i\) and column tile size \(t_j\), write \(i=b_it_i+e_i\), \(j=b_jt_j+e_j\), with \(0\leq e_i\lt t_i\) and \(0\leq e_j\lt t_j\). Edge tiles clip the index range to the original domain. Reordering tile loops outside element loops changes which neighboring updates are considered together. This may help reuse, but a tile directive alone is not a promise to stage values in a GPU's shared memory.

The argument order matters for non-square tiles. OpenACC's tile size list starts with the innermost associated loop. With i outside j, tile(32,4) means up to 32 j values and four i values per tile. Reversing those numbers makes a different shape. The rule is specified in OpenACC 3.3, §2.9.8, pp. 61–62. Square demonstration tiles conceal this possible mistake.

For a 10-row by 13-column domain and tiles of four rows by five columns, there are \(\lceil10/4\rceil\lceil13/5\rceil=9\) tiles. Six tiles have full row extent, three have two rows, and the last tile column contains only three columns. Counting the clipped extents gives \((4+4+2)(5+5+3)=130\) valid elements. A rectangular launch envelope of nine full tiles would have 180 element slots, so fifty slots must be masked or otherwise avoided. Edge handling is part of correctness.

A five-point Jacobi tile with both dimensions at least two and \(a\) rows and \(b\) columns needs the tile interior plus two row strips and two column strips from the old array. Ignoring corner values that the stencil does not read, there are \(ab+2a+2b\) distinct old values. For a four-by-32 tile this is 200 old values for 128 updates. Independent scalar updates request four old loads each, or 512 load operands. This arithmetic identifies potential reuse; it does not establish 512 physical memory transactions or prove that a compiler loads only 200 values.

Actual traffic depends on caches, coalescing, boundary behavior, and the generated code. Coalescing means that accesses by neighboring GPU lanes can be serviced together as memory transactions. The row-major j direction gives adjacent locations, so mapping vector lanes along j is a plausible starting point. The tile calculation supplies a hypothesis to investigate, not a measured bandwidth saving. Avoid treating a logical load count as an observed number of bytes fetched from device memory.

Gang, worker, and vector describe a mapping hierarchy W9L6 10:32

A gang is a coarse independent group, a worker is a subdivision within a gang, and vector lanes provide the finest partitioning. Their significance is which iterations and private values belong together. Gangs have no portable global barrier inside one compute region. A program that makes one gang spin until another gang writes a flag can deadlock if the producer gang is not scheduled. Express a global phase boundary with completion of one compute operation before the next dependent operation.

A vector length specifies a logical width, not the total number of data items the operation can process. A vector can execute several strips of an inner loop. For an inner trip count n and logical width v, a simple utilization model gives \(\eta=n/[v\lceil n/v\rceil]\), assuming each strip costs the same and every lane has equal work. For \(n=4,v=8\), \(\eta=1/2\); for \(n=12,v=8\), it is 3/4. This is a count of useful lane slots, not a prediction that wall time is exactly doubled or multiplied by 4/3.

The small vector diagrams in W9L6 are useful for that counting exercise. Real NVIDIA hardware executes a warp, a scheduling group of 32 threads. A streaming multiprocessor is the GPU hardware unit that hosts and schedules resident thread blocks and their warps. On this platform's GCC backend, choosing a logical vector width of four does not create a physical four-thread warp. The GCC 13.3 nvptx manual, §12.2, describes the implementation's mapping: vector execution uses threads, workers use warps, and the warp size is 32. Treat that as implementation evidence, not universal OpenACC terminology.

For Jacobi, a natural first map partitions rows across gangs and columns across vector lanes. Adjacent column indices give adjacent doubles, and each row has the same arithmetic count. Collapse gives the compiler a larger combined domain. Tiling requests a rectangular organization. Workers may help when a small inner loop leaves too little work at the finest level, but adding them also changes resources and sharing. The logical hierarchy constrains legality; register use, residency, and the compiler's choices affect throughput.

A register is a fast per-thread storage location in the GPU execution model. Register pressure is the amount demanded by the generated code. If demand exceeds the chosen allocation, values can spill to memory-backed storage. Occupancy is the fraction of a hardware unit's supported thread or warp capacity that is resident. More occupancy can help hide memory latency, but it does not change the number of arithmetic operations and does not guarantee higher useful throughput. None of these hardware quantities is measured by a source-level count of gangs.

The practical stopping rule is to tune a small justified set, preserve correctness, and compare the same work with the same timing boundary. Do not specify every launch dimension merely because a directive permits it. A fixed gang count can restrict a larger device, while a larger vector length can change resource use or leave short dimensions underfilled. The consortium guide's hardware-mapping discussion explains why extra mapping detail can reduce performance portability.

The next program compares three mappings for twenty resident Jacobi sweeps. It allocates four arrays on the host, about 8.45 MB total, and two on the device, about 4.23 MB. Each variant starts from the same boundary and interior values. The serial reference uses the same two-array recurrence. The name jacobi_step denotes one reference sweep and returns the maximum change; the fixed-sweep driver intentionally does not use that change as a convergence test. A production solve would stop at a specified tolerance or max_iter.

The timer uses a monotonic wall clock, which advances independently of changes to civil time. Its interval begins after the data region has copied arrays to the device and ends before its copyout. It includes twenty synchronous kernel submissions, their completions, host loop control, and pointer swaps. It excludes allocation, initialization, the serial reference, the initial transfer, and the final transfer. There is no per-variant warmup outside the interval. Runtime startup is exercised by the witness, but first encounters with a particular kernel remain within the timing boundary.

#define _POSIX_C_SOURCE 200809L
#include <stdio.h>
#include <stdlib.h>
#include <math.h>
#include <time.h>
#include <openacc.h>
#define N 512
#define S (N+2)
#define M (S*S)
#define IDX(i,j) ((i)*S+(j))
#define STEPS 20
static double wall(void) { struct timespec t; clock_gettime(CLOCK_MONOTONIC,&t); return t.tv_sec+1e-9*t.tv_nsec; }
static void init(double *u,double *v) {
  for(int k=0;k<M;k++) u[k]=v[k]=0;
  for(int j=1;j<=N;j++) u[IDX(0,j)]=v[IDX(0,j)]=1;
}
static double jacobi_step(const double *u,double *unew) {
  double delta=0;
  for(int i=1;i<=N;i++) for(int j=1;j<=N;j++) {
    int k=IDX(i,j); unew[k]=0.25*(u[k-S]+u[k+S]+u[k-1]+u[k+1]);
    delta=fmax(delta,fabs(unew[k]-u[k]));
  }
  return delta;
}
int main(void) {
  double *u=malloc(M*sizeof *u), *unew=malloc(M*sizeof *unew);
  double *ref=malloc(M*sizeof *ref), *tmp=malloc(M*sizeof *tmp);
  if(!u||!unew||!ref||!tmp) return 3;
  init(ref,tmp);
  for(int t=0;t<STEPS;t++){ jacobi_step(ref,tmp); double *s=ref;ref=tmp;tmp=s; }
  int gpu=0;
  #pragma acc serial copyout(gpu)
  { gpu=acc_on_device(acc_device_nvidia); }
  if(!gpu) return 2;
  printf("nvidia_execution=%d N=%d steps=%d\n",gpu,N,STEPS);
  const char *names[]={"row-vector32","collapse-vector128","tile32x4"};
  for(int mode=0;mode<3;mode++) {
    init(u,unew); double elapsed=0;
    #pragma acc data copy(u[0:M],unew[0:M])
    {
      double begin=wall();
      for(int t=0;t<STEPS;t++) {
        if(mode==0) {
          #pragma acc parallel loop gang vector_length(32) present(u[0:M],unew[0:M])
          for(int i=1;i<=N;i++) {
            #pragma acc loop vector
            for(int j=1;j<=N;j++) { int k=IDX(i,j); unew[k]=0.25*(u[k-S]+u[k+S]+u[k-1]+u[k+1]); }
          }
        } else if(mode==1) {
          #pragma acc parallel loop collapse(2) gang vector vector_length(128) present(u[0:M],unew[0:M])
          for(int i=1;i<=N;i++) for(int j=1;j<=N;j++) { int k=IDX(i,j); unew[k]=0.25*(u[k-S]+u[k+S]+u[k-1]+u[k+1]); }
        } else {
          #pragma acc parallel loop tile(32,4) gang vector vector_length(128) present(u[0:M],unew[0:M])
          for(int i=1;i<=N;i++) for(int j=1;j<=N;j++) { int k=IDX(i,j); unew[k]=0.25*(u[k-S]+u[k+S]+u[k-1]+u[k+1]); }
        }
        double *s=u;u=unew;unew=s;
      }
      elapsed=wall()-begin;
    }
    double error=0;
    for(int k=0;k<M;k++) error=fmax(error,fabs(u[k]-ref[k]));
    printf("%s ms=%.3f max_error=%.3g\n",names[mode],1e3*elapsed,error);
    if(error>1e-12) return 1;
  }
  free(u);free(unew);free(ref);free(tmp); return 0;
}

Asynchrony is an ordering graph, not a speed promise W9L7 2:19

Suppose task A fills array a, task B fills array b, and task C computes their sum. A and B have disjoint writes and can be submitted independently; C depends on both. A correct synchronous schedule A, B, C is one topological order of the graph. An asynchronous implementation can allow A and B to overlap while retaining the two edges into C. The optimization removes unnecessary ordering between independent tasks and keeps necessary ordering between producers and consumers.

Operations submitted to one numbered activity queue by the same host thread retain their submission order. Different queue numbers do not establish an order between their operations. An explicit wait supplies the missing relation when the consumer needs another queue's result. These are the central rules of the OpenACC advanced-feature guide's asynchronous section. Multiple queues express opportunity; execution resources can still serialize them.

Use async(1) to place work in queue one and allow the submitting host thread to continue. A following ordinary host read is not thereby delayed until the device result arrives. A blocking wait waits for the relevant previously submitted work on the current device before that thread proceeds. It does not stop every host thread in the process, and a wait on device zero does not silently drain device one's queues. The scope is an essential part of the synchronization contract.

There are two distinct ways to join the example. A blocking wait for both producers lets the host submit C after both finish. Alternatively, enqueue wait(1) async(2) after B in queue two, then enqueue C in queue two. B precedes C through queue order; A precedes C through the inserted queue dependency. The host can keep running. A later update of c in queue two followed by a blocking wait makes c safe to read on the host.

This table specifies a dependency design, not an additional executed listing. A queue wait has a direction. Inserting a wait on queue one for queue two, then launching C in queue two without an edge from one, does not necessarily enforce A before C. A dependency graph makes the error visible without relying on a race to manifest during a run. The graph should remain acyclic; mutually waiting queues are not an overlap strategy.

Data lifetime extends through completion, not merely submission. If an asynchronous kernel reads a host buffer through a later transfer, the host must preserve that buffer until the transfer is done. If an asynchronous update writes host memory, ordinary host code must not inspect or overwrite it prematurely. A device allocation must survive all queued uses. Put the final wait before freeing memory, leaving a mapped data lifetime, or reusing a staging buffer. A pointer staying in scope is insufficient when its allocation has already been released.

Jacobi exposes a subtler trap. Within a sweep the cells are independent, but sweep t+1 requires results from sweep t. Enqueueing successive sweeps into one queue preserves this relation. Alternating sweeps between queues one and two without waits does not. Alternating independent image blocks between two queues is valid because the blocks write disjoint pixel ranges. The same queue pattern can therefore be valid for one algorithm and invalid for another; the dependency graph, rather than the syntax, determines correctness.

For a simple pipeline model, divide independent work into m equal chunks. Let c seconds be the compute time per chunk and d seconds the output-transfer time. Assume one compute engine and one transfer engine, negligible submission overhead, enough buffering, and the ability to overlap these engines. A synchronous schedule costs \(m(c+d)\). The first chunk takes c+d to emerge; each additional completed chunk costs the slower stage, giving

\[ T_{\mathrm{pipe}}=c+d+(m-1)\max(c,d). \tag{25.2} \]

For four chunks with c=3 ms and d=2 ms, the serial stage sum is 20 ms and the ideal pipeline time is 14 ms. The model's speed ratio is 20/14, about 1.43. If c=d, the large-m limit approaches two; if one stage dominates, the limit approaches one. The result follows from shared engine capacity, not from the number of queue identifiers. Four queues cannot make the single compute engine finish four equal compute stages simultaneously.

These are hypothetical numbers, not measurements on the laptop. Real transfers may require pinned host memory, meaning pages kept resident for device transfer, and suitable hardware engines. Pageable host memory can require staging or synchronization. NVIDIA's CUDA Best Practices Guide, §10.1.2, describes those CUDA-level conditions. An OpenACC runtime can implement transfers differently; source-level async alone does not prove physical overlap. A device timeline or equivalent instrumentation would be needed to establish it here.

Device routines and a bounded image pipeline W9L7 11:20

The image example supplies independent work with unequal costs. A pixel represents the complex number \(c=c_r+\mathrm{i}c_i\), where \(\mathrm{i}^2=-1\). Starting at \(z_0=0\), iterate \(z_{k+1}=z_k^2+c\) while its squared magnitude does not exceed four, up to a fixed cap of 64 steps. Writing \(z_k=x_k+\mathrm{i}y_k\) gives \(x_{k+1}=x_k^2-y_k^2+c_r\) and \(y_{k+1}=2x_ky_k+c_i\). Save the old x before updating either component.

The returned escape count is a finite computation. A pixel that reaches the cap has not been proved to belong to the Mandelbrot set; it merely did not escape within this budget. Near the boundary, floating-point rounding can change the iteration at which a threshold is crossed. For a transparent scalar check, c=1 gives successive z values 0, 1, 2, 5, so the program's count is three. For c=−2, the orbit reaches 2 and stays there, so a test using magnitude strictly greater than two reaches the cap. Changing a less-than-or-equal comparison would change that boundary behavior.

A host function is not automatically available as a device-callable implementation in every compiler situation. routine seq requests a device routine whose internal work is sequential at the calling lane. That does not serialize all pixels: different callers can execute the same sequential function on different inputs. It also does not grant arbitrary host-library or operating-system access inside the function. The example uses only bounded arithmetic and control flow, keeping the device-call contract small.

The OpenACC 3.3, §2.15.1, pp. 82–87, give the routine model; the checked code places its routine directive before the definition and device call. Other routine levels describe internal gang, worker, or vector parallelism and require compatible calling contexts. They are not independent choices of a new accelerator for every call. A routine that consumes a hierarchy level can constrain which parallelism remains available to its caller.

Partition the 97 image rows into four strips using endpoints \(y_b=\lfloor97b/4\rfloor\). Their row counts are 24, 24, 24, and 25. The last row is therefore included even though the height is not divisible by four. Assign strip b to queue \(b\bmod2\). The percent operation in C means remainder; it produces queue IDs zero and one here. It does not divide the image into a number of queues equal to half the number of blocks as a general rule. The original W9L7 frame shows this remainder-based reuse.

Each strip's kernel and output update use the same queue. The update consequently waits for its own kernel, and reusing that queue for a later strip keeps its earlier operations ordered. Different strips use disjoint memory ranges, so no cross-queue dependence is needed. The final wait precedes data-region exit and host verification. The host output array remains allocated throughout. These are the facts that make the pipeline legal, regardless of whether transfers actually overlap kernels.

The complete listing has no input files and produces no image file. It computes 12,416 pixel counts, transfers them in strips, and compares every pixel with host execution of the same routine. Maximum device image storage is 49,664 bytes when int is four bytes, as on this implementation. Its finite cap bounds even pixels whose orbit never escapes. The comparison tests CPU/device agreement and partition coverage, while the c=1 and c=−2 reasoning checks the intended scalar convention.

#include <stdio.h>
#include <stdlib.h>
#include <openacc.h>
#define WIDTH 128
#define HEIGHT 97
#define PIXELS (WIDTH*HEIGHT)
#pragma acc routine seq
static int escape_count(int x,int y) {
  double cr=-2.0+3.0*x/(WIDTH-1), ci=-1.0+2.0*y/(HEIGHT-1);
  double zr=0,zi=0; int it=0;
  while(it<64 && zr*zr+zi*zi<=4.0) {
    double next=zr*zr-zi*zi+cr; zi=2.0*zr*zi+ci; zr=next; it++;
  }
  return it;
}
int main(void) {
  int *image=malloc(PIXELS*sizeof *image); if(!image) return 3;
  int gpu=0;
  #pragma acc serial copyout(gpu)
  { gpu=acc_on_device(acc_device_nvidia); }
  if(!gpu) return 2;
  #pragma acc data create(image[0:PIXELS])
  {
    for(int block=0;block<4;block++) {
      int y0=block*HEIGHT/4, y1=(block+1)*HEIGHT/4;
      int start=y0*WIDTH, count=(y1-y0)*WIDTH, queue=block%2;
      #pragma acc parallel loop collapse(2) present(image[0:PIXELS]) async(queue)
      for(int y=y0;y<y1;y++) for(int x=0;x<WIDTH;x++)
        image[y*WIDTH+x]=escape_count(x,y);
      #pragma acc update self(image[start:count]) async(queue)
    }
    #pragma acc wait
  }
  long sum=0; int errors=0;
  for(int y=0;y<HEIGHT;y++) for(int x=0;x<WIDTH;x++) {
    int k=y*WIDTH+x; errors+=(image[k]!=escape_count(x,y)); sum+=image[k];
  }
  printf("nvidia_execution=%d pixels=%d queues=2 errors=%d checksum=%ld\n",gpu,PIXELS,errors,sum);
  free(image); return errors?1:0;
}

nvidia_execution=1 pixels=12416 queues=2 errors=0 checksum=257269

The checksum of 257,269 records the tested grid and cap. The full elementwise comparison is stronger than that checksum because distinct erroneous images can have the same sum. With contraction disabled, this grid produced exact integer-count agreement between host and device. A different grid close to a fractal boundary may require interpreting discrepancies rather than forcing agreement by changing a tolerance on integer counts. The code checks the computation it actually defines.

No timeline or asynchronous speedup is claimed for this listing. It demonstrates a correct two-queue submission pattern with a device routine, not physical concurrency. A meaningful overlap study would compare synchronous and asynchronous versions with identical initialization, transfers, cap, image dimensions, and completion boundary, then inspect the execution timeline. A shorter host submission interval alone would only show that the host returned sooner; it would not show that the completed image became available sooner.

Chunk size is an engineering variable. Very small chunks multiply launches and update calls; very large chunks reduce opportunities to interleave work. Equal row counts also need not mean equal execution times: pixels near a complicated boundary can use the full iteration cap while other pixels escape quickly. A balance model should therefore consider measured chunk costs or a justified workload proxy. Row count is a storage measure, not a direct measure of arithmetic work.

Device selection creates separate ownership domains W9L8 1:48

A device number is local to a device type and its visible runtime inventory. It is not an MPI rank, a host-thread number, or a globally unique physical identifier. Query the available devices of the intended type, validate the count, and select a legal index. The runtime calls acc_get_num_devices and acc_set_device_num implement those operations. OpenACC 3.3, §3.2.1 and §3.2.4–3.2.5, specifies the inventory and current-thread selection interface.

Moving the current selection from device zero to device one does not migrate device zero's allocations or synchronize its queues. A host address can correspond to separate mappings on separate devices. Queue one on device zero and queue one on device one are different activity queues. Thus allocation, submission, waiting, and deletion must all occur with the intended device selected. This is the memory-location analogue of proving iteration ownership before choosing a loop map.

For an independent one-dimensional output of n elements and p selected devices, assign device d the half-open interval \([\lfloor dn/p\rfloor,\lfloor(d+1)n/p\rfloor)\). Adjacent intervals meet at the same integer endpoint, so they neither overlap nor leave a gap. The first endpoint is zero and the last is n. Summing interval lengths telescopes to n. A half-open interval contains its first index and excludes its last, matching C's less-than loop convention.

The lengths differ by at most one, because division with remainder writes \(n=ap+r\), with \(0\leq r\lt p\), and every interval has a or a+1 elements. This balances element counts, not arbitrary per-element work. For a Mandelbrot image it may still leave unequal execution times; for the affine integer output below each element has the same simple operation count. The decomposition proof is independent of whether one or several devices are available.

The following example uses at most four devices and just 301 output elements. It explicitly requires the NVIDIA device type. With one physical GPU, p is one and the entire output belongs to device zero. That is the tested one-device path, not host fallback. The same source contains a p-greater-than-one path, but that path was not executed on this machine and remains an unvalidated multi-device template. No multi-GPU speedup, transfer between GPUs, or peer-link behavior is inferred.

The first loop selects each device, creates only its chunk mapping, enqueues computation and an update, and moves on. The second loop revisits each selected device, waits for its outstanding operations, then deletes its mapping. The host allocation survives both loops. Output values use global indices despite chunk-local storage, making an offset mistake detectable. The witness is checked on every selected device. Memory consumption is a few kilobytes, and the program performs a fixed amount of work.

#include <stdio.h>
#include <stdlib.h>
#include <openacc.h>
#define N 301
int main(void) {
  int devices=acc_get_num_devices(acc_device_nvidia);
  if(devices<1) return 2;
  int p=devices<4?devices:4;
  int *out=malloc(N*sizeof *out), witness[4]={0}; if(!out) return 3;
  for(int d=0;d<p;d++) {
    int lo=d*N/p, hi=(d+1)*N/p, count=hi-lo;
    int *chunk=out+lo;
    acc_set_device_num(d,acc_device_nvidia);
    #pragma acc serial copyout(witness[d:1])
    { witness[d]=acc_on_device(acc_device_nvidia); }
    #pragma acc enter data create(chunk[0:count])
    #pragma acc parallel loop present(chunk[0:count]) async(1)
    for(int j=0;j<count;j++) chunk[j]=3*(lo+j)+1;
    #pragma acc update self(chunk[0:count]) async(1)
  }
  for(int d=0;d<p;d++) {
    int lo=d*N/p, hi=(d+1)*N/p, count=hi-lo; int *chunk=out+lo;
    acc_set_device_num(d,acc_device_nvidia);
    #pragma acc wait
    #pragma acc exit data delete(chunk[0:count])
  }
  int errors=0, gpu=1; long sum=0;
  for(int d=0;d<p;d++) gpu=gpu&&witness[d];
  for(int i=0;i<N;i++){ errors+=(out[i]!=3*i+1);sum+=out[i]; }
  printf("nvidia_devices=%d selected=%d nvidia_execution=%d errors=%d checksum=%ld\n",devices,p,gpu,errors,sum);
  free(out); return errors||!gpu?1:0;
}

nvidia_devices=1 selected=1 nvidia_execution=1 errors=0 checksum=135751

The actual run observed one NVIDIA device, selected that one, and checked all 301 values. The checksum follows independently from \(\sum_{i=0}^{300}(3i+1)=3(300\cdot301/2)+301=135,751\). That arithmetic verifies the displayed sum without assuming that a successful launch implies correct indexing. The program also compares each element, so a compensating pair of wrong outputs cannot pass merely by preserving the total.

The return-code check allows the printed inventory to differ on another machine; the program still requires a positive inventory, successful NVIDIA execution, and zero element errors. A machine with more than four devices intentionally uses only four, preserving the stated bounds. Running that path would require new multi-device evidence. The present result establishes selection, allocation, submission, update, and completion on device zero only.

For a real multi-device application, separate memory costs from work costs. Replicating a large read-only input on p devices uses p times that input's storage, even if the output is partitioned. A stencil additionally needs halo values, neighboring data outside a device's owned interior. The independent affine example has no such communication. Its clean decomposition cannot be transferred to Jacobi without adding halo exchange and a global convergence decision when required.

OpenMP and MPI change who owns a device W9L8 5:02

OpenMP, the shared-memory threading interface, can assign one host thread to each device on a node. A node is one computer with its own operating system, host memory, and attached accelerators. Each thread selects a device before establishing mappings or submitting work. The shared host output array can hold disjoint subimages from different threads, but shared memory does not make overlapping writes safe. Ownership of both the host ranges and the device mappings must remain explicit.

An OpenMP barrier means that the participating host threads have arrived. If each thread has merely submitted asynchronous device work, its arrival need not mean that work has completed. Each thread must wait for its device work before exposing those results to the host phase or finishing a lifetime that owns the mapping. With synchronous device operations, that completion is already part of returning from the operation. Retaining the same rule when async is later added prevents a previously correct host barrier from becoming an incomplete substitute.

Creating p requested host threads does not always guarantee a team of exactly p under every runtime configuration. A robust design partitions according to the actual team or distributes device indices through a host worksharing loop, so every intended device assignment is covered. Thread-to-device selection is local execution state, so set it in the thread that will submit the operations. The single-thread program above deliberately avoids claiming that any OpenMP/device interaction was tested.

MPI, the Message Passing Interface, instead gives each rank a separate process address space. A rank is its identifier within a communicator, a group and communication context. Each rank can own a subimage, compute it on an assigned device, transfer it to its host memory, and gather host subimages into a root process. A gather collects the distributed contributions; unequal subimage lengths require counts and displacements appropriate to the chosen collective, such as Gatherv rather than an equal-count Gather.

On multiple nodes, a global rank is not automatically a legal local device index. If every node has four GPUs, global rank five must not blindly select device five on its node. Derive a node-local rank, meaning its ordinal among ranks on that same node, and map it against the node's visible device inventory. Mapping by local rank modulo device count allows sharing but can cause contention. It is a policy decision, not evidence that sharing improves utilization.

host_data use_device exposes the device address of a mapped object to host code. It does not move the data, wait for its producer, or make an ordinary MPI library understand GPU pointers. The OpenACC 3.3 host-data construct, §2.8, pp. 55–56, defines this address substitution. Device-buffer communication requires a suitable GPU-aware communication implementation and compatible runtime support. Even accepting a device pointer does not prove that a direct peer path or a particular interconnect was used.

A conservative host-staged send first completes the device producer, updates the sending host buffer, and sends that host buffer. The receiver completes reception, updates the corresponding device mapping, and only then launches a consumer. A GPU-aware send can avoid the explicit staging steps, but still needs producer completion and buffer lifetimes through communication completion. An asynchronous OpenACC queue and an MPI nonblocking request are two different completion mechanisms; neither automatically completes the other.

This chapter tests neither MPI/device communication nor OpenMP multi-device submission. They are architectural extensions that preserve the recording's progression toward multiple nodes. The tested single-device APIs establish a small foundation; the next implementation step must add and verify communication contracts rather than interpret one physical GPU as a hidden multi-GPU system. Rank multiplicity and device multiplicity measure different resources.

What the verified examples establish

The numerical checks establish the four printed programs on the stated single-GPU installation. Every program rejects execution that lacks its NVIDIA witness. That distinguishes actual accelerator execution from a successful host fallback. The integer matrix product and affine partition have exact arithmetic checks; Jacobi compares every grid value with a serial twenty-sweep reference; the image compares every escape count. These checks are deliberately bounded and reproducible. They are not a general compiler validation suite.

Six exercises with full worked solutions

1. Derive the collapse bijection for the interior

A Jacobi grid has five interior rows and five interior columns. Give an explicit flattening and inverse, locate q=17, and explain whether flattening permits two consecutive sweeps to execute independently.

Solution

Use \(q=5(i-1)+(j-1)\), with \(1\leq i,j\leq5\). The range is zero through 24. Integer division gives \(i=\lfloor q/5\rfloor+1\) and \(j=(q\bmod5)+1\). For q=17, quotient three and remainder two give i=4 and j=3. Substitution returns \(5\cdot3+2=17\), checking both the offset and the ordering convention.

Uniqueness follows because every nonnegative q has one quotient and remainder with remainder between zero and four. Thus no pair is duplicated and all 25 pairs are covered. The flattened domain contains only one sweep. The next sweep reads the outputs of the first, so changing the enumeration does not remove that dependency. Keep a completion or same-queue ordering edge between them.

2. Compute tiles and the limit of a reuse estimate

Partition a 9-row by 10-column Jacobi interior into tiles of four rows by eight columns. How many tiles and valid elements result? Which tile arguments correspond to i outside j? For a full tile, compare independent old-value load operands with distinct old values needed by the five-point update.

Solution

There are \(\lceil9/4\rceil\lceil10/8\rceil=3\cdot2=6\) tiles. Row extents are four, four, and one; column extents are eight and two. The total count is \((4+4+1)(8+2)=90\). The six full launch rectangles would have \(6\cdot32=192\) slots, so an implementation must avoid or mask 102 out-of-domain positions. Specify tile(8,4), since the first tile argument belongs to the inner j loop.

A full four-by-eight tile has 32 updates. Four old loads per update give 128 logical load operands. Unique old values are \(32+2\cdot4+2\cdot8=56\); corners are not stencil neighbors. The ratio 128/56 is about 2.29. It is a potential reuse factor under ideal sharing, not a measured reduction in memory transactions. Cache behavior and the compiler's staging determine physical traffic.

3. Give a counterexample to unsafe accumulation

Two collapsed k iterations execute C += a[k]*b[k] for one matrix output. Take C initially zero and the two products to be three and five. Show a lost-update execution and repair the ownership without atomics.

Solution

Both iterations can read zero. One forms three and the other forms five. If the writes occur in that order, the final value is five; reversing them leaves three. Neither equals the required eight. Having different k values does not imply different write locations. Independent does not prevent either schedule because the assertion supplied incorrect information.

Assign one output pair to one logical owner, initialize its private sum to zero, and execute both k contributions sequentially before the single output store. This gives zero plus three plus five, hence eight. Alternatively, an explicitly supported reduction can generate private partial sums and combine them. That repair introduces a reduction operation and its arithmetic-order consequences; simply collapsing another loop is insufficient.

4. Diagnose an asynchronous graph and a buffer lifetime

A fills a in queue one. B fills b in queue two. C adds a and b in queue two, followed by an asynchronous update of c in queue two. The host immediately reads c and frees all buffers. State the two missing edges and a correct repair that permits the host to do unrelated work.

Solution

Queue order already supplies B before C and C before the update. It does not supply A before C, nor update completion before the host read and free. Enqueue wait(1) async(2) between B and C. This joins A into queue two without requiring the host to block at that point. Then enqueue C and the update in queue two as before.

The host may perform unrelated work that touches none of the pending buffers. Before reading c or freeing any mapped allocation used by the queued tasks, execute a blocking wait(2). Now both producers, C, and the update have completed. Waiting only for queue one would still leave queue two outstanding. Freeing after submission rather than after completion violates lifetime even if the host never reads the numerical output.

5. Make a design judgment about the pipeline

Eight equal independent chunks each require 1 ms of computation and 4 ms of output transfer. Under the two-engine assumptions of (25.2), compare synchronous and ideal pipelined completion times. Would adding eight queues rather than two remove the transfer bottleneck? Name evidence needed before calling the model an observed speedup.

Solution

The synchronous time is \(8(1+4)=40\) ms. The ideal pipeline time is \(1+4+7\cdot4=33\) ms, giving a ratio \(40/33\approx1.21\). The eight transfers alone occupy the transfer engine for 32 ms, so there is little compute time to hide. As chunk count grows with unchanged per-chunk costs, the ratio approaches \((1+4)/4=1.25\).

Extra queues do not create transfer-engine bandwidth. Two can express an alternating pipeline if buffers and scheduling permit it, while eight may add management overhead without increasing engine capacity. To claim an observed speedup, time the completed output with identical work, transfers, and initialization boundaries in both versions. Capture a timeline showing actual overlap if overlap is the asserted explanation. Correctness, pinned-memory or staging behavior, and chunk imbalance also require inspection; none follows from queue count.

6. Design the next bounded implementation check

For n=301 and p=4, compute the device intervals used by the partition program. Explain what the actual one-device run verifies and design a bounded extension that could validate p=4 when four devices become available.

Solution

The endpoints are \(\lfloor301d/4\rfloor\) for d=0 through four: 0, 75, 150, 225, 301. Thus the intervals are [0,75), [75,150), [150,225), and [225,301), with lengths 75, 75, 75, and 76. They contain all 301 indices exactly once. Their global affine values sum to 135,751, matching the closed-form sum derived above.

The actual p=1 run verifies only device zero's selection, mapping, kernel, update, wait, deletion, and complete output. It does not execute transitions between devices or validate simultaneous mappings. With four available devices, retain the same small n, initialize host outputs to a sentinel, record a witness and selected index on each device, submit all chunks, and revisit every device for wait and cleanup. Compare all values and ownership ranges after completion. Retain per-device identities and complete outputs or checks. This would validate a bounded four-device correctness case; measuring speedup would require a separate workload and timing design, and it would still not establish a peer-transfer path.
