OpenACC I: directives, parallel loops, and data management

A 1024 × 1024 Jacobi problem needs two arrays of 8,421,408 bytes each, including their boundary cells. Moving both arrays to and from an accelerator on every one of 1000 sweeps would move 33.69 billion bytes across the host–device connection. Keeping them resident for the iteration reduces that particular array traffic to 33.69 million bytes if both arrays are copied at entry and exit. The arithmetic is unchanged. The difficult decisions are which iterations may run together, which copy of an array is current, and how long each device allocation remains alive. OpenACC exposes those decisions with directives while preserving an ordinary C, C++, or Fortran program.

Grounded in W9L3, Introduction to OpenACC, W9L4, Parallelization of loops using OpenACC, and W9L5, OpenACC Data Management, from the NPTEL course High Performance Scientific Computing. The slides credit NVIDIA Corporation and OpenACC materials. Lecture material: single-source incremental acceleration; the host/device model; pairing and dependent recurrences; parallel, loop, kernels, and reduction; compiler feedback; structured and unstructured data lifetimes; array sections; update; structures and dynamic members. Research extensions: the OpenACC 3.3 specification supplies precise execution, data, reduction, and pointer rules; the GNU runtime manual supplies activation of directives; the GNU NVIDIA-target documentation explains its compilation backend; the NVIDIA Getting Started Guide distinguishes that vendor's target options; the OpenACC Best Practices Guide supplies the data-locality workflow. Original teaching constructions: the version-and-lifetime model, dependence proofs, traffic calculation, serial comparisons, finite programs, Jacobi checks, and six exercises. The Jacobi program is a correctness demonstration; no GPU speedup is claimed.

Objects, versions, and the running problem

The host is the processor executing the main application and issuing accelerator work. A device is a target selected to execute a compute region, a delimited part of the program intended for that target. Here the host is a central processing unit (CPU) and the checked execution target is an NVIDIA graphics processing unit (GPU). OpenACC is a programming interface comprising compiler directives and runtime routines. A directive communicates intent to a compiler; a clause refines a directive with information such as which data to copy. These are descriptions of program behavior, not requests for a particular number of physical transistors to participate.

Our formal objects are a host allocation \(A_H\), a corresponding device allocation \(A_D\), and a mapping that associates a host address interval with device storage. The subscripts identify locations rather than two different mathematical arrays. Each allocation contains a version of the values. Write \(v_H(A)\) and \(v_D(A)\) for the logical version last written on each side. These are reasoning labels, not counters maintained by OpenACC. An allocation can exist while its values are obsolete. A copy operation changes the destination values; an allocation operation alone does not initialize them. A lifetime is the interval during which the device storage is retained by the program's data environment.

Three questions therefore precede every compute region. Does every accessed device location exist? Does it contain the version needed by the calculation? Are accesses within the region independent or explicitly combined? The first question concerns presence, the second coherence, and the third ordering. A correct answer to one does not answer the others. A live device array full of yesterday's boundary conditions is present and still wrong. Conversely, a perfectly independent loop cannot use a device address after its allocation has ended.

The running numerical problem is the steady Laplace equation on the unit square, with dimensionless temperature \(u\). There are \(N\) interior points per direction, grid spacing \(h=1/(N+1)\), and \((N+2)^2\) stored values including boundaries. The top edge is one at interior edge positions; the remaining boundaries and four corner cells are zero. The corner convention is explicit because two adjacent Dirichlet boundary prescriptions would otherwise disagree there. It does not change the interior five-point stencil. C stores rows contiguously: cell \((i,j)\) has index \(i(N+2)+j\).

Jacobi iteration reads the old array u, writes a different array unew, and swaps their roles after a completed sweep. For interior indices \(1\le i,j\le N\), define the update norm \(r_k\), with \(k\) the completed sweep number, by

\[ u^{k+1}_{i,j}=\frac{u^k_{i-1,j}+u^k_{i+1,j}+u^k_{i,j-1}+u^k_{i,j+1}}4, \qquad r_k=\max_{i,j}|u^{k+1}_{i,j}-u^k_{i,j}|. \tag{24.1} \]

This maximum is a scalar reduction, a combination of many contributions into one result. It is an update norm, not the temperature error relative to the exact differential-equation solution. The driver stops when it falls below tol, the chosen tolerance, or when max_iter, the iteration limit, is reached. A stopped program must identify which condition occurred. Meeting an iteration limit proves neither convergence nor discretization accuracy.

A C double occupies eight bytes on the checked platform. A byte is eight bits; MB denotes \(10^6\) bytes and MiB denotes \(2^{20}\) bytes. One 1026-square array occupies \(1026^2\times8=8{,}421{,}408\) bytes, about 8.42 MB or 8.03 MiB. Two arrays occupy about 16.84 MB. The runnable Jacobi example uses \(N=32\), so two device arrays contain only 18,496 bytes. The larger grid supplies a cost model; it is not an unreported benchmark.

Incremental acceleration and the limits of single source W9L3 2:48

The practical starting point is an existing sequential program with a trustworthy answer. Parallelize one region, compare its results, then retain or revise that change before annotating another region. Single source means that one maintained source describes both ordinary host code and accelerated regions. It reduces the risk that a bug fix reaches only one of several independently maintained implementations. It does not assign a numerical probability of correctness. The lecture's three-version comparison illustrates maintenance burden; it supplies no evidence that errors become exactly one third as likely.

Portability has several meanings. Source portability means a compiler for another target can accept the program. Functional portability means it computes the intended result there. Performance portability means it performs acceptably across targets under stated workloads and metrics. The first does not imply the second if the program contains invalid dependence assertions or incoherent data access. The second does not imply the third if one target needs a different loop mapping or if transfer time overwhelms useful computation. These distinctions give the incremental workflow its purpose: compile, check correctness, inspect behavior, then assess performance.

The generic machine has logically distinct host and device storage. Actual hardware can share some or all memory; the specification's memory model (§1.3) covers those cases. We reason as though the arrays were separate, and explicitly establish the needed copies. This makes the program's requirements visible even when a shared-memory implementation can avoid a physical transfer. A test that succeeds because host and device happen to see the same storage may conceal a missing update that fails on a discrete GPU.

Removing the compiler's OpenACC activation option can leave a sequential computational core when directives are ignored, but the complete programs here also call OpenACC runtime functions. Those calls still require declarations and linkage. A serial reference is therefore provided explicitly where it matters; deleting one flag is not a universal recipe for producing a stand-alone serial executable. Likewise, a compiler cannot create a working backend for an unsupported architecture merely because the directive syntax is portable. The historical slide's platform list is a course-era illustration, not a current support matrix.

Hardware selection has a compile-time component and a runtime component. The compiler must generate code for a supported target. The runtime can then select among available compatible devices, with behavior depending on the implementation. A successful build proves neither that an accelerator was available nor that execution used it. All five programs deliberately request NVIDIA execution and fail if no such device is exposed. The first program additionally begins with a compute region that reports whether that region actually executed on an NVIDIA device. Its execution witness complements the explicit device selection and value checks used by the programs. This closes a common evidentiary gap: host fallback can produce correct answers without having executed GPU instructions.

A parallel loop requires a dependence argument W9L3 12:06

Let \(R_i\) be the set of memory locations read by iteration \(i\), and \(W_i\) those written. For ordinary non-atomic accesses, a sufficient independence condition for distinct iterations \(i\ne j\) is \(W_i\cap W_j=\varnothing\), \(W_i\cap R_j=\varnothing\), and \(R_i\cap W_j=\varnothing\). Shared reads are allowed. This is a sufficient test for the simple loops below, not a full definition of every legal parallel algorithm: a reduction explicitly permits a shared logical result while supplying private partial results and a combination operation.

Pairing consumes \(2n\) inputs and produces \(n\) outputs with \(y_i=x_{2i}+x_{2i+1}\). Iteration \(i\) writes only \(y_i\). With non-overlapping input and output arrays, no iteration writes anything another reads, so any order produces the same result. The non-overlap assumption matters. Passing output=input+1 can make an earlier output overwrite a later input. A signature containing two pointers does not prove that their pointees are different storage. Either establish non-aliasing from the allocation and call sites or choose an algorithm that tolerates overlap.

The slide supplies twelve inputs: 6, 3, 10, 7, 2, 4, 3, 8, 9, 2, 0, 1. Six independent additions give 9, 17, 6, 11, 11, 1. The next program reproduces that finite example. It has no external input, writes only standard output, and checks every result against a literal expected array. Its first compute region uses acc_on_device(acc_device_nvidia) inside the region, rather than inferring execution from a host-side device count. The runtime routine's distinction is specified in §3.2.15.

#include <openacc.h>
#include <stdio.h>
int main(void) {
    int input[12] = {6,3,10,7,2,4,3,8,9,2,0,1};
    int output[6] = {0}, expect[6] = {9,17,6,11,11,1};
    int on_gpu = 0;
    if (acc_get_num_devices(acc_device_nvidia) < 1) return 2;
    acc_set_device_type(acc_device_nvidia);
    #pragma acc serial copyout(on_gpu)
    { on_gpu = acc_on_device(acc_device_nvidia); }
    if (!on_gpu) return 3;
    #pragma acc parallel loop copyin(input[0:12]) copyout(output[0:6])
    for (int i=0; i<6; ++i) output[i]=input[2*i]+input[2*i+1];
    for (int i=0; i<6; ++i) if (output[i]!=expect[i]) return 4;
    printf("nvidia_execution=%d\npairs:", on_gpu);
    for (int i=0; i<6; ++i) printf(" %d",output[i]);
    puts("");
    return 0;
}

The device witness is a separate check from arithmetic. A one means that the witness region executed on an NVIDIA target. The output test catches incorrect indexing or copying in the pairing region; the explicit device selection and target build constrain its execution path. Neither check measures occupancy, bandwidth, or speedup. A different machine may fail the availability test even though its compiler accepts these directives.

The contrasting recurrence is a[i] += a[i-1] for increasing \(i\). With initial entries 1 through 10, the sequential result is 1, 3, 6, 10, 15, 21, 28, 36, 45, 55. Iteration \(i\) consumes the value written by iteration \(i-1\), so \(W_{i-1}\cap R_i\ne\varnothing\). Distributing adjacent iterations concurrently changes which version each reads. Splitting the array into contiguous chunks does not repair the missing dependence at each chunk boundary. Alternating indices does not repair it either.

The result of a faulty parallel version is not one prescribed wrong array. It depends on the schedule, generated code, and memory behavior; a favorable schedule can even reproduce the sequential answer. The lecture's wrong arrays illustrate possible schedules. They are not a runtime contract. We do not run an intentionally invalid parallel recurrence and treat one observed answer as a theorem. A parallel prefix-sum algorithm can compute this operation correctly, but it changes the algorithm by introducing coordinated stages or hierarchical partial sums. A directive alone does not supply that transformation.

Parallel creates gangs; loop distributes iterations W9L4 2:15

A C or C++ directive begins with #pragma acc; a free-form Fortran directive begins with !$acc. The remaining text names a construct and its clauses. A structured block has one entry and one exit under the language rules; its braces in C delimit the controlled region. A combined parallel loop construct supplies both a compute region and an immediately following loop. The syntax is short because the compiler supplies the lower-level launch and work assignment.

A gang is an independently scheduled group of workers; a worker can execute vector lanes, the finest parallel level in this abstract hierarchy. These logical levels should not be identified with a CPU core or a fixed GPU thread count without reference to the backend. Detailed tuning belongs to the next chapter. The essential distinction here is between creating a parallel region and distributing a loop's iterations. A bare parallel region begins with gang-redundant execution: code outside gang-level worksharing can execute once per gang. OpenACC 3.3 §2.5.1 makes this explicit.

Consequently, enclosing a host-style loop in parallel is not by itself a proof that each iteration executes exactly once globally. The intended idiom is parallel loop, or a loop directive properly nested in a compute region. The loop associates the iteration set with worksharing. The slide's single-loop C illustration contains j < N while declaring and incrementing i; the intended condition is i < N. That is a visible code typo, not a claim about the spoken explanation. Copying examples mechanically would preserve a source defect while missing the idea they illustrate.

Two loops with a cross-loop dependence need a global order. Suppose one fills a[i], and a second reads all of a to build another array. Two separate synchronous compute regions provide a completion point between the phases. Placing both gang-distributed loops inside one parallel region does not insert a global barrier between independent gangs. One gang might begin the second loop while another is still filling an element that it reads. The lecture's recommendation to give each loop its own parallel construct is useful here. It is an engineering default, not a declaration that every multi-loop parallel region is illegal.

Global independence can also be more conservative than necessary. If each worker produces and consumes its own local data without cross-gang communication, some operations can share a region safely. But the programmer must establish that property under the actual work mapping; textual order inside one gang is not global order. Our Jacobi implementation uses one completed compute region per sweep precisely because every new sweep reads values produced across the entire grid during the previous sweep.

Nested loops require the same reasoning at each level. In matrix multiplication, different output coordinates \((i,j)\) can be independent while the inner sum over \(k\) contributes to one output. Parallelizing only the outer coordinates and performing each inner sum sequentially is a valid starting algorithm. Parallelizing the inner sum requires a reduction or another correct combination. Adding a directive to every loop can create a race instead of extra useful parallelism. The Jacobi interior differs: every \((i,j)\) update writes a distinct output, so flattening the two-dimensional iteration space is safe.

Reduction and kernels assign different responsibilities W9L4 12:10

A reduction separates local accumulation from final combination. For a sum, independent participants begin with additive identity zero, accumulate their assigned contributions, and combine partial sums with addition. The original initial value is included once according to the construct's reduction semantics. For a maximum, participants combine with max; the implementation supplies an appropriate private identity. We initialize the original maximum to zero only when every contribution is nonnegative. That choice would be wrong for an arbitrary array of negative values if zero were intended to be excluded from the answer.

The lecture also lists product, minimum, bitwise, and logical reductions. The operator must make sense for the variable type and must have the required combination semantics. Choosing a legal operator does not prove it represents the desired scientific quantity: a minimum temperature, a maximum update, and a sum of energy contributions are different diagnostics. The programs below exercise only sum and maximum; the operator catalogue is not presented as an execution test of every case.

The declaration reduction(+:sum) supplies more than mutual exclusion. It permits a different association of additions. In real arithmetic the sum is associative. In floating-point arithmetic each operation rounds to a representable number, so different reduction trees can differ in their final bits. Binary64, the 64-bit binary format used by double on this machine, has 53 bits of significand precision including the leading bit. Exact equality is justified for our small integer-valued sums because all intermediate integers fit that precision. A general scientific sum should use a justified error tolerance or a reproducible summation method.

The lecture's reduction-restriction slide prohibits an array element and a structure member. Those statements need separate treatment against the edition used here. OpenACC 3.3 §2.5.15 permits an array element or subarray, while still prohibiting a member of a composite variable as the reduction variable. Its revision history records the extension to arrays, subarrays, and composite variables. This chapter uses a scalar temporary, a simple portable pattern that avoids confusing a standard's available feature with an installed compiler's implemented subset. We have not tested array reductions merely by citing their specification.

A kernels region asks the compiler to analyze the region and generate accelerator kernels while preserving its sequential meaning. A kernel is a separately launched device computation. The compiler can select different parallel decompositions for different loops and can leave a dependent loop sequential. By contrast, parallel loop expresses the programmer's independence assertion, unless altered by the applicable loop clauses. The compiler need not recover the intended sequential recurrence after the programmer asserts a false independence property. The two constructs offer different information and obligations rather than two guaranteed performance levels.

The slide phrase “compiler guarantees correctness” describes the required preservation of semantics by a conforming translation of a valid kernels region. It does not validate the numerical algorithm, initialize an uninitialized array, repair stale data, or rule out compiler defects. Neither can it eliminate ambiguous pointer aliasing for every program. A compiler can remain conservative and generate less parallelism than expected. Inspection of feedback is therefore useful even when the result is correct: a device kernel can execute sequential work and provide no acceleration.

Fortran array assignment provides a related distinction. A statement such as b(:)=2*a(:)+1 expresses elementwise work without an explicit do loop in the source. A kernels region lets the compiler analyze such array operations. A loop directive instead associates with an actual following loop construct; placing it before an arbitrary array assignment is not the same syntax. The opportunity for parallelism comes from the operation's semantics, not the presence of a written loop counter. The finite checks here are C programs and do not establish execution of a Fortran implementation.

The next original program uses a kernels region to compute 64 odd integers \(b_i=2i+1\), then uses explicit sum and maximum reductions. Its separate kernels region contains the dependent prefix recurrence, which must retain its sequential meaning. The checks compare every array entry, not just a checksum. The mathematical sum is \(\sum_{i=0}^{63}(2i+1)=64^2=4096\); the maximum is 127. The prefix endpoint is \(10\times11/2=55\). These independent identities discriminate indexing, reduction, and dependence failures.

#include <openacc.h>
#include <stdio.h>
int main(void) {
    enum { n=64 };
    double a[n], b[n], sum=0.0, largest=0.0;
    int prefix[10];
    if (acc_get_num_devices(acc_device_nvidia)<1) return 2;
    acc_set_device_type(acc_device_nvidia);
    for(int i=0;i<n;++i) a[i]=(double)i;
    for(int i=0;i<10;++i) prefix[i]=i+1;
    #pragma acc data copyin(a[0:n]) copyout(b[0:n])
    {
        #pragma acc kernels present(a[0:n],b[0:n])
        {
            for(int i=0;i<n;++i) b[i]=2.0*a[i]+1.0;
        }
        #pragma acc parallel loop present(b[0:n]) reduction(+:sum) reduction(max:largest)
        for(int i=0;i<n;++i) {
            sum+=b[i];
            if(b[i]>largest) largest=b[i];
        }
    }
    /* A kernels region must preserve this sequential dependence. */
    #pragma acc kernels copy(prefix[0:10])
    {
        for(int i=1;i<10;++i) prefix[i]+=prefix[i-1];
    }
    for(int i=0;i<n;++i) if(b[i]!=2.0*i+1.0) return 3;
    for(int i=0;i<10;++i) if(prefix[i]!=(i+1)*(i+2)/2) return 4;
    if(sum!=4096.0 || largest!=127.0) return 5;
    printf("sum=%.0f max=%.0f prefix_last=%d\n",sum,largest,prefix[9]);
    return 0;
}

sum=4096 max=127 prefix_last=55

The output confirms these three checks on the tested toolchain. It does not establish that the kernels compiler found a parallel transformation for the prefix loop. Correct preservation of a dependence often means leaving it serial. There is no timing comparison here from which to infer that kernels and parallel have equal performance, or that one is faster. Such a comparison would need generated-code inspection and controlled measurements for a particular workload.

Data regions describe storage lifetimes W9L5 2:47

Moving computation to the device creates a second program-design problem: the values must be where the computation will read them. A structured data region surrounds a block and can retain its arrays across several compute regions. Each compute region also has an implicit data environment, but repeatedly creating a short-lived environment can repeatedly transfer arrays. The Best Practices Guide's Data Regions discussion recommends widening data scope to reuse device data across computation. The scope should follow actual reuse rather than the smallest syntactic loop.

The four elementary clauses encode input and output intent. The following table assumes discrete storage, an array that is initially absent, and one simple structured lifetime with no enclosing mapping. These assumptions matter: nested present data has different reference-count behavior. “Uninitialized” means the clause supplies no initial values; the allocation is not promised to contain zeros.

ClauseAt entryAt exitTypical role
copy(a[0:n])Allocate and copy host values inCopy device values out and release storageInput modified into output
copyin(a[0:n])Allocate and copy host values inRelease storageRead-only input
copyout(a[0:n])Allocate without initializationCopy values out and release storageOutput completely assigned on device
create(a[0:n])Allocate without initializationRelease storageDevice temporary

For vector addition \(c_i=a_i+b_i\), inputs \(a,b\) need copyin, while a fully written result \(c\) needs copyout. Copying an old \(c\) into the device would transfer values never used. Copying unchanged \(a,b\) back would transfer values the host already has. The key phrase is “fully written”: if only an interior region of \(c\) is written, a subsequent whole-array copyout can overwrite meaningful host boundary values with uninitialized device entries. Either initialize those boundaries or limit the copied-out section.

For Jacobi both ping-pong arrays must contain valid boundaries before either becomes the input. The interior output of the first sweep does not assign its boundary. Using create(unew) without initializing that boundary would leave the next sweep reading unspecified values. Our finite program copies the initialized contents of both arrays in and both arrays out. It transfers more than the theoretically minimal final output, but its ownership is simple and its boundary invariant is transparent. Optimization should preserve that invariant before reducing bytes.

The present clause expresses the requirement that a specified region of data is already available in the device data environment. It is a presence assertion, not a request to copy the latest host version. The specification (§2.7.5) defines its error behavior for missing or partly present data. Using it in a computational helper documents that the caller owns the data lifetime. It also prevents that helper from quietly introducing an unplanned transfer as a substitute for an absent mapping.

Nested clauses do not mean repeated unconditional copies. OpenACC retains structured and dynamic references to mappings. In the ordinary nested case, a copyin of already-present data acquires a reference to the existing allocation rather than refreshing its values. The matching end releases the reference rather than deleting storage still owned by an enclosing lifetime. A copy nested inside an outer data region likewise does not promise to make device changes visible to the host immediately when that inner region ends. Explicit update is the tool for an actual mid-lifetime synchronization.

This distinction is an ownership rule. Think of a library function borrowing a device array from its caller. The function may use it and release its own structured reference, while the caller retains ownership. Releasing the borrower must not destroy the caller's storage. The version labels from the formal model supply a second, separate obligation: borrowing an allocation says nothing about whether the values are current. Reference lifetime is bookkeeping for existence; it is not bookkeeping for every host write.

Array sections must describe the actual storage W9L5 5:00

A C array section a[start:length] contains length elements beginning at start. The section a[8:4] means indices 8, 9, 10, 11, not 8 through 4 and not 8 through 12. The number is in elements, so four doubles mean 32 bytes. A Fortran section uses lower and inclusive upper bounds: a(9:12) contains four elements in a conventional one-based array. A literal transcription between languages can therefore transfer the wrong number of entries.

The quarter-array slide makes this visible. Its C section array[i*N/4:N/4] contains \(N/4\) entries when \(N\) is divisible by four. Its displayed Fortran lower and upper bounds differ by \(N/4\), which gives \(N/4+1\) entries under inclusive bounds. For a zero-based conceptual interval starting at \(q\) with length \(n_s\), the inclusive endpoint is \(q+n_s-1\). With conventional one-based Fortran quarters, use bounds \(iN/4+1\) and \((i+1)N/4\), for \(i=0,1,2,3\). This correction follows the visible slide and language indexing, without alleging a spoken mistake.

Multidimensional notation adds a storage-layout constraint. A rectangular interior of a row-major C array generally contains gaps between rows because each row also contains boundary columns. Such a rectangle is not the same as one contiguous interval. OpenACC 3.3 §2.7.1 requires contiguous sections for these data clauses, with complete inner extents for statically sized C dimensions. Our solver avoids an ambiguous multidimensional section by allocating each full grid as one contiguous one-dimensional array and mapping all \((N+2)^2\) elements.

A double ** is not automatically a contiguous matrix. It can point to a table of pointers whose rows are separate allocations. Copying the outer pointer or its pointer table does not establish device storage for every row. This is why storage representation belongs in the model before directive selection. Flattening the grid makes its size, alignment of logical rows, boundary locations, and lifetime explicit. It does not claim a particular optimization of device memory transactions; that is a separate mapping question.

Unstructured lifetimes require explicit ownership W9L5 10:48

Some data outlives a single lexical scope. A library can allocate in one function, compute through many calls, and free in another. enter data with copyin or create starts an unstructured device lifetime. exit data with copyout or delete releases the corresponding dynamic reference. “Unstructured” refers to where the lifetime begins and ends; it does not relax the need for a consistent owner or make deallocation automatic.

The lecture's vector-add example initially exits only the result array. Its input arrays remain mapped until their dynamic references are released. The improved example deletes them too. In a repeated simulation step, retaining an intended input is useful; retaining abandoned inputs is a leak. The same visible state can mean either reuse or a bug depending on who owns the lifetime. Write the ownership contract at the application programming interface (API) boundary: who creates the mapping, which functions borrow it, and who performs the last exit.

The simple rule “match enters and exits” is useful for one acquisition per object. Nested or repeated acquisitions require the reference-count model, and finalize has stronger release semantics. We use one entry and one exit per object, with no forced finalization. A function that deletes storage still borrowed by another component violates their shared ownership agreement even if its local enter/exit count looks balanced. Data must also remain live until all work using it has completed; this chapter uses synchronous operations so that completion precedes release.

Synchronize values during an existing lifetime W9L5 15:47

A long lifetime is useful only if the right values are used. update device(a[0:n]) transfers host values into the existing device copy. update self(b[0:n]) transfers device values into the host copy; host is an alternative name for that direction. These operations synchronize values without ending the mapping. The direction names describe the destination. They do not express which side has changed automatically. The programmer must know which version should win.

Consider a host routine that changes boundary conditions during a resident simulation. The device mapping still exists, so present succeeds. But unless the changed boundary values are copied to the device, the next sweep solves the old boundary problem. Conversely, a host diagnostic reading the array after a device sweep sees stale values until a device-to-host update or final copyout occurs. The update directive (§2.14.4) supplies these transfers; it does not decide their mathematical necessity.

The update diagram in the lecture shows a changed device array \(B\) flowing to its host copy, but the displayed self-update line names \(A\). For the arrow drawn, the operand must be \(B\). The destination rule is otherwise unchanged. It is safer to reason from source version, destination version, and required next reader than to memorize “in” and “out” without specifying the viewpoint.

The next program creates eight input entries \(a_i=i\), computes \(b_i=2i\), and explicitly updates the host output for a check. It then changes only the host input to \(100+i\). A nested compute region with copyin(a) reuses the already-present old device input: the host observes \(b_i=i\), which the program deliberately expects at this stage. Finally, update device(a) refreshes the device values and the last region produces \(2(100+i)\). No uninitialized value or race is used to demonstrate the stale version.

#include <openacc.h>
#include <stdio.h>
int main(void) {
    enum { n=8 };
    double a[n], b[n];
    int ok=1;
    if(acc_get_num_devices(acc_device_nvidia)<1) return 2;
    acc_set_device_type(acc_device_nvidia);
    for(int i=0;i<n;++i) { a[i]=i; b[i]=-1; }
    #pragma acc data copyin(a[0:n]) copyout(b[0:n])
    {
        #pragma acc parallel loop present(a[0:n],b[0:n])
        for(int i=0;i<n;++i) b[i]=2*a[i];
        #pragma acc update self(b[0:n])
        for(int i=0;i<n;++i) if(b[i]!=2*i) ok=0;
        for(int i=0;i<n;++i) a[i]=100+i;
        /* Already present: nested copyin does not refresh a. */
        #pragma acc parallel loop copyin(a[0:n]) present(b[0:n])
        for(int i=0;i<n;++i) b[i]=a[i];
        #pragma acc update self(b[0:n])
        for(int i=0;i<n;++i) if(b[i]!=i) ok=0;
        #pragma acc update device(a[0:n])
        #pragma acc parallel loop present(a[0:n],b[0:n])
        for(int i=0;i<n;++i) b[i]=2*a[i];
    }
    for(int i=0;i<n;++i) if(b[i]!=2*(100+i)) ok=0;
    printf("before_refresh=0 after_refresh=%.0f last=%.0f\n",b[0],b[n-1]);
    return ok?0:5;
}

before_refresh=0 after_refresh=200 last=214

The printed zero before refresh refers to the checked first element of the intermediate result; the last two numbers are the final output's first and last elements. The checks inside the data region record failure in a host flag rather than returning out of the structured block. This preserves structured control flow and lets the lifetime end normally. The example deliberately uses a discrete-memory target: a shared-memory execution could make host writes immediately visible and would not test this same stale-copy scenario.

Structures contain pointers as well as values W9L5 18:36

A C structure containing only inline scalar fields can be moved as one aggregate object. A structure containing a pointer describes two objects: the descriptor and the allocation it points to. Copying the descriptor copies its bits, including a host pointer value. That value is not generally a usable device address. The runtime needs a mapping for the pointee and an attachment connecting the device-side pointer to the device allocation. §2.6.4 defines these pointer actions.

The next program defines a Vector descriptor with an integer length and a dynamically allocated array. Its entry function maps the descriptor first and then the member's array section, allowing the pointer attachment action. Its compute function borrows both mappings. Its exit function copies out and releases the member before deleting the descriptor. The host pointer remains valid until the host allocation is freed after checking all 16 outputs. The size is fixed for the duration; resizing while attached would require a new lifetime and attachment plan.

#include <openacc.h>
#include <stdio.h>
#include <stdlib.h>
typedef struct { int n; double *arr; } Vector;
static void enter(Vector *v) {
    #pragma acc enter data copyin(v[0:1])
    #pragma acc enter data copyin(v->arr[0:v->n])
}
static void compute(Vector *v) {
    int n=v->n;
    #pragma acc parallel loop present(v[0:1],v->arr[0:n])
    for(int i=0;i<n;++i) v->arr[i]=3*v->arr[i]+1;
}
static void leave(Vector *v) {
    #pragma acc exit data copyout(v->arr[0:v->n])
    #pragma acc exit data delete(v[0:1])
}
int main(void) {
    Vector v={16,NULL};
    if(acc_get_num_devices(acc_device_nvidia)<1) return 2;
    acc_set_device_type(acc_device_nvidia);
    v.arr=malloc((size_t)v.n*sizeof *v.arr);
    if(!v.arr) return 3;
    for(int i=0;i<v.n;++i) v.arr[i]=i;
    enter(&v);
    compute(&v);
    leave(&v);
    int ok=1;
    for(int i=0;i<v.n;++i) if(v.arr[i]!=3*i+1) ok=0;
    printf("attached_vector first=%.0f last=%.0f verified=%d\n",v.arr[0],v.arr[v.n-1],ok);
    free(v.arr);
    return ok?0:4;
}

attached_vector first=1 last=46 verified=1

The first and last values, one and 46, follow from \(3i+1\) at indices zero and fifteen. The full elementwise check verifies the interior too. This is an actual test of the installed compiler's handling of this structure pattern. It does not establish arbitrary deep-copy support, graphs of aliased pointers, automatic C++ object construction on the device, or every possible attachment ordering. For a C++ member function, the implicit this pointer is another pointer whose referent must be available; passing a method name does not transport the object graph.

A resident Jacobi solver preserves a numerical invariant

The stencil in (24.1) fits the independence test. Iteration \((i,j)\) reads only u and writes only its own unew[i,j]. Distinct interior coordinates have distinct row-major indices: if \(i(N+2)+j=i'(N+2)+j'\), then \((i-i')(N+2)=j'-j\); the right side has magnitude less than \(N+2\), so both sides must be zero. Thus \(i=i'\) and \(j=j'\). Because the arrays do not overlap, no output can destroy another iteration's input. Collapsing the two loops exposes one iteration space of \(N^2\) pairs without changing this proof.

Each updated value is an average of four old values. If all old values lie in \([0,1]\), their average lies there too. Both arrays begin with boundary values in that interval, and only interior entries are changed. Induction therefore gives the discrete maximum-principle check \(0\le u^k_{i,j}\le1\) at every completed sweep. After the first sweep, the interior row next to the unit top edge is one quarter and deeper interior rows remain zero. These hand checks help distinguish an accidentally stable but wrong stencil from the intended one.

There is another relationship to inspect before choosing a stopping test. Define the discrete Laplacian of the old grid by \(\Delta_hu_{i,j}=(u_{i-1,j}+u_{i+1,j}+u_{i,j-1}+u_{i,j+1}-4u_{i,j})/h^2\). Subtracting \(u^k_{i,j}\) from (24.1) gives \(u^{k+1}_{i,j}-u^k_{i,j}=h^2\Delta_hu^k_{i,j}/4\). Hence \(\|\Delta_hu^k\|_\infty=4r_k/h^2\). A fixed update tolerance becomes a different residual threshold as the grid is refined. Neither quantity alone bounds the continuum error without additional analysis.

The program below implements jacobi_step with a maximum reduction. The host loop calls it synchronously, receives the norm, swaps two host pointer aliases, and checks the iteration conditions. The allocations named a and b remain fixed in the outer data clause; only the aliases u and unew swap. A present clause resolves the current alias to the corresponding existing allocation. Copying out both original allocations at the end makes either parity of the final pointer safe. Freeing either allocation before that end would invalidate the mapping.

Inputs are fixed: \(N=32\), tolerance \(10^{-8}\), and iteration caps of 63 and 64 in two independent runs. The CPU reference uses ordinary loops with separate storage. The program checks every final value, including boundaries, for finiteness and the interval bound; compares the whole grid and final update norm to the serial calculation within \(10^{-12}\); and verifies the step counts. The two parities are intentional: a driver that always returns the original allocation can accidentally pass an even-step test and fail an odd-step test. Total host arrays occupy 36,992 bytes; the two explicit device grids occupy 18,496 bytes, excluding runtime bookkeeping.

#include <openacc.h>
#include <math.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#define IDX(i,j) ((i)*(N+2)+(j))
static double jacobi_step(int N,const double *u,double *unew) {
    int M=(N+2)*(N+2);
    double diff=0;
    #pragma acc parallel loop collapse(2) present(u[0:M],unew[0:M]) reduction(max:diff)
    for(int i=1;i<=N;++i) for(int j=1;j<=N;++j) {
        int k=IDX(i,j);
        double v=0.25*(u[k-(N+2)]+u[k+(N+2)]+u[k-1]+u[k+1]);
        unew[k]=v;
        double d=fabs(v-u[k]);
        if(d>diff) diff=d;
    }
    return diff;
}
static double serial_step(int N,const double *u,double *unew) {
    double diff=0;
    for(int i=1;i<=N;++i) for(int j=1;j<=N;++j) {
        int k=IDX(i,j);
        unew[k]=0.25*(u[k-(N+2)]+u[k+(N+2)]+u[k-1]+u[k+1]);
        double d=fabs(unew[k]-u[k]);
        if(d>diff) diff=d;
    }
    return diff;
}
static void init(int N,double *a,double *b) {
    int M=(N+2)*(N+2);
    memset(a,0,(size_t)M*sizeof *a);
    memset(b,0,(size_t)M*sizeof *b);
    for(int j=1;j<=N;++j) a[IDX(0,j)]=b[IDX(0,j)]=1;
}
int main(void) {
    const int N=32, M=(N+2)*(N+2);
    double *a=malloc((size_t)M*sizeof *a), *b=malloc((size_t)M*sizeof *b);
    double *r=malloc((size_t)M*sizeof *r), *s=malloc((size_t)M*sizeof *s);
    if(!a||!b||!r||!s) { free(a);free(b);free(r);free(s);return 2; }
    if(acc_get_num_devices(acc_device_nvidia)<1) return 3;
    acc_set_device_type(acc_device_nvidia);
    for(int max_iter=63;max_iter<=64;++max_iter) {
        const double tol=1e-8;
        init(N,a,b); init(N,r,s);
        double *u=a,*unew=b,*ref=r,*refnew=s;
        int steps=0,refsteps=0;
        double diff=1,refdiff=1;
        #pragma acc data copy(a[0:M],b[0:M])
        {
            while(steps<max_iter && diff>tol) {
                diff=jacobi_step(N,u,unew);
                double *tmp=u;u=unew;unew=tmp;
                ++steps;
            }
        }
        while(refsteps<max_iter && refdiff>tol) {
            refdiff=serial_step(N,ref,refnew);
            double *tmp=ref;ref=refnew;refnew=tmp;
            ++refsteps;
        }
        double err=0;
        for(int k=0;k<M;++k) {
            if(!isfinite(u[k]) || u[k]<0 || u[k]>1) return 4;
            double e=fabs(u[k]-ref[k]); if(e>err) err=e;
        }
        if(steps!=max_iter || refsteps!=steps || err>1e-12 || fabs(diff-refdiff)>1e-12) return 5;
        printf("steps=%d status=iteration_cap serial_match=%d bounds=pass\n",steps,err<=1e-12);
    }
    free(a);free(b);free(r);free(s);
    return 0;
}

steps=63 status=iteration_cap serial_match=1 bounds=pass
steps=64 status=iteration_cap serial_match=1 bounds=pass

Both runs reach their iteration caps, and the output identifies this explicitly. A serial match validates the parallel and data-lifetime transformation for these finite cases; it does not independently prove the shared stencil formula, the correctness of the physical boundary problem, or convergence on a larger grid. The independence proof, first-sweep calculation, range invariant, serial comparison, and pointer-parity test address different failure modes. Agreement between two implementations alone would be weaker if both copied the same wrong formula.

The maximum reduction returns a host scalar each sweep because the host needs it for stopping. This is a small synchronization and transfer cost even when both large arrays remain resident. Checking only every several sweeps could reduce host/device interaction, but it changes the stopping schedule and must be analyzed separately. Replacing Jacobi with an in-place update to save one array would change both its dependency structure and its numerical iteration. The present code favors an auditable invariant over an unstated algorithm change.

Separate array traffic, launch cost, and device work

Let \(m=8(N+2)^2\) be the bytes in one grid array, and let \(K\) be a fixed number of completed sweeps. Consider an intentionally simple policy that copies both arrays in and out for each sweep. Its explicit array traffic is \(Q_{\rm naive}=4Km\) bytes: two arrays enter and two leave each time. Keeping both arrays resident across all sweeps gives \(Q_{\rm resident}=4m\). This counts transfers requested by these policies on a discrete-memory target; it is not a trace of all runtime transactions or of cache traffic inside the GPU.

With the opening values \(N=1024\), \(m=8{,}421{,}408\), and \(K=1000\), the two counts are 33,685,632,000 and 33,685,632 bytes. Their ratio is exactly 1000. A norm of eight bytes returned per sweep adds 8000 bytes of scalar payload, small in byte count but accompanied by synchronization. Launch metadata, allocation management, driver work, and protocol overhead are omitted from the array count. A ratio of counted bytes is not a ratio of program runtimes.

For an illustrative time model, let \(B_t\) be effective host–device transfer bandwidth in bytes per second, \(\alpha_t\) the fixed cost of one transfer in seconds, \(\ell\) one synchronous kernel launch/completion overhead in seconds, and \(t_c\) the useful device computation time per sweep. Assume symmetric transfer bandwidth, four bulk transfers under each copy cycle, no overlap, and unchanged computation. Ignore allocation and scalar-norm costs temporarily. Write \(T_{\rm naive}\) and \(T_{\rm resident}\) for the estimated total execution times under the respective policies. The resulting estimates are

\[ T_{\rm naive}\approx Kt_c+K\ell+4K\alpha_t+\frac{4Km}{B_t},\qquad T_{\rm resident}\approx Kt_c+K\ell+4\alpha_t+\frac{4m}{B_t}. \tag{24.2} \]

Residency eliminates repeated large-array movement in this model but does not eliminate \(K\) launches or \(K\) computations. If useful device work is very small, the launch term can dominate. If computation is very large, changing transfer policy has a smaller effect on total time. The formula also explains why reading a complete grid back every sweep defeats the original locality objective even though the arrays remain allocated.

Take hypothetical \(B_t=10^{10}\) bytes/s, or 10 GB/s, and set transfer latency to zero just to isolate the byte term. The naive transfer contribution is 3.3685632 seconds; the resident contribution is 0.0033685632 seconds. These numbers are arithmetic examples, not measurements of the laptop. If useful computation plus launch cost were 0.5 seconds in both policies, the totals would be about 3.869 and 0.5034 seconds, a ratio about 7.69 rather than 1000. Adding positive transfer latency changes both totals according to their transfer counts.

GPU-local memory traffic is another boundary. A stencil reads neighboring values and writes an output within device memory; caches can reuse those reads. The host–device byte count above says nothing directly about that internal traffic or its bandwidth. Nor does it give arithmetic intensity unless the memory boundary and operation count are specified. There are at least two bandwidth questions: how efficiently arrays reach the GPU, and how efficiently resident kernels use its own memory system. Data regions mainly address the first.

A defensible measurement would fix the grid, precision, stopping rule or sweep count, and included work; warm up or report first-use effects; repeat trials; and verify results for each variant. End-to-end time includes the transfers and final completion required for a usable answer. A kernel-only interval excludes them and must be named accordingly. This chapter makes no timing listing, so no compile-startup duration or host-fallback result is promoted into a performance number. The model identifies what a future experiment must distinguish.

What has been established and what remains target-dependent

Five complete programs were compiled and executed with the installed GCC offload toolchain on 2026-10-28 UTC. Their checks establish the finite pairing results, scalar reductions, preservation of the prefix recurrence under kernels, nested-present behavior followed by explicit update, one descriptor-and-pointee attachment pattern, and resident Jacobi agreement at two iteration parities. The device witness reports NVIDIA execution. This is stronger than merely recognizing a pragma and narrower than validating every OpenACC feature or every input.

The compiler emitted a vector-length warning for the serial witness and linker warnings about relocations in a position-independent executable; all checks completed with exit code zero. Those diagnostics are retained in the execution evidence. A successful run does not erase them or certify compatibility with another compiler, driver, GPU, or memory model. In particular, documentation of a standard feature is different evidence from execution of that feature by an installed implementation.

Source portability still leaves tuning choices. We have not measured gang/worker/vector geometry, asynchronous overlap, transfer bandwidth, GPU speedup, or multiple devices. All compute and transfer phases here are synchronous. Adding async would require explicit completion edges before host reads, pointer lifetime endings, and result timing; the next chapter develops those obligations. The traffic example identifies avoided array payload under explicit assumptions and makes no empirical throughput claim.

Numerical correctness also has layers. Serial agreement checks an implementation transformation. The maximum principle checks an invariant of the stencil. The update norm checks progress of an iteration. None alone validates the physical model or bounds discretization error. Preserve these separate tests when optimizing: an impressive kernel rate is irrelevant if it solves the wrong boundary problem or returns the previous ping-pong buffer.

Six exercises with reasoned solutions

1. Counterexample: independent indices but overlapping arguments

The pairing function writes output[i]=input[2*i]+input[2*i+1]. For four initial inputs 10, 2, 3, 4 and two outputs, suppose output=input+2. Identify a conflicting pair of accesses and give two possible results according to execution order. Would testing only inputs 1, 2, 3, 4 expose the problem?

Solution

Iteration zero writes input[2], which iteration one reads. With zero first, that entry becomes \(10+2=12\), then one reads 12 and four to produce 16. With one first, it reads the original three and four, producing seven at position three, after which zero writes 12 at position two. The two output pairs are therefore \((12,16)\) and \((12,7)\). The dependence sets intersect: \(W_0\cap R_1\) contains input position two. For arbitrary inputs, the overlap invalidates the independence proof.

The alternative inputs 1, 2, 3, 4 accidentally hide the conflict: zero writes three over an existing three, so both illustrated orders give \((3,7)\). Observing one successful answer cannot establish independence. Separate input/output allocations or explicitly constrain overlap. This is a deterministic analysis of conflicting accesses, not an experiment that depends on provoking one race outcome.

2. Derive a residual tolerance from the update norm

Derive the relation between \(r_k\) in (24.1) and the maximum norm of the old grid's discrete Laplacian. For \(N=99\), what update tolerance ensures this discrete residual is at most \(10^{-3}\)? Does that certify the continuum solution's error?

Solution

Subtract the old center value from the neighbor average and multiply by four. The numerator is exactly \(h^2\Delta_hu^k_{i,j}\). Taking the largest absolute value gives \(\|\Delta_hu^k\|_\infty=4r_k/h^2\). Here \(h=1/100=0.01\), so \(h^2=10^{-4}\). Requiring \(4r_k/10^{-4}\le10^{-3}\) gives \(r_k\le2.5\times10^{-8}\). Using a fixed \(10^{-3}\) update tolerance instead would allow a residual as large as 40.

This bounds a discrete equation residual, not directly the discretization error or continuum temperature error. Converting residual to discrete solution error needs an inverse-operator bound and consistent boundary conditions. Comparing that discrete solution with the continuum solution additionally needs a discretization analysis, with attention to the non-smooth corner boundary data. The arithmetic does not provide those missing steps.

3. Compute a transfer budget and reject an invalid speedup claim

For \(N=1024\) and \(K=1000\), reproduce the naive and resident array-traffic counts. Suppose a hypothetical transfer bandwidth is 10 GB/s and all other work totals 0.5 seconds. Ignore latency. Compute the two total times and explain why a 1000-fold byte reduction does not imply a 1000-fold program speedup.

Solution

One array has \(m=8(1026)^2=8{,}421{,}408\) bytes. Four copies per sweep give \(4Km=33{,}685{,}632{,}000\) bytes; four copies for one resident lifetime give \(4m=33{,}685{,}632\) bytes. Dividing by \(10^{10}\) bytes/s gives 3.3685632 and 0.0033685632 seconds. Add the unchanged 0.5 seconds to obtain 3.8685632 and 0.5033685632 seconds. Their ratio is approximately 7.69.

The byte ratio concerns one component of the time. Useful work and launches remain. In the limiting case that those unchanged terms dominate, eliminating transfers barely changes total time. With positive transfer latency the naive policy also pays many more fixed costs, but their actual values require measurement. Nothing in this hypothetical calculation supplies the laptop's measured bandwidth or speedup.

4. Diagnose a present but stale boundary array

An outer data copyin(a[0:n]) region is active. A host routine changes a[0] from zero to one. A helper uses parallel loop copyin(a[0:n]), expecting the device to read one. Explain the failure on separate host/device storage and repair it. Would replacing copyin with present alone repair it?

Solution

The outer region already owns a device mapping initialized with zero at that location. The host assignment changes \(v_H(a)\) but leaves \(v_D(a)\) unchanged. The nested copyin normally acquires the present allocation; it does not unconditionally refresh it. The helper therefore reads the old device value zero. Use update device(a[0:1]) after the host assignment and before the helper to copy the one required element, provided that section is valid within the existing mapping.

Changing the helper to present makes its lifetime assumption clearer but does not synchronize values. Conversely, a host diagnostic after device modification needs update self in the opposite direction. With asynchronous execution, completion ordering would be an additional obligation; this exercise assumes synchronous phases. On shared-memory targets the bug may be hidden by direct access to the same storage, which is why correctness testing should include the intended separate-memory model.

5. Design judgment: who owns a vector's device storage?

A library constructs a descriptor with a pointer, performs ten compute calls, then destroys it. Should each compute call independently enter and exit all data, or should construction and destruction own one unstructured lifetime? State the safe ordering and one condition under which the second design becomes invalid.

Solution

If the same vector remains valid across calls and intermediate host access is controlled, one lifetime owned by construction/destruction avoids repeated transfers. Map the descriptor, map its pointee with the required attachment, let compute calls borrow both through present clauses, copy out needed results, release the pointee, then release the descriptor. Only afterward free the host storage. Ownership belongs to the library object; a borrowed compute call must not delete it.

The design becomes invalid if the host reallocates the array while retaining the old mapping and attachment. The new host pointer and storage interval no longer describe the mapped object. Reallocation needs an explicit transition that completes existing work, releases or updates the old mapping, and establishes the new descriptor/pointee relationship. Repeated unrelated vectors can instead justify separate shorter lifetimes. Lifetime length follows semantic reuse, not a universal preference for unstructured directives.

6. Implementation check: expose a ping-pong parity error

A solver swaps u and unew correctly during iteration but always returns the original allocation a. Design a finite test that exposes this without a timing measurement. Explain the checks already provided by the printed Jacobi program and a useful extension for a production solver.

Solution

Initialize both buffers identically at boundaries and set the interior to zero. After one sweep, the top interior row becomes one quarter in the updated buffer while the original interior remains zero. Returning the original allocation therefore fails immediately. After two sweeps the newest result returns to the original allocation, so a test restricted to even counts can hide the bug. Check both an odd and an even count and compare the buffer identified by the final active pointer against a serial reference.

The printed program uses 63 and 64 capped sweeps, compares every stored cell and the final norm, checks finiteness and bounds, and checks that the expected cap was reached. These tests exercise data lifetime, reduction, and pointer parity without asserting convergence. A production extension should also include a case that genuinely meets its tolerance before the cap and confirms that the returned buffer and reported norm correspond to the same final sweep. Another useful independent check is a manufactured discrete solution or a known small-grid solution; serial agreement alone can share a formula error. Any added experiment must report its actual completion status and preserve the same bounded-resource discipline.
