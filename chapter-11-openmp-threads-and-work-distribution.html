OpenMP I: shared-memory threads and the distribution of work

A loop of \(10^{9}\) independent iterations computes \(\pi\) by the midpoint rule. On one thread it runs in about 1.0 s on the machine used for this chapter. The loop reads and writes no array, so a model with perfect division of work predicts \(T_p=T_1/p\), which is 0.08 s on 12 threads. The first parallel version in the lecture, timed on the machine named in the slide (a dual-core Intel Core i5 at 1.7 GHz), took 1.86 s on one thread, 1.03 s on two and 0.97 s on four, a speedup of 1.9 on four threads. The same algorithm, compiled without optimization on this chapter's machine, reaches a speedup of 1.3 on four threads; with its partial sums moved 64 bytes apart it reaches 2.8; no build exceeds 4.5 on any team size up to 24. This chapter defines the execution model of OpenMP threads, shows how the iterations of a loop are assigned to threads, derives the bounds that the numbers must satisfy, and identifies which of them the measurements violate and why.

The objects of the chapter and the running case

The chapter studies one kind of program: a sequential program in which some regions are executed by several threads that share memory. A thread is a sequence of instructions with its own program counter and its own call stack. The threads of one process address the same memory. The operating system decides on which processor, and when, each thread runs.

The formal model has four parts. Execution. An event is one execution of one operation by one thread. The events of one thread are totally ordered by program order. A parallel region is a block of code that a team of \(p\) threads executes. The thread that reaches the region is the encountering thread; it becomes thread number 0 of the new team, and the other threads of the team have the numbers \(1,\dots,p-1\). The fork orders the encounter before the first event of every team thread. The join orders the last event of every team thread before the first event after the region. Two events of different team threads inside one region are unordered unless a synchronization construct orders them; this chapter uses no construct that does so, apart from the join. A schedule is a total order of all events that respects program order, the fork and the join. The operating system and the hardware choose the schedule; the program does not. Storage. A memory unit is a location that one load or store accesses as a whole. A shared variable is one object, made of one or more memory units, that every thread of the team references. A private variable is a separate object for each thread. Cost. Each thread \(t\) of a region spends a time \(w_t\) on its share of the work, and the region lasts as long as its slowest thread plus the cost of forking and joining. Performance symbols. \(p\) is the number of threads in the team, \(m\) the number of logical processors of the machine, \(T_1\) and \(T_p\) the wall-clock times of the program on one and on \(p\) threads, \(S_p=T_1/T_p\) the speedup, \(E_p=S_p/p\) the parallel efficiency, \(f\) the serial fraction of \(T_1\) (defined exactly in the section on Amdahl's law), \(\kappa\) the cost, per thread, of starting and ending a parallel region, and \(b=64\ \mathrm{B}\) the size of a cache line. Each symbol is repeated at its first substantive use.

The running case is the midpoint-rule computation of \(\pi\). The integral \(I=\int_0^1 \frac{4}{1+x^2}\,dx\) equals \(\pi\). For \(N\) subintervals of width \(h=1/N\), the midpoint rule is \(M_N=h\sum_{i=0}^{N-1}f\bigl((i+\tfrac12)h\bigr)\) with \(f(x)=4/(1+x^2)\). The lecture uses this problem because its \(N\) iterations are independent: no iteration reads a value that another iteration writes. The only dependence is the final addition of the \(N\) terms.

OpenMP is directives, a runtime library and environment variables W3L6 0:06

The lecture describes OpenMP as an application programming interface (API) for writing parallel applications, built from compiler directives and library routines, and motivates it by the research groups that own legacy serial codes and cannot rewrite them from the start. The directives let a programmer parallelize an existing Fortran, C or C++ program one region at a time. The lecture adds that later versions of the interface handle non-uniform memories, vectorization and GPU programming. Dagum and Menon (1998) describe OpenMP, in the abstract of their paper, as a set of compiler directives and callable runtime library routines that extend Fortran, and separately C and C++, to express shared-memory parallelism, with accompanying environment variables; the abstract states that OpenMP builds on the X3H5 concepts and extends them to coarse-grain parallelism (IEEE Computational Science & Engineering 5(1), pp. 46–55; only the abstract could be read). The three parts named there are the ones the lecture's solution stack shows: directives processed by the compiler, a runtime library, and environment variables, resting on an operating system with thread support and on the hardware.

The lecture dates the start of the specification to about 1997. Menon's 1998 conference slides give the dates of the first two specifications as October 1997 for Fortran 1.0 and August 1998 for C/C++ 1.0 (Menon, Cray User Group 1998, slide 5); the slides do not say whether the second date was planned or achieved. The lecture also shows that the length of the specification grew across versions and states that the interface covers many more features than a short course can treat. It therefore limits itself to the "common core" of 21 items: the parallel construct, the routines that set and query the number of threads and the thread number, the timer, the OMP_NUM_THREADS variable, barrier and critical synchronization, work-sharing loops, reductions, loop schedules, data-sharing clauses, nowait, single and tasks. This chapter covers the first group, up to the timer and the environment variable. Chapter 12 covers synchronization, loop work-sharing, schedules and data-sharing clauses, and chapter 13 the memory model and tasks.

The lecture restricts itself to a symmetric multiprocessor: a multi-core processor with one shared address space in which every core reaches every memory location at about the same cost. It excludes non-uniform memory access and GPUs from this part. The restriction is part of the model of this chapter. The cost of a memory access is treated as independent of which thread makes it, except where the section on false sharing shows an effect of the caches.

The directive syntax in C and C++ is #pragma omp construct [clause [clause]…]. The Fortran form is !$OMP construct. A construct applies to the structured block that follows it: a block with one point of entry at the top and one point of exit at the bottom (the lecture's slide; OpenMP 5.2 §4.3, p. 76, adds that a structured block may call exit(), as the lecture says). A program that uses library routines includes omp.h and is compiled with an OpenMP flag, -fopenmp for gcc. A compiler that supports a preprocessor defines the macro _OPENMP as yyyymm, the year and month of the specification version it supports (§3.3, p. 69). The gcc 13.3 used here defines it as 201511, the date of version 4.5. This chapter takes its definitions from version 5.2 (November 2021); every construct and routine it uses is also accepted by this compiler.

The specification states one more property that governs how a directive is read. The interface is intended to support programs that execute correctly both as parallel programs and as sequential programs, with the directives ignored and a stub library supplied. It then states that a conforming program may execute correctly as a parallel program and not as a sequential program, or may produce different results as a parallel program (§1.3, p. 23). A directive is therefore not a hint that leaves the result unchanged. It changes what the program means, and the programmer must establish that the changed program is correct.

The model explains how many outputs are possible. The lecture's two definitions, stated at W3L6 14:14, are these. Tasks are concurrent when several are active, none is ordered with respect to the others, and each makes forward progress under some scheduling policy. They execute in parallel when they make forward progress at the same time. A program on one processor can therefore be concurrent without being parallel. The lecture names the converse case as well: tasks that run in lock step, as in SIMD (single instruction, multiple data) execution, are parallel without being concurrent in this sense. For the set of possible results, the distinction does not matter: the model of the previous section describes both cases by the set of schedules. Each thread executes the events \(H\) (print hello ) and \(L\) (print world\n, which ends the line) in this order. With \(p\) threads there are \(2p\) events, partitioned into \(p\) chains of length 2. A schedule is an interleaving of the chains, and the number of interleavings is the multinomial coefficient \((2p)!/(2!)^p\): 6 for \(p=2\), 90 for \(p=3\), 2520 for \(p=4\). An output is the string of \(H\) and \(L\) symbols, because the threads print the same text. A string is a possible output exactly when every prefix has at least as many \(H\) as \(L\), since each \(L\) is preceded by the \(H\) of its own thread; every such string arises from some schedule. These strings are the ballot sequences, and their number is the Catalan number \(\mathrm{Cat}_p=\binom{2p}{p}/(p+1)\): 2, 5 and 14 for \(p=2,3,4\), and 208 012 for \(p=12\). The model assumes that one printf call is not divided by another call, which is consistent with the whole strings in the lecture's sample output. The listing enumerates all schedules for \(p\le4\) and checks both counts. It is a check for small \(p\), not a proof of the general formula.

"""Count the executions and the distinct outputs of p threads that each run H then L."""
from math import factorial


def executions(chains):
    """Yield every interleaving of the chains that keeps each chain's own order."""
    if all(not c for c in chains):
        yield ()
        return
    for k, c in enumerate(chains):
        if c:
            rest = chains[:k] + (c[1:],) + chains[k + 1:]
            for tail in executions(rest):
                yield ((k, c[0]),) + tail


print(" p  executions  (2p)!/2^p  distinct outputs")
for p in (2, 3, 4):
    chains = tuple(("H", "L") for _ in range(p))     # H prints "hello ", L prints "world\n"
    runs = list(executions(chains))
    outputs = {"".join(event for _, event in run) for run in runs}
    print(f"{p:2d} {len(runs):11d} {factorial(2 * p) // 2**p:10d} {len(outputs):17d}")

Fork–join execution and the size of the team W3L6 17:55

The lecture states the OpenMP execution model as fork–join parallelism. The program starts as one thread, the initial thread. At each parallel construct the encountering thread forks a team of threads. When the region ends, the team ends, and the program continues as one thread until the next region. A region can contain another region; the lecture's slide draws one nested region. The specification gives the same model (§1.3, pp. 23–24) and adds that a nested region creates a team of one thread when nested parallelism is disabled. This chapter uses one level of parallelism.

The specification fixes three properties of a team that the model needs. When a thread encounters a parallel construct, it becomes the primary thread of the new team with thread number zero. All threads of the team, including the primary thread, execute the region, and the number of threads in the team stays constant until the region ends. The thread numbers are consecutive whole numbers from zero to one less than the team size (§10.1, p. 223). An implicit barrier ends the region. After it, only the primary thread continues (§1.3, p. 24). The routine omp_get_thread_num returns the caller's thread number, and omp_get_num_threads returns the size of the team of the innermost enclosing region (§18.2.2, p. 349). Outside any parallel region both describe the initial thread: the team size is 1 and the thread number is 0.

How many threads the team has. The lecture states that the number is determined by the operating system through an environment variable, and that a program can set it with omp_set_num_threads. The specification places the decision in the runtime, not the operating system, through the internal control variable nthreads-var. Its initial value is implementation defined, and the environment variable OMP_NUM_THREADS sets it (§21.1.2, p. 600). The routine omp_set_num_threads sets it for the subsequent regions of the calling task (§18.2.1, p. 348), so a call in the program takes precedence over the environment variable for those regions. Algorithm 2.1 of the specification (§10.1.1, pp. 226–227) then determines the actual size. If the variable dyn-var (dynamic adjustment) is false and the requested number does not exceed the available number, the team has exactly the requested size. If dyn-var is true, the team has between one and the requested number of threads. If dyn-var is false and the request exceeds the available number, the behavior is implementation defined. The lecture's statement that a system may give fewer threads than requested refers to these last two cases. The consequence for programs is that the requested size is not a guarantee. A program must read the team size inside the region.

The lecture sets 24 threads on a machine with 8 processors. The 24 threads run in turn on the 8 processors, and the greetings arrive in another order. The model is unchanged: there are 24 chains and the operating system chooses the schedule. What changes is the cost, which the section on overhead measures.

The next program checks these statements. It reads _OPENMP and the team size and thread number outside a region, calls omp_set_num_threads(4) while the environment requests 6 threads, and then runs a region in which every thread increments the element of an array selected by its own thread number. The elements are distinct memory units, so the writes do not conflict. The program prints how many threads had each thread number. Its output is the same for every schedule, so the check is exact. The run uses OMP_NUM_THREADS=6.

Shared and private storage, redundant execution and the data race W4L1 1:41

The lecture's example creates a team of 4 threads that each call a function pooh(ID, A), where A is an array of 1000 doubles declared before the region and ID is the thread number, followed by printf("all done\n") after the region. The lecture draws four calls pooh(0,A) to pooh(3,A) side by side, one copy of A shared by all, and a barrier before the printf. Two statements follow from this example. First, the threads execute the same code redundantly, and the only difference between them is the value of ID. If pooh ignores its first argument, the program does \(p\) times the work of the serial program, and \(T_p\ge T_1\) even with perfect parallel hardware. A region reduces the time only when the threads use their thread number or the team size to divide the work. Second, the end of the region is a barrier: all done prints once, after every thread has finished.

Which variables are shared. The lecture states two rules for the data in a region. A variable declared before the region is shared by all threads, and a variable declared inside the region is private to each thread. The specification states the same rules for C and C++ (version 5.2, §5.1.1, p. 97 for the predetermined rule and p. 99 for the implicit rule). A variable with automatic storage duration declared in a scope inside the construct is private. In a parallel construct without a default clause, a variable that is referenced but declared outside is shared. Here A is shared, and ID, declared inside the block, is private: each thread has its own variable of that name. Chapter 12 treats the other attributes and the clauses that change them.

The data race. Shared data are useful because threads can exchange results through them, and dangerous for the same reason. The specification defines the hazard in its memory model (§1.4.1, p. 27): two memory operations are unordered if the memory consistency guarantees of §1.4.6 do not specify the order in which they must complete. "If multiple threads write to the same memory unit (…) then a data race occurs if the writes are unordered. Similarly, if at least one thread reads from a memory unit and at least one thread writes to that same memory unit then a data race occurs if the read and write are unordered. If a data race occurs then the result of the program is unspecified." In the model of this chapter, two operations on the same memory unit by different threads of one region, at least one of which is a write, are in a data race unless a fork, a join or a synchronization construct orders them. The other orderings that the specification lists belong to chapter 13. The definition has two consequences. The result of a program with a race is not merely uncertain among a few values: the specification assigns it no meaning. And the definition refers to memory units. Two threads that write different elements of an array write different memory units, because the minimum unit that an update may rewrite along with its neighbours is no larger than the base language requires (p. 27). The writes do not race even if the elements are adjacent. The next sections show that adjacent elements can still cost time.

A race observed. The program below has four threads that each increment a shared counter 1 000 000 times and also increment a private counter. The shared counter is volatile, which forces the compiler to load it and store it in every iteration; volatile is a property of the C language that stops the compiler from keeping the value in a register. It does not make the increment indivisible and does not order it with respect to other threads, so it does not prevent the race. Without it, an optimizing compiler would keep the counter in a register and the program would not show the effect. Each thread then stores its private count in its own slot of an array, and the initial thread adds the slots after the join. The expected value is 4 000 000. A schedule that loses updates is the following: thread A loads the value 7, thread B loads the value 7, both store 8, and one increment is lost. The run is one sample on this machine, and a data race has no defined result, so another run prints another value for the shared counter. The program is correct only in its last line, because the private partial counts are written to distinct memory units and the join orders them before the sum.

#include <stdio.h>
#include <omp.h>

#define PER_THREAD 1000000L
#define THREADS 4
#define PAD 8

static volatile long shared_count = 0;   /* one location, written by every thread */
static long partial[THREADS * PAD];      /* one location per thread, 64 bytes apart */

int main(void)
{
    #pragma omp parallel num_threads(THREADS)
    {
        int id = omp_get_thread_num();
        long mine = 0;                    /* declared inside the block: private */
        for (long k = 0; k < PER_THREAD; k++) {
            shared_count++;               /* load, add, store: not atomic */
            mine++;
        }
        partial[id * PAD] = mine;
    }
    long total = 0;
    for (int t = 0; t < THREADS; t++) total += partial[t * PAD];
    printf("expected             %ld\n", PER_THREAD * THREADS);
    printf("shared counter       %ld\n", (long)shared_count);
    printf("sum of private parts %ld\n", total);
    return 0;
}

The midpoint rule for \(\pi\): cost and error W4L1 5:34

The lecture computes \(\pi\) from \(\int_0^1 4/(1+x^2)\,dx\) by summing the areas of rectangles of equal width whose height is the integrand at the middle of the interval. The slide writes the sum from \(i=0\) to \(N\), which has \(N+1\) terms, and the code on the next slides loops \(i=0,\dots,N-1\); this chapter uses the \(N\) terms of the code. The lecture then states that a larger number of steps gives a more accurate answer at a higher cost. This section states how much more.

Cost. Each iteration computes x = (i + 0.5) * step (one addition, one multiplication), 1.0 + x * x (one multiplication, one addition), 4.0 / (…) (one division) and sum += (one addition): six floating-point operations, so \(F=6N\). The loop reads and writes no array, so the data moved between memory and the processor is negligible and the loop is limited by the arithmetic, in particular by the division and by the dependence of each addition on the previous sum. On this machine the one-thread loop with \(N=10^{9}\) takes about 1.0 s in the timing listing of the false-sharing section, which is 1.0 ns per iteration and 6 Gflop/s by this count of six operations. Because no iteration depends on another except through the sum, the work can be divided among threads without changing any single term.

Error. Let \(E_N=I-M_N\) be the error and \(M\) a bound with \(|f''(x)|\le M\) on \([a,b]=[0,1]\). The condition on the derivative is that \(f\) has a continuous second derivative. On the subinterval of width \(h\) centred at \(c\), Taylor's theorem with the integral remainder gives \(f(x)=f(c)+f'(c)(x-c)+R(x)\) with \(|R(x)|\le\tfrac12M(x-c)^2\). The linear term integrates to zero over the symmetric interval, so the integral over the subinterval differs from \(h f(c)\) by at most \(\tfrac12M\int_{-h/2}^{h/2}s^2\,ds=Mh^3/24\). Summing the \(N\) subintervals, with \(Nh=b-a\), gives the bound of OpenStax Calculus Volume 2, Theorem 3.5 (eq. 3.12),

\[ |E_N|\le\frac{M(b-a)h^2}{24}. \tag{11.1} \]

For \(f(x)=4/(1+x^2)\), the derivatives are \(f'(x)=-8x/(1+x^2)^2\), \(f''(x)=(24x^2-8)/(1+x^2)^3\) and \(f'''(x)=96x(1-x^2)/(1+x^2)^4\). The third derivative is positive on \((0,1)\), so \(f''\) increases from \(-8\) at \(x=0\) to \(2\) at \(x=1\), and \(M=\max|f''|=8\), attained at \(x=0\). Equation (11.1) gives \(|E_N|\le h^2/3\).

The bound is not sharp. Apply the same Taylor expansion one order further: the integral over a subinterval equals \(hf(c)+\tfrac{h^3}{24}f''(c)+O(h^5)\). Summing, the error is \(\tfrac{h^2}{24}\,h\sum_i f''(c_i)+O(h^4)\), and the sum \(h\sum_i f''(c_i)\) is itself a midpoint sum for \(\int_0^1 f''\,dx=f'(1)-f'(0)\). For a function with four continuous derivatives this gives

\[ I-M_N=\frac{h^2}{24}\bigl[f'(b)-f'(a)\bigr]+O(h^4). \tag{11.2} \]

Here \(f'(1)=-2\) and \(f'(0)=0\), so \(I-M_N=-h^2/12+O(h^4)\): the midpoint sum overestimates \(\pi\) by \(h^2/12\), which is one quarter of the bound \(h^2/3\). Applying the argument once more to the sum of \(f''\) gives the next term as \(-\tfrac{7h^4}{5760}[f'''(b)-f'''(a)]\); that quantity is zero here because \(f'''(0)=f'''(1)=0\). The listing evaluates \(M\) on a grid and prints the ratio \((M_N-\pi)/(h^2/12)\) for \(N=10,100,1000\), together with the check of (11.1). The program is serial and deterministic, so the check is exact.

The SPMD program: cyclic and block distribution of iterations W4L1 10:53

The lecture's parallel program is a single program that every thread executes, with the work divided by the thread number and the team size. The lecture calls the pattern single program, multiple data (SPMD). Its structure has five steps. The program fixes the team size with omp_set_num_threads. Inside the region each thread reads its number \(\mathrm{id}\) and the team size \(n_{\text{thr}}\) (the slides write numthrds and nthrds). Thread 0 copies the team size to the shared variable nthreads, so that only one thread writes it. Each thread sums its own iterations into sum[id], an array promoted from the scalar. After the region, one loop adds the partial sums, in thread order, and multiplies by \(h\). The last loop is serial: the lecture notes that the global sum is computed outside the parallel region.

Why the loop can be divided. Let \(\mathrm{Rd}(i)\) be the set of memory units that iteration \(i\) reads and \(\mathrm{Wr}(i)\) the set that it writes. Two iterations \(i\ne j\) are independent if \(\mathrm{Wr}(i)\) is disjoint from \(\mathrm{Rd}(j)\cup\mathrm{Wr}(j)\) and \(\mathrm{Wr}(j)\) is disjoint from \(\mathrm{Rd}(i)\); independent iterations may run in any order or at the same time without changing the result, and a loop whose iterations are pairwise independent has no loop-carried dependence. In the \(\pi\) loop, iteration \(i\) reads \(i\), step, x and sum, and writes x and sum. The variable x is declared inside the region, so each thread has its own. The variable sum is read and written by every iteration, so no two iterations are independent as the serial program is written. The dependence is a reduction: the iterations combine their terms with one associative operation, addition, into one variable. Giving each thread a private partial sum removes the conflict: \(\mathrm{Wr}(i)\) then contains only the partial sum of the thread that runs \(i\), and the \(p\) partial sums are combined once, after the join. The price is stated in the specification and appears in the listing below: addition of floating-point numbers is not associative in practice, so the combined value depends on how the terms were grouped.

Distributions. Let the iteration set be \(\{0,\dots,N-1\}\). A distribution is a function that assigns each iteration to one thread. The slide's first program uses the cyclic distribution: thread \(t\) executes the iterations \(i\equiv t\pmod{n_{\text{thr}}}\), starting at \(i=\mathrm{id}\) with step \(n_{\text{thr}}\), so the threads take turns. The slide's alternative uses the block distribution: with \(q=\lfloor N/n_{\text{thr}}\rfloor\), thread \(t\) executes \(i\in[tq,(t+1)q)\), and the last thread executes the remainder up to \(N\). If \(N=pq+r\) with \(0\le r\lt p\), then the iteration counts are \(q+1\) for \(r\) threads and \(q\) for the others in the cyclic case, and \(q\) for the first \(p-1\) threads and \(q+r\) for the last in the block case. The lecture says that, for this problem, the choice "does not make too much of a difference": both give the same answer. The listing below checks the counts and the answers for \(N=100003\), not a multiple of 4, with 4 threads and with each partial sum in its own 64-byte slot. Both sums are formed in the same way, in fixed thread order, so the printed values do not depend on the schedule, and the check is exact. The program stops with an error if the runtime gives fewer than 4 threads.

#include <stdio.h>
#include <stdlib.h>
#include <math.h>
#include <omp.h>

#define NUM_THREADS 4
#define PAD 8                              /* 8 doubles = 64 bytes per slot */

static long num_steps = 100003;            /* not a multiple of NUM_THREADS */

static double run(int block, long *count, int *nthreads)
{
    static double sum[NUM_THREADS * PAD];
    double step = 1.0 / (double)num_steps;
    omp_set_num_threads(NUM_THREADS);
    #pragma omp parallel
    {
        int id = omp_get_thread_num();
        int numthrds = omp_get_num_threads();
        double x, acc = 0.0;
        long n = 0;
        if (id == 0) *nthreads = numthrds;
        if (!block) {                      /* cyclic distribution */
            for (long i = id; i < num_steps; i += numthrds) {
                x = (i + 0.5) * step;
                acc += 4.0 / (1.0 + x * x);
                n++;
            }
        } else {                           /* block distribution, remainder to the last thread */
            long istart = id * (num_steps / numthrds);
            long iend = (id == numthrds - 1) ? num_steps : (id + 1) * (num_steps / numthrds);
            for (long i = istart; i < iend; i++) {
                x = (i + 0.5) * step;
                acc += 4.0 / (1.0 + x * x);
                n++;
            }
        }
        sum[id * PAD] = acc;
        count[id * PAD] = n;
    }
    double pi = 0.0;
    for (int t = 0; t < *nthreads; t++) pi += sum[t * PAD] * step;   /* serial, in thread order */
    return pi;
}

Load balance. The distribution decides how the work is divided. A thread \(t\) with the set \(I_t\) of iterations spends \(w_t=\sum_{i\in I_t}c(i)\), where \(c(i)\) is the cost of iteration \(i\). The region ends at the join, so its duration is at least

\[ T_{\text{region}}\ge\max_t w_t,\qquad E_{\text{dist}}=\frac{W}{p\,\max_t w_t},\quad W=\sum_{i=0}^{N-1}c(i). \tag{11.3} \]

The quantity \(E_{\text{dist}}\) is the efficiency of the distribution: it equals 1 exactly when every thread has the same load, and it is the largest speedup divided by \(p\) that the distribution allows on \(p\) equally fast processors. For the \(\pi\) loop, \(c(i)\) is constant, so the load is proportional to the iteration count, and the counts above give \(E_{\text{dist}}\ge1-p(p-1)/N\) in the block case and \(E_{\text{dist}}\ge1-p/N\) in the cyclic case; for \(N=10^8\) and \(p\le12\) both differ from 1 by less than \(1.4\times10^{-6}\). The distribution matters when \(c(i)\) varies. Take \(c(i)=i+1\), as in a loop whose inner loop runs from 0 to \(i\). The total is \(W=N(N+1)/2\). For \(p\) blocks of \(N/p\) iterations, the last block has the largest load, \(\tfrac{N^2}{2}\cdot\tfrac{2p-1}{p^2}\) for large \(N\), so

\[ E_{\text{block}}\to\frac{p}{2p-1}\quad(N\to\infty),\qquad E_{\text{cyclic}}\ge1-O(p/N). \tag{11.4} \]

The block distribution wastes about half of the threads' time for large \(p\), because the last thread carries almost twice the average load. In the cyclic distribution thread \(t\) takes the iterations \(t,t+p,\dots\). The loads of neighbouring threads differ by about \(N/p\), and the loads of threads 0 and \(p-1\) by about \((p-1)N/p\), out of about \(N^2/(2p)\) each: a relative difference of less than \(2p/N\). }

Speedup, efficiency and Amdahl's law W4L1 16:14

The rest of this section builds the tools for that problem, and later sections test the candidate explanations.

Definitions. The lecture defines speedup as the ratio of the sequential time to the parallel time, \(S_p=T_1/T_p\) (the slides write \(S(P)\) and \(\mathrm{Time}_{\mathrm{seq}}(1)/\mathrm{Time}_{\mathrm{par}}(P)\)), perfect linear speedup as \(S_p=p\), and superlinear speedup as \(S_p\gt p\), which the lecture attributes to cache effects: the data of each thread may fit in the caches that \(p\) processors have in total although the data of the single thread did not. The efficiency \(E_p=S_p/p\) is the fraction of linear speedup. The lecture also writes the sequential time as the time to load the data, to compute \(N\) independent tasks and to consume the results, \(T_{\text{load}}+N\,T_{\text{task}}+T_{\text{consume}}\), and the parallel time as \(T_{\text{load}}+(N/p)\,T_{\text{task}}+T_{\text{consume}}\), with the remark that parallelism speeds up only the concurrent part.

Amdahl's law from its assumptions. Amdahl's 1967 paper (AFIPS Conference Proceedings 30, pp. 483–485, in the 2007 IEEE SSCS News reprint) contains no equation; the editors of the reprint state that it has no equations and a single figure. It argues that data-management housekeeping, which Amdahl puts at 40 % of the instructions executed in production runs, appears sequential; that this fraction might be halved in a dedicated environment but is very unlikely to be reduced by a factor of three; and that this overhead "alone would then place an upper limit on throughput of five to seven times the sequential processing rate". The formula that carries his name is a later formalization. It is derived here from three stated assumptions.

  1. A1, fixed split. The one-thread time divides as \(T_1=T_s+T_\parallel\), where \(T_s=fT_1\) is the time of the part that no thread can share (the serial fraction is \(f\), \(0\le f\le1\)) and \(T_\parallel=(1-f)T_1\) is the time of the part that threads can share. The numbers \(f\) and \(T_1\) belong to a fixed problem size \(N\) and do not depend on \(p\).
  2. A2, perfect division. On \(p\) threads, the sharable part takes \(T_\parallel/p\): the work divides into equal parts, and every thread proceeds at the speed of the single thread.
  3. A3, no added cost. The serial part takes \(T_s\) as before, and creating, ending and synchronizing the threads costs nothing.

Then

\[ T_p=fT_1+\frac{(1-f)T_1}{p},\qquad S_p=\frac{1}{f+(1-f)/p},\qquad E_p=\frac{1}{1+(p-1)f}. \tag{11.5} \]

The slides write \(\alpha\) for \(f\). Three properties follow. First, \(S_p\le1/f\), because the denominator is at least \(f\); and \(S_p\le p\), because the denominator is at least \(1/p\). Second, \(S_p\) increases with \(p\), since \(dS_p/dp=(1-f)/\bigl(p^2(f+(1-f)/p)^2\bigr)\ge0\), and \(S_p\to1/f\) as \(p\to\infty\): the lecture's values are 10 for a program that is 90 % parallelizable and 1000 for \(f=0.001\). Third, the efficiency falls below one half when \(p\gt1+1/f\), and the speedup reaches half of its limit at \(p=(1-f)/f\): at \(p=999\) for \(f=0.001\). The program below tabulates (11.5) and applies it to the lecture's table. Amdahl's own figures follow from \(1/f\): for housekeeping reduced from 40 % to 20 % and to about 13 % (a factor of two and a factor of about three), \(1/f\) is 5 and 7.5, close to the "five to seven" of his text; this reading is made here and is not an equation of the paper. The program is deterministic, so the check is exact.

"""Amdahl's law from its three assumptions: tables, limits and a diagnostic."""

def speedup(f, p):
    """S_p = T_1 / T_p with T_p = f T_1 + (1 - f) T_1 / p."""
    return 1.0 / (f + (1.0 - f) / p)


def serial_fraction(s, p):
    """Solve S_p = 1 / (f + (1 - f) / p) for f, given a measured speedup s."""
    return (1.0 / s - 1.0 / p) / (1.0 - 1.0 / p)

The cost of a parallel region and the choice of the thread count W4L1 22:16

The lecture states that the serial part of the \(\pi\) program includes the initial setup, the creation of the threads, their destruction at the end of the region and the global sum, and that the overhead grows with the number of threads because time goes to thread management. It concludes that beyond a threshold the program slows down, and that a program started with 1000 threads "might get a time which is worse off than 1.86 seconds". The remedy it names is to tune the number of threads, either with omp_set_num_threads or, without recompiling, with export OMP_NUM_THREADS, after a timing study that also varies the problem size.

A model. Relax assumption A3 and let each thread add a cost \(\kappa\) to the region, for creating or waking it and for the barrier that ends the region. With \(f=0\) for clarity, \(T_p=T_1/p+\kappa p\), where \(T_1\) is the single-thread time of the loop. The derivative \(-T_1/p^2+\kappa\) vanishes at

\[ p^{*}=\sqrt{\frac{(1-f)\,T_1}{\kappa}} \tag{11.7} \]

(with \(f\) restored), and the second derivative \(2T_1/p^3\) is positive, so \(p^*\) is the minimum of \(T_p\). The model has the same shape as the lecture's argument: the time falls, reaches a minimum and rises. It also has a break-even size: the region is worth executing on \(p\) threads only if \(T_1(1-1/p)\gt\kappa p\), which for \(p=8\) means \(T_1\gt 9.1\,\kappa\).

The cost, measured. The program below times regions that do almost nothing, one volatile write per thread to a private cache line, so that the compiler cannot remove them.   1. Time the program on one thread, \(T_1\), with the repetition rule of the lecture (several runs, the minimum or the mean stated).

  4. Repeat the timing at another problem size \(N\). If \(E_p\) improves as \(N\) grows at fixed \(p\), the loss is an overhead that does not grow with \(N\), which (11.7) describes.
  5. Choose the smallest \(p\) whose \(E_p\) meets the requirement, not the \(p\) with the smallest \(T_p\), when the processors have other uses.

False sharing: cache-line arithmetic and a measurement

The first SPMD program stores the partial sums in the array sum[NUM_THREADS] and every iteration of every thread updates its own element. The race analysis above shows the program is correct: the elements are distinct memory units. The next question is whether the memory system treats them as independent.

Cache lines. Processors do not move single words between memory and the caches. They move cache lines, blocks of consecutive bytes. Drepper ("What every programmer should know about memory", 2007, §3.2, p. 15) writes that early caches used lines of 32 bytes and that "nowadays the norm is 64 bytes"; on this machine the guest reports a line size of 64 bytes (the session above). The address of a byte lies in line \(\lfloor a/b\rfloor\) with \(b=64\). A double or long occupies 8 bytes, so 8 of them fit in a line when the array starts at a multiple of 64. Take an array of 8-byte elements, aligned to 64 bytes, with element \(t\sigma\) used by thread \(t\), where \(\sigma\) is the stride in elements. The thread's element is at byte \(8t\sigma\) and lies in line

\[ \ell(t)=\Bigl\lfloor\frac{8t\sigma}{64}\Bigr\rfloor=\Bigl\lfloor\frac{t\sigma}{8}\Bigr\rfloor. \tag{11.8} \]

Threads \(t\) and \(t'\) share a line exactly when \(\ell(t)=\ell(t')\). At \(\sigma=1\), threads 0 to 7 share line 0. At \(\sigma=2\) four threads share a line, at \(\sigma=4\) two threads, and at \(\sigma\ge8\) each thread has its own line. In general \(\min(p,8/\sigma)\) threads share a line for \(\sigma\le8\). The lecture's array sum[2], with the team of 2 threads, is 16 bytes. An array of \(n\le8\) doubles whose address is a multiple of 8 starts at one of the 8 byte offsets \(0,8,\dots,56\) within a line, and it crosses into the next line exactly when the start offset plus \(8n\) exceeds 64, which happens for \(n-1\) of the 8 offsets. For \(n=2\) the two elements share a line for 7 of the 8 offsets, and for \(n=4\) all four elements share a line for 5 of the 8 (at least two of them always share a line). If the offsets are equally likely, the two elements of sum[2] therefore share a line with probability 7/8, and all four elements of sum[4] share one with probability 5/8; an array declared with aligned(64), as in the programs below, always starts at offset 0.

Why sharing a line costs time. A core must hold a line in an exclusive state in its level-1 data cache before it can write to it. Drepper (§6.4.1, pp. 65–66) states that when several threads write to a line, a request for ownership is sent for each write in the worst case, and that a write becomes expensive although the threads use different memory locations. The effect is called false sharing: the program shares no data, and the hardware shares a line. It is a performance property and not a correctness property. The data race rules of the specification refer to memory units and do not mention lines. Drepper's test program, in which threads only increment a location 500 million times, took 390 %, 734 % and 1147 % of the time with one line per thread (he divides the time with one line by the time with separate lines) for 2, 3 and 4 threads, that is 3.9, 7.3 and 11.5 times as long, on a four-processor machine with Pentium 4 processors. The same test on a single-processor quad-core Core 2 machine showed a slight overhead that did not grow with the number of cores (§6.4.1, pp. 66–67). The size of the effect depends on the machine.

A dedicated measurement. The program below has each thread increment its own volatile long counter \(10^{8}\) times. The counters are \(\sigma\) elements apart in an array aligned to 64 bytes, and \(\sigma\) runs through 1, 2, 4, 8, 16. The volatile qualifier forces a load and a store in every iteration; it is not a synchronization mechanism, and here it only stops the compiler from keeping the counter in a register. #include <stdio.h>
#include <stdlib.h>
#include <omp.h>

#define MAXT 2048
#define MAXSTRIDE 8
#define REPS 5

static long num_steps = 1000000000;

/* sum[id * stride]: stride 1 packs the slots of 8 threads into one 64-byte line,
   stride 8 gives each thread its own line. The array is 64-byte aligned. */
static double sum[MAXT * MAXSTRIDE] __attribute__((aligned(64)));

static double run(int p, int stride, double *pi_out)
{
    double step = 1.0 / (double)num_steps;
    double t0 = omp_get_wtime();
    omp_set_num_threads(p);
    #pragma omp parallel
    {
        int id = omp_get_thread_num();
        int numthrds = omp_get_num_threads();
        double x;
        sum[id * stride] = 0.0;
        for (long i = id; i < num_steps; i += numthrds) {
            x = (i + 0.5) * step;
            sum[id * stride] += 4.0 / (1.0 + x * x);
        }
    }
    double pi = 0.0;
    for (int t = 0; t < p; t++) pi += sum[t * stride] * step;
    *pi_out = pi;
    return omp_get_wtime() - t0;
}

int main(int argc, char **argv)
{
    int stride = argc > 1 ? atoi(argv[1]) : 1;
    int plist[] = {1, 2, 4, 8, 12, 24};
    double t1 = 0.0, pi = 0.0;
    if (argc > 3) {                    /* ./pi_O2 8 once P: one run with P threads, thread creation included */

        double t = run(p, stride, &pi);
        printf("p = %4d, one run: %.3f s\n", p, t);
        return 0;

    printf("stride %d (%d bytes between slots)\n", stride, stride * 8);
    printf("%4s %8s %6s %6s\n", "p", "time s", "S_p", "E_p");

    }
    printf("pi = %.9f\n", pi);
    return 0;
}

Four observations follow from the sample. (1) At -O0 the lecture's array, stride 1, nearly stops scaling: \(S_4=1.3\) and \(S_8=1.0\), against 2.8 and 3.8 with stride 8; the unpadded version is 2.1 times slower at \(p=4\) and 3.8 times slower at \(p=8\). This reproduces the shape of the lecture's table, in which three and four threads gain at most 6 % over two. (2) At -O2 stride 1 and stride 8 are within 15 % of each other at every \(p\). The largest difference, 0.282 s unpadded against 0.323 s padded at \(p=4\), has the padded version slower, which is the opposite of the direction of false sharing, and the times at \(p=1\), where no line is shared, differ by 0.5 %. These differences measure the variation of the machine. With optimization, gcc keeps sum[id*stride] in a register during the loop and stores it once, which removes the writes that cause the sharing. (The assembly that gcc 13.3 generates at -O2 shows the partial sum held in a register during the loop and stored once after it.) The transformation is allowed because a program without a race has no other thread that may access the element during the loop. The lecture's measurement used icpc -O2; whether that compiler removed the sharing was not tested. Whether a loop of this form suffers from false sharing depends on the compiler's decisions, which the programmer does not see. (3) With padding and optimization, \(S_p\) is 1.81 at \(p=2\), 3.05 at \(p=4\), 3.70 at \(p=8\), 3.95 at \(p=12\) and 4.08 at \(p=24\); it is below \(p\) at every \(p\) (\(E_p\) is 0.90 at \(p=2\) and 0.46 at \(p=8\)); the last paragraph of this section explains why. (4) At -O0 with stride 1 the time is not monotone in \(p\): \(p=24\) (0.97 s) is faster than \(p=12\) (1.53 s) and \(p=8\) (2.04 s). By (11.8) with \(\sigma=1\), the 8 slots of a team of 8 lie in one line and all 8 writers run at once. At \(p=12\) the slots fill one line of 8 and one line of 4. At \(p=24\) they fill three lines of 8, and only 12 of the 24 threads run at any moment, about 4 writers per line. The time falls in the same order. This hypothesis was not tested.

Apply (11.6) to the padded -O2 table. The experimental serial fraction is 0.10 at \(p=2\), 0.10 at \(p=4\), 0.17 at \(p=8\), 0.19 at \(p=12\) and 0.21 at \(p=24\). It stays near 0.1 up to \(p=4\) and then rises, so, as in the lecture's table, no single serial fraction fits. The program's actual serial part takes a few microseconds. The failing assumption is again A2. The next measurement separates the machine from the program. It starts \(c\) independent copies of the single-thread loop at the same time, with no threads and no shared data, and takes the time of the slowest copy. The quantity \(C_c=c\,T_1/(\text{slowest time})\) is \(c\) times the speed of the slowest copy, in units of the speed of one copy that runs alone.

Each copy reports its best of 5 repetitions. A repetition that runs after other copies have finished meets less contention, so \(C_c\) may be slightly too large.

With \(T_1=1.002\) s from the one-copy line, \(C_c=1.73,\ 3.00,\ 3.92,\ 4.92\) for \(c=2,4,8,12\) copies, below \(c\) at every \(c\). Let \(v_k\) be the speed at which logical processor \(k\) runs this loop, relative to the one-copy run, and let \(v_{\min}\) be the smallest \(v_k\) among the processors in use. Then \(C_c=c\,v_{\min}\). \(C_c\) is not the total throughput of the machine, which is \(\sum_k v_k\). The threaded loop is limited by the same quantity. Its cyclic distribution gives every thread \(N/p\) iterations of equal cost, so by (11.3) the region ends when the slowest thread ends:

\[ S_p=p\,v_{\min}(p)\le\sum_k v_k . \]

The padded -O2 threaded loop (\(S_p=1.81,\ 3.05,\ 3.70\) and \(3.95\) at \(p=2,4,8,12\)) attains 104 %, 102 %, 94 % and 80 % of \(C_p\), the value of \(C_c\) at \(c=p\). The values above 100 % are the noise of the two measurements. The hybrid processor (section on the model) explains why \(p\,v_{\min}\) stops growing. From the copies, \(v_{\min}\) is 0.87 for 2 copies, 0.75 for 4, 0.49 for 8 and 0.41 for 12. The value below 1 at 2 copies has three possible causes that this chapter did not separate: the load of other jobs (the machine was shared during the capture), a lower turbo frequency with two busy cores, and placement of both copies on the two hardware threads of one P-core. An earlier session gave 0.96 for 2 copies. Four copies fit on the four P-cores. The slowest of the four runs at 0.75, which is consistent with P-cores that run below the single-core turbo frequency when four are busy, or with the load of other jobs; neither was measured. From 5 copies on, at least one copy runs on an E-core, whose maximum turbo frequency is 0.75 of a P-core's (3.30 against 4.40 GHz), or shares a P-core with another copy. The slowest copy then runs at about half the speed of a lone copy, and \(p\,v_{\min}\) stays between 3.9 and 4.9 for \(p\) from 8 to 12. The speedup at \(p=24\) (4.08) is slightly larger than at \(p=12\) (3.95), a difference within the noise of this sample. In earlier runs the speedup at \(p=24\) was larger than at \(p=12\) by 0.1 to 0.5. A hypothesis for this difference is the following. The operating system time-slices 24 threads on 12 logical processors and moves them between processors. A processor that finishes its threads takes over threads that are still waiting, so the work per processor is no longer equal, and \(S_p\) moves from \(p\,v_{\min}\) toward \(\sum_k v_k\). The explanation \(S_p=p\,v_{\min}\) fits the tables of this section for \(p\le8\), where the threaded loop attains 94 % to 104 % of \(C_p\). It does not account for \(p=12\), where the threaded loop attains 80 % of \(C_{12}\). The best-of-5 rule of the copies may overstate \(C_{12}\) (the caveat above); this chapter did not test it. The explanation \(S_p=p\,v_{\min}\) does not rest on a measurement of placement, which the guest does not let this chapter control. A direct test records omp_get_wtime() at the end of each thread's loop. At \(p=8\) and \(p=12\) the explanation \(S_p=p\,v_{\min}\) predicts two or three groups of finishing times, the slowest group about twice as long as the fastest. The specification does not require omp_get_wtime to be consistent across threads (§18.10.1, p. 414), so the test needs a clock that is, such as clock_gettime(CLOCK_MONOTONIC). The speeds \(v_k\) depend on the loop: the integer recurrence of triangle.c reached \(S_8=6.47\) with the cyclic distribution in this sample (6.88 and 6.95 in earlier runs), against 3.70 for the \(\pi\) loop. \(C_c\) must therefore be measured for each loop. The plateau near 4 is a property of this loop on this machine, not of the machine alone.

The model of schedules and storage establishes four things. The set of possible outputs of a region is the set of interleavings, and a count (\((2p)!/2^p\) schedules, \(\mathrm{Cat}_p\) outputs for the first program) shows why tests cannot cover it. A variable is shared or private by two rules that depend only on where it is declared. A data race is a pair of unordered conflicting accesses to one memory unit, and the specification gives a program with a race no defined result. The distribution of iterations decides the load of each thread, and (11.3) bounds the speedup that a distribution allows.

The model leaves out most of what OpenMP offers. It has no synchronization construct, so it cannot express a program that needs an order between threads; chapter 12 adds them. It has no memory model beyond the definition of a race, so the claim that a race-free program behaves as if one of the schedules had run is not proved here; the specification's relaxed-consistency model, in which each thread may have its own temporary view of memory, is the subject of chapter 13. It assumes one level of parallelism and a symmetric machine, as the lecture does, and it does not treat non-uniform memory, affinity, or GPUs.

The quantitative results have their own limits. Amdahl's law (11.5) holds under A1 to A3 and is violated by both tables of this chapter, because A2 fails. The lecture's machine has two cores. This chapter's machine has logical processors of different speeds, so a team with equal shares runs at \(p\) times the speed of its slowest thread. The overhead model (11.7) uses a cost per thread measured for a region that does no work, and it does not describe the run in which 1000 threads were created. The false-sharing measurements are one machine, one compiler and one session each, with other jobs on the machine. The sizes of the effects (2.0 to 2.6 times for the counters at \(p=8\), 3.8 times for the \(\pi\) program at -O0) are properties of this machine and of the build flags. Some explanations rest on the hybrid processor: the plateau of the speedup, and the speedups above \(p\) against the one-thread reference. One explanation rests on the full occupation of the logical processors: the rise of the region cost at \(p=10\) to 12. These explanations are consistent with the measurements. They were not tested by control of thread placement, which the WSL 2 guest does not allow.

The \(\pi\) problem has a single reduction, so the structure of the partial sums is simple. The book's other running problem, the Jacobi iteration, updates large arrays in every sweep; the analysis of this chapter assumes that memory traffic is negligible and does not predict its speedup.

Exercises

Exercise 1 (derive). In the model \(T_p=fT_1+(1-f)T_1/p+\kappa p\), find the team size \(p^*\) that minimizes \(T_p\) and the minimum time. Show that for \(f=0\) the minimum time is \(2\sqrt{\kappa T_1}\) and that at \(p^*\) the overhead \(\kappa p^*\) equals the compute time \(T_1/p^*\). For \(T_1=10\ \mu\mathrm{s}\) and \(\kappa=0.17\ \mu\mathrm{s}\), compute \(p^*\) and the speedup \(T_1/T_{p^*}\).

Solution

Differentiate: \(dT_p/dp=-(1-f)T_1/p^2+\kappa\). It is zero at \(p^*=\sqrt{(1-f)T_1/\kappa}\), and the second derivative \(2(1-f)T_1/p^3\) is positive for \(f\lt1\), so this is a minimum. Substituting, \((1-f)T_1/p^*=\sqrt{(1-f)T_1\kappa}\) and \(\kappa p^*=\sqrt{(1-f)T_1\kappa}\): the two terms are equal, and \(T_{p^*}=fT_1+2\sqrt{(1-f)\kappa T_1}\). For \(f=0\) the minimum is \(2\sqrt{\kappa T_1}\). With \(T_1=10\ \mu\mathrm{s}\) and \(\kappa=0.17\ \mu\mathrm{s}\): \(p^*=\sqrt{10/0.17}=7.7\), and \(T_{p^*}=2\sqrt{1.7}\ \mu\mathrm{s}=2.6\ \mu\mathrm{s}\), a speedup of \(10/2.6=3.8\). At the integer team sizes 7 and 8 the model gives \(10/7+0.17\times7=2.62\ \mu\mathrm{s}\) and \(10/8+0.17\times8=2.61\ \mu\mathrm{s}\), so the speedup is 3.8 for both. The speedup that this region can reach, 3.8, is half of \(p^*=7.7\), because half of the minimum time is overhead.

Exercise 2 (compute). A loop has \(N=1000\) iterations of cost \(c(i)=i+1\), run by \(p=4\) threads. Compute the load \(w_t\) of every thread and the efficiency \(E_{\text{dist}}\) of (11.3) for the cyclic distribution and for the block distribution of the lecture. Compare the block value with \(p/(2p-1)\).

Solution

The total is \(W=1000\times1001/2=500\,500\). Cyclic. Thread \(t\) takes the iterations \(t,t+4,\dots,t+996\), 250 of them, with costs \(t+1,t+5,\dots,t+997\), an arithmetic series with sum \(250(2t+998)/2\): 124 750 for \(t=0\), 125 000, 125 250 and 125 500 for \(t=3\). The maximum is 125 500, so \(E_{\text{dist}}=500\,500/(4\times125\,500)=0.997\). Block. \(N/p=250\), so thread \(t\) takes \(i\in[250t,250t+250)\) with costs \(250t+1,\dots,250t+250\), sum \(250(500t+251)/2\): 31 375, 93 875, 156 375 and 218 875. They add to 500 500. The maximum is 218 875, so \(E_{\text{dist}}=500\,500/(4\times218\,875)=0.572\). The limit \(p/(2p-1)=4/7=0.571\). The block distribution allows a speedup of at most \(4\times0.572=2.29\), the model value that the program in the chapter prints for \(N=40000\), and the cyclic distribution allows 3.99.

Exercise 3 (counterexample). A student claims: "If threads write only to distinct array elements, the program has no data race and its performance is not affected by the other threads." Use results of this chapter to show that the first half is true and the second half is false, for one program.

Solution

Take the \(\pi\) program with the partial-sum array at stride 1, compiled with -O0. Thread \(t\) writes only sum[t], and the \(p\) elements are distinct memory units, so by the definition quoted from §1.4.1 no two threads write the same memory unit and there is no data race; the specification's rule that the update granularity is no larger than the base language requires (p. 27) means the adjacent double elements do not interfere as memory units. The program is nevertheless affected: in the sample, \(S_4=1.3\) against 2.8 for the same program with the elements 64 bytes apart, and at \(p=8\) the unpadded program is 3.8 times slower than the padded one. Both programs are correct and compute the same sum. The first half of the claim concerns memory units of the language, and the second half concerns cache lines of the hardware, which the language does not mention. The claim also fails differently at -O2, where the compiler removes the repeated writes and the two versions run within the variation of the machine (at most 15 % apart, with the padded version the slower at \(p=4\)), so the performance depends on the build as well.

Exercise 4 (diagnose an assumption). Take the speedups \(S_p=1.81,\ 3.05,\ 3.70\) of the padded -O2 \(\pi\) program at \(p=2,4,8\), and the values \(C_c=1.73,\ 3.00,\ 3.92\) (\(c\) times the speed of the slowest copy) of \(c=2,4,8\) independent copies of its single-thread loop (values of the sample runs in the text). (a) Compute \(f_{\exp}\) at each \(p\) with (11.6). (b) Explain why the \(\pi\) program cannot have a serial fraction of that size. (c) State which assumption of Amdahl's law fails. Replace \(p\) by \(C_p\) in the sharable part of (11.5), with \(f\) of the order of the program's true serial fraction, and compare the model with the three speedups.

Solution

(a) \(f_{\exp}=(1/S-1/p)/(1-1/p)\): at \(p=2\), \((0.5525-0.5)/0.5=0.105\); at \(p=4\), \((0.3279-0.25)/0.75=0.104\); at \(p=8\), \((0.2703-0.125)/0.875=0.166\). (b) The serial part of the program is the final loop of at most 8 additions and the fork and join of the region, about a microsecond per region at \(p=8\) (1.03 µs in the section on overhead), against a run of about 1.0 s. The serial fraction is of order \(10^{-6}\), five orders below the fitted values, and the fitted values rise from \(p=4\) to \(p=8\), which a fixed \(f\) cannot do. (c) Assumption A2 fails: the sharable part does not divide by \(p\), because with equal shares the region runs at \(p\) times the speed of its slowest thread, and on this hybrid processor that speed falls as \(p\) grows. Replace \(p\) by the measured capacity: \(S_p=1/(f+(1-f)/C_p)\approx C_p\) for \(f\approx10^{-6}\). The model gives 1.73, 3.00 and 3.92 against the measured 1.81, 3.05 and 3.70, so the measured speedups are 104 %, 102 % and 94 % of the model, and no value is off by more than 6 %. The model explains the gap between \(S_p\) and \(p\) with one measured function \(C_p\). Its remaining error is of the size of the noise of the two measurements, which this exercise does not separate from effects of the team itself. The lecture's table has the same structure with \(C_p=\min(p,2)\).

Exercise 5 (design judgment). A loop computes b[i] = g(a[i]) for \(i=0,\dots,N-1\) with \(N=10^{8}\), where every call of g costs the same. Another loop computes b[i] = h(a[i], i) where the cost of h grows linearly with \(i\). Choose a distribution of iterations for each, and give the quantitative reasons. For the cyclic distribution with chunks of \(k\) consecutive iterations, find the smallest \(k\) at which neighbouring threads never write the same cache line of b (an array of doubles aligned to 64 bytes).

Solution

For the first loop all iterations cost the same, so (11.3) gives \(E_{\text{dist}}\ge1-p(p-1)/N\) for the block distribution; for \(N=10^8\) and \(p\le12\) this differs from 1 by less than \(1.4\times10^{-6}\). The cyclic distribution with chunk 1 assigns neighbouring elements of b to different threads, so by (11.8) threads \(t\) and \(t+1\) write into one line for 8 consecutive elements: the false-sharing situation of the measurement. The block distribution has one boundary between two threads, so at most \(p-1\) lines are shared in total, a negligible fraction of \(N/8\) lines. Choose the block distribution. For the second loop the cost grows with \(i\), so the block distribution gives \(E_{\text{dist}}\to p/(2p-1)\), about 0.57 for \(p=4\) and 0.53 for \(p=8\); choose a cyclic distribution. A chunk of \(k\) consecutive iterations writes \(8k\) bytes of b. Chunks of whole lines never share a line when \(8k\) is a multiple of 64, that is, \(k\) is a multiple of 8, and the smallest such chunk is \(k=8\). A chunk of 8 doubles is one line, so no two threads write the same line; the loads of two threads differ by at most about \(kN\) out of \(N^2/(2p)\) each, a relative difference of about \(2kp/N=16p/N\), negligible for \(N=10^{8}\). Chapter 12, on parallel loops and their schedules, covers how OpenMP expresses such distributions.

Exercise 6 (implementation and measurement). Change the program of the false-sharing section to use 4-byte counters (volatile int), strides \(\sigma=1,2,4,8,16,32\) elements, and \(p=8\). Predict, before running, how many threads share a line at each stride and which strides should give the same time. Run it and compare.

Solution

The change is three lines of falseshare.c: the declaration becomes static volatile int counter[MAXT * MAXSTRIDE] __attribute__((aligned(64)));, MAXSTRIDE becomes 32, and the label stride >= 8 ? 1 : 8 / stride becomes stride >= 16 ? 1 : 16 / stride. A line now holds 16 counters. Thread \(t\) uses byte \(4t\sigma\) and is in line \(\lfloor t\sigma/16\rfloor\). For \(p=8\): at \(\sigma=1\) the threads occupy bytes 0 to 31, all in line 0, so 8 threads share a line; at \(\sigma=2\) they occupy bytes 0 to 56, still line 0, so 8 threads share a line; at \(\sigma=4\) they occupy bytes 0 to 112, two lines with 4 threads each; at \(\sigma=8\), 2 threads per line; at \(\sigma=16\) and 32, one thread per line. The prediction is that \(\sigma=1\) and \(\sigma=2\) take the same time and are the slowest, then \(\sigma=4\), then \(\sigma=8\), and that \(\sigma=16\) and 32 are the fastest and equal. The run in the same session as the other timing samples gave, for \(p=8\): 0.466, 0.456, 0.418, 0.282, 0.162 and 0.159 s for \(\sigma=1,2,4,8,16,32\) (an earlier run gave 0.629, 0.608, 0.388, 0.330, 0.209 and 0.248 s). The order, the equality of \(\sigma=1\) and 2, and the equality of \(\sigma=16\) and 32 (2 % apart) agree with the prediction. The one-line case is 2.9 times slower than the one-line-per-thread case at \(\sigma=16\) (3.0 in the earlier run), larger than the 2.0 to 2.6 times for 8-byte counters in four runs; this chapter did not determine why.
