Concurrency and synchronization: races, locks, atomic instructions and barriers

Four threads each add 1 to one shared counter 1 000 000 times, with a short computation between the additions. The correct total is 4 000 000. Without synchronization, the program of this chapter printed 1 740 739 in the sample run below, which is 43.5 % of the correct total. Six runs of the same program printed totals between 0.90 and 1.87 million. With a mutex, the total is correct and the run takes 203.7 ms, against 31.6 ms for one thread that performs all 4 000 000 additions: the four threads are 6.4 times slower than one. An atomic fetch-and-add takes 102.7 ms. Four private counters that are added to the shared total once, at the end, take 8.7 ms and give the same total, 23 times faster than the mutex. This chapter defines the objects behind these numbers: schedules, data races, critical sections, locks, atomic instructions and barriers. It proves exactly when the unsynchronized program is right, derives a bound on the speedup that a lock allows, and tests the bound against measurements. It shows with an exhaustive search and with a hardware test that a lock built from ordinary loads and stores fails on this machine unless a fence orders them, and it ends with the failure that locks themselves can cause.

The objects of the chapter and the running case

The chapter studies programs in which several threads of one process share memory. A thread is a sequence of instructions with its own program counter and call stack; the threads of one process address the same memory (chapter 11 gives the same definition for OpenMP threads). The operating system decides on which processor, and when, each thread runs. The chapter takes the memory operations of a thread from a small set. A load copies the value of a memory location into a register. A store copies a register into a memory location. A read-modify-write operation (RMW) loads a location, computes a new value and stores it as one step that no other thread's operation on that location can enter; the section on atomic instructions defines the RMW operations that hardware provides. An event is one execution of one operation by one thread. The events of one thread are totally ordered by program order. A schedule is a total order of all events of all threads that respects every program order. The operating system and the hardware choose the schedule; the program does not.

Memory model. Until the section on Peterson's algorithm, the chapter assumes sequential consistency. Lamport (1979, p. 690) states it for a multiprocessor: "the result of any execution is the same as if the operations of all the processors were executed in some sequential order, and the operations of each individual processor appear in this sequence in the order specified by its program." In this model a memory operation takes effect at one point of the schedule, and a load returns the value of the latest earlier store to its location. The assumption is false for the hardware of this chapter's machine, and the section on Peterson's algorithm shows how and what it costs.

Conflicts, data races and race conditions. Two operations conflict when they are on the same memory location and at least one of them modifies it (C11 draft N1570, §5.1.2.4 ¶4, p. 17). An operation A happens before an operation B when A precedes B in the program order of one thread, or when A is a release operation that synchronizes with an acquire operation B that reads the value A wrote, or by transitivity of these two rules (§5.1.2.4 ¶11, p. 18, for synchronizes with; ¶16 and ¶18, p. 19, for happens before; the standard's full definition adds rules for dependencies that this chapter does not use). A lock release is such a release and a lock acquisition is such an acquire; the section on mutual exclusion states this for mutexes. The standard then defines the hazard: "The execution of a program contains a data race if it contains two conflicting actions in different threads, at least one of which is not atomic, and neither happens before the other. Any such data race results in undefined behavior" (§5.1.2.4 ¶25, p. 20). The chapter uses two terms with distinct meanings. A data race is the standard's notion: a pair of conflicting, unordered operations of which one is not atomic. A race condition is a property of a program and its inputs: the result depends on the schedule, so that two schedules give two results. A program can have either one without the other; the section on the lost update gives a program with a race condition and no data race.

Synchronization. A synchronization primitive is an operation that orders events of different threads. The chapter treats three: the lock with its acquire and release, the atomic instruction (with the C11 functions that compile to it) and the barrier. An atomic operation with relaxed memory order is indivisible but is neither a release nor an acquire, so it creates no happens-before relation between threads (N1570 §7.17.3 ¶2, p. 275: "For memory_order_relaxed, no operation orders memory"). A critical section is a region of code that at most one thread may execute at a time with respect to a given shared resource; mutual exclusion is that property. A barrier is a point that no thread passes until all threads of a group have reached it.

The running case. One shared variable x of type long starts at 0. Each of \(p\) threads executes \(n\) iterations. An iteration computes for a time \(w\) on private data, which is the part of the work that needs no synchronization, and then performs the update x = x + 1. The compiler turns the update into a load of x, an addition in a register and a store to x (the assembly that gcc 13.3 emits at -O2 for the program below has a separate movq load and movq store for the volatile counter). The correct final value is \(pn\). The case stands for any program in which threads add contributions to one result: the hit count of a Monte Carlo estimate, a histogram bin, the global sum of the midpoint-rule loop for \(\pi\) of chapter 11, or a residual norm in the Jacobi iteration. The work time \(w\) is a loop of 8 dependent multiply–adds in the programs below, about 8 ns per iteration (8.4 ms for \(10^6\) iterations on one thread in the thread sweep of the section on atomic instructions). Where the chapter varies the number of updates between shared updates, it calls that number the batch size \(K\): a thread adds to a private counter and updates the shared variable once every \(K\) iterations.

Performance symbols. The book-wide symbols apply: \(p\) is the number of threads, \(T_1\) and \(T_p\) are the wall-clock times of the program on one thread and on \(p\) threads, \(S_p=T_1/T_p\) is the speedup. The chapter adds \(n\) (iterations per thread), \(w\) (work per iteration outside the critical section), \(c\) (the time per critical section, including acquiring and releasing the lock), \(K\) (the batch size) and \(\varphi=c/(w+c)\) (the fraction of an iteration that is critical). Each symbol is repeated at its first substantive use.

Concurrency, interleaving and overlap W2L6 1:08

The lecture starts from the observation that a sequential program executes its instructions in the order the programmer wrote, and that a parallel program uses several cores that each perform a task independently, although the tasks may have to interact. It then separates two situations. On one core, the operating system switches between the tasks of a program by time slicing, so that "the execution of these threads is interleaved over time, because the CPU core can execute only one thread at a time." The lecture calls this concurrency. On several cores, the system assigns a thread to each core and the threads run in parallel. The lecture's figure, credited to Stallings, draws three processes as bars over time. With one processor (panel a) only one bar is running at any time, and the others are blocked. With two processors (panel b) two bars run at the same time, so the executions are interleaved and also overlapped.

What the chapter takes from this. For the correctness of a program, the number of cores does not matter. What matters is the set of schedules that the system can produce, as defined in the section on the model. On one core, the kernel may switch threads at any instruction boundary, because an interrupt may arrive after any instruction. On several cores, instructions of different threads also overlap in time. The model of this chapter describes both cases by the same object, a total order of events, and the section on Peterson's algorithm states when that description is wrong. The lecture's term "concurrency" for time slicing on one core is the special case of one processor. Chapter 11 records the definitions of the recording W3L6: tasks are concurrent when several are active, none is ordered with respect to the others, and each makes forward progress under some scheduling policy; they run in parallel when they make progress at the same time. This chapter uses the same sense in a form that a proof can use: two events are concurrent when neither happens before the other.

How many schedules there are. A program of \(p\) threads with \(s\) events each has

\[ \frac{(ps)!}{(s!)^{p}} \tag{8.1} \]

schedules, because a schedule chooses which positions of the sequence of \(ps\) events belong to each thread. For the running case an iteration has two events that matter, a load and a store, so \(s=2n\). For \(p=2\) and \(n=1\) the count is 6. For \(p=4\) and \(n=10^{6}\), the case of the lead, it is a number with about 4.8 million decimal digits (computed from the logarithm of the gamma function, \(\log_{10}\approx 4\,816\,470\)). No test can visit these schedules, and the operating system does not sample them uniformly. The next section shows that almost all of them give a wrong result, so the correctness of the program must be argued, not observed.

One core is enough for a race. The interleaving in the lecture's second table (next section) does not need two processors: every step of it occurs at its own time, and a single core that switches threads between the load and the store of an increment produces it. The effect is rare on one core, because the switch must fall inside a window of a few cycles. The session below runs the program of the next section on one logical processor (taskset -c 0) three times. No update was lost in the three samples, each of 4 000 000 updates. That is a statement about how often the kernel switches threads at that point, and the theorem of the next section holds on one core as it does on four.

The lost update: a data race and a race condition W2L6 4:39

The lecture defines a race condition as the situation in which two threads try to access the same variable at the same time, and it says that this "is likely to cause problems sometimes". It names two consequences: the result of the computation is indeterminate, which the lecture explains as "you can't tell for sure what it will be", and inconsistent, which it explains as a result that varies across runs. Its example has two threads that each increment a shared variable x that starts at 0. A thread reads the value, increases it and writes it back. The lecture shows two schedules of the six steps. Table 8.1 reproduces them, with the increase folded into the write because it acts on a register.

The lecture's wording, made precise. Three statements of the lecture need a sharper form. First, nothing in schedule B happens "at the same time": the four steps occur one after another, so the race exists on one processor, as the previous section measured. A race condition needs a conflict between operations that nothing orders, and simultaneity is not required. Second, "indeterminate" and "inconsistent" describe one property seen from two sides: the result is a function of the schedule, so two runs with two schedules give two results. The C standard states a stronger consequence for a data race, which the model section quotes: the behavior is undefined, which allows the compiler to assume that no data race occurs. Third, a race condition does not require a data race. The programs below show both cases.

Theorem 8.1 (lost update). Let \(p\) threads each execute \(n\) increments of x, starting from 0, and let each increment be a load followed later by a store of the loaded value plus 1. Under sequential consistency, (a) the final value of x is at most \(pn\); and (b) it equals \(pn\) if and only if the \(pn\) intervals from a load to its own store are pairwise disjoint, that is, if and only if the schedule runs the increments one after another, each as an unbroken load–store pair.

Proof. Let \(x(t)\) be the value of x and \(s(t)\) the number of stores executed up to time \(t\). Claim 1: \(x(t)\le s(t)\) at all times. It holds at the start, since both are 0, and a load changes neither side. A store at time \(t\) writes \(r+1\), where \(r=x(t_L)\) was loaded at an earlier time \(t_L\). By the claim at \(t_L\), \(r\le s(t_L)\le s(t^-)\), the number of earlier stores, so the new value satisfies \(r+1\le s(t^-)+1=s(t)\). At the end \(s=pn\), which proves (a). Claim 2: if \(x(t)=s(t)\) just after a store at \(t\), then no store occurred between that increment's load and its store, and \(x(t_L)=s(t_L)\). Equality means \(r+1=s(t^-)+1\), and \(r\le s(t_L)\le s(t^-)\) forces \(s(t_L)=s(t^-)\) and \(x(t_L)=s(t_L)\). For (b), suppose the intervals are pairwise disjoint. Then the schedule is a sequence of whole increments, each loading the current value and storing its successor, so \(x\) grows by 1 per increment and ends at \(pn\). Conversely, suppose the final value is \(pn=s\). The equality \(x=s\) holds after the last store, so by Claim 2 no store lies inside the interval of that last increment, and the equality holds at its load time. No store lies between that load and the last store, so the equality holds just after the previous store, and Claim 2 applies to that store as well. Repeating the step backwards shows that no store lies inside the interval of any increment. Two intervals that overlap would have to contain a store of the other increment, either because one nests in the other or because they cross, so the intervals are disjoint. \(\blacksquare\)

Corollary 8.2 (counting). Schedules with the correct result are the orders in which the \(pn\) indivisible increments can run, and their number is

\[ \frac{(pn)!}{(n!)^{p}}, \tag{8.2} \]

out of the \((2pn)!/((2n)!)^p\) schedules of (8.1). For \(p=2\) the share of correct schedules is \(\binom{2n}{n}/\binom{4n}{2n}\), which is about \(\sqrt2\,4^{-n}\) for large \(n\). The share falls by a factor of 4 for each added increment per thread. For \(p=4\) and \(n=1000\) it is about \(10^{-2408}\).

Check by exhaustive search. The program counts all schedules of small cases by their final value, with a memoized search over the state (program counters, registers, value of x). It asserts the total of (8.1) and the number of correct schedules of (8.2) for every case. The listing prints the share of correct schedules and the smallest and largest final values. The search is deterministic, so the check is exact.

"""Count the schedules of p threads that each increment a shared counter n times.

One increment is two steps: load (register := x) and store (x := register + 1).
A schedule is an interleaving that keeps each thread's own order.
The search counts schedules by final value of x, without listing them.
A schedule gives the correct value p*n exactly when the p*n increments do not overlap,
so the number of correct schedules is the number of orders of p*n indivisible increments.
"""
from functools import lru_cache
from math import factorial


def final_values(p, n):
    """Return {final value of x: number of schedules that end with it}."""
    steps = 2 * n

    @lru_cache(maxsize=None)
    def go(pcs, regs, x):
        if all(pc == steps for pc in pcs):
            return ((x, 1),)
        out = {}
        for t in range(p):
            pc = pcs[t]
            if pc == steps:
                continue
            npcs = pcs[:t] + (pc + 1,) + pcs[t + 1:]
            if pc % 2 == 0:                                   # load
                sub = go(npcs, regs[:t] + (x,) + regs[t + 1:], x)
            else:                                             # store
                sub = go(npcs, regs, regs[t] + 1)
            for value, count in sub:
                out[value] = out.get(value, 0) + count
        return tuple(sorted(out.items()))

    return dict(go((0,) * p, (0,) * p, 0))


print(" p n  schedules  correct  share  smallest  largest  distinct")

    counts = final_values(p, n)

    assert total == factorial(2 * n * p) // factorial(2 * n) ** p

The program on the machine. The listing below is the running case. Its worker runs the iterations of the section on the model: a work step, an increment of a private counter mine, and, once every batch iterations, one shared update of the strategy chosen by mode. With batch equal to 1 every iteration updates the shared counter. The program runs each strategy three times and prints the first total (the totals of the racing strategies change from run to run) and the minimum time. The input is the thread count, the iterations per thread, the number of work steps and the batch size. The two racing strategies are the first rows of interest. plain read-modify-write is the program of the lecture: a volatile long that every thread loads, adds 1 to and stores. The qualifier volatile forces the compiler to perform the load and the store in every iteration; it does not make the update atomic, and under the C standard the program has a data race. load then store (atomic) declares the counter _Atomic and does the update as an atomic load followed by an atomic store, both with relaxed memory order. Every conflicting access is then atomic, so the program has no data race in the sense of the standard. The remaining rows are the subject of the following sections. The run is one sample on the machine of the model section; the check is the return code.

#include <pthread.h>
#include <stdatomic.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <time.h>

enum { SERIAL, PLAIN, SPLIT, MUTEX, TAS, CAS, FETCH_ADD, PRIVATE, NMODES };
static const char *name[NMODES] = {
    "serial (1 thread)", "plain read-modify-write", "load then store (atomic)",
    "mutex", "spinlock, test-and-set", "spinlock, compare-and-swap",
    "atomic fetch-and-add", "private count, one add"};

static int nthreads, work_steps;
static long batch = 1;
static long per_thread;
static int mode;

static volatile long plain_count;           /* data race when shared */
static _Atomic long atomic_count;
static pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
static atomic_flag tas_lock = ATOMIC_FLAG_INIT;
static _Atomic int cas_lock;
static volatile uint64_t sink[64 * 8];      /* keeps the work from being optimized away */

static inline uint64_t work(uint64_t w)     /* work_steps dependent multiply-adds */
{
    for (int k = 0; k < work_steps; k++)
        w = w * 6364136223846793005ULL + 1442695040888963407ULL;
    return w;
}

static inline void flush(long v)            /* one shared update that adds v */
{
    switch (mode) {
    case SERIAL:
    case PLAIN:  plain_count = plain_count + v; break;
    case SPLIT:
        atomic_store_explicit(&atomic_count,
            atomic_load_explicit(&atomic_count, memory_order_relaxed) + v,
            memory_order_relaxed);
        break;
    case MUTEX:
        pthread_mutex_lock(&lock);
        plain_count = plain_count + v;
        pthread_mutex_unlock(&lock);
        break;
    case TAS:
        while (atomic_flag_test_and_set_explicit(&tas_lock, memory_order_acquire))
            ;
        plain_count = plain_count + v;
        atomic_flag_clear_explicit(&tas_lock, memory_order_release);
        break;
    case CAS: {
        int expected = 0;
        while (!atomic_compare_exchange_strong_explicit(&cas_lock, &expected, 1,
                   memory_order_acquire, memory_order_relaxed))
            expected = 0;
        plain_count = plain_count + v;
        atomic_store_explicit(&cas_lock, 0, memory_order_release);
        break;
    }
    case FETCH_ADD:
    case PRIVATE: atomic_fetch_add_explicit(&atomic_count, v, memory_order_relaxed); break;
    }
}

static void *worker(void *arg)
{
    long id = (long)arg, mine = 0;
    long every = (mode == PRIVATE) ? per_thread + 1 : batch;   /* private: shared update only at the end */
    uint64_t w = 88172645463325252ULL + id;
    for (long i = 0; i < per_thread; i++) {
        w = work(w);
        mine++;
        if (mine == every) { flush(mine); mine = 0; }
    }
    if (mine) flush(mine);
    sink[id * 8] = w;
    return NULL;
}

static double now(void)
{
    struct timespec t;
    clock_gettime(CLOCK_MONOTONIC, &t);
    return t.tv_sec + 1e-9 * t.tv_nsec;
}

static double run(int m, long *result)
{
    pthread_t t[64];
    int p = (m == SERIAL) ? 1 : nthreads;
    long n = (m == SERIAL) ? per_thread * nthreads : per_thread;
    long save = per_thread;
    mode = m;
    per_thread = n;
    plain_count = 0;
    atomic_store(&atomic_count, 0);
    double t0 = now();
    for (long k = 0; k < p; k++) pthread_create(&t[k], NULL, worker, (void *)k);
    for (int k = 0; k < p; k++) pthread_join(t[k], NULL);
    double dt = now() - t0;
    per_thread = save;
    *result = (m == SPLIT || m == FETCH_ADD || m == PRIVATE) ? atomic_load(&atomic_count) : plain_count;
    return dt;
}

int main(int argc, char **argv)
{
    nthreads = argc > 1 ? atoi(argv[1]) : 4;
    per_thread = argc > 2 ? atol(argv[2]) : 1000000;
    work_steps = argc > 3 ? atoi(argv[3]) : 8;
    batch = argc > 4 ? atol(argv[4]) : 1;
    long expected = per_thread * nthreads;
    printf("threads %d, increments per thread %ld, work steps %d, batch %ld, expected %ld\n",
           nthreads, per_thread, work_steps, batch, expected);
    printf("%-28s %10s %9s %9s\n", "strategy", "result", "lost", "ms");
    for (int m = 0; m < NMODES; m++) {
        long result = 0, first = 0;

Mutual exclusion and the critical section W2L6 9:39

The lecture introduces the remedy with a lock and a key. Two people who want one room are kept apart by a lock: the first to enter locks the door, and the second waits until the first leaves. The lecture's figure applies this to the shared variable \(x\) in four numbered steps. Thread 1 gets access to \(x\) (step 1). Thread 2 also wants access and has to wait (step 2). Thread 1 completes its access (step 3). Then thread 2 gets access (step 4). The variable goes from 0 to 1 to 2, so the result is correct. The lecture then names the price: threads wait, and the slide says that this "may lead to reduction in application performance". The lecture adds that the results stay consistent. It concludes that the amount of synchronization should be minimized by restructuring the code, and sometimes the algorithm.

The lecture then defines the unit that the lock protects. Every thread that uses the shared variable performs three tasks: read it, operate on it (for example, increment it) and write it. A thread that only reads needs no protection. The code that performs the three tasks is the critical section. The lecture says it is critical because its execution "should not be interrupted by any other thread", and that once one thread has entered its critical section and left it, another thread may enter its own critical section for the same variable. The protected resource may be a memory location, a peripheral device, a network connection or a data structure. The thread acquires a lock before the section and releases it after.

What a correct solution must satisfy. The statement "no other thread may interrupt" mixes two requirements, and the literature separates them. Dijkstra (EWD123, §2.1, pp. 11–18 of the typescript) states the problem for two cyclic processes that each pass through a critical section, "critical in the sense that the processes have to be constructed in such a way, that at any moment at most one of the two is engaged in its critical section". He adds three conditions. The solution may not assume anything about the relative speeds of the processes. A process that is stopped well outside its critical section must not be able to block the other (p. 13). And it must be impossible to arrange speeds so that the decision about which process enters first is postponed forever (p. 16). Dijkstra assumes that a read of a common variable and an assignment to it are each indivisible. For threads of this chapter, the four requirements are these.

  1. Exclusion. At most one thread is inside a critical section for a given resource at any time.
  2. No speed assumptions. The argument for exclusion does not depend on how fast threads run or on the number of processors.
  3. Progress. A thread that is not inside, and not trying to enter, a critical section does not prevent another thread from entering.
  4. No indefinite postponement. A thread that tries to enter eventually enters. A stronger form, bounded waiting, limits how many entries by other threads can precede its own; chapters on operating systems use that name.

The lecture's wording corresponds to the first requirement only, and with a correction. A thread inside a critical section can be interrupted by the kernel and descheduled while it holds the lock; the requirement is that no other thread enters a critical section for the same resource in the meantime. The other threads that need the lock wait, and the threads that do not need it continue. A descheduled lock holder is a performance hazard, because the waiting threads cannot proceed until it runs again; the section on atomic instructions measures a case that is consistent with this hazard.

There is a second job that the lock has to do, and the lecture does not mention it. The results of the critical section must be visible to the next thread that enters. The POSIX specification says that applications must restrict access so that no thread reads or modifies a memory location while another may be modifying it, that this is done with functions that synchronize thread execution and also synchronize memory, and that the list of these functions includes pthread_mutex_lock, pthread_mutex_unlock, pthread_barrier_wait and pthread_spin_lock (POSIX Issue 7, §4.12, Memory Synchronization). It ends with the sentence "Applications may allow more than one thread of control to read a memory location simultaneously", which is the lecture's remark about threads that only read. The C standard states the same for mutexes in a note: all operations on a given mutex occur in a single total order, and each acquisition reads the value written by the last release (N1570 §5.1.2.4 ¶13, NOTE 6, p. 18). Together with the definition of happens-before in the section on the model, this makes the release of a lock happen before the next acquisition, and so everything that the first thread wrote in the critical section happens before everything that the next thread reads there.

Two wrong solutions. Dijkstra builds his solution through rejected trials, and two of them are worth keeping. The first trial uses a variable turn that says whose turn it is. It satisfies exclusion, but a process must wait for the other even when the other is far from its critical section, and a stopped process blocks the other forever; it fails requirement 3 (EWD123 p. 13). The second trial gives each process a flag that says "I am inside", and each process waits until the other's flag is clear and then sets its own. Dijkstra's argument (p. 14) is that the first process can find the other's flag clear, the second can do the same immediately afterwards, and both "will conclude that they can enter their own section safely": it fails requirement 1. The second trial is the natural first attempt at a lock, and it is also what the lecture's mutex looks like if the test of the 0/1 variable and its change are two steps. The section on Peterson's algorithm checks both trials by exhaustive search.

The price of waiting, as a bound. The lecture's statement that synchronization costs performance has a precise form. Let each of \(p\) threads perform \(n\) iterations. An iteration does work of duration \(w\) outside any critical section and then one critical section of duration \(c\), measured from the start of the lock acquisition to the end of the lock release. Let \(T_1\) be the time of the serial program that performs all \(pn\) iterations. Three assumptions hold. (B1) The critical sections of different iterations are mutually exclusive, so their time intervals do not overlap. (B2) Each critical section lasts at least \(c\). (B3) \(T_1=pn(w+c)\). By B1 and B2 the \(pn\) critical sections occupy \(pn\) disjoint intervals of length at least \(c\) inside the interval \([0,T_p]\), so \(T_p\ge pnc\). Each thread alone needs at least \(n(w+c)\), so \(T_p\ge n(w+c)\). Hence

\[ T_p \;\ge\; \max\bigl\{\,n\,(w+c),\;p\,n\,c\,\bigr\}, \qquad S_p=\frac{T_1}{T_p}\;\le\;\min\Bigl\{p,\;\frac{w+c}{c}\Bigr\}=\min\Bigl\{p,\;\frac1{\varphi}\Bigr\}, \tag{8.3} \]

with \(\varphi=c/(w+c)\), the critical fraction of an iteration. The ceiling \(1/\varphi\) is the limit of Amdahl's law with the serial fraction \(f=\varphi\) as \(p\) grows (chapter 11 derives the law and lists its assumptions). The bound (8.3) is weaker than Amdahl's law for finite \(p\), because the critical sections of one thread may overlap the private work of the others, which Amdahl's model does not allow: Amdahl's model makes the fraction \(\varphi\) serial for the whole program; the lock serializes the critical sections only among themselves. When \(w\) is small against \(c\), no number of threads helps, and \(T_p\) grows in proportion to \(p\) when the number of iterations per thread is fixed, because the critical sections of all threads queue behind each other. The bound separates two regimes. With \(w\ge(p-1)c\), the second term of the maximum is not larger than the first, and the lock may not limit the time. With \(w\lt(p-1)c\), the lock limits it. The bound is a necessary condition and not a prediction: it uses the time \(c\) of a section that runs alone, and it leaves out the time to hand a lock from one core to the next, which the measurements below show to exceed \(c\) by a large factor. It also does not say how many threads wait or sleep.

Restructuring: batch the shared updates. The lecture's remedy has a form that the model can analyze. A thread that adds its contributions to a private variable and updates the shared variable once every \(K\) iterations has \(n/K\) critical sections instead of \(n\). If the critical section of a batch lasts \(c\) as before, the bound becomes

\[ T_p \;\ge\; \max\bigl\{\,n\,(w+c/K),\;p\,(n/K)\,c\,\bigr\}, \tag{8.4} \]

and the critical fraction falls to \(c/(Kw+c)\). The limit \(K=n\) gives \(T_p\ge nw\), a speedup of \(p\). The section on mutex locks tests this bound against the measurements of the batch-size sweep.

Mutex locks W2L6 22:50

The lecture's lock is the mutex, short for mutual exclusion. Its example, from a slide with #include <pthread.h>, declares pthread_mutex_t count_mutex and long count and defines a function increment_count that calls pthread_mutex_lock(&count_mutex), executes count = count + 1 and calls pthread_mutex_unlock(&count_mutex). The section between the two calls is the critical section. For the inside of a mutex, the lecture says that every mutex has an associated binary variable that holds 0 or 1, initialized to 1. A thread that enters the critical section decreases it to 0, which acquires the lock. Another thread that tries to enter sees the value 0 and waits. The thread that holds the lock sets the value back to 1 when it leaves.

What the abstraction does and does not say. The 0/1 variable is the abstraction of a binary semaphore: a counter that can be 0 or 1, with an acquire that waits for 1 and sets 0 and a release that sets 1. As a model of mutual exclusion it is correct on one condition that the lecture's wording hides: the test of the value and its change to 0 must be one indivisible step. If a thread first sees 1 and then, in a separate step, sets 0, then two threads can both see 1, and both enter. That is the second trial of Dijkstra in the previous section. The exhaustive search in the section on Peterson's algorithm finds a schedule of 6 steps in which both threads enter. The indivisible step is what the atomic instructions of the next sections provide.

A POSIX mutex is not exactly a binary semaphore. It has an owner. The specification of pthread_mutex_lock says that the call blocks while another thread holds the mutex, that it returns with the calling thread as owner, and that unlocking a mutex that the caller does not hold gives undefined behavior for the default and the normal types and an error for the error-checking type (POSIX Issue 7, pthread_mutex_lock, table of relock and unlock behavior). A semaphore has no owner, so any thread may release it. The ownership is what lets an implementation detect two programming errors that the deadlock section shows: the second lock of one thread, and the release by a thread that never locked.

Real mutexes also do more than one variable can. Drepper (2011, pp. 6–8) develops a mutex on the Linux futex (a kernel facility that lets a thread sleep on a memory word until another thread wakes it) in three versions. The final design keeps the state in one integer with three values, 0 for unlocked, 1 for locked with no waiters, and 2 for locked with one or more waiters. A thread acquires an unlocked mutex with one compare-and-swap, and releases it with one atomic decrement. A thread that finds the mutex held sets the value to 2 with an atomic exchange and sleeps in the kernel by a system call. The release of a mutex in state 2 wakes one sleeping thread by another system call. The design separates a fast path with no system call from a slow path in which waiting threads sleep and do not use a processor. The article describes a design for the Linux kernel's futex facility. It is not a statement about the implementation that this machine's C library uses, which this chapter did not inspect.

Locks from loads and stores: Peterson's algorithm and the store buffer

The lecture says that atomic instructions need the cooperation of the hardware. This section asks why. Can two threads exclude each other with ordinary loads and stores only? Dijkstra posed this problem in 1965 for processes that share only memory cells, and the answer under sequential consistency is yes. Peterson (1981) gave a short solution for two threads. The paper (Information Processing Letters 12(3), pp. 115–116) could not be opened for this chapter, so the algorithm below is the form found in textbooks, and the exhaustive search that follows tests that form. Each thread \(i\) has the other thread \(j=1-i\). The shared variables are two flags flag[0] and flag[1], both 0 at the start, and an integer turn. Thread \(i\) runs

flag[i] = 1;                          /* I want to enter */
turn = j;                             /* but you may go first */
while (flag[j] == 1 && turn == j)
    ;                                 /* wait */
/* critical section */
flag[i] = 0;                          /* I am done */

Mutual exclusion under sequential consistency. Suppose that both threads are in the critical section at the same time \(t^*\). Each thread wrote turn once in its entry protocol: thread 0 wrote 1 (write \(w_0\)) and thread 1 wrote 0 (write \(w_1\)). The two writes are ordered, so let \(w_0\) come first; the other case is symmetric. Thread 1 left its loop at a test before \(t^*\), so at that test the condition flag[0] == 1 && turn == 0 was false. After \(w_1\), turn is 0 until some thread writes it again, and neither thread writes it again before the critical section: thread 0's write \(w_0\) came earlier, and thread 1's write is \(w_1\). So turn == 0 at the test, and the test must have read flag[0] == 0. But thread 0 wrote flag[0] = 1 before \(w_0\), and \(w_0\) precedes \(w_1\), which precedes the test. Thread 0 resets its flag only after it leaves the critical section, which is after \(t^*\), and so after the test. The test therefore read flag[0] == 1, which contradicts the previous sentence. The proof uses one fact: the order of the writes in the schedule is the order in which the later reads of the other thread see them. The proofs of progress and of bounded waiting need further arguments that this chapter does not give, and the search below does not test them.

An exhaustive search over two memory models. The program below checks lock algorithms for two threads, each of which enters the critical section once and leaves. A state is the program counter and register of each thread, the memory, and the store buffer of each thread. The search visits every reachable state and asks whether both program counters can be at the critical-section instruction in one state. It has two memory models. In SC a store writes memory at once. In TSO the model follows the rules of x86-TSO, the programmer's model of Sewell and others (2010, §3.1). Each thread has a FIFO store buffer. A store enters the buffer of its thread. A load returns the newest value that the thread's own buffer holds for the address, or, if there is none, the value in memory. The oldest buffered store may reach memory at any time. A fence (MFENCE) is enabled only when the thread's buffer is empty. A locked instruction, which includes XCHG, first empties the buffer of its thread and then reads and writes memory in one step. Sewell and others let the instruction end only when the buffer is empty (their rule 7); because no other thread can read or propagate meanwhile, emptying the buffer first gives the same reachable states. The algorithms are Dijkstra's second trial (called check-then-set here: wait while the other flag is 1, then set one's own), Peterson's algorithm, Peterson's algorithm with a fence between the write of turn and the first read, and a test-and-set lock (a locked exchange of the lock variable with 1, repeated until it returns 0). The search finds the shortest violating schedule by breadth first search. Its output is deterministic.

       at any time; fence and xchg first empty the buffer of their thread
       (rules 1-5 and 7 of Sewell et al., CACM 53(7), 2010, section 3.1).
"""
from collections import deque

VARS = ("flag0", "flag1", "turn", "lock", "busy0", "busy1")
IDX = {v: i for i, v in enumerate(VARS)}


def naive(i, fence=False):
    """Dijkstra's check-then-set: wait while the other busy flag is 1, set own, enter."""
    j = 1 - i
    return [("ld", "r", f"busy{j}"),        # 0
            ("jeq", "r", 1, 0),             # 1  other is busy: look again
            ("st", f"busy{i}", 1),          # 2
            ("cs",),                        # 3
            ("st", f"busy{i}", 0),          # 4
            ("end",)]                       # 5


def peterson(i, fence=False):
    j = 1 - i
    prog = [("st", f"flag{i}", 1),          # 0
            ("st", "turn", j)]              # 1
    if fence:
        prog.append(("fence",))
    n = len(prog)
    prog += [("ld", "r", f"flag{j}"),       # n     wait while flag[j] and turn == j
             ("jeq", "r", 0, n + 4),        # n+1   flag[j] is 0: enter
             ("ld", "r", "turn"),           # n+2
             ("jeq", "r", j, n),            # n+3   turn is j: look again
             ("cs",),                       # n+4
             ("st", f"flag{i}", 0),         # n+5
             ("end",)]
    return prog


def test_and_set(i, fence=False):
    return [("xchg", "r", "lock", 1),       # 0  r := lock; lock := 1, as one locked step
            ("jeq", "r", 1, 0),             # 1  lock was held: try again
            ("cs",),                        # 2
            ("st", "lock", 0),              # 3
            ("end",)]


def initial(progs):
    return (tuple(0 for _ in progs), tuple(0 for _ in progs),
            tuple(0 for _ in VARS), tuple(() for _ in progs))


def successors(state, progs, tso):
    pcs, regs, mem, bufs = state
    for t, prog in enumerate(progs):
        # a buffered store reaches memory
        if tso and bufs[t]:
            (var, val), rest = bufs[t][0], bufs[t][1:]
            m = list(mem); m[var] = val
            b = list(bufs); b[t] = rest
            yield (f"T{t} buffer -> memory: {VARS[var]} = {val}", (pcs, regs, tuple(m), tuple(b)))
        op = prog[pcs[t]]
        kind = op[0]
        npc = list(pcs); nreg = list(regs); m = list(mem); b = list(bufs)
        npc[t] += 1
        if kind == "st":
            var, val = IDX[op[1]], op[2]
            if tso:
                b[t] = bufs[t] + ((var, val),)
                text = f"T{t} store {op[1]} = {val} (buffered)"
            else:
                m[var] = val
                text = f"T{t} store {op[1]} = {val}"
        elif kind == "ld":
            var = IDX[op[2]]
            val = mem[var]
            for v, x in reversed(bufs[t]):
                if v == var:
                    val = x
                    break
            nreg[t] = val
            text = f"T{t} load {op[2]} -> {val}"
        elif kind == "jeq":
            if regs[t] == op[2]:
                npc[t] = op[3]
            text = f"T{t} test r == {op[2]}"
        elif kind == "fence":
            if bufs[t]:
                continue                     # enabled only when the buffer is empty
            text = f"T{t} fence"
        elif kind == "xchg":
            if bufs[t]:
                continue                     # a locked instruction first empties the buffer
            var = IDX[op[2]]
            nreg[t] = mem[var]; m[var] = op[3]
            text = f"T{t} xchg {op[2]}: old {mem[var]}, new {op[3]}"
        elif kind == "cs":
            text = f"T{t} enters the critical section"
        elif kind == "end":
            npc[t] -= 1
            continue
        yield (text, (tuple(npc), tuple(nreg), tuple(m), tuple(b)))


def check(maker, tso, fence=False):
    progs = [maker(0, fence), maker(1, fence)]
    in_cs = [[k for k, op in enumerate(p) if op[0] == "cs"][0] for p in progs]
    start = initial(progs)
    parent = {start: None}
    queue = deque([start])
    while queue:
        s = queue.popleft()
        if s[0][0] == in_cs[0] and s[0][1] == in_cs[1]:
            trace = []
            while parent[s]:
                text, prev = parent[s]
                trace.append(text); s = prev
            return len(parent), trace[::-1]
        for text, nxt in successors(s, progs, tso):
            if nxt not in parent:
                parent[nxt] = (text, s)
                queue.append(nxt)
    return len(parent), None

The step of the proof that fails. The proof used the order of the writes in the schedule as the order in which reads see them. In the TSO model a load may complete before an earlier store of the same thread to another address has reached memory. This is the weakness of the memory model. Lamport (1979) stated it for a two-process mutual-exclusion protocol that sets its own flag first and then reads the other flag, as Peterson's entry does: process 1 executes a := 1; if b = 0 then critical section, and process 2 executes b := 1; if a = 0 then critical section. His note shows that the protocol fails if a memory module does not execute two requests in the order in which it received them (a different hardware mechanism with the same effect as a store buffer), and it states requirements that a computer must meet to execute such protocols correctly. The minimal pattern is the store-buffering test of Sewell and others (2010, §1): thread 0 executes x = 1 and then reads y; thread 1 executes y = 1 and then reads x. Sequential consistency forbids the outcome in which both reads return 0. The x86-TSO model allows it, and the authors present it as a behavior of real x86 multiprocessors.

The hardware shows it. The first test is the store-buffering test, written with C11 atomics. In each round both threads agree on a start time about 20 µs ahead, wait for it by reading the clock, load both variables to bring their lines into both caches, then perform the two operations, and a counter records rounds in which both reads returned 0. The two variables sit on separate cache lines. The listing runs 100 000 rounds with relaxed memory order, and again with sequentially consistent order. The memory order is a macro argument on purpose: the compiler needs a constant. An earlier draft of this harness chose the order with a run-time variable and observed no outcome with both reads 0 in 500 000 rounds on each of six pairs of logical processors. gcc treats a memory-order argument that is not a compile-time constant as sequentially consistent, and the assembly of that draft stored with xchg, which is a locked instruction. Because the outcome depends on timing, the check is the return code.

What follows for locks. The lecture's statement is right, and the reason is stronger than indivisibility. A lock built from atomic read-modify-write instructions works because such an instruction both reads and writes in one step, and because it orders the accesses around it: on x86 it empties the store buffer. Peterson's algorithm and Dekker's two-process solution (which Dijkstra presents in EWD123 §2.1) are correct only on a machine, or in a language, that gives sequential consistency or the fences that restore it. Modern lock implementations use atomic instructions, and the language's release and acquire operations are what the lock functions use inside.

The lecture defines atomics as "instructions that execute without any interruption" and gives two examples, from Silberschatz's textbook. test_and_set(target) takes a pointer to a Boolean. It copies the old value into a local variable rv, sets *target to true and returns rv. A lock uses it in the loop while (test_and_set(&lock)) ; /* do nothing */, then the critical section, then lock = false, with lock initialized to false. compare_and_swap(value, expected, new_value) copies *value to temp, assigns new_value to *value if *value == expected, and always returns temp, the original value. A lock uses it in the loop while (compare_and_swap(&lock, 0, 1) != 0) ;, then the critical section, then lock = 0. A further slide states that atomic operations are performed on a memory location, that is, an address, and that the hardware ensures that no other thread can access the location until the atomic operation is complete.

Reading the two loops. The slides' loops are the reference for this section. The test-and-set loop spins while the function returns true: true means that the old value was true and another thread holds the lock, so the thread enters when the function returns false. The compare-and-swap loop spins while the result is not 0, and it enters when the result is 0, the old value of an unlocked lock. Both loops use the function's return value as the old value of the lock variable. A reader who takes "returns true" or "returns 1" as the entry condition reverses both loops; the locks of the listing below follow the slides.

What "atomic" means. The phrase "without interruption" is inexact. An interrupt can arrive between two instructions of a thread, and the kernel can switch threads there. An atomic operation is indivisible with respect to the other threads: no operation of another thread on the same location takes effect between its read and its write. The C11 draft defines the compare-and-exchange functions as follows: "Atomically, compares the value pointed to by object for equality with that in expected, and if true, replaces the value pointed to by object with desired, and if false, updates the value in expected with the value pointed to by object", and calls the operations "atomic read-modify-write operations" (N1570 §7.17.7.4 ¶2, p. 283). The function atomic_flag_test_and_set "atomically sets the value pointed to by object to true", again as an atomic read-modify-write operation (§7.17.8.1 ¶2, p. 285). The function atomic_fetch_add atomically replaces the value with the result of the addition and returns "the value pointed to by object immediately before the effects" (§7.17.7.5 ¶3–4, pp. 284–285). The standard also says that "all modifications to a particular atomic object M occur in some particular total order, called the modification order of M" (§5.1.2.4 ¶7, p. 18). This order is what lets one argue about locks.

Why the test-and-set lock excludes. Let the lock variable start false and be changed only by test_and_set, which sets it to true, and by the holder's store of false at the exit. All operations on it are ordered. A test_and_set returns false only if the variable was false just before it. After such a call the variable is true, and it stays true until a store of false. The only such store is the one the holder executes when it leaves the critical section. Consider two threads that both entered; each entered on a call that returned false. The variable was false before the second of the two calls, and after the first call it was true; so a store of false lies between them, which only the first thread can have executed, when it left. So the second thread entered after the first one left, and the critical sections do not overlap. The same argument holds for the compare-and-swap lock, where the call that changes 0 to 1 plays the role of the call that returns false. The argument gives exclusion only. When no thread is inside and the variable is false, the next call succeeds, so a free lock is taken. It does not give bounded waiting: nothing orders the threads that fail, and one thread can lose every time.

The locks on the machine. The listing implements the lecture's two spinlocks with C11 atomics, and next to them the pthread mutex, each around a plain long counter that nothing else protects. The test-and-set lock uses atomic_flag_test_and_set_explicit with acquire order to take the lock and atomic_flag_clear_explicit with release order to free it. The compare-and-swap lock uses atomic_compare_exchange_strong_explicit; on failure the function writes the old value into expected, so the loop resets it to 0. The release and acquire orders carry the second job of a lock from the section on mutual exclusion: the store of the release synchronizes with the exchange of the next acquisition that reads its value, so the counter written in one critical section happens before the counter read in the next (N1570 §7.17.3 ¶3–4, p. 275, and §5.1.2.4 ¶11, p. 18). With relaxed order the lock variable would still be atomic, but the standard would give no happens-before between the sections, and the accesses to the counter would form a data race. Four threads add 100 000 times each, and the program prints the total for each lock. The output is deterministic when the locks work.

#include <pthread.h>
#include <stdatomic.h>
#include <stdio.h>

#define THREADS 4
#define PER_THREAD 100000L

enum { MUTEX, TAS, CAS };
static const char *name[] = {"pthread mutex", "test-and-set spinlock", "compare-and-swap spinlock"};

static pthread_mutex_t mutex = PTHREAD_MUTEX_INITIALIZER;
static atomic_flag tas_lock = ATOMIC_FLAG_INIT;       /* clear = free, set = held */
static _Atomic int cas_lock;                          /* 0 = free, 1 = held */
static long count;                                    /* ordinary variable, protected by the lock */
static int kind;

static void acquire(void)
{
    if (kind == MUTEX) {
        pthread_mutex_lock(&mutex);
    } else if (kind == TAS) {
        while (atomic_flag_test_and_set_explicit(&tas_lock, memory_order_acquire))
            ;                                         /* returned true: held, look again */
    } else {
        int expected = 0;
        while (!atomic_compare_exchange_strong_explicit(&cas_lock, &expected, 1,
                   memory_order_acquire, memory_order_relaxed))
            expected = 0;                             /* a failed exchange wrote the old value here */
    }
}

static void release(void)
{
    if (kind == MUTEX) pthread_mutex_unlock(&mutex);
    else if (kind == TAS) atomic_flag_clear_explicit(&tas_lock, memory_order_release);
    else atomic_store_explicit(&cas_lock, 0, memory_order_release);
}

static void *worker(void *arg)
{
    (void)arg;
    for (long i = 0; i < PER_THREAD; i++) {
        acquire();
        count = count + 1;                            /* critical section: load, add, store */
        release();
    }
    return NULL;
}

int main(void)
{
    for (kind = MUTEX; kind <= CAS; kind++) {

Compare-and-swap builds any update. A lock is one use of compare-and-swap. The loop "read the old value, compute the new value, try to install it, and retry if the value changed" turns any function of one word into an atomic update. The standard has atomic addition for integers and none for double in this form, and the midpoint-rule sum for \(\pi\) of chapter 11 adds double terms. The listing below adds each term to a shared total with a compare-and-swap loop on the bit pattern of the double, and compares it with the strategy of the lecture's cache figure: each thread sums in a private variable and adds it once. The weak form of the function is used in the loop. The standard says a weak compare-and-exchange may fail spuriously even if the values are equal, so that it can map to "load-locked store-conditional machines" (N1570 §7.17.7.4 ¶4–5, p. 284). In a loop a spurious failure only causes one more iteration, and OpenMP 5.2 notes that a weak form can improve performance when a compare-and-swap is used in a loop (§15.8.3, p. 311, note on the weak clause). A thread whose attempt fails knows that another thread's store changed the word, if the function is the strong form. This is why such a loop is lock-free: a descheduled thread cannot keep the others from finishing, as a descheduled lock holder can. The sum is checked against \(\pi\) with a tolerance of \(10^{-9}\), not bit for bit, because floating-point addition is not associative and the order of the additions depends on the schedule (chapter 11 measured differences of 2 units in the last place for two distributions of one loop).

#include <pthread.h>
#include <stdatomic.h>
#include <stdint.h>

#include <string.h>

#define THREADS 4
#define NUM_STEPS 1000000L

static _Atomic uint64_t total;                 /* bit pattern of a double */
static int private_sums;                       /* 0: one CAS update per term, 1: one per thread */

/* x <- x + v as a compare-and-swap loop: any update function can be built this way. */
static void atomic_add_double(_Atomic uint64_t *x, double v)
{
    uint64_t old = atomic_load_explicit(x, memory_order_relaxed), desired;
    do {
        double d;
        memcpy(&d, &old, sizeof d);
        d += v;
        memcpy(&desired, &d, sizeof desired);
    } while (!atomic_compare_exchange_weak_explicit(x, &old, desired,
                 memory_order_relaxed, memory_order_relaxed));   /* on failure old is reloaded */
}

static void *worker(void *arg)
{
    long id = (long)arg;
    double h = 1.0 / (double)NUM_STEPS, mine = 0.0;
    for (long i = id; i < NUM_STEPS; i += THREADS) {
        double x = (i + 0.5) * h, term = h * 4.0 / (1.0 + x * x);
        if (private_sums) mine += term;
        else atomic_add_double(&total, term);
    }
    if (private_sums) atomic_add_double(&total, mine);
    return NULL;
}

static double run(int priv)
{
    pthread_t t[THREADS];
    double sum;
    uint64_t bits = 0;
    atomic_store(&total, bits);                /* the bit pattern 0 is the double 0.0 */
    private_sums = priv;
    for (long k = 0; k < THREADS; k++) pthread_create(&t[k], NULL, worker, (void *)k);
    for (int k = 0; k < THREADS; k++) pthread_join(t[k], NULL);
    bits = atomic_load(&total);
    memcpy(&sum, &bits, sizeof sum);
    return sum;
}

The lecture introduces the barrier with a level crossing on a railway line. Vehicles arrive at the closed gate at different times and wait; when the gate opens, all of them proceed together. The gate is a synchronization method for all the arriving vehicles. For threads the lecture states: all threads must wait together at some point; the program is divided into phases by a barrier; all threads of a phase reach the barrier before any of them goes further; so the program phases before and after the barrier cannot be concurrent. It names three uses: enforcing dependencies, maintaining consistency across shared data, and implementing checkpointing, in which the state of a parallel program is saved so that, after a hardware failure, the program restarts from the last checkpoint and not from the beginning.

A definition that a proof can use. Consider a barrier used by \(p\) threads, repeatedly. Let \(B_k(i)\) be the event in which thread \(i\) arrives at the barrier for the \(k\)-th time, and \(D_k(i)\) the event in which it leaves it for the \(k\)-th time. The barrier property is: for all \(k\) and all threads \(i\) and \(j\), \(B_k(j)\) happens before \(D_k(i)\). Every thread arrives in round \(k\) before any thread leaves in round \(k\). The property gives the lecture's three uses at once. Suppose thread \(j\) writes a value before its \(k\)-th arrival and thread \(i\) reads it after its \(k\)-th departure. Program order and the barrier property chain the write to the read by happens-before, so the read sees the write and no data race exists (a dependency, and consistency of shared data). The OpenMP 5.2 specification states the same for the barrier construct: all threads of the team must enter the barrier region and complete the explicit tasks bound to it "before any of the threads continue execution beyond the barrier" (§15.3.1, p. 301). A restriction of the construct gives the rule that makes barriers dangerous: each barrier region must be encountered by all threads of the team or by none (p. 302). The POSIX function pthread_barrier_wait blocks the caller until the required number of threads have called it, returns the constant PTHREAD_BARRIER_SERIAL_THREAD to one unspecified thread and zero to the others, and resets the barrier for reuse (POSIX Issue 7, pthread_barrier_wait); it also synchronizes memory (§4.12).

Implementing a barrier. The simplest barrier keeps a counter of the threads that have not arrived. Each arriving thread decrements it atomically and then waits until it is released, and the last one to arrive releases the others. If the same variables are used again for the next barrier, a fast thread can reach the next barrier while a slow thread has not yet left the previous one, and the counter can be disturbed. Mellor-Crummey and Scott (1991, §3.1, pp. 33–34) describe this flaw of the obvious formulation, which needs two spinning episodes, and the sense-reversing barrier that removes one of them (their Figure 8, p. 34). Each thread keeps a private Boolean local_sense. A thread flips its local_sense on arrival. It then atomically decrements count. If the result was 1, the thread is the last: it resets count to \(p\) and then writes its local_sense to the shared sense. Any other thread spins until sense equals its local_sense.

The correctness argument is short. In round \(k\), every thread flips to the same value \(s_k\), and the shared sense holds \(s_{k-1}\) until the last arrival writes \(s_k\). So no thread of round \(k\) leaves before the last arrival. The last arrival resets count before it writes sense. A released thread that at once enters round \(k+1\) flips to \(s_{k+1}=s_{k-1}\) and decrements a count that is already reset. It also cannot leave early, because sense equals \(s_k\), not \(s_{k+1}\), until the last arrival of round \(k+1\) writes it. The listing implements this barrier with C11 atomics, next to pthread_barrier_wait. A waiting thread yields the processor after 2000 spins, so that the barrier still progresses when there are more threads than free processors. The program has three modes. The default mode is the check: \(p\) threads run 20 000 phases of two steps. In step 1 thread \(i\) writes the round number \(r\) to its own slot, then all threads reach a barrier; in step 2 each thread reads all \(p\) slots and counts the slots that do not hold \(r\); then all reach a second barrier. The second barrier is needed. Without it a fast thread could write \(r+1\) to its slot while a slow thread still reads round \(r\); the reading and the later writing of one slot are another conflict that the barrier must order. The output of the default mode is exact: the number of wrong reads for each barrier. The other two modes are used in the sessions below.

#define _GNU_SOURCE
#include <pthread.h>
#include <sched.h>
#include <stdalign.h>
#include <stdatomic.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <time.h>

#define MAXT 16

static int nthreads, use_pthread, use_barrier = 1;
static long phases;
static pthread_barrier_t pb;

/* Centralized sense-reversing barrier (Mellor-Crummey and Scott 1991, Figure 8). */
static alignas(64) _Atomic int count;
static alignas(64) _Atomic int sense;

static void barrier_wait(int *local_sense)
{
    if (use_pthread) { pthread_barrier_wait(&pb); return; }
    *local_sense = !*local_sense;                         /* each thread toggles its own sense */
    if (atomic_fetch_sub(&count, 1) == 1) {               /* the last thread to arrive */
        atomic_store_explicit(&count, nthreads, memory_order_relaxed);
        atomic_store(&sense, *local_sense);               /* releases every waiting thread */
    } else {
        for (int spins = 0; atomic_load(&sense) != *local_sense; spins++)
            if (spins > 2000) sched_yield();
    }
}

static alignas(64) _Atomic long slot[MAXT * 8];           /* slot of thread i: slot[i * 8] */
static alignas(64) _Atomic long violations;

static void *worker(void *arg)
{
    int id = (int)(long)arg, local_sense = 0;
    long bad = 0;
    for (long r = 1; r <= phases; r++) {
        atomic_store_explicit(&slot[id * 8], r, memory_order_relaxed);   /* phase 1: write own slot */
        if (use_barrier) barrier_wait(&local_sense);
        for (int k = 0; k < nthreads; k++)                               /* phase 2: read all slots */
            if (atomic_load_explicit(&slot[k * 8], memory_order_relaxed) != r) bad++;
        if (use_barrier) barrier_wait(&local_sense);                     /* nobody writes round r+1 early */
    }
    atomic_fetch_add(&violations, bad);
    return NULL;
}

static double run(void)
{
    pthread_t t[MAXT];
    struct timespec a, b;
    atomic_store(&count, nthreads); atomic_store(&sense, 0); atomic_store(&violations, 0);
    memset((void *)slot, 0, sizeof slot);
    pthread_barrier_init(&pb, NULL, nthreads);
    clock_gettime(CLOCK_MONOTONIC, &a);
    for (long k = 0; k < nthreads; k++) pthread_create(&t[k], NULL, worker, (void *)k);
    for (int k = 0; k < nthreads; k++) pthread_join(t[k], NULL);
    clock_gettime(CLOCK_MONOTONIC, &b);
    pthread_barrier_destroy(&pb);
    return (b.tv_sec - a.tv_sec) + 1e-9 * (b.tv_nsec - a.tv_nsec);
}

Checkpointing. The lecture's third use needs a qualification. A barrier gives a point at which no thread is in the middle of a phase, so the shared state at that point is consistent and can be saved. When synchronization fails: deadlock

The lecture's summary presents the synchronization methods as the remedy for the side effects of concurrency. The lecture's material ends with the remedies; it does not treat how the remedy itself can fail. A set of threads is deadlocked when each thread of the set waits for an event that only another thread of the set can cause, so that none of them ever proceeds. For locks the event is the release of a lock that another thread of the set holds. Four conditions must hold together for such a deadlock to arise: the resource is held exclusively (mutual exclusion); a thread holds one resource while it waits for another (hold and wait); a resource cannot be taken away from its holder (no preemption); and the threads form a cycle in which each waits for a resource held by the next (circular wait). The conditions are named after Coffman, Elphick and Shoshani (1971, ACM Computing Surveys 3(2), pp. 67–78). The article could not be opened for this chapter, and the attribution rests on its bibliographic record and on the Wikipedia article on deadlock, which states that the four conditions are known as the Coffman conditions from their first description in that article. Removing one condition prevents the deadlock. A lock cannot do without the first, and the other three are the ones a program can change.

    pthread_mutexattr_t attr;                  /* one thread that locks the same mutex twice */
    pthread_mutex_t self;
    pthread_mutexattr_init(&attr);
    pthread_mutexattr_settype(&attr, PTHREAD_MUTEX_ERRORCHECK);
    pthread_mutex_init(&self, &attr);
    pthread_mutex_lock(&self);
    int err = pthread_mutex_lock(&self);
    printf("second lock of an error-checking mutex by its owner: %s\n",
           err == EDEADLK ? "EDEADLK" : "other");
    return 0;
}

  thread 0 holds m0 and timed out on m1
  thread 1 holds m1 and timed out on m0

With opposite lock orders, both threads hold their first lock and time out on the second: all four conditions hold, and the cycle is thread 0 waiting for m1 held by thread 1 and thread 1 waiting for m0 held by thread 0. With a common order both threads succeed. The error-checking mutex reports EDEADLK where the normal mutex would hang.

Why a common lock order works. Number the locks and require every thread to acquire locks in increasing order. Suppose a cycle of waiting threads \(T_1,\dots,T_k\) existed, where \(T_i\) waits for a lock \(L_i\) that \(T_{i+1}\) holds (indices mod \(k\)). Thread \(T_{i+1}\) acquired \(L_i\) before it requested \(L_{i+1}\), so the order requires \(L_i\lt L_{i+1}\). Around the cycle this gives \(L_1\lt L_2\lt\dots\lt L_k\lt L_1\), which is impossible. A common order removes circular wait. The price is that every code path must know the global order, including paths that reach a second lock through a call. A barrier can deadlock in a different way: if one thread of a team never reaches a barrier that all the others wait at, the others wait forever, which is why OpenMP states that every barrier region must be encountered by all threads of a team or by none (OpenMP 5.2, p. 302). Two MPI processes that each start a blocking send of a large message before they post a receive can form the same cycle; chapter 14 treats point-to-point messages.

The lecture ends with a summary. Concurrency is an essential aspect of parallel programming; it introduces side effects that can lead to incorrect results; and the lecture states that "higher performance can never be at the cost of accuracy", so the side effects must be mitigated. Synchronization methods overcome race conditions, locks implement critical sections, atomics implement mutual exclusion, and barriers keep threads synchronous. The last bullet says that parallel programming frameworks such as OpenMP, MPI and CUDA provide primitives based on these basic techniques. The summary slide writes "critical conditions" where the lecture means critical sections.

"Accuracy" needs a definition. A parallel program that adds floating-point terms in a different order than the serial program does not give the same bits (chapter 11 found a difference of 2 units in the last place between two distributions of one loop). The program cas_pi.c gives the same digits within \(10^{-9}\) for two orders of addition. The statement is therefore true with a definition: a parallel result is acceptable when it equals the serial result within a stated tolerance that accounts for rounding, and unacceptable when the difference comes from a lost update or a race. The tolerance is a decision of the programmer and the lecture does not give one.

The model of schedules, conflicts and synchronization establishes four things. A program with a shared counter and no synchronization is correct for exactly those schedules in which the increments do not overlap, and almost no schedule has that property (Theorem 8.1 and Corollary 8.2). A lock gives mutual exclusion if its acquisition is an atomic read-modify-write, by the argument on the order of operations on the lock variable, and it must also order memory, by release and acquire. The cost of a lock has a floor, bound (8.3), and a batch of \(K\) updates divides it by \(K\), bound (8.4), which the sweep confirmed from \(K=1000\) on. A barrier has a precise property that separates phases and makes the data of one phase visible in the next.

The model leaves out most of what concurrent programming needs. It assumes sequential consistency except in the section on Peterson's algorithm, and that section tests one algorithm for two threads on one processor model. It says nothing about weaker memory models such as those of ARM or POWER processors, which this machine cannot test. It proves exclusion for the spinlocks and not progress or fairness: a thread can lose every race for a test-and-set lock, the spinlock collapses at 12 threads on this machine for a reason that this chapter did not test, and priority inversion and lock convoys are not treated. It does not treat reader–writer locks, condition variables, counting semaphores, lock-free data structures (which need an argument against the ABA problem), transactional memory or the synchronization of GPU threads. Chapters 12 and 13 treat the OpenMP forms and memory model, chapters 14 to 16 message passing, and chapters 19 to 22 GPU threads.

The quantitative results have their own limits. Bounds (8.3) and (8.4) are necessary conditions, and the measured times are 7.5 to 7.7 times the bound at \(K=1\) and 1.05 to 1.06 times at \(K\ge1000\); the time per shared update is not constant (section on mutex locks), and the model has no term for the cost of handing a lock over. Three explanations were offered and not tested: the cause of the higher cost per update at \(K=10\) and 100 (sleeping and waking through the kernel, or cache-line transfers), the collapse of the test-and-set spinlock from 8 threads on (descheduling of the lock holder), and the dependence of the plateau at 8 and 12 threads on the processor's layout. All timings come from one machine, one compiler and one session, with other jobs present and with no control of thread placement; each timing is the minimum of 3 repetitions, and the totals of the racing strategies vary from run to run. The Peterson and store-buffering results hold for this processor family under WSL 2 and say nothing about the memory model of other processors.

Exercises

Exercise 1 (derive). Let the time of a batched run be modelled as \(T_p\approx T_{\text{work}}+(pn/K)\,c_{\text{eff}}\), where \(T_{\text{work}}=nw\) is the private work time of one thread, \(pn/K\) is the number of shared updates in all, and \(c_{\text{eff}}\) is the extra time per shared update. Derive the smallest batch size \(K^{*}\) at which the shared updates add at most a fraction \(\varepsilon\) to \(T_{\text{work}}\). Evaluate it for \(p=4\) and \(p=12\) with \(\varepsilon=0.05\), \(w=8.4\) ns and \(c_{\text{eff}}=100\) ns (the mutex values of the batch-size sweep at \(K=10\) and \(K=100\)), and compare the prediction for \(p=4\), \(K=1000\) with the measured 8.9 ms.

Solution

The overhead fraction is \(\bigl[(pn/K)c_{\text{eff}}\bigr]/(nw)=pc_{\text{eff}}/(Kw)\). Requiring \(pc_{\text{eff}}/(Kw)\le\varepsilon\) gives \(K^{*}=\lceil pc_{\text{eff}}/(\varepsilon w)\rceil\). For \(p=4\): \(4\times100/(0.05\times8.4)=952.4\), so \(K^{*}=953\). For \(p=12\): \(12\times100/(0.05\times8.4)=2857.1\), so \(K^{*}=2858\); the batch must grow in proportion to \(p\), because the number of shared updates per unit of work grows with the number of threads. For \(p=4\) and \(K=1000\), the model gives \(T_4\approx 10^{6}\times8.4\ \mathrm{ns}+4000\times100\ \mathrm{ns}=8.4+0.4=8.8\) ms, an overhead of 4.8 %. The measured mutex time is 8.9 ms, 6 % above the 8.4 ms of the private count. The model is 0.1 ms (1.1 %) below the measured time, and it is a fit, not a derivation: \(c_{\text{eff}}\) is the measured quantity, 97.5 and 121.8 ns at \(K=100\) and 10, and the sweep cannot resolve it at \(K=1000\), where the extra time of 0.5 ms is of the size of the variation between samples (\(\pm0.3\) ms in the session).

Exercise 3 (counterexample). A student claims: "If every access to the shared variable is atomic, the program has no race condition." Use the program of this chapter to show that the statement is false, and say what is true about such a program.

Solution

The row load then store (atomic) of counter.c declares the counter _Atomic and performs the update as an atomic load followed by an atomic store. Every access is atomic. Take two threads with one increment each, and the schedule in which both load 0 before either stores: both store 1, and the final value is 1, not 2 (schedule B of Table 8.1). The program therefore has a race condition: the result depends on the schedule. The sample run kept 1 956 317 of 4 000 000 updates. What is true is the weaker statement of the C standard: if all conflicting accesses are atomic, the program has no data race (N1570 §5.1.2.4 ¶25: a data race needs two conflicting actions "at least one of which is not atomic"), so its behavior is defined, but its result can still depend on the schedule. The atomicity of a load and of a store separately does not make the pair indivisible. A single atomic read-modify-write, such as atomic_fetch_add, does, and the row atomic fetch-and-add keeps all updates.

Exercise 4 (diagnose an assumption). A reader proposes to place the fence in Peterson's algorithm between the two stores, after flag[i] = 1 and before turn = j, in place of the position after turn = j. The exhaustive search of the TSO model, run on this variant, finds a violation of mutual exclusion in 16 steps: thread 0 stores flag0, the buffer reaches memory, the fence runs, thread 0 stores turn = 1 (buffered), loads flag1 and reads 0, and enters; thread 1 stores flag1, flushes, fences, stores turn = 0, which reaches memory, and then thread 0's buffered turn = 1 reaches memory; thread 1 loads flag0, reads 1, loads turn, reads 1, and enters. Identify the sentence of the proof of mutual exclusion that fails, and explain why a fence in the other position keeps it true.

Solution

The failing sentence is "After \(w_1\), turn is 0 until some thread writes it again, and neither thread writes it again before the critical section". It treats a write as taking effect when it is issued. In the trace, thread 0 issues turn = 1 (step 4) before thread 1 issues turn = 0 (step 10), but the write of thread 0 reaches memory later (step 12) and overwrites the other. So \(w_0\) is the last write to reach memory, and thread 1's test reads turn == 1 and lets it pass. The decisive load by thread 0, of flag1 at step 5, ran while thread 0's own store of turn was still in its buffer; the fence at step 3 had emptied the buffer of the earlier store only. A fence placed after turn = j forces both stores of the thread to reach memory before it loads the other flag. Then, for any thread that reads the other flag, its two writes are visible to the other thread before it reads; that restores the sentence of the proof. The search confirms this position for one entry per thread: safe in all 274 states.

Exercise 5 (design judgment). Choose a synchronization strategy for each of three programs: (a) and (b) on 12 threads, (c) with four worker threads, and justify the choice with numbers of this chapter. (a) The midpoint-rule loop for \(\pi\) with \(10^{9}\) iterations of about 1 ns each, which sums into one double. (b) A histogram of 256 bins of 8 bytes, updated by \(10^{8}\) samples, each sample costing about 20 ns to generate. (c) Four worker threads that take jobs of about 1 ms each from one shared queue.

Solution

(a) Choose private partial sums and one combining step per thread. An atomic add per iteration costs 31 ns at \(p=12\) in the thread sweep (374.9 ms for \(12\times10^{6}\) updates), so \(10^{9}\) updates would take at least 31 s, against about \(10^{9}\times1\ \mathrm{ns}/12=0.08\) s of work. With \(w=1\) ns and \(c=31\) ns, bound (8.3) gives \(S_p\le(w+c)/c=1.03\): twelve threads would run at the speed of one. With private sums, there are 12 shared updates in all, and \(K=n=8.3\times10^{7}\). The result differs from the serial one in rounding only, within the tolerance of \(\pi\) at \(10^{-9}\) that cas_pi.c checks. (b) Choose one private histogram per thread and merge them at the end. The private copies take \(12\times256\times8=24\,576\) bytes, and the merge is \(12\times256=3072\) additions. An atomic add per sample would put 256 words on 32 cache lines (8 words per 64-byte line) and let neighbouring bins share lines; the cost per update would be of the order of the 31 ns measured for one shared word, against 20 ns of work per sample, so the atomic version could not use the twelve threads well. That last statement is an estimate and was not measured. (c) Choose a mutex around the queue. The bound (8.3) needs \(w\ge(p-1)c\) for the lock not to limit the time. Here \(w\approx1\) ms and \(c\) is below 0.15 µs (the mutex cost 47 to 122 ns per update in the sweeps), so \(w\) is more than \(2\times10^{3}\) times larger than \(3c\) (1 ms against at most 0.45 µs); the lock is idle almost all the time, and the simplest correct primitive costs nothing measurable.

Exercise 6 (implementation and measurement). Add two spinlocks to counter.c: a test-and-test-and-set lock, which spins on an ordinary atomic load of the lock word and attempts the exchange only when the load shows the lock free, and the same lock with the x86 pause hint in the spin loop. Predict, before running, how each compares with the plain test-and-set lock at \(p=4\), 8 and 12. Then run it and compare.

Solution

The change is one new case in flush, with the lock word _Atomic int lock_word:

case TTAS:                                    /* add TTAS_PAUSE to the enum for the second variant */
    for (;;) {
        while (atomic_load_explicit(&lock_word, memory_order_relaxed))
            __builtin_ia32_pause();               /* omit this line for the plain variant */
        if (!atomic_exchange_explicit(&lock_word, 1, memory_order_acquire)) break;
    }
    plain_count = plain_count + v;
    atomic_store_explicit(&lock_word, 0, memory_order_release);
    break;

The prediction from the usual argument is that spinning on a load lets all waiting threads share the line in the cache and reduces the traffic of failed exchanges, so the test-and-test-and-set lock should beat the test-and-set lock at 8 and 12 threads, with pause adding a further gain. The run, one session with other jobs present, gave these times for \(10^{6}\) iterations per thread: at \(p=4\), mutex 192.9 ms, test-and-set 265.1, test-and-test-and-set 390.7, with pause 345.8; at \(p=8\), 605.0, 955.8, 882.7 and 875.7; at \(p=12\), 826.1, 2067.1, 1785.8 and 1540.8. The prediction held at \(p=8\) and 12 for the plain test-and-test-and-set lock, by 8 % and 14 %, and failed at \(p=4\), where it was 47 % slower. The pause hint was faster than the plain variant by 11 % at \(p=4\), 0.8 % at 8 and 14 % at 12; against test-and-set at 12 threads it was 25 % faster. The three spinlocks of this exercise were slower than the mutex at 12 threads, by a factor of 1.9 to 2.5. So the textbook improvement of the spinlock is small and uneven on this machine, and the mutex remains the better choice at 12 threads. The session does not show why. One run per configuration cannot give the spread, and a repeated measurement is the first step of a fuller answer.
