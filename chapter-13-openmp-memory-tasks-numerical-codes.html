OpenMP III: memory ordering, tasks, and trustworthy numerical parallelism

A heat solver performs 1000 sweeps over a 1000 × 1000 interior grid. Each sweep has a million independent stencil updates, but the next sweep must see all of them. Put the parallel directive on the outer loop and there are 1000 team activations for the update phase; put it on the inner loop and there are one million. Give every thread the same inner-loop counter and the numerical result can become meaningless. The same three questions govern a linked-list traversal and a million-sample integral: which operations may overlap, which storage may they touch, and what event certifies completion? We answer them before interpreting a speedup.

Grounded in W4L4, OpenMP Memory Model, Irregular Parallelism, and Tasks, W4L5, Parallelization of example codes using OpenMP, Part 1, and W4L6, Part 2, in the NPTEL course High Performance Scientific Computing (Prof. Shivasubramanian Gopalakrishnan, IIT Bombay). Lecture material: temporary memory views and flush; linked-list conversion to an indexed loop; task creation, single, task data environments, taskwait, recursive Fibonacci and task-based π; a two-array heat solver, private indices and timing; outer versus inner parallel loops; trapezoidal and Monte Carlo integration with reductions. W4L4 credits slides to the Argonne Training Program on Exascale Computing, 2024. Research extensions: OpenMP 5.2 specifies the guarantees; Netlib's Templates for the Solution of Linear Systems distinguishes Jacobi from successive overrelaxation; the Linux rand manual explains hidden generator state; Salmon and colleagues (2011) establish counter-based random-number generation as a parallel design; Vigna's public-domain SplitMix implementation supplies the indexed transformation used here. Original teaching constructions: the event and task graph, publication proof, lifetime counterexample, task-granularity bounds, complete numerical checks, fixed-block sampling experiment, all runnable programs and the six worked exercises. Taskgroup and task dependences are specification-based extensions, not topics claimed for these recordings.

The objects of the chapter and the running case

A team consists of \(p\) OpenMP threads executing one parallel region. Each thread initially executes an implicit task, the work associated with that region. An explicit task is a package of code and its data environment generated by a task construct. A thread is an execution resource; a task is work that a resource can execute. One thread can execute many tasks. Creating a thousand tasks does not request a thousand operating-system threads.

Model the computation by a directed acyclic graph \(\mathcal G=(\mathcal V,\mathcal E)\). Its vertices are finite pieces of computation; a directed edge \(a\to b\) means that correctness requires \(a\) to finish before \(b\) consumes its result. A valid execution respects these edges. The total operation count is the work \(W\). The maximum operation count along a directed path is the span \(D\), under a unit-cost model for operations. Even ideal identical processors require at least \(\max(W/p,D)\) operation-time units. Real scheduling adds task creation, synchronization, memory traffic and unequal processor speeds.

There is a second graph at the level of memory events. A memory object is a storage location with a lifetime. An event reads or writes such an object. Two accesses conflict if they touch the same memory unit and at least one writes it. Write \(a\prec b\) for an ordering established by program execution and OpenMP synchronization, including its transitive consequences. A programmer must establish this order for conflicting accesses by different threads. Merely expecting one thread to run first supplies no edge. The memory model determines when the required order also makes a value visible.

Our regular running case remains the book's Jacobi solver. It stores a dimensionless temperature \(u_{i,j}\) on an \((N+2)\times(N+2)\) grid, with \(N\) interior points per direction, indices \(1\le i,j\le N\), and spacing \(h_g=1/(N+1)\) on the unit square. The top boundary is one, the other edges zero, and the interior starts at zero. A second array unew stores the next iterate. A sweep reads only u and writes one distinct element of unew per cell. The edge from every sweep to the next is essential even though cells within one sweep are independent.

The irregular companion is a singly linked list: each node contains an input integer, a result slot, and a pointer to the next node. The topology is immutable during processing. A serial cursor discovers nodes; tasks process their payloads. Here the correctness graph contains discovery edges along the list and one result-publication edge for every node. It does not require one payload computation to precede the next. This distinction is the opportunity that tasks exploit.

We use \(T_1\) and \(T_p\) for elapsed wall-clock times with one and \(p\) threads, \(S_p=T_1/T_p\) for speedup, and \(E_p=S_p/p\) for efficiency. A baseline must identify the implementation and timed interval. An OpenMP program with one thread includes OpenMP overhead; it is not automatically the fastest serial implementation. The verification machine is the previously described Intel Core i5-12450H laptop, with four performance cores supporting two hardware threads each and four efficient cores, running GCC 13.3 under WSL Ubuntu 24.04. Hardware threads are not interchangeable physical cores.

Memory ordering: a flush is not a meeting point W4L4 1:18

A shared address space supplies common names for memory, not a promise that every source-level access instantly observes every other thread's latest assignment. The OpenMP 5.2 memory model, §1.4.1, permits temporary thread views. It also defines a data race through unordered conflicting accesses. The temporary view is an abstraction: an implementation may use registers, caches or other mechanisms. It is not a requirement that every core have one stale physical copy of every variable.

Cache coherence and program synchronization answer different questions. Coherence can keep a hardware cache line consistent while the compiler retains a value in a register or moves an operation across another operation. Conversely, a synchronization guarantee need not flush every cache line to dynamic RAM. Correctness should be proved in terms of language-level ordering and visibility. A diagram that draws arrows from registers to main memory cannot by itself prove an OpenMP program correct.

A strong flush has a specified flush set, the variables to which it applies. It constrains the encountering thread's reordering and reconciles its temporary view for those variables. Its details, including release and acquire flushes, are in §1.4.4. It does not make another thread reach a particular statement. For an original example, one thread executes value = 42; and then flush(value); another reads value before that assignment. Nothing in the writer's flush moves the earlier reader into the future. An agreed communication protocol still has to establish the order.

The W4L4 flush slide says that a flush makes other threads see the most recent value. Read that as an informal account of visibility after the required synchronization, not a complete communication protocol. The same recording subsequently warns that flush does not bring threads together. The precise specification distinguishes a visibility operation from the execution order needed to use it. In particular, adding flush to an ordinary shared-flag spin loop is not a general repair for unsynchronized conflicting accesses.

A barrier is stronger in a different direction: all participating threads must arrive, and accesses before it can be consumed after it under the model's synchronization guarantees. A critical region provides exclusion and ordering between matching acquisitions. Task completion constructs order completed task effects before the continuation they release. The memory-consistency rules, §1.4.6, explain why ordinary race-free programs using these synchronization constructs do not need extra explicit flush directives.

The following publication proof is deliberately short. Exactly one thread assigns 42 inside single. Its implicit ending barrier precedes every thread's read into its own array slot. Thus the write precedes all reads. The final parallel-region join precedes the serial verification of all slots. There are no concurrent writes to one slot. Inputs are fixed; the only effects are local shared-memory updates and one printed confirmation. The program checks ordering and visibility, not cache-line traffic.

#include <stdio.h>
#include <omp.h>
int main(void) {
    int value = 0, observed[4] = {0};
    #pragma omp parallel num_threads(4) default(none) shared(value,observed)
    {
        #pragma omp single
        value = 42;
        observed[omp_get_thread_num()] = value;
    }
    for (int i=0; i<4; ++i) if (observed[i]!=42) return 1;
    puts("single barrier publishes 42 to every participating thread");
    return 0;
}

single barrier publishes 42 to every participating thread

The result follows from the synchronization contract, rather than the relative speeds of four threads. Removing the single barrier with nowait would remove this proof: a thread that did not execute the single block could read before publication. A later parallel-region join protects the final serial check, but it cannot repair an earlier read of the wrong value.

Discover irregular work once; execute its payloads as tasks W4L4 6:38

A canonical counted loop exposes its iteration space before execution. Following a next pointer does not: the next address depends on the node just reached. One solution is a preprocessing pass that counts the list, allocates an array of pointers, fills it in a second traversal, and distributes the resulting indexed loop. W4L4 shows this approach before introducing tasks. It trades extra traversal and pointer storage for a familiar worksharing schedule. If the list will be processed repeatedly, that one-time conversion may be useful.

Tasks instead separate discovery from processing. The discovering thread follows the list once and generates a task for each node. Other team threads may execute generated tasks while discovery continues. The task construct, §12.5, permits immediate or deferred execution by the current team. There is no promised task-to-thread assignment or FIFO execution order. The OpenMP runtime schedules tasks onto team threads; the operating system separately schedules those threads onto hardware.

Place the traversal inside single so that only one implicit task discovers the list. Otherwise every thread could generate a complete duplicate traversal. Section 11.1 specifies that single selects one team thread, which need not be the primary thread, and normally ends with a barrier. This barrier also gives the verification code a natural point at which generated tasks are complete.

The cursor requires particular care. firstprivate(p) copies the pointer value when each task is encountered; it does not clone the node. The copy preserves that task's node address even while the discovering thread advances its own cursor. The firstprivate rules, §5.4.4, describe this initialization. Each task writes its own node's result. The node objects themselves remain alive until all tasks finish. Copying an address cannot extend the lifetime of the object at that address.

The listing constructs eight nodes with inputs 20 through 27 and computes the corresponding Fibonacci numbers by a deliberately redundant recursive function. Here Fibonacci numbers are \(b_0=0\), \(b_1=1\), and \(b_n=b_{n-1}+b_{n-2}\) for integer \(n\ge2\). Inputs differ, so payload costs differ. Output is collected serially after the parallel join and compared node by node with a serial reference. The program neither mutates links nor deallocates live nodes.

#include <stdio.h>
#include <omp.h>
typedef struct Node { int n; long result; struct Node *next; } Node;
static long fib(int n) { return n<2 ? n : fib(n-1)+fib(n-2); }
int main(void) {
    Node nodes[8];
    for (int i=0; i<8; ++i) {
        nodes[i].n=20+i; nodes[i].result=-1;
        nodes[i].next=i==7 ? NULL : &nodes[i+1];
    }
    #pragma omp parallel num_threads(4) default(none) shared(nodes)
    {
        #pragma omp single
        {
            for (Node *p=&nodes[0]; p; p=p->next) {
                #pragma omp task firstprivate(p)
                p->result=fib(p->n);
            }
        }
    }
    long total=0;
    for (int i=0; i<8; ++i) {
        if (nodes[i].result!=fib(nodes[i].n)) return 1;
        total+=nodes[i].result;
    }
    printf("nodes=8 sum=%ld all node results match serial\n",total);
    return 0;
}

nodes=8 sum=503283 all node results match serial

The sum is a compact display; the actual assertion checks every node, so two compensating errors cannot pass merely by preserving the total. The example establishes a correct decomposition, not a speedup claim. For only eight small payloads, runtime overhead can dominate. It also retains a serial discovery chain: tasks do not make a singly linked list randomly addressable.

Suppose there are \(m\) nodes, total payload service time \(C=\sum_{r=1}^m c_r\) on identical reference workers, maximum individual payload \(c_{\max}\), and serial discovery-plus-generation cost \(g\) per node. Then any execution has lower bounds \(C/p\), \(c_{\max}\) and \(mg\), subject to those modeling assumptions. Discovery may overlap processing, so adding these bounds is unjustified. A very long list of tiny nodes is generation-limited; one enormous node is indivisibility-limited. Batching several discovered nodes into one task reduces generation overhead but can worsen balance.

Nondeterministic output order is not automatically a data race. W4L4 illustrates task scheduling with the words “car” and “race.” Two synchronized append operations can legally occur in either order, producing different sentences. In contrast, two unsynchronized updates of one shared counter conflict and fail the memory-model contract. If order matters, encode an edge; if only the multiset of results matters, collect results by stable indices as above. “The answer varied” is evidence to investigate, not a complete diagnosis.

Task completion includes a lifetime obligation W4L4 17:04

Data-sharing attributes are relative to a construct. A variable shared among one team may be private to a surrounding task. An explicit task can share an automatic variable from its parent, but the parent must preserve that storage until the child finishes. Section 5.1.1 gives task defaults: storage shared by all relevant enclosing implicit tasks remains shared; other non-predetermined variables normally become firstprivate. Explicit clauses make the intended ownership easier to audit.

Private storage begins without a copied scalar value; firstprivate begins with a snapshot; shared refers to the original object. These are not interchangeable annotations for performance. A task given private(p) cannot safely dereference its uninitialized private pointer. A task given shared(p) may observe a cursor that the parent has already advanced, and can race with those advances. A task given firstprivate(p) receives the intended address, but still needs the pointed-to node to remain alive.

A plain taskwait waits for child tasks that the current task generated before that point; it does not directly wait for arbitrary descendants. This scope is explicit in §15.5. Suppose parent A generates child B, B generates grandchild C, and B then returns without waiting. A's taskwait can finish after B completes while C remains active. Reading C's result at that point is unsafe unless another synchronization orders it. A barrier at the end of the whole parallel region can be too late for a read inside A.

taskgroup provides the appropriate larger completion set. Its associated set includes tasks generated in the region and their relevant descendants in the same team; leaving the group waits for that set. This is the specification extension from §15.4. In the program, one task creates a descendant that writes a, while another writes b. Only after the group ends does the single thread read both into c. All three integers outlive the parallel region.

#include <stdio.h>
int main(void) {
    int a=0, b=0, c=0;
    #pragma omp parallel num_threads(4) default(none) shared(a,b,c)
    {
        #pragma omp single
        {
            #pragma omp taskgroup
            {
                #pragma omp task shared(a)
                {
                    #pragma omp task shared(a)
                    a=7;
                }
                #pragma omp task shared(b)
                b=11;
            }
            c=a+b;
        }
    }
    if (c!=18) return 1;
    puts("taskgroup includes descendant: 7 + 11 = 18");
    return 0;
}

taskgroup includes descendant: 7 + 11 = 18

The numerical check is simple because the purpose is completion scope. A delay is unnecessary: correctness must hold whether the descendant runs immediately, last, or on the generating thread. Replacing the taskgroup by a plain parent-level taskwait changes the guarantee even if a particular run still happens to print 18. A successful schedule cannot prove that a missing edge exists.

One can also express dataflow between sibling tasks using dependence locators. For example, a producer marked depend(out:token) and a later generated sibling consumer marked depend(in:token) establish an order through matching storage. The token identifies a dependence; OpenMP does not inspect arbitrary pointer reachability or infer the entire program's numerical dependencies. The exact sibling and storage-matching rules are in OpenMP 5.2, §15.9.5. A taskwait joins children; dependences describe particular edges. Neither excuses freeing a shared buffer too early.

Finally, single nowait removes the single construct's barrier, not the eventual parallel join. This can overlap unrelated work with outstanding tasks. It is valid only if that intervening work does not consume their unfinished outputs or end their storage lifetime. Removing synchronization is a graph transformation: first identify every edge it supplied, then establish that those edges are unnecessary or supplied elsewhere.

Recursion creates parallelism; a cutoff makes it affordable W4L4 22:35

The naive Fibonacci recurrence has two independent recursive calls but repeats most subproblems. If \(W_n\) counts constant-cost function activations, then \(W_n=W_{n-1}+W_{n-2}+1\). Set \(Z_n=W_n+1\); the recurrence becomes \(Z_n=Z_{n-1}+Z_{n-2}\). Its characteristic roots solve \(r^2=r+1\), giving the dominant root \(\varphi=(1+\sqrt5)/2\). Therefore \(W_n=\Theta(\varphi^n)\), also bounded above by \(O(2^n)\) as the lecture states. This explains the exponential work rather than treating the displayed upper bound as an exact growth rate.

Under ideal unlimited parallelism, the two branches overlap and the span follows \(D_n=\max(D_{n-1},D_{n-2})+O(1)=\Theta(n)\). Large work divided by small span suggests abundant parallelism. It says nothing about whether doing all that work is sensible. An iterative algorithm computes \(b_n\) in \(O(n)\) additions with constant auxiliary storage. For one Fibonacci number, replacing an exponential algorithm is usually the decisive optimization.

The recursive task example is useful for studying storage and synchronization. The parent invocation allocates x and y in its stack frame. Its children must share those result objects. Each child receives its own input value n. A taskwait precedes return x+y, so the frame remains alive until both values are produced. Each child uses the same rule recursively. By induction, completion of a child now implies completion of that child's entire recursive computation, even though a taskwait directly waits only for immediate children.

The implementation switches to serial recursion for inputs below 20. That cutoff bounds task generation while preserving the mathematical recurrence. It checks \(b_{30}=832040\), a value that fits in the signed long type on the verification system. It does not accept arbitrary large inputs: overflow and exponential cost would require a different algorithm and representation.

#include <stdio.h>
static long serial(int n) { return n<2 ? n : serial(n-1)+serial(n-2); }
static long fib(int n) {
    if (n<20) return serial(n);
    long x=0, y=0;
    #pragma omp task shared(x) firstprivate(n)
    x=fib(n-1);
    #pragma omp task shared(y) firstprivate(n)
    y=fib(n-2);
    #pragma omp taskwait
    return x+y;
}
int main(void) {
    long result=0;
    #pragma omp parallel num_threads(4) default(none) shared(result)
    {
        #pragma omp single
        result=fib(30);
    }
    if (result!=832040 || result!=serial(30)) return 1;
    printf("fib(30)=%ld matches serial; cutoff=20\n",result);
    return 0;
}

fib(30)=832040 matches serial; cutoff=20

Let \(M\) be the number of generated tasks, \(t_g\) their average creation-and-scheduling overhead, and \(T_{\mathrm{useful}}\) the useful work's reference service time. If task overhead is to remain below a fraction \(\epsilon\) of useful time in a simple serial accounting, require \(Mt_g\le\epsilon T_{\mathrm{useful}}\). A task that does \(c\) seconds of work should consequently have \(c\ge t_g/\epsilon\) on that model. This is a granularity guideline, not a parallel runtime bound: generation can overlap execution and overhead can contend.

The same divide-and-conquer structure can integrate \(4/(1+x^2)\) on \([0,1]\). The midpoint estimate uses \(n\) steps, width \(\Delta=1/n\), sample \(x_i=(i+1/2)\Delta\), and result \(\Delta\sum_{i=0}^{n-1}4/(1+x_i^2)\). Split the integer interval \([0,n)\) into disjoint halves until a leaf has at most 10000 points. A parent creates one child task, computes the other half itself, waits, then adds the two sums. Every point belongs to exactly one leaf because the half-open intervals partition at their common midpoint.

Inputs and split points are fixed, so this construction fixes the addition tree independently of the task schedule for a fixed executable. It checks an absolute error below \(10^{-10}\) against the C library's value of π with one million samples. That comparison checks numerical accuracy here; it is not a proof that arbitrary integrands or compiler transformations preserve the same error.

#include <stdio.h>
#include <math.h>
#define NUM_STEPS 1000000L
#define GRAIN 10000L
static double integrate(long lo,long hi) {
    if (hi-lo<=GRAIN) {
        double sum=0.0, h=1.0/NUM_STEPS;
        for (long i=lo;i<hi;++i) {
            double x=(i+0.5)*h;
            sum+=4.0/(1.0+x*x);
        }
        return sum;
    }
    long mid=lo+(hi-lo)/2;
    double left=0.0,right=0.0;
    #pragma omp task shared(left) firstprivate(lo,mid)
    left=integrate(lo,mid);
    right=integrate(mid,hi);
    #pragma omp taskwait
    return left+right;
}
int main(void) {
    double pi=0.0;
    #pragma omp parallel num_threads(4) default(none) shared(pi)
    {
        #pragma omp single
        pi=integrate(0,NUM_STEPS)/NUM_STEPS;
    }
    if (fabs(pi-acos(-1.0))>1e-10) return 1;
    printf("pi=%.12f analytic-error below 1e-10\n",pi);
    return 0;
}

pi=3.141592653590 analytic-error below 1e-10

The task-π slide uses a strict upper loop bound, i < Nfinish. Its two recursive calls share a boundary value as an argument, but their half-open index sets are disjoint. Our independently written version preserves that convention while using a smaller workload and a different leaf threshold; it creates one child task and evaluates the other half in the current task.

W4L4 compares task π with several earlier π implementations, but the displayed examples do not establish that tasks are universally faster than a reduction loop. The same lecture recommends ordinary loop constructs for ordinary loops and emphasizes granularity. A fair benchmark would fix sample count, precision, compiler options, hardware, timed region and numerical tolerance before comparing task and loop implementations. The task tree adds flexibility that this regular integral does not need; its value here is making the join and dataflow explicit.

Parallelize the heat stencil without changing the numerical method W4L5 0:40

For a thin plate with constant conductivity, no internal heat source, no variation through its thickness and a time-independent temperature, conservation of heat gives \(\partial^2u/\partial x^2+\partial^2u/\partial y^2=0\). Fixed temperatures on the boundary are Dirichlet data. The physical steady problem has no initial condition in time, but an iterative algebraic solver still needs an initial guess. Starting the interior at zero is such a guess, not an additional physical condition.

The lecture's plate differs from the book's standard plate: its top and left edges are zero, while its bottom and right edges rise linearly toward 100. With continuous coordinates chosen from the zero corner, the compatible ideal boundary data have the exact solution \(u(x,y)=100xy\): both second derivatives vanish and all four edge values agree. This gives a stronger check than remembering several digits at one near-corner point. The book's unit top-edge case remains the executable example here so that Chapters 9, 12 and 13 share a numerical problem.

Expand the two neighboring values in the x direction about a grid point. Their sum is \(2u+h_g^2u_{xx}+O(h_g^4)\), so subtracting \(2u\) and dividing by \(h_g^2\) approximates \(u_{xx}\) with error \(O(h_g^2)\), assuming four bounded derivatives. Repeat in y and add. The interior discrete equation and the Jacobi update are

\[ \frac{u_{i-1,j}-2u_{i,j}+u_{i+1,j}}{h_g^2}+\frac{u_{i,j-1}-2u_{i,j}+u_{i,j+1}}{h_g^2}=0, \qquad u^{(k+1)}_{i,j}=\frac{u^{(k)}_{i-1,j}+u^{(k)}_{i+1,j}+u^{(k)}_{i,j-1}+u^{(k)}_{i,j+1}}4. \tag{13.1} \]

Here \(k\) is the iteration number. Each new value uses exclusively old values. This is Jacobi, as defined by Netlib's Jacobi-method description. W4L5 calls the demonstrated code successive overrelaxation, but its visible two-array four-neighbor calculation is Jacobi. Successive overrelaxation instead relaxes successive Gauss–Seidel updates and involves an extrapolation factor. There is no such factor or successive use of new neighbors in this kernel.

Two further details matter when reproducing the demonstration. Its displayed finite-difference equation omits the factor two on each center value; (13.1) supplies it, agreeing with the actual four-neighbor average. Its boundary code uses a slope of 100.0/NR while the boundary index reaches NR+1. For 1000 interior rows this reaches 100.1 at the corner. A specification whose corner is exactly 100 uses the divisor 1001. These are different boundary problems, and matching a reported near-corner temperature cannot resolve that difference.

After assembling all interior equations one obtains a sparse linear system \(A\mathbf u=\mathbf b\), where \(A\) represents the stencil and \(\mathbf b\) contains known boundary contributions. An iterative method is not unconditionally more efficient than every direct method. Its cost depends on convergence, tolerance, preconditioning, matrix structure and available algorithms. The decision here is narrower: preserve the existing Jacobi iteration while exposing its within-sweep independence.

In a row-parallel loop, the associated outer index is private by OpenMP's loop rules. An inner C counter declared outside the parallel construct can remain shared; explicitly privatizing it, or declaring it inside the loop body, avoids conflicting increments. The latter is the listing's choice. The lecture's initial missing-private experiment returns varying answers, then its corrected indices recover its serial result. The fundamental defect is shared mutable index storage, not a failure of floating-point accuracy.

There are two inter-sweep hazards. First, overwriting the old array before all neighbors have read it changes the method and creates races. Second, swapping shared array pointers before every new cell is written lets the next sweep consume unfinished data. A separate combined parallel-for ends before the serial driver swaps pointers, so its join supplies the required order. A persistent parallel region can reduce activation overhead, but must retain a barrier after cell updates and a safe synchronization around the shared swap and termination decision.

The update norm is \(r_k=\max_{i,j}|u^{(k+1)}_{i,j}-u^{(k)}_{i,j}|\), in the same temperature units as the grid. For this stencil the maximum discrete Laplacian of the old iterate is \(4r_k/h_g^2\). Thus a small update norm alone is not a grid-independent differential-equation residual tolerance. Nor does running exactly 1000 iterations prove convergence on every grid. Fixed iteration counts are useful for controlled timing, while a solver intended to return a converged result must state its termination test.

The executable uses \(N=32\), tol=1e-8, and max_iter=20000. Both arrays retain identical boundaries; four heap allocations avoid large automatic arrays. Each parallel sweep is compared, cell by cell and norm by norm, with an independently executed serial sweep before the pointers are swapped. It fails if the tolerance is not reached. The maximum reduction combines finite nonnegative differences; unlike a floating-point sum, this maximum does not change merely because its combining order changes.

#include <stdio.h>
#include <stdlib.h>
#include <math.h>
#define IDX(i,j) ((size_t)(i)*(N+2)+(j))
static double jacobi_step(int N,const double *u,double *unew) {
    double diff=0.0;
    #pragma omp parallel for num_threads(4) default(none) shared(N,u,unew) reduction(max:diff)
    for (int i=1;i<=N;++i) {
        for (int j=1;j<=N;++j) {
            size_t q=IDX(i,j);
            unew[q]=0.25*(u[q-N-2]+u[q+N+2]+u[q-1]+u[q+1]);
            diff=fmax(diff,fabs(unew[q]-u[q]));
        }
    }
    return diff;
}
static double step_serial(int N,const double *u,double *unew) {
    double diff=0.0;
    for (int i=1;i<=N;++i) for (int j=1;j<=N;++j) {
        size_t q=IDX(i,j);
        unew[q]=0.25*(u[q-N-2]+u[q+N+2]+u[q-1]+u[q+1]);
        diff=fmax(diff,fabs(unew[q]-u[q]));
    }
    return diff;
}
int main(void) {
    const int N=32,max_iter=20000;
    const double tol=1e-8;
    size_t count=(size_t)(N+2)*(N+2);
    double *u=calloc(count,sizeof *u),*unew=calloc(count,sizeof *unew);
    double *ref=calloc(count,sizeof *ref),*next=calloc(count,sizeof *next);
    if (!u || !unew || !ref || !next) return 2;
    for (int j=0;j<N+2;++j) u[IDX(0,j)]=unew[IDX(0,j)]=ref[IDX(0,j)]=next[IDX(0,j)]=1.0;
    int iter=0;
    double diff=1.0;
    while (iter<max_iter && diff>=tol) {
        diff=jacobi_step(N,u,unew);
        double rd=step_serial(N,ref,next);
        for (size_t q=0;q<count;++q) if (unew[q]!=next[q]) return 3;
        if (diff!=rd) return 4;
        double *tmp=u;u=unew;unew=tmp;
        tmp=ref;ref=next;next=tmp;
        ++iter;
    }
    if (diff>=tol) return 5;
    printf("N=32 converged before 20000 sweeps; all cells and update norms match serial\n");
    free(u);free(unew);free(ref);free(next);
    return 0;
}

N=32 converged before 20000 sweeps; all cells and update norms match serial

This check establishes equivalence of the two implementations on the stated input and successful termination at the stated update threshold. It does not certify the continuum solution's discretization error. The discontinuous corner data of the unit-top-edge plate also require care in smoothness-based error claims. For the lecture's smooth bilinear manufactured solution, substituting the exact grid values into the stencil gives zero residual in exact arithmetic, which isolates solver error from truncation error.

A speedup compares like with like. W4L5 first times a whole executable externally, later times a code interval internally, and modifies the program while adding OpenMP. Different intervals and builds can explain a difference, but they do not quantify its causes. The recording attributes a reduced one-thread internal time to excluding program-loading overhead. That attribution is not isolated by the available measurements: setup work, printing, compilation changes and clock scope also differ. An interval subtraction alone cannot identify loading cost.

Now count constructs before counting seconds. Let \(K\) be the number of sweeps, \(N\) the number of interior rows, and \(t_a\) the effective cost of activating and completing one team region on the chosen runtime. The update phase uses \(K\) combined parallel regions when the directive encloses the outer loop, versus \(KN\) when it encloses only the inner loop. If both phases traverse \(N\) rows, these counts double. In the visible lecture code the update traverses \(N\) rows but the copy traverses \(N+2\) rows, including both boundary rows. Its outer placement therefore activates \(2K\) regions, while inner placement activates \(K[N+(N+2)]\). At \(K=N=1000\) these are 2000 and 2,002,000, respectively—approximately two million.

A first accounting model is

\[ T_{\mathrm{outer}}\approx T_{\mathrm{cell}}/p+Kt_a+T_{\mathrm{other}},\qquad T_{\mathrm{inner}}\approx T_{\mathrm{cell}}/p+KNt_a+T_{\mathrm{other}}. \tag{13.2} \]

Here \(T_{\mathrm{cell}}\) is useful cell-update service time and \(T_{\mathrm{other}}\) collects copying and other work under the same convention. The predicted extra overhead is \(K(N-1)t_a\). The model assumes similar cell work and locality and suppresses scheduling and bandwidth effects. It explains why a mathematically identical loop can slow down while remaining correct; it does not turn observed time differences into a pure measurement of thread creation.

The recording describes creating and destroying threads at every region. The logical fork and join are required, but implementations can reuse worker threads, so repeated operating-system thread creation is not implied. Team activation, work distribution, synchronization and wakeups still cost time. Keeping this distinction avoids attributing all overhead to a mechanism that was not measured.

The local program isolates update directive placement on a small 128-by-128 interior grid for twelve sweeps. Both variants perform the same serial copy after every sweep; only update-region placement changes. For each of one, two and four requested threads it runs five timed trials and reports the minimum and maximum. Each timed trial includes initialization only before the clock, then updates and copies inside the clock. It prints activation counts per trial, independent of scheduler behavior. These tiny trials deliberately expose overhead and should not be extrapolated to a production grid.

#include <stdio.h>

static double u[N+2][N+2],v[N+2][N+2];
static void init(void) {
    for(int i=0;i<N+2;++i) for(int j=0;j<N+2;++j) u[i][j]=v[i][j]=(i==0 ? 1.0 : 0.0);
}

            #pragma omp parallel for num_threads(p)

A reduction preserves the integral's terms, not their addition order W4L6 15:35

For an integrand \(g(x)\) on \([a,b]\), the composite trapezoidal rule divides the interval into \(n\) equal subintervals of width \(\Delta=(b-a)/n\), with endpoints \(x_i=a+i\Delta\). The trapezoid on subinterval i has area \(\Delta[g(x_i)+g(x_{i+1})]/2\). Adding disjoint subintervals gives

\[ \mathcal T_n=\frac{\Delta}{2}\sum_{i=0}^{n-1}\bigl[g(x_i)+g(x_{i+1})\bigr] =\Delta\left[\frac{g(a)}2+\sum_{i=1}^{n-1}g(x_i)+\frac{g(b)}2\right]. \tag{13.3} \]

The two formulas are algebraically identical: interior endpoints occur twice in the subinterval sum and boundary endpoints once. The first makes independent loop iterations especially clear. Every iteration computes two local endpoints and one contribution. The shared sum is the only conflicting destination. A reduction gives each participant an accumulator and combines the partial sums without unsynchronized updates of the original object.

For the lecture's \(g(x)=x^2\), \(a=0\), \(b=1\), the exact integral is \(1/3\). We can check more than a rounded decimal. Since \(\sum_{i=1}^{n-1}i^2=(n-1)n(2n-1)/6\), equation (13.3) yields

\[ \mathcal T_n=\frac1n\left[\frac1{n^2}\frac{(n-1)n(2n-1)}6+\frac12\right] =\frac13+\frac1{6n^2}. \tag{13.4} \]

The positive error matches convexity: a chord lies above this parabola. At \(n=1000\), the discretization error is \(1.666666667\times10^{-7}\). Printing only six decimal places can hide that error; getting “0.333333” is not proof of exact integration. Doubling n reduces the exact-arithmetic error by four for this quadratic.

The program implements the independent-trapezoid form and uses reduction(+:integral). Both endpoint variables are declared within the iteration, so no thread shares another's temporary endpoint. The iteration variable is declared in the for statement and needs no explicit private clause. In the lecture, placing private(i) before that declaration produces a compiler error because the name is not yet in scope at the directive, not because all loop variables are forbidden in a private clause.

Its numerical assertion compares the computed result with the finite-n formula (13.4), allowing \(2\times10^{-14}\) absolute floating-point error. The printed discretization error is calculated analytically and is deterministic. A shared unsynchronized integral += ... would have a data race; adding the reduction repairs that storage conflict. The program's purpose is accuracy and data ownership, not a timing contest on 1000 inexpensive iterations.

#include <stdio.h>
#include <math.h>
int main(void) {
    const int n=1000;
    const double h=1.0/n;
    double integral=0.0;
    #pragma omp parallel for num_threads(4) default(none) shared(n,h) reduction(+:integral)
    for (int i=0;i<n;++i) {
        double x1=i*h,x2=(i+1)*h;
        integral+=0.5*h*(x1*x1+x2*x2);
    }
    double exact=1.0/3.0+1.0/(6.0*n*n);
    if (fabs(integral-exact)>2e-14) return 1;
    printf("trapezoid n=1000 analytic discretization error=%.9e\n",1.0/(6.0*n*n));
    puts("parallel result agrees with finite-n formula within 2e-14");
    return 0;
}

trapezoid n=1000 analytic discretization error=1.666666667e-07
parallel result agrees with finite-n formula within 2e-14

OpenMP need not combine partial sums in the serial left-to-right order. In finite-precision arithmetic, \((a+b)+c\) can differ from \(a+(b+c)\). For example, in ordinary binary64 rounding, adding 1 to \(10^{16}\) loses that unit, so a sequence containing \(10^{16},-10^{16},1\) can sum to either zero or one under different parenthesizations. A race-free result can therefore vary in its final bits. The relevant checks are an error criterion and algorithmic invariants; bitwise identity requires additional control over operation order.

For the fixed-grid Jacobi comparison, every cell uses the same four-neighbor expression and only a finite max is reduced, so exact equality is reasonable for these builds. For the trapezoidal sum, demanding exact serial equality would reject some valid parallel implementations. Distinguish reproducibility of the mathematical problem, tolerance-level numerical agreement, and bitwise repeatability of a particular execution strategy. They are different requirements with different costs.

Random sampling adds a state-management problem W4L6 22:40

Let \(X_i\) be independent random variables uniformly distributed on \([0,1]\), and let \(Y_i=X_i^2\). “Independent” means that joint probabilities factor, while “uniform” means that an interval's probability equals its length. The Monte Carlo estimator is \(\widehat\mu_n=n^{-1}\sum_{i=0}^{n-1}Y_i\). Under this ideal probabilistic model, expectation is \(\mathbb E[Y_i]=\int_0^1x^2\,dx=1/3\). The fourth moment gives \(\mathbb E[Y_i^2]=\int_0^1x^4\,dx=1/5\), so

\[ \operatorname{Var}(Y_i)=\frac15-\frac19=\frac4{45},\quad \operatorname{Var}(\widehat\mu_n)=\frac4{45n},\quad \operatorname{SE}(\widehat\mu_n)=\sqrt{\frac4{45n}}. \tag{13.5} \]

Variance measures mean squared deviation from the mean; standard error is the standard deviation of the estimator. Independence removes the cross-covariance terms in the variance of the sum. If samples are correlated, those terms need not vanish and (13.5) can be wrong. At one million samples its standard error is about \(2.9814\times10^{-4}\). A central-limit normal approximation would give a rough 95% interval with half-width 1.96 standard errors, about \(5.84\times10^{-4}\); this is not a deterministic bound on one run.

To reduce the standard error by ten under the same model, multiply sample count by one hundred. That \(n^{-1/2}\) rate is slower than the trapezoidal rule's \(n^{-2}\) error for this smooth one-dimensional quadratic. Monte Carlo becomes attractive for high-dimensional or irregular integration because it avoids a full tensor grid, though its variance and sample-generation cost can still worsen with the problem. Its usefulness is conditional, not a reason to choose it over deterministic quadrature for every smooth integral.

The lecture seeds rand with the current time, then privatizes the sample variable and reduces the sum. These clauses handle the visible sample and accumulator storage, but not the generator's hidden state. The Linux rand manual documents both its repeatable seeded sequence and its hidden mutable state. On the documented Linux implementation it is marked MT-Safe; it would therefore be wrong to assert that concurrent calls necessarily cause a library data race. Internal synchronization can instead serialize generation, while thread scheduling changes which iteration receives which draw. Portability, throughput, stream assignment and numerical repeatability remain separate concerns.

A time-based seed also makes regression tests harder and is not guaranteed unique: two launches within the same clock unit can receive the same seed. It does not make samples “more random” merely by changing on each launch. A reproducible experiment should record its generator, seed, sample-index mapping and summation rule. Repeatability then enables debugging; it does not establish statistical validity.

Salmon, Moraes, Dror and Shaw (2011), §2, develop generators that transform counters and keys rather than advancing one shared state in sequential order. Their specific Random123 generators have their own design and testing evidence. The teaching program below uses a simpler indexed adaptation of Vigna's public-domain SplitMix transformation, not Random123. It takes a fixed seed, adds an odd-increment multiple of sample index modulo \(2^{64}\), applies the documented mixing operations, and maps the upper 53 bits to a double in \([0,1)\). No thread mutates shared generator state.

This indexing ensures that sample i is the same regardless of scheduling. It does not prove that samples are IID. A deterministic generator has a finite period, and this particular integer transformation is a permutation before the floating conversion. Statistical estimates based on (13.5) remain an ideal-model diagnostic, not a certification of this sequence or a confidence guarantee for arbitrary applications. Scientific production code should select and test a generator appropriate to its statistical demands.

Summation needs a second design choice. Split the million sample indices into fixed blocks of 1000. Each iteration processes one block in increasing index order and writes one distinct partial sum. Threads dynamically claim blocks; after the join a serial loop adds partial sums in block order. Thus both sample mapping and the arithmetic grouping remain fixed when the thread count changes. The array of 1000 doubles costs only 8000 bytes on this system, and the serial final sum has only 1000 terms. This is a conscious exchange of a small serial stage for repeatability.

The program runs its estimator once with one requested thread and once with four, tests exact equality, and checks the estimate against the known integral using an intentionally loose absolute threshold of 0.005. That threshold is a smoke test, not a probabilistic guarantee. It prints the ideal IID-model standard error separately. All inputs are fixed, and its only persistent effects are local allocations and printed output.

#include <stdio.h>
#include <stdint.h>
#include <stdlib.h>
#include <math.h>
#include <omp.h>
#define SAMPLES 1000000L
#define BLOCK 1000L
/* Indexed adaptation of Vigna's public-domain SplitMix64 output transformation. */
static double sample(uint64_t i) {
    uint64_t z=UINT64_C(123456789)+UINT64_C(0x9e3779b97f4a7c15)*(i+1);
    z=(z^(z>>30))*UINT64_C(0xbf58476d1ce4e5b9);
    z=(z^(z>>27))*UINT64_C(0x94d049bb133111eb);
    z^=z>>31;
    return (z>>11)*0x1.0p-53;
}
static double integrate(int p) {
    const long nb=(SAMPLES+BLOCK-1)/BLOCK;
    double *partial=calloc((size_t)nb,sizeof *partial);
    if(!partial) exit(2);
    #pragma omp parallel for num_threads(p) schedule(dynamic,1)
    for(long b=0;b<nb;++b) {
        long hi=(b+1)*BLOCK;if(hi>SAMPLES)hi=SAMPLES;
        double sum=0.0;
        for(long i=b*BLOCK;i<hi;++i) {double x=sample((uint64_t)i);sum+=x*x;}
        partial[b]=sum;
    }
    double sum=0.0;
    for(long b=0;b<nb;++b)sum+=partial[b];
    free(partial);return sum/SAMPLES;
}
int main(void) {
    omp_set_dynamic(0);
    double a=integrate(1),b=integrate(4);
    if(a!=b || fabs(a-1.0/3.0)>0.005) return 1;
    printf("samples=1000000 estimate=%.9f\n",a);
    printf("IID-model standard error=%.9f\n",sqrt(4.0/(45.0*SAMPLES)));
    puts("p=1 and p=4 results are bitwise equal with fixed blocks");
    return 0;
}

Six worked exercises

1. Derive a legal publication order

A producer writes payload=73, executes flush(payload), and returns. A consumer reads the ordinary shared payload without any other synchronization. Explain why the read is not guaranteed to return 73. Give a barrier-based repair and identify the necessary event edges.

Solution

The producer's flush constrains its own view and relevant reordering; it does not prove that the consumer read occurs after the write. The two accesses can be unordered, creating a data race. Put the write in a single region without nowait inside a parallel region and place each consumer read after that region. The single ending barrier supplies write → barrier arrival → barrier completion → read. The write occurs exactly once and all participating threads encounter the same single and barrier. A flush after the write alone lacks the cross-thread execution edge. A final join after the read cannot retroactively repair it.

2. Compute useful task granularity

A list has 100000 nodes. Task generation costs 0.4 µs per node and each payload costs 2 µs on identical workers. Ignore memory effects and suppose eight workers are available. Compute the discovery and useful-work lower bounds. How many nodes per task make creation overhead at most 5% of useful work in the simple accounting model?

Solution

Serial generation costs 100000 × 0.4 µs = 40 ms. Payload work is 200 ms, whose eight-worker lower bound is 25 ms. Since discovery and processing can overlap, the lower bound is the maximum, 40 ms, not their sum. With b nodes per task, creation overhead relative to useful service time is 0.4/(2b)=0.2/b. Require 0.2/b ≤ 0.05, giving b ≥ 4. This assumes batching removes the per-node task-generation cost while pointer traversal itself is negligible; a real cursor still pays to discover every node. Four-node batches do not guarantee eight-worker efficiency if expensive nodes cluster or one batch dominates.

3. Construct a descendant-completion counterexample

A creates B; B creates C, which writes an automatic result variable belonging to A. B does not wait for C. A executes taskwait and immediately returns its result. Describe an allowed execution that makes this unsafe and repair it in two ways.

Solution

B may enqueue C and finish. A's taskwait then observes completion of its direct child B and resumes even though C has not executed. Reading the result is unordered with C's write; returning can additionally destroy its storage before C writes. One repair encloses generation in a taskgroup and reads the result only after the group completes. Another makes B wait for its own child before completing; then completion of B transitively certifies completion of C. Both require the correct shared result object rather than a firstprivate result copy. Adding sleeps is not a repair because duration does not establish synchronization.

4. Diagnose a grid tolerance assumption

A Jacobi solver reports an update norm below \(10^{-8}\). Compare the corresponding maximum discrete Laplacian bound on grids with N=31 and N=127. Does using the same update threshold give the same differential-equation residual threshold?

Solution

For this stencil, the old-grid discrete Laplacian norm is four times the update norm divided by squared spacing. At N=31, spacing is 1/32, so the bound is 4 × 10⁻⁸ × 32² = 4.096 × 10⁻⁵. At N=127 it is 4 × 10⁻⁸ × 128² = 6.5536 × 10⁻⁴, sixteen times larger. The same update threshold therefore permits a larger differential residual on the finer grid. To target a fixed differential residual threshold ε, choose the update threshold ε times squared spacing divided by four. That still controls algebraic residual rather than directly certifying continuum solution error.

5. Choose a method before choosing a thread count

For integrating x² on [0,1], compare n=1000 trapezoidal subintervals with n=1000000 ideal IID Monte Carlo samples. Compute the exact trapezoidal error and the Monte Carlo standard error. Explain why one million parallel random samples are not automatically the better method.

Solution

Equation (13.4) gives trapezoidal error 1/(6 × 1000²) = 1.6667 × 10⁻⁷. Equation (13.5) gives Monte Carlo standard error √(4/(45 × 10⁶)) = 2.9814 × 10⁻⁴, about 1789 times larger than that deterministic error despite about a thousand times more sample points. These compare a deterministic error with a stochastic scale, not two hard bounds. The quadratic is smooth and one-dimensional, an especially favorable case for trapezoidal quadrature. Monte Carlo's strengths emerge with different domain structure, dimension or sampling opportunities. Reducing parallel runtime does not improve an estimator's error per sample.

6. Implement a reproducibility and placement experiment

Modify the fixed-block Monte Carlo program to test p=1,2,4 with dynamic scheduling and block sizes 250,1000,4000. State which equalities should hold and which need only agree numerically. Design a five-trial directive-placement comparison whose timed intervals remain comparable.

Solution

For each fixed block size, the generator maps the same index to the same sample, block-local sums run in increasing index order, and the final loop adds blocks in increasing order. With the same executable and arithmetic settings, changing thread count or dynamic assignment therefore preserves the arithmetic graph and should preserve bitwise results. Changing block size changes grouping, so low bits may differ even though the generated sample sequence is identical. Compare those results with a stated floating-point tolerance; do not interpret low-bit differences as random-sampling variation. Keep the same seed, sample count and generator in all runs.

For placement, choose fixed N and sweep count, initialize outside the timed interval, use the same stencil expression, boundary values and copying strategy, and move only the update directive. Warm the runtime consistently or report cold starts separately. Run each requested thread count and placement five times, recording every time and the min/max or another declared summary. Compare completed grids after timing. Retain compiler flags and activation counts, and alternate or otherwise state trial order if thermal drift is a concern. A larger test can improve timer resolution, but do not infer a speedup by comparing an update-only interval with a whole-program interval.
