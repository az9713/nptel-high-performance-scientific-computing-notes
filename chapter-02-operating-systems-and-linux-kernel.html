Operating systems and the Linux kernel

A parameter sweep starts 100 000 runs of a small serial program, each run as a new process. On the machine used for this chapter, creating and ending one process that prints one line takes 0.46 to 0.70 ms when the program is linked dynamically and 0.31 to 0.42 ms when it is linked statically (five runs of the program in the section on launching). The sweep therefore spends 46 to 70 s, or 31 to 42 s, in process creation before any solver computes. The dynamic program makes 35 system calls. Entering and leaving the kernel 35 times costs at least 2.9 µs (35 × 84 ns, the smallest measured call), under 1 % of the launch time. The rest is work done inside the kernel: inside the calls fork, execve and mmap, which copy page tables, build the new address space and map the program and its libraries; in about 70 page faults that the program never requests; and in process exit. This chapter defines the objects that an operating system manages (processes, address spaces, privilege modes, system calls), follows one command, ./hello, from the shell to the first instruction of the program, and measures each step on a Linux kernel. Its structure follows the two lectures: the purpose of an operating system, the layers between a program and the hardware, and the subsystems of the Linux kernel.

The objects of the chapter and the running case

The chapter studies one kind of system: a computer whose processors run programs in two privilege modes, under a kernel. The definitions below are used in every later section.

Processor and privilege mode. A processor executes the instructions of one thread at a time. At every instant it is in one of two privilege modes. In user mode it refuses privileged instructions (instructions that change the page tables, disable interrupts or halt the processor) and it reaches only the memory that the current page tables mark as accessible to user programs. In kernel mode it executes every instruction and reaches all memory. A privileged instruction in user mode does not execute: the processor raises an exception, which transfers control to the kernel. The program privileged.c in the next section observes this.

Kernel. The kernel is the code and the data that run in kernel mode. A program in user mode cannot read or write them. The section on the kernel shows that the kernel is not a process.

Entry to the kernel. Control passes from user mode to the kernel by one of three events. A system call is a request by the program: it executes a special instruction (syscall on x86-64) after placing a request number and arguments in registers. An exception is a fault caused by the instruction just executed, such as an access to an unmapped address or a privileged instruction in user mode. A page fault is the exception that an access to a virtual address raises when the page that holds it is not mapped, or is not mapped for the kind of access made; the kernel then maps a page or ends the process. An interrupt is a request from a device or a timer, unrelated to the instruction being executed. The kernel documentation of the x86-64 entry code lists these entry points: the syscall instruction, interrupts, and architecturally defined exceptions (Linux kernel documentation, x86 entry code). A signal goes the other way: it is a notification that the kernel delivers to a process. Signal 11, SIGSEGV, reports an invalid memory access or an instruction that the processor refused. On x86-64 this chapter assumes, without a source that it opened, that a privileged instruction in user mode raises a general-protection exception, which Linux reports to the process as SIGSEGV; the observed signal 11 in the next section agrees.

Process and thread. Ritchie and Thompson define an image as "a computer execution environment" that "includes a memory image, general register values, status of open files, current directory and the like", and a process as "the execution of an image" (Ritchie and Thompson, §V). This chapter writes a process as \(P=(A,O,\kappa,\mathcal T)\). \(A\) is its address space, the set of mappings from virtual pages (fixed-size blocks of addresses, 4096 bytes here) to physical page frames (blocks of physical memory of the same size), each with permissions. \(O\) is its table of open files: a map from small integers, the file descriptors, to open files. \(\kappa\) is its credentials, the user and group identity that the kernel checks on file access (chapter 3). \(\mathcal T\) is its set of threads. As in chapter 11, a thread is a sequence of instructions with its own program counter and call stack; every thread has its own register state and its own scheduling state, and the threads of one process share \(A\) and \(O\). The kernel schedules threads: the Linux scheduling manual speaks throughout of the scheduling of a thread (sched(7)). A process with one thread is the case studied until chapter 11.

System call interface. A system call has a number \(n\) and up to six integer arguments. On x86-64 Linux the number goes into register rax, the arguments into rdi, rsi, rdx, r10, r8 and r9, the instruction is syscall, and the result returns in rax (syscall(2), the tables of instruction, number register and argument registers). The C library wraps each call in a function that stores an error code in errno. The time that one call costs is \(t_{\mathrm{sys}}\); the section on the kernel measures it.

The running case. A user types ./hello in a shell. hello is a program that prints one line and ends. Six events lead from the keystroke to the end: (E1) the shell creates a child process; (E2) the child replaces its program by hello; (E3) the kernel builds the new address space and returns to user mode at the first instruction of the new image; (E4) for a dynamically linked program, the dynamic loader maps the C library; (E5) main runs and calls the kernel to write the line; (E6) the process ends and the shell learns the exit status. Four quantities describe the case: the number \(s\) of system calls, the cost \(t_{\mathrm{sys}}\) of one call, the number \(n_f\) of page faults, and the time \(t_{\mathrm{launch}}\) from E1 to E6. The lectures do not follow a command through these events; the chapter does, and it places each lecture topic at the event where it acts.

What an operating system does: multiplexing, protection and abstraction W1L1 0:48

The lecture defines an operating system as software that manages the hardware and software resources of a computer, the first thing loaded on a computer; the slide says that without one a computer "cannot function effectively". It gives eight reasons for having one: complex hardware, security, many concurrent tasks, memory and file storage, interaction with users, peripheral devices, error handling and networking. W1L1 4:37 lists eight components that do this work. The two lists of eight overlap. This section reduces them to three mechanisms, and Table 2.1 assigns each lecture component to the mechanisms it implements.

Multiplexing divides one resource among several users, over time or in space: processor time among threads, physical memory among address spaces, a network link among connections. Protection prevents one process from reading, writing or disabling the resources of another process or of the kernel. Abstraction presents one uniform interface over differing hardware, such as the file, the process and the socket.

Why protection needs two privilege modes. Suppose every program could execute every instruction. A program could disable interrupts and then loop. No timer interrupt would return control to the scheduler, so the processor could not be multiplexed against the will of that program. A program could also change the page-table base register and read any memory. Multiplexing and isolation therefore need a set of instructions that only the kernel can execute, and two privilege modes provide that set. This argument follows from the definitions of the mechanisms. It shows that hardware needs a privilege mode for the isolation to be enforceable, and it does not show that two modes are the only possible design.

The next program tests the argument on this machine. It creates three child processes with fork and reports how each ends; fork is defined in the section on launching, and here only its effect matters: the child runs the chosen function while the parent waits and reads the child's termination status. The first child makes an ordinary system call. The second executes hlt, a privileged instruction that halts the processor. The third stores to address 0, which no mapping covers. The program is specific to x86-64 because of hlt, and its output is the same on every run.

#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

static void halt_cpu(void)  { __asm__ volatile("hlt"); }              /* privileged instruction (x86-64) */
static void write_null(void) { *(volatile int *)0 = 1; }              /* store to an unmapped address */
static void harmless(void)  { (void)getpid(); }                       /* an ordinary system call */

static void run(const char *name, void (*body)(void))
{
    pid_t pid = fork();
    if (pid == 0) { body(); _exit(0); }
    int status = 0;
    waitpid(pid, &status, 0);
    if (WIFSIGNALED(status))
        printf("%-14s killed by signal %d (%s)\n", name, WTERMSIG(status), strsignal(WTERMSIG(status)));
    else
        printf("%-14s exited with status %d\n", name, WEXITSTATUS(status));
}

int main(void)
{
    run("getpid():", harmless);
    run("hlt:", halt_cpu);
    run("store to 0:", write_null);
    return 0;
}

getpid():      exited with status 0
hlt:           killed by signal 11 (Segmentation fault)
store to 0:    killed by signal 11 (Segmentation fault)

The system call succeeds. The privileged instruction and the store each end the child with signal 11, Segmentation fault. The processor does not execute hlt in user mode, and the kernel, which receives the exception, ends the child. The store to address 0 faults for a different reason: the page tables of the child have no mapping for that address, the kernel's page-fault handler finds no region that contains it, and the kernel delivers the same signal. In both cases the parent continues. A fault in one process does not stop the kernel or the other processes, which is the protection property the argument above requires.

Kinds of operating system, and why high performance computing uses Linux W1L1 9:04

The lecture names four types of operating system, "based on the type of computer they control and the sort of applications they support": single-user single-task (a first-generation mobile phone), real-time (industrial machinery, medical equipment), single-user multitasking (Windows, macOS, Android) and multi-user multitasking (Linux). W1L1 11:58 adds that on an HPC system many users are logged in at once and each has several jobs.

The four boxes do not lie on one axis. Three independent properties are mixed. The first is the number of users that the system serves at the same time. The second is the number of tasks that run concurrently. The third is whether the system guarantees a bound on the time to respond to an event. A real-time system differs from the others on the third property only: a real-time system can serve one task or many. The type "real-time" is therefore not a third value of the property that separates the other three. Linux is multi-user and multitasking by default. It also offers real-time scheduling policies, SCHED_FIFO and SCHED_RR, with static priorities from 1 to 99, which always preempt ordinary threads (sched(7)), and the KernelNewbies summary of Linux 6.12, released on 17 November 2024, reports that the real-time preemption patch set (PREEMPT_RT), developed for about 20 years, was merged into the mainline kernel in that release (KernelNewbies, Linux 6.12; a secondary source).

A multi-user system gives every process credentials \(\kappa\), checks every access to a file or device against them, and keeps the processes of different users apart by the protection mechanism of the previous section. A cluster needs this property because many people share the same nodes. Chapter 3 treats the permission rules.

History. The slide at W1L1 12:40 states that Linux has its roots in Unix, developed in 1969 at Bell Labs by Ken Thompson and Dennis Ritchie, and that Andrew Tanenbaum developed MINIX in the late 1980s, whose limitations led to Linux. Ritchie and Thompson date the earliest of four Unix versions to "circa 1969-70" and say that it ran on the PDP-7 and PDP-9 computers (§I). They add that the second version ran on "the unprotected PDP-11/20 computer" and that the third "incorporated multiprogramming" and ran on the PDP-11/34, /40, /45, /60 and /70. The paper does not link the two facts, but they agree with the argument of the previous section: multiprogramming appeared on the machines that offered memory protection. The same paper describes a system that runs on the PDP-11/70 and the Interdata 8/32, so by 1978 Unix had been ported to a second processor architecture.

Torvalds's own account of the start of Linux consists of newsgroup posts that he collected in 1992 (Torvalds, 1992). On 25 August 1991 he wrote to comp.os.minix that he was "doing a (free) operating system (just a hobby, won't be big and professional like gnu) for 386(486) AT clones". The same collection says that version 0.01 of the sources was made available "sometimes around this time", and that it contained no binaries. The lecture gives September 1991 for the first release. That is consistent with the posts; the exact day is not established by the sources that were opened. Torvalds also writes that the early licence was "much more restrictive than the GNU copyleft" because it allowed no money to change hands, and that this "changed with 0.12", which "was out January 5th" 1992. The lecture states that Linux adopted the GNU General Public License in 1992. The year agrees with Torvalds's account of version 0.12. The passage does not name the licence, so the identity of the licence rests on the lecture. The lecture dates kernel 1.0 to 1994, and the kernel.org archive lists linux-1.0.tar.gz with the date 13 March 1994 (kernel.org, v1.0).

The lecture says that Linus Torvalds joined hands with the GNU project to build a complete free system. Torvalds's post of 5 October 1991 reports that bash, gcc, GNU make and other GNU programs run under the new kernel. This supports the statement: the kernel came from one project, and the compilers, the shell and the utilities from another.

Four statements of the lecture were not checked against a source: the release of the first major distributions, Slackware and Debian, in 1993; the release years of Ubuntu (2004) and Android (2008); and the statement that in 2020 Linux had become the most popular operating system among its users. The chapter does not rely on them.

The Tanenbaum–Torvalds exchange. Twenty-four days after version 0.12, on 29 January 1992, Tanenbaum posted "LINUX is obsolete". He defined the two kernel designs that the next sections use. In a monolithic system "the whole operating system is a single a.out file that runs in 'kernel mode'" and "contains the process management, memory management, file system and the rest". In a microkernel-based system "most of the OS runs as separate processes, mostly outside the kernel", communicating "by message passing". Torvalds replied the same day: "True, linux is monolithic, and I agree that microkernels are nicer" (Open Sources, appendix A). The section on the kernel returns to this exchange with measurements.

Linux in high performance computing. The lecture states at W1L1 15:28 that Linux is "the heart of HPC systems" because many users run many jobs on the same machine. The first half of the reason is the multi-user, multitasking property described above. The TOP500 statistics page for the operating system family could not be read (the page loads its numbers with scripts that were not executed), so this chapter states no share of the TOP500 list for Linux. The lecture also lists the properties of Linux: open source, community support, a kernel base, multi-user multitasking, regular updates, many variants from mobile to server, customization, performance and stability, and several package managers (apt, yum, dnf). Chapter 1 and chapter 6 describe the systems themselves.

The layers between a program and the hardware W1L1 17:05

The lecture's diagram has four layers: the user, the application, the operating system, and the hardware. Inside the operating system it places three parts: the shell, the system libraries, and the kernel. It describes the shell as an interface to the kernel, the system libraries as "a bridge connecting applications and the kernel, offering a standardized and efficient method for applications to engage with the underlying system", and the kernel as the part that talks to the hardware. This section turns each part into an interface that a program can observe.

The shell is a program in user mode. Ritchie and Thompson describe it as a command-line interpreter that "reads lines typed by the user and interprets them as requests to execute other programs" (§VI). The system library, here the C library libc, is a collection of functions that run in user mode. A function such as puts formats data in user mode and, when it needs the kernel, executes a system call. The kernel offers the system call interface defined in the section on the model. The code of the shell, of the library and of the program all runs in user mode. Only the kernel runs in kernel mode.

The layering of the lecture is not strict. A program can call the kernel directly without the library, as the later measurement of syscall(SYS_getpid) does. The lecture says that an application goes to the shell first. This is true only at the moment of launching: after the shell has started the program, the shell waits, and the program's own system calls do not pass through it (Ritchie and Thompson §VI: "When the command is finished, the shell resumes its own execution").

From ./hello to the first instruction

The six events of the running case can now be named with the objects of the model. E1. The shell reads the line ./hello. The name contains a slash, so the shell takes it as a path and does not search for it (POSIX.1-2024, Shell and Utilities, §2.9.1.4, Command Search and Execution: the search applies only to a command name that contains no slash; Ritchie and Thompson §VI already allow a command that "may be a path name including the '/' character"). The shell calls fork. Ritchie and Thompson state that after fork "the process splits into two independently executing processes" that "have independent copies of the original memory image, and share all open files" (§5.1). POSIX.1-2024 states that the child "shall be an exact copy of the calling process" except for details such as a unique process identifier (POSIX.1-2024, fork). The Linux manual adds that the two processes "run in separate memory spaces", that at the time of fork both spaces have the same content, and that fork is implemented with copy-on-write pages (the two processes share the pages, read-only, until one of them writes to a page, and then the kernel gives the writer a private copy), so that its only penalty is "the time and memory required to duplicate the parent's page tables, and to create a unique task structure for the child" (fork(2), description and notes). The C library implements fork with the clone system call, as the trace below shows.

E2. The child calls execve. This call "causes the program that is currently being executed by the calling process to be replaced with a new program, with newly initialized stack, heap, and (initialized and uninitialized) data segments" (execve(2)). Ritchie and Thompson describe the same primitive: "All the code and data in the process invoking execute is replaced from the file" (§5.3). E3. ELF (Executable and Linkable Format) is the file format of Linux executables; its program headers list the segments to map, and the header of type PT_INTERP names the program interpreter. For an ELF executable, the kernel opens the file through the virtual file system, reads its headers, and creates the mappings for its loadable segments. For a dynamically linked ELF executable, "the interpreter named in the PT_INTERP segment is used to load the needed shared objects" (execve(2)). The kernel then returns to user mode at the entry point of the new image. In the full trace (dyn.txt, of which the previous section shows the filtered lines), the first calls after execve are brk, mmap, access("/etc/ld.so.preload") and the opening of /etc/ld.so.cache. The cost of a launch. Let \(t_{\mathrm{launch}}\) be the wall-clock time from the fork in the parent to the return of waitpid, and \(t_{\mathrm{run}}\) the time that the program then needs for its own work. The fraction of the time that the launch consumes is

\[ \varphi=\frac{t_{\mathrm{launch}}}{t_{\mathrm{launch}}+t_{\mathrm{run}}}. \tag{2.1} \]

The next program measures \(t_{\mathrm{launch}}\) for the one-line program in its two forms, built by the command in the listing. Its inputs are the two executables tiny_dyn and tiny_static. For each form it starts the program 1000 times with fork, execl and waitpid, with the output redirected to /dev/null, and it keeps the smallest time of 7 rounds in which the two forms alternate. It also reads the number of minor page faults of the children with getrusage(RUSAGE_CHILDREN) (a minor fault is a page fault that the kernel resolves without reading from a disk, for example by mapping a zero-filled page or a page already in memory), and it measures the cost of one minor fault as the time to write the first byte of each page of a fresh 64 MiB mapping. The product of the faults per launch and the cost of one fault estimates the time that faults take, under the assumption that a fault during a launch costs as much as a first write to a zero-filled page. That assumption is approximate: a fault on a page of an executable file does other work. The run is checked by its return code, and the output is one sample run.

#include <fcntl.h>
#include <stdio.h>

#include <sys/wait.h>
#include <time.h>
#include <unistd.h>

#define LAUNCHES 1000

static double now(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return ts.tv_sec + ts.tv_nsec * 1e-9;
}

/* Seconds per minor fault: first write to each page of a fresh 64 MiB mapping. */
static double fault_cost(void)
{
    long page = sysconf(_SC_PAGESIZE), bytes = 64L << 20;
    char *p = mmap(NULL, bytes, PROT_READ | PROT_WRITE, MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    madvise(p, bytes, MADV_NOHUGEPAGE);
    double t0 = now();
    for (long off = 0; off < bytes; off += page) p[off] = 1;
    double t = now() - t0;
    munmap(p, bytes);
    return t / (bytes / page);
}

/* Run `path` LAUNCHES times with fork, exec and wait; report time and minor faults per launch. */
static double launch(const char *path, double *faults)
{
    struct rusage before, after;
    getrusage(RUSAGE_CHILDREN, &before);
    double t0 = now();
    for (int i = 0; i < LAUNCHES; i++) {
        pid_t pid = fork();
        if (pid == 0) {
            int null = open("/dev/null", O_WRONLY);
            dup2(null, 1);
            execl(path, path, (char *)NULL);
            _exit(127);
        }
        waitpid(pid, NULL, 0);
    }
    double t = (now() - t0) / LAUNCHES;
    getrusage(RUSAGE_CHILDREN, &after);
    *faults = (double)(after.ru_minflt - before.ru_minflt) / LAUNCHES;
    return t;
}

int main(void)
{
    double fc = fault_cost();
    printf("one minor fault (first touch of a page): %.2f us\n", fc * 1e6);
    const char *prog[] = {"/tmp/hpsc-launch-ch02/tiny_dyn", "/tmp/hpsc-launch-ch02/tiny_static"};
    double best[2] = {1e30, 1e30}, faults[2] = {0, 0};
    for (int r = 0; r < 7; r++)                      /* alternate the two programs in every round */
        for (int k = 0; k < 2; k++) {
            double t = launch(prog[k], &faults[k]);
            if (t < best[k]) best[k] = t;
        }
    for (int k = 0; k < 2; k++)
        printf("%-14s %6.1f us per launch, %5.1f minor faults per launch, faults alone: %4.1f us\n",
               prog[k], best[k] * 1e6, faults[k], faults[k] * fc * 1e6);
    return 0;
}

The kernel: privileged code, system calls and loadable modules W1L2 2:27

The lecture defines the kernel as the platform on which programs and services run, a bridge between the software and the hardware that manages resources, handles hardware communication and keeps processes executing. At W1L2 3:28 it states that the Linux kernel is monolithic, which it explains as running "as a single large process in a privileged mode" (the slide at W1L2 4:45). It adds that the kernel supports loadable kernel modules, and that it creates for every process a "virtual machine" through which the process reaches the hardware.

What monolithic means. Tanenbaum's definition, quoted in the section on history, is that the whole operating system is one binary that runs in kernel mode and contains process management, memory management, the file system "and the rest". This definition does not call the kernel a process. A process, as defined in the model, is an execution of an image with its own address space and with state that the kernel keeps. The kernel is the code that keeps that state. When a process makes a system call, the kernel code runs on behalf of the calling thread, and strace attributes the call to the process that made it. The lecture's phrase "single large process" is therefore a description of one binary in one privileged mode and not of a process in the sense of the model.

What the "virtual machine" is. The slide at W1L2 9:45 draws a box labelled "Virtual Machine" between each process and the kernel. What the kernel gives each process is two things. The first is a virtual processor: the thread sees its own registers, and the kernel saves and restores them when it switches between threads. The second is virtual memory: the process sees its own address space \(A\), whatever the other processes do. Together they make each process behave as if it had a dedicated computer, which is what the lecture means. They are not a virtual machine in the sense of a hypervisor, where a guest runs its own kernel. The machine of this chapter contains both layers: the WSL 2 virtual machine runs the Linux kernel 6.6.87.2, and every process of the guest runs under that single kernel. The lecture also assigns the creation of these machines to the virtual file system. That assignment is not supported by the kernel documentation, which describes the virtual file system as an abstraction layer over file systems; the section on the virtual file system returns to it.

The cost of one system call. A request to the kernel costs more than a call to a function in the same program, because the processor changes mode, the kernel entry code runs, and the return restores the user state. The kernel documentation lists the entry point for the syscall instruction among the entry points of the x86-64 entry code (entry code). It also states that on processors that need page-table isolation, the kernel changes the page-table base register at every entry and exit, a move that costs "on the order of a hundred cycles" each (page-table isolation, section on overhead). The guest here reports Not affected, so that cost is absent from the numbers below. The next program measures three costs per call: an ordinary function call that the compiler cannot remove, the system call getpid through syscall(SYS_getpid), and clock_gettime, which the C library serves from the vDSO, a small shared object that the kernel maps into every process. The Linux manual states that the vDSO exists because some calls are used so often that "the context-switch overhead that results from exiting user space and entering the kernel" can dominate performance (vdso(7)), and it lists __vdso_clock_gettime among the exported symbols. The listing keeps the smallest time of 5 repetitions of 5 000 000 calls. It is checked by its return code.

Amortizing the cost. A program that moves \(S\) bytes with calls that each move \(b\) bytes makes \(S/b\) calls. Let \(a\) be the fixed time of one call, independent of \(b\), and \(B\) the rate at which the kernel copies data. The total time and the fraction of it that is fixed per-call cost are

\[ T(b)=\frac{S}{b}\,a+\frac{S}{B},\qquad \frac{T_{\text{calls}}}{T}=\frac{aB}{aB+b}. \tag{2.2} \]

The fixed cost equals the copy time when \(b^{*}=aB\). The model assumes that \(a\) and \(B\) are constant, which holds while the data stay in a cache that the copy can use. The next program tests it on a file read. It writes a 64 MiB file in /tmp, so that the data sit in the page cache (the memory in which the kernel keeps recently used file data), and it reads the file with read calls of 1 byte to 64 KiB. For each size it keeps the smallest time of three passes, with at most 2 000 000 calls per pass. It fits the line \(t=a+b/B\) through the seven points by least squares. The run is checked by its return code.

#include <fcntl.h>
#include <stdio.h>
#include <time.h>
#include <unistd.h>

#define CALLS 2000000L                           /* at most this many calls per measurement */

static double now(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return ts.tv_sec + ts.tv_nsec * 1e-9;
}

int main(void)
{
    static char buf[MAXCHUNK];
    int fd = open("/tmp/chunks.dat", O_RDWR | O_CREAT | O_TRUNC, 0600);
    unlink("/tmp/chunks.dat");                        /* the open descriptor keeps the file alive */
    for (long done = 0; done < FILE_BYTES; done += MAXCHUNK)
        if (write(fd, buf, MAXCHUNK) != MAXCHUNK) return 1;      /* the data now sit in the page cache */
    long size[] = {1, 8, 64, 512, 4096, 32768, 65536};
    int n = sizeof size / sizeof size[0];
    double x[8], y[8];
    printf("%8s %14s %14s\n", "bytes", "ns per call", "GB/s");
    for (int i = 0; i < n; i++) {
        long calls = FILE_BYTES / size[i];
        if (calls > CALLS) calls = CALLS;
        double best = 1e30;
        for (int r = 0; r < 3; r++) {
            lseek(fd, 0, SEEK_SET);
            double t0 = now();
            for (long k = 0; k < calls; k++)
                if (read(fd, buf, size[i]) != size[i]) return 1;
            double t = (now() - t0) / calls;
            if (t < best) best = t;
        }
        x[i] = size[i];
        y[i] = best * 1e9;
        printf("%8ld %14.1f %14.2f\n", size[i], y[i], size[i] / best / 1e9);

The scheduler: fair shares, preemption and the cost of switching W1L2 11:18

The lecture states that the process scheduler decides how processes are allocated to the processor, with the goal of maximizing processor utilization and sharing the time equally. Its slide lists the key elements: scheduling policies (round robin, first come first served, shortest job next, completely fair scheduler), process states (running, waiting, ready, blocked), preemptive and non-preemptive scheduling, context switching and load balancing. The lecture explains preemptive scheduling as taking the processor from a running process when a higher-priority process arrives.

Definitions. A thread is runnable when it needs a processor, and blocked when it waits for an event such as the completion of input. A burst \(\tau_j\) is the processor time that job \(j\) needs. The waiting time of a job is the time during which it is runnable and does not run. A scheduler is preemptive when it can remove a running thread from the processor before that thread blocks or ends. A quantum \(q\) is the longest time that a thread runs before the scheduler may switch. A context switch saves the state of one thread, restores the state of another and costs a time \(t_{\mathrm{cs}}\).

Policies on four jobs. Take four jobs that arrive together at time 0, with bursts \(\tau_A=8\), \(\tau_B=4\), \(\tau_C=9\), \(\tau_D=5\) ms, one processor, no switching cost, and jobs that run to completion in the chosen order. If the order is \(\sigma\) and \(\tau_{(i)}\) is the burst of the job in position \(i\), the job in position \(k\) waits \(\sum_{i\lt k}\tau_{(i)}\), so the sum of the waiting times and the mean waiting time are

\[ \sum_{k=1}^{n}\sum_{i\lt k}\tau_{(i)}=\sum_{i=1}^{n}(n-i)\,\tau_{(i)},\qquad \bar w=\frac1n\sum_{i=1}^{n}(n-i)\,\tau_{(i)}. \tag{2.3} \]

The weights \(n-i\) fall as the position \(i\) rises. Suppose two neighbouring positions \(i\) and \(i+1\) hold bursts with \(\tau_{(i)}\gt \tau_{(i+1)}\). Swapping them changes the sum by \((n-i)\tau_{(i+1)}+(n-i-1)\tau_{(i)}-(n-i)\tau_{(i)}-(n-i-1)\tau_{(i+1)}=\tau_{(i+1)}-\tau_{(i)}\lt 0\). Every swap that removes an inversion lowers the sum, and an order with no inversion is the order of non-decreasing bursts. That order, shortest job first (SJF), therefore has the smallest mean waiting time. The proof assumes bursts that are known in advance, simultaneous arrival and no switching cost. With arrivals spread in time it does not hold as stated, and a long job can wait without bound while short jobs keep arriving. The program computes first come first served (FCFS), SJF and round robin (RR), in which each job in turn runs for at most \(q\) and then joins the end of the queue, for three quanta. It also checks the claim for all 24 orders. It is deterministic.

"""Mean waiting time of four jobs under first-come-first-served, shortest-job-first
and round-robin scheduling on one CPU; all jobs arrive at time 0."""
from itertools import permutations

bursts = {"A": 8, "B": 4, "C": 9, "D": 5}      # CPU time each job needs, in ms


def fcfs_waits(order):
    """Waiting time of each job when the jobs run to completion in the given order."""
    clock, waits = 0, {}
    for job in order:
        waits[job] = clock
        clock += bursts[job]
    return waits


def round_robin_waits(quantum):
    """Waiting time = completion time - burst, for a cyclic queue with the given quantum."""
    remaining = dict(bursts)
    queue, clock, done = list(bursts), 0, {}
    while queue:
        job = queue.pop(0)
        run = min(quantum, remaining[job])
        clock += run
        remaining[job] -= run
        if remaining[job]:
            queue.append(job)
        else:
            done[job] = clock
    return {job: done[job] - bursts[job] for job in bursts}


def mean(waits):
    return sum(waits.values()) / len(waits)


sjf = sorted(bursts, key=bursts.get)
print("FCFS  order A B C D :", fcfs_waits("ABCD"), f"mean {mean(fcfs_waits('ABCD')):.2f} ms")
print("SJF   order", " ".join(sjf), ":", fcfs_waits(sjf), f"mean {mean(fcfs_waits(sjf)):.2f} ms")

What Linux does. The Linux manual names SCHED_OTHER as "the standard Linux time-sharing scheduler that is intended for all threads that do not require the special real-time mechanisms". The policies SCHED_FIFO and SCHED_RR are real-time policies with static priorities 1 to 99, and a runnable thread of a real-time policy always preempts a SCHED_OTHER thread. The manual states that "all scheduling is preemptive" (sched(7)). The lecture's round robin and first-come-first-served therefore exist in Linux as real-time policies, and the ordinary policy is the fair-share scheduler. The kernel documentation of the Completely Fair Scheduler (CFS) describes its model as an "ideal, precise multi-tasking CPU" on which \(n\) runnable tasks each run at \(1/n\) of the speed, and states that CFS tracks a virtual runtime per task (CFS scheduler). The documentation of the EEVDF scheduler states that the kernel began the transition to it in version 6.6 and that it also "aims to distribute CPU time equally among all runnable tasks with the same priority" (EEVDF scheduler). Fair share and nice levels. The nice value of a thread biases its share of the processor. In the fair-share model a thread \(i\) with weight \(\omega_i\) gets the share \(\omega_i/\sum_j \omega_j\) of a processor that runnable threads share. The kernel documentation on nice levels states that nice levels are multiplicative, so that two tasks whose nice levels differ by 1 split the processor 55 % to 45 % wherever the pair starts, and that a task at nice \(+19\) receives 1.5 % of the processor (nice-level design). If each step multiplies the weight by a constant factor \(r\), the share of the thread at nice \(k\) against a thread at nice 0 is

\[ \text{share}(k)=\frac{1}{1+r^{k}}. \tag{2.4} \]

The two figures of the documentation give two values of \(r\): the 55/45 split gives \(r=0.55/0.45=1.222\), and the 1.5 % at \(k=19\) gives \(r=(1/0.015-1)^{1/19}=1.246\). Both figures are rounded. The kernel source settles the factor: the table sched_prio_to_weight in kernel/sched/core.c (Linux 6.6.87) is built with "a multiplier of 1.25" and gives the weights 1024, 335, 110 and 15 for nice 0, 5, 10 and 19 (kernel.org, stable tree, tag v6.6.87, lines 11550 to 11571). The table predicts shares of 24.7 % and 9.7 % for nice 5 and nice 10 against nice 0; the rounded 55/45 figure (\(r=1.222\)) predicts 26.8 % and 11.9 %. At nice \(+19\) the table gives \(15/1039=1.44\) %, which the documentation rounds to 1.5 %. The next program tests this. Two children are pinned to processor 0 with sched_setaffinity, so they must share it. Each child adds its nice value with nice, and counts blocks of 100 000 empty loop iterations until a common deadline 2 s away, and reports the count through a pipe. The share of a child is its count over the total. The loop makes no system call except the read of the clock, which the vDSO serves without entering the kernel. Any change of the running child therefore comes from the timer interrupt and not from a request of the child. The run takes 6 s and is checked by its return code.

#include <stdio.h>
#include <sys/wait.h>
#include <time.h>
#include <unistd.h>

#define RUN_SECONDS 2.0

static double now(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return ts.tv_sec + ts.tv_nsec * 1e-9;
}

/* Fork a child that is pinned to CPU 0, adds `nice_value` to its nice value, and counts
   blocks of 100000 empty loop iterations until the wall-clock time `deadline`.
   The child reports its count through the pipe end `fd`. */
static pid_t spawn(int nice_value, double deadline, int fd)
{
    pid_t pid = fork();
    if (pid == 0) {
        cpu_set_t set;
        CPU_ZERO(&set);
        CPU_SET(0, &set);
        sched_setaffinity(0, sizeof set, &set);
        errno = 0;
        if (nice(nice_value) == -1 && errno) _exit(1);
        unsigned long count = 0;
        do {
            for (int k = 0; k < 100000; k++) __asm__ volatile("" ::: "memory");
            count++;
        } while (now() < deadline);
        (void)!write(fd, &count, sizeof count);
        _exit(0);
    }
    return pid;
}

{

    waitpid(a, NULL, 0);
    waitpid(b, NULL, 0);

}

int main(void)

The cost of a switch. Let \(t_{\mathrm{cs}}\) be the cost of one context switch. With a quantum \(q\), the fraction of the processor time that threads can use is

\[ \eta=\frac{q}{q+t_{\mathrm{cs}}}. \tag{2.5} \]

The next program estimates \(t_{\mathrm{cs}}\) from a ping-pong. Two processes are connected by two pipes. The parent writes one byte, the child reads it and writes one back, and the parent reads that byte; 50 000 rounds. When both processes are pinned to processor 0, each message wakes a process that cannot run until the other blocks, so a round trip contains two process switches, four pipe system calls and two wake-ups. The measured time of a round trip is therefore an upper bound on \(2t_{\mathrm{cs}}\), and half of it an upper bound on \(t_{\mathrm{cs}}\). The listing also runs the pair on processors 0 and 2, where no switch is needed. It keeps the smallest of three runs and is checked by its return code.

#define _GNU_SOURCE
#include <sched.h>
#include <stdio.h>
#include <sys/wait.h>
#include <time.h>
#include <unistd.h>

#define ROUNDS 50000
#define REPS 3

static double now(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return ts.tv_sec + ts.tv_nsec * 1e-9;
}

static void pin(int cpu)
{
    cpu_set_t set;
    CPU_ZERO(&set);
    CPU_SET(cpu, &set);
    sched_setaffinity(0, sizeof set, &set);
}

/* Two processes pass one byte back and forth through two pipes, ROUNDS times.
   One round trip is 2 writes and 2 reads. With both processes on one CPU each
   round trip also needs 2 process switches. Returns seconds per round trip. */
static double pingpong(int cpu_parent, int cpu_child)
{
    int up[2], down[2];
    char c = 'x';
    if (pipe(up) || pipe(down)) return -1.0;
    pid_t pid = fork();
    if (pid == 0) {
        pin(cpu_child);
        for (int i = 0; i < ROUNDS; i++) {
            (void)!read(up[0], &c, 1);
            (void)!write(down[1], &c, 1);
        }
        _exit(0);
    }
    pin(cpu_parent);
    double t0 = now();
    for (int i = 0; i < ROUNDS; i++) {
        (void)!write(up[1], &c, 1);
        (void)!read(down[0], &c, 1);
    }
    double t = now() - t0;
    waitpid(pid, NULL, 0);
    return t / ROUNDS;
}

int main(void)
{
    double same = 1e30, diff = 1e30;
    for (int r = 0; r < REPS; r++) {
        double a = pingpong(0, 0), b = pingpong(0, 2);
        if (a < same) same = a;
        if (b < diff) diff = b;
    }
    printf("both processes on CPU 0:       %.2f us per round trip\n", same * 1e6);
    printf("processes on CPU 0 and CPU 2:  %.2f us per round trip\n", diff * 1e6);
    return 0;
}

The lecture assigns to the "memory management unit" the management of physical and virtual memory, the mapping between the two, the page tables, the translation lookaside buffer (TLB), memory protection and cache control, so that every process gets a fair share of memory. Two statements need a correction before the model is stated. The memory management unit (MMU) is a part of the processor, not a component of the kernel; the kernel builds the tables that the MMU reads. The lecture describes the TLB as a small memory that stores recent data. It stores recent address translations. The kernel documentation states that "CPUs maintain a cache of such translations called Translation Lookaside Buffer" because address translation "requires several memory accesses" (Linux kernel documentation, concepts overview, section on huge pages).

The model. The kernel documentation states that virtual memory "abstracts the details of physical memory from the application software, allows to keep only needed information in the physical memory (demand paging) and provides a mechanism for the protection and controlled sharing of data between processes". Every access uses a virtual address, and the processor translates it to a physical address. Physical memory is divided into page frames. Page tables describe the mappings, are organized hierarchically, and the pointer to the top-level table sits in a register; "the high bits of the virtual address are used to index an entry in the top level page table" and the lowest bits are the offset inside the page (concepts overview, section on the virtual memory primer). On x86-64, Linux supports 48-bit and 57-bit virtual addresses, with four-level and five-level page tables (Linux kernel documentation, x86-64 memory map). This chapter uses the 48-bit, four-level case with pages of 4096 bytes. An address then has 12 offset bits and four indices of 9 bits each. A table page of 4096 bytes holds 512 entries of 8 bytes, which is consistent with the 9-bit index. This chapter assumes, without a source that it opened, that an entry takes 8 bytes and that a table page holds 512 of them; the measurement below is consistent with that assumption and does not fix it.

The size of the tables. To map a contiguous region of \(S\) bytes, the kernel needs \(n_p=\lceil S/4096\rceil\) entries at the lowest level, which fill \(N_1=\lceil n_p/512\rceil\) table pages. The next level needs one entry per table page of the level below, so \(N_\ell=\lceil n_p/512^{\ell}\rceil\) for \(\ell=1,\dots,4\). The tables occupy

\[ M(S)=4096\sum_{\ell=1}^{4}\left\lceil\frac{n_p}{512^{\ell}}\right\rceil\ \text{bytes},\qquad \frac{M(S)}{S}\approx\frac{1}{512}\left(1+\frac1{512}+\frac1{512^2}+\frac1{512^3}\right)=0.196\ \%\ \text{for large dense }S. \tag{2.6} \]

The next program splits one virtual address into its four indices and its offset, rebuilds the address from them, and evaluates (2.6) for three sizes. It assumes a start aligned to the span of one top-level entry, and its output is deterministic.

Demand paging and copy-on-write. The program below creates an anonymous 64 MiB mapping (memory that no file backs) with mmap and writes the first byte of each page twice, and counts the minor faults of the process with getrusage. A minor fault is a fault that the kernel resolves without disk input. The program then calls fork, and the child writes every page once more. The parent checks that its own pages are unchanged. Inputs: none. Outputs: faults per page and one check. The output is deterministic because the counts are the page counts.

#define _GNU_SOURCE

#include <sys/mman.h>

#include <unistd.h>

{
    struct rusage ru;

}

        fflush(stdout);

The first write to each page costs one minor fault, 1.00 per page, and the second pass costs none: mmap reserved the addresses, and the kernel allocated a frame, filled it with zeros and mapped it when the page was first touched. The child's write pass again costs 1.00 fault per page. After fork the child shares every frame with the parent, and the first write by the child to a page makes the kernel copy that page into a new frame: this is copy-on-write, as the manual of fork states. The parent's pages still hold the parent's value, so the child's writes did not reach the parent. This is the isolation property of \(A\) that the model requires.

The cost of a minor fault is 1.7 to 2.5 µs in the launch measurement. A fault serves 4096 bytes, so the rate at which a fresh array is first written is 1.6 to 2.4 GB/s, against about 10 GB/s for copying data that are already in memory (the fit of the previous section). Initializing a large array that was just allocated is therefore slower than any later pass over it, a fact that chapter 7 meets again in the discussion of non-uniform memory and of first touch.

The virtual file system, inter-process communication and the claim that everything is a file W1L2 14:35

The lecture states that the virtual file system (VFS) is an abstraction layer that lets the kernel interface with different file systems in a uniform way. Its slide lists the key elements: the superblock (an entire mounted file system), the inode (metadata about a file or directory), the dentry (a directory entry), mount points, file-system operations and types, and the file descriptor table. The kernel documentation describes the VFS as "the software layer in the kernel that provides the filesystem interface to userspace programs" and as "an abstraction within the kernel which allows different filesystem implementations to coexist" (Linux kernel documentation, VFS, introduction). It adds that the system calls open, stat, read, write and chmod are called from a process context. The lecture says at W1L2 9:36 that the VFS is responsible for creating a virtual machine for each new process. The documentation does not assign to the VFS the creation of anything per process. The chapter takes the per-process objects to be the address space and the table of open files of the model, and the VFS to be the code that serves the calls on the open files. Chapter 3 treats the inode, the directory entry and the permission bits.

One interface, several kinds of object. The table \(O\) of the model maps a file descriptor to an open file. A call such as read(fd, buffer, n) names only the descriptor. The kernel finds the open file and runs the read operation of whatever the descriptor refers to: a file of a file system, a device driver, a pipe or a socket. The next program opens one object of each kind, writes 5 bytes with write, and reads them back with read when the object has a read end. It also reads from a directory. The output is deterministic.

#define _GNU_SOURCE

static const char *kind(int fd)
{
    struct stat st;
    fstat(fd, &st);

    if (S_ISDIR(st.st_mode)) return "directory";
    if (S_ISCHR(st.st_mode)) return "character device";
    if (S_ISFIFO(st.st_mode)) return "pipe (FIFO)";
    if (S_ISSOCK(st.st_mode)) return "socket";
    return "other";
}

int main(void)
{

    unlink("fdtypes.tmp");                   /* the open descriptor keeps the file alive */

    int dev = open("/dev/null", O_WRONLY);

    struct { const char *name; int wfd, rfd; } t[] = {
        {"file",      file,  file},
        {"/dev/null", dev,   -1},
        {"pipe",      pp[1], pp[0]},
        {"socket",    sp[0], sp[1]},
    };
    char buf[16];
    for (int i = 0; i < 4; i++) {

        ssize_t r = -2;                      /* -2: this entry has no read end */

        }
        printf("%-10s %-17s write returned %zd, read returned %zd\n", t[i].name, kind(t[i].wfd), w, r);

    printf("%-10s %-17s read returned %zd (%s)\n", "directory", kind(dir), r, strerror(errno));

The network subsystem and inter-process communication. At W1L2 16:09 the lecture describes the network subsystem as the code that processes, routes and manages network packets, with a socket interface between programs and the kernel and with layers from the link layer to the application layer. Threads of one process need no such mechanism for data, because they share \(A\), and chapter 11 starts from this fact. Processes of different programs share data only through one of the mechanisms above, and the lecture states that these mechanisms are what the higher-level parallel programming models build on.

The model of privilege modes, processes and system calls establishes four things. Multiplexing and isolation need instructions that only the kernel can execute, and an attempt to execute one in user mode ends the process, not the kernel. A process is an address space, a table of open files, credentials and threads, and the kernel runs on behalf of its threads. A system call costs 87 ns on this guest, 176 to 194 times an ordinary call, and a program must amortize it over at least a few kilobytes of data per call. The ordinary Linux scheduler divides a processor among runnable threads in the ratio of their weights, and a nice step multiplies the weight by 1.25 (the kernel table uses a multiplier of 1.25; the measured shares at nice 5 and 10 match it to within the 1-point spread of the runs).

The model leaves out most of what an operating system does. It treats the scheduler on one processor, and it omits the migration of threads between processors, the placement of memory on non-uniform machines, swapping, and the scheduling of disk and network input. It covers threads only as members of one process; the creation of threads with clone belongs to chapter 11. It does not describe containers, control groups or virtual machines beyond the one remark about the WSL 2 guest. Security appears only as the isolation between processes; permissions are in chapter 3.

The quantitative results have their own limits. All times belong to one WSL 2 guest on one hybrid processor, and a bare-metal Linux, or a guest that needs page-table isolation, would show other costs. The launch decomposition explains 22 to 30 % of the launch time at a fault cost of 1.7 to 2.5 µs (34 to 37 % in a loaded run), and the remaining 70 to 78 % (63 % in the loaded run) is not attributed. The estimate that faults account for a quarter of the launch assumes that a fault during a launch costs as much as the first write to a zero-filled page. The explanation offered for the slow exchange of messages between processors is a hypothesis that was not tested. The scheduler of the guest kernel is EEVDF according to the release notes of Linux 6.6; the scheduler's own source was not read. The share of Linux in the TOP500 list, the dates for Slackware and Debian, Ubuntu and Android, the 2020 popularity claim, and the exact day of the first Linux release were not established.

Exercises

Exercise 1 (derive). \(n\) jobs arrive together at time 0, and each needs the same burst \(\tau=mq\), where \(q\) is the quantum of a round-robin scheduler and \(m\) is a whole number. Switching is free. Derive the mean waiting time under round robin and under FCFS, and evaluate both for \(n=4\), \(\tau=8\) ms and \(q=1\) ms.

Solution

Under FCFS the job in position \(i\) (counting from 0) waits \(i\tau\), so the mean is \((n-1)\tau/2\), which is 12 ms for \(n=4\) and \(\tau=8\) ms. Under round robin all jobs have the same remaining time at every round, so no job ends before the last round. In each of the first \(m-1\) rounds, every job runs one quantum, which takes \(nq\) in total. In the last round the job in position \(i\) runs from \((m-1)nq+iq\) to \((m-1)nq+(i+1)q\), so it completes at \((m-1)nq+(i+1)q\). Its waiting time is its completion time minus its burst: \((m-1)nq+(i+1)q-mq\). The mean over \(i=0,\dots,n-1\) is \((m-1)nq+\tfrac{n+1}{2}q-mq=(n-1)\left(\tau-\tfrac q2\right)\). For \(n=4\), \(q=1\) ms and \(\tau=8\) ms this is \(3\times7.5=22.5\) ms, against 12 ms for FCFS. The ratio of the two means is \(2(\tau-q/2)/\tau=2-q/\tau\), which is 1.875 here and tends to 2 as \(\tau/q\) grows. With equal bursts round robin delays every completion to the last round; its benefit is the bound \((n-1)q\) on the delay of the first service, which FCFS does not give.

Exercise 2 (compute). A program reads a 4 GiB file that is in the page cache. Use \(a=180\) ns and \(B=10\) GB/s, round values from the fits of the chapter (180 to 195 ns, 9.7 to 10.5 GB/s). Compute the time for reads of \(b=1\), 512, 4096 and 65 536 bytes. Find the smallest \(b\) for which the per-call cost is at most 5 % of the total time. Compare the first and the last time.

Solution

\(S=4\,\mathrm{GiB}=4.295\times10^{9}\) B, so \(S/B=0.4295\) s, and \(Sa=4.295\times10^{9}\times180\times10^{-9}\ \mathrm{s}=773.1\) s. By (2.2), \(T(b)=773.1/b+0.4295\) s. For \(b=1\): 773.5 s. For \(b=512\): \(1.510+0.430=1.94\) s. For \(b=4096\): \(0.189+0.430=0.618\) s. For \(b=65\,536\): \(0.0118+0.4295=0.441\) s. The per-call share is \(aB/(aB+b)\), with \(aB=180\times10^{-9}\times10^{10}=1800\) B. It is at most 0.05 when \(1800\le0.05(1800+b)\), that is \(b\ge19\times1800=34\,200\) B. The ratio of the first and last time is \(773.5/0.441=1750\). The model agrees with the measured per-call times to within 10 % in the sample run, but it is a fit to a file in the page cache; a file that must come from a disk adds the time of the device, which this model does not contain.

Exercise 3 (counterexample). A student says: "A program that makes no system call never enters the kernel." Give a program from this chapter that disproves the claim, and count how many times it enters the kernel.

Solution

The loops that touch memory in pagefault.c contain only stores, and no system call. The first pass over the 64 MiB mapping nevertheless enters the kernel 16 384 times, once per page, through the page-fault exception (the output line "1.00 minor faults per page"). At 1.7 to 2.5 µs per fault, that is 28 to 41 ms for a loop that makes no request. The children of fairshare.c give a second counterexample: their loops make no system call, and the kernel still removes them from the processor by timer interrupts, because they share one processor and each gets half of it. The claim is true for one of the three events that enter the kernel, the system call, and false for exceptions and interrupts. The statement "the kernel runs only when a program asks for it" would make the isolation and the multiplexing of the model impossible.

Exercise 4 (diagnose an assumption). A student reads the one-processor ping-pong, 2.8 to 3.3 µs per round trip, and concludes: "moving a thread to another processor costs at most one context switch, about 1.5 µs." Find the assumption that fails, and give a corrected bound for the cost of a switch.

Solution

The one-processor round trip contains two switches and also four pipe system calls and two wake-ups. Each pipe call costs at least a minimal system call, 84 ns or more, so the four calls take at least 0.34 µs. The cost of one switch is at most \((\text{round trip}-0.34\ \mu\mathrm{s})/2\), which is 1.22 to 1.50 µs for round trips of 2.78 to 3.34 µs. This bound is slightly tighter than the half round trip. The failing assumption is that the cost of moving a thread equals the cost of switching between two threads on one processor. The two-processor measurement contradicts it: a round trip between processors 0 and 2 took 31.7 to 40.2 µs, 10 to 14 times as long, although no switch occurs on either processor. The extra time belongs to waking a thread on another processor, which the switch cost does not contain. A model of the cost of moving threads between processors must include that wake-up, and the cost of the cold caches after a move, which this chapter did not measure.

Exercise 5 (design judgment). A sweep must run \(10^{5}\) cases of a solver that needs 20 ms each, on a node with 12 logical processors. Option A starts one process per case, linked dynamically. Option B is option A with static linking. Option C starts 12 worker processes that each loop over their share of the cases. Use the launch times of this chapter and choose an option, with numbers.

Solution

The compute time is \(10^{5}\times20\) ms \(=2000\) s of processor time, or about 167 s on 12 processors. Option A adds \(10^{5}\times0.46\) to \(0.70\) ms \(=46\) to 70 s of processor time. By (2.1) the fraction is \(\varphi=0.46/20.46=2.2\ \%\) to \(0.70/20.70=3.4\ \%\), so the sweep takes about 4 to 6 s longer in wall-clock time on 12 processors (\(46/12\) to \(70/12\)). Option B costs 31 to 42 s, \(\varphi=1.5\) to \(2.1\ \%\), which saves about 15 to 28 s of processor time. Option C starts 12 processes, so the launch cost is 12 launches, below 10 ms in total. These estimates assume that the launches are spread over the 12 processors. A solver that links more shared libraries than the C library (for example the math library or an MPI library) has more mmap calls and more faults per launch, so 0.46 to 0.70 ms is a lower estimate for it. Option C wins by 2 % to 3 % of the run time. It gives up isolation: a case that corrupts memory or fails in the middle takes down the worker and all the cases queued behind it, and state that a case leaves in global variables reaches the next case. For a solver that is known to be clean, choose C. For a solver that is not, choose A or B: the 2 % to 3 % is the price of a fresh address space for each case, and B recovers part of it if the solver has no need for dynamic libraries. The estimate counts only the launch of the process; it does not count the time that a shell script spends on its own work for each case, which chapter 5 discusses.

Exercise 6 (implementation and measurement). The manual says that fork costs "the time and memory required to duplicate the parent's page tables". Predict how the time of fork followed by waitpid depends on the amount of memory the parent has touched. Then measure it for parents that have touched 0, 16, 64, 256 and 512 MiB.

Solution

The page-table memory of the parent grows in proportion to the touched memory, by (2.6) about 0.2 % of it, and fork copies the entries of every touched page, so the prediction is a time that is the sum of a constant (the cost of the process with no touched memory) and a term proportional to the number of touched pages. The program below touches the memory in a parent with mmap, then repeats fork with an immediately ending child 200 times, and keeps the smallest time. The last column is the added time per 1000 touched pages.

#define _GNU_SOURCE
#include <stdio.h>
#include <sys/mman.h>
#include <sys/wait.h>
#include <time.h>
#include <unistd.h>

#define REPS 200

static double now(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return ts.tv_sec + ts.tv_nsec * 1e-9;
}

int main(void)
{
    long page = sysconf(_SC_PAGESIZE);
    long mib[] = {0, 16, 64, 256, 512};
    printf("%10s %12s %14s %18s\n", "touched", "pages", "fork+wait us", "us per 1000 pages");
    double base = 0;
    for (int i = 0; i < 5; i++) {
        long bytes = mib[i] << 20;
        char *p = NULL;
        if (bytes) {
            p = mmap(NULL, bytes, PROT_READ | PROT_WRITE, MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
            madvise(p, bytes, MADV_NOHUGEPAGE);
            for (long off = 0; off < bytes; off += page) p[off] = 1;
        }
        double best = 1e30;
        for (int r = 0; r < REPS; r++) {
            double t0 = now();
            pid_t pid = fork();
            if (pid == 0) _exit(0);
            waitpid(pid, NULL, 0);
            double t = now() - t0;
            if (t < best) best = t;
        }
        if (i == 0) base = best;
        printf("%7ld MiB %12ld %14.1f %18.1f\n", mib[i], bytes / page, best * 1e6,
               bytes ? (best - base) * 1e6 / (bytes / page / 1000.0) : 0.0);
    }
    return 0;
}

The sample run gives 98 µs for a parent with no touched memory, 252 µs for 16 MiB, 0.84 ms for 64 MiB, 3.3 ms for 256 MiB and 8.5 ms for 512 MiB. Over six runs the ranges are 98 to 105 µs, 252 to 285 µs, 0.84 to 1.00 ms, 3.2 to 3.9 ms and 8.5 to 9.4 ms. The prediction holds in form: the time rises with the number of touched pages, from 98 µs to 8.5 ms, a factor of 87. A line through the points at 16 MiB and 256 MiB of the sample has a slope of 49.6 ns per page, and predicts 0.86 ms at 64 MiB (3 % above the sample) and 6.6 ms at 512 MiB (23 % below the sample). The time per page is therefore not constant: the added time per 1000 pages rises from 38 µs at 16 MiB to 64 µs at 512 MiB in the sample, and from 37 to 71 µs over all runs (the 16 MiB point ranges from 37 to 45 µs, the 512 MiB point from 64 to 71 µs). The cause of the rise was not found; a larger table that no longer fits in a cache is a candidate that this exercise did not test. The cost per page, 38 to 64 ns, is 48 to 80 times the 0.8 ns that moving the 8 bytes of an entry takes at 10 GB/s. The timed interval contains both the copy of the entries in fork and their removal when the child exits. The kernel therefore does work for each page beyond copying its entry. A candidate mechanism, not tested here: for each present anonymous page, fork duplicates the reverse-mapping reference of the page (copy_present_pte calls page_try_dup_anon_rmap in mm/memory.c, Linux 6.6.87), and the child's exit drops it, so the work touches the metadata of the page and not only its 8-byte entry. The consequence for a launcher is direct: a parent that holds 512 MiB of touched data pays about 8.5 ms for each fork, 87 times the cost of a small parent, so a sweep driver should start its children from a small process.
