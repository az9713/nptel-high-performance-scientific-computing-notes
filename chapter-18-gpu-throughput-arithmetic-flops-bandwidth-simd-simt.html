GPU throughput arithmetic: FLOPS, memory bandwidth, SIMD and SIMT

The local GPU's queried configuration gives an FP32 arithmetic model of 6.144 trillion operations per second. A streaming triad nevertheless performs about 30 billion operations per second in one captured run, while moving about 180 billion logical bytes per second. That is not a contradiction: the triad performs only one sixth of an operation per byte. Conversely, an A100's advertised 156 TFLOP/s Tensor rate does not mean that every FP32 instruction executes at that rate. To interpret either number, identify the operation, precision, hardware units, clock convention and data path before multiplying anything.

Lecture material: V100 and A100 Tensor throughput arithmetic, GDDR and HBM, interface widths and transfer rates, DDR and PAM4, memory-bandwidth examples, scalar and vector pipelines, SIMD versus SIMT, and thread/block/grid mapping. Original teaching constructions: dimensional checks, correction of operation and signaling counts, the triad running case, ideal pipeline simulation, property query, bounded memory/FMA experiments and six worked exercises.

Count work, count traffic, and name the measured interval

A floating-point operation, abbreviated FLOP, is an arithmetic operation on a specified floating-point format. A FLOP count \(F\) is work, while FLOP/s is a rate \(P=F/t\), where \(t\) is elapsed seconds. “FLOPS” conventionally names that rate. A multiply and an add count as two operations. A fused multiply-add, or FMA, computes a product plus an addend with one final rounding and conventionally counts as two FLOPs even when implemented by one instruction. Counting instructions and counting arithmetic operations are different tasks.

The format is part of the claim. FP32 denotes ordinary 32-bit single precision and FP64 64-bit double precision. FP16 is a shorter floating-point format. TensorFloat-32, abbreviated TF32, is a Tensor arithmetic mode with a reduced input significand compared with FP32 while retaining its exponent range. Input storage and accumulator precision need not be identical. A rate specified for one mode cannot be relabeled as a rate for another merely because its final output occupies a 32-bit array.

A streaming multiprocessor, or SM, contains instruction schedulers, registers and execution pipelines. Let \(n_{\mathrm{SM}}\) be the number of enabled SMs, \(q_{\mathrm{FMA}}\) the supported scalar FMA-equivalent results per SM per clock in a stated mode, and \(\nu_{\mathrm{SM}}\) the assumed SM clock frequency in hertz. A compatible arithmetic throughput model is \(P_{\mathrm{peak}}=2n_{\mathrm{SM}}q_{\mathrm{FMA}}\nu_{\mathrm{SM}}\). The factor two counts multiply and add; it says nothing about memory transfers. A full chip diagram can contain more units than an enabled product exposes.

The memory model uses \(w\) for data-interface width in bits and \(r_b\) for the effective bit rate per data pin in bit/s. Its ideal payload bandwidth is \(B_{\mathrm{peak}}=wr_b/8\) bytes/s. Memory capacity \(C_{\mathrm{mem}}\), measured in bytes, answers a separate question: how much can be stored. Increasing capacity does not necessarily increase interface width or transfer rate. The clock driving arithmetic and a clock reported for memory are also distinct quantities.

The running operation is a triad, \(c_i=a_i+2b_i\), for \(n\) array elements. Its arithmetic count is \(F=2n\), whether the compiler uses an FMA or a separate multiply and add. Counting one read of each input and one write of the output gives logical traffic \(Q=3sn\), where \(s\) is bytes per element. With FP32, \(s=4\) and the arithmetic intensity is \(I=F/Q=1/6\) FLOP/byte. These are source-level requested bytes, not a hardware-counter measurement of DRAM transactions.

The measured arithmetic rate is \(F/t\) and effective bandwidth \(B_{\mathrm{eff}}=Q/t\). They satisfy \(P=I B_{\mathrm{eff}}\) by their definitions. This identity checks accounting; it is not an independent demonstration that the external memory interface is saturated. Caches, transaction granularity, memory-controller scheduling and write traffic can make physical memory bytes differ from the logical count.

The numerical GPU experiments use an Intel Core i5-12450H laptop, an NVIDIA GeForce RTX 3050 Laptop GPU under WSL 2, and the installed CUDA 13.3 toolkit. Every runtime call and kernel launch is checked, and every printed computation is validated against a deterministic expected value. CUDA events delimit device work; allocation, initialization and copying results to the host occur outside the timed interval. Four sequential captures supply limited repeat ranges, not confidence intervals or power-controlled peak measurements.

Tensor throughput is an operation count, not a count of cores W6L6 0:06

Chapter 17 introduced scalar peak rates and distinguished full-chip diagrams from enabled products. Matrix multiply-accumulate throughput requires a separate operation count. For matrices \(A\) of shape \(m\times k\), \(B\) of shape \(k\times n\), and \(C,Y\) of shape \(m\times n\), the operation is \(Y=AB+C\). Here \(i\) indexes rows, \(j\) columns and \(\ell\) the contracted dimension, ranging respectively from one to \(m,n,k\). Each output is \(Y_{ij}=C_{ij}+\sum_{\ell=1}^kA_{i\ell}B_{\ell j}\). An implementation can perform \(k\) scalar FMAs per output, giving the conventional work count

\[ F_{\mathrm{MMA}}=2mnk. \tag{18.1} \]

For \(4\times4\) matrices, equation (18.1) gives 64 scalar FMAs or 128 FLOPs. A bare \(AB\), counted without an initial accumulation, instead uses four multiplies and three adds for each of sixteen outputs: \(16(4+3)=112\) elementary operations. The lecture slide lists four multiplies and three adds but then labels four operations per output before doubling for FMA. The coherent interpretation is four FMA-equivalents per output in \(AB+C\), not four individual FLOPs in a standalone dot product.

The V100 whitepaper, printed pp. 14–16, explicitly specifies 64 floating-point FMA operations per Tensor Core per clock, eight Tensor Cores per SM, and 640 in the enabled V100. It defines \(Y=AB+C\) with FP16 multiply inputs and accumulation that can be FP32. Thus the V100 SXM2 arithmetic at the slide's 1.53 GHz is \(640\times64\times2\times1.53\times10^9=125.3376\times10^{12}\) FLOP/s, conventionally rounded to 125 TFLOP/s.

The units expose the meaning of every factor: Tensor Cores, multiplied by scalar FMAs per Tensor Core per cycle, multiplied by FLOPs per FMA, multiplied by cycles per second. Multiplying the factor 640 by another full SM count would double-count the hierarchy. Using the full GV100 diagram's 84 SMs instead of the enabled V100's 80 would describe a different configuration. The pipeline's throughput also is not the latency of a complete CUDA matrix instruction or an arbitrary large matrix multiplication.

A100 makes the distinction between hardware count and throughput especially important. The lecture's table contains 64 FP64 and 512 TF32 FMA-equivalent results per SM per cycle. These are not 64 or 512 physical Tensor Cores in each SM. The A100 whitepaper, printed pp. 19 and 28, specifies four Tensor Cores per SM, 108 enabled SMs and 432 Tensor Cores for that A100 configuration. The full GA100 design has 128 SMs and 512 Tensor Cores in total.

Using the aggregate per-SM throughput directly, dense FP64 Tensor arithmetic is \(108\times64\times2\times1.41\ \mathrm{GHz}=19.49184\) TFLOP/s. Dense TF32 Tensor arithmetic is \(108\times512\times2\times1.41\ \mathrm{GHz}=155.93472\) TFLOP/s. Once the factor already means results per SM, the number of physical Tensor Cores per SM is not multiplied again. The two descriptions can be converted into each other only when the per-core throughput and supported arithmetic mode are correctly specified.

Ordinary A100 scalar FP32 arithmetic is approximately 19.5 TFLOP/s for this configuration, not the 156 TF32 Tensor rate. FP64 Tensor operations and FP32 scalar operations can have similar numerical rates while executing different instructions. A matrix algorithm can access Tensor throughput only when its operations, layout and precision are suitable. Elementwise addition cannot be transformed into a matrix multiply merely by renaming its arrays as tensors.

Sparsity adds another denominator. The doubled advertised sparse rate assumes a supported structured pattern, such as two nonzero values out of a group of four, and associated metadata. It is often reported as dense-equivalent work accomplished while skipping prescribed zeros. It does not mean the hardware executed twice as many arbitrary dense FMAs. A comparison must state whether \(F\) counts actually executed arithmetic, a dense-equivalent workload or an application-specific useful result.

Precision can change scientific conclusions even when throughput improves. TF32 uses fewer input fraction bits than FP32; accumulating in FP32 cannot restore information already removed from an input. An application must account for its sensitivity to input rounding before accepting a reduced-precision operation. The throughput table alone proves no accuracy guarantee. Exercise 3 constructs a cancellation example that makes this distinction concrete.

GDDR and HBM trade interface organization, not arithmetic precision W6L6 8:12

Graphics double data rate memory, GDDR, commonly places discrete memory packages around a GPU on a board. High-bandwidth memory, HBM, places stacked memory dies close to the GPU through advanced packaging and a wide interface. Proximity and interface width help explain bandwidth and energy characteristics, but neither acronym establishes a universal latency, capacity or cost ordering for all products and generations.

The lecture's comparison table calls a GDDR interface of 32 or 64 bits per chip wider than an HBM interface of 1024 bits per stack. Those widths refer to different packaging units, and the numeric inequality goes the other way. A conventional HBM2 stack is connected through two 512-bit controllers in the cited V100/A100 designs, giving 1024 bits per stack. V100's four such stacks give 4096 bits; the discussed A100 configuration has five stacks and 5120 bits. The corresponding whitepaper diagrams specify these arrangements.

Capacity requires an independent count. Six packages of 1 GB each provide 6 GB of nominal capacity; replacing them with compatible 2 GB packages can provide 12 GB without changing the aggregate data width. Conversely, activating more independently connected interfaces can increase width if the controller and board support them. Two packages can also share aspects of an interface organization, so multiplying package count by a guessed chip width is not a substitute for a board specification.

Unused positions in a board photograph do not prove that extra memory can be installed. The GPU controller, wiring, package organization, firmware and electrical design must support the configuration. A photograph can motivate a hypothesis, while interface diagrams and product documentation establish the supported arrangement. The same caution applies to assuming that an HBM stack is physically inside the GPU silicon: the memory dies and GPU die are distinct components connected through packaging.

GDDR, HBM and cache capacity also describe different levels of the memory hierarchy. A GPU can read a reused value from an on-chip cache without traversing its external interface again. A kernel's effective bandwidth can therefore exceed a DRAM pin-rate calculation if its requested bytes repeatedly hit cache. Such a result needs a stated traffic boundary, not an immediate claim that the external memory specification has been exceeded.

The useful design question is which interface supplies the data that limit the operation. Arithmetic pipelines access registers; a streaming array operation reaches global memory through caches; transferring an input from a CPU uses a host–device path such as PCI Express (PCIe). A GPU's local memory bandwidth does not describe PCIe, NVIDIA's GPU interconnect NVLink, or a Message Passing Interface (MPI) network. Those paths also differ in whether a quoted number is one-direction bandwidth or a sum over both directions.

For example, the A100 whitepaper states 25 GB/s in each direction per NVLink and twelve links. Their ideal sum is 300 GB/s in one direction and 600 GB/s when both directions are added. A one-direction transfer cannot be assigned 600 GB/s simply because that aggregate number is advertised. This link arithmetic is separate from the 1555 GB/s local HBM specification and is not measured by our array kernels. A100 whitepaper, printed pp.16–17.

Multiply width by a fully specified bit rate W6L6 12:07

If \(w\) data pins each transfer \(r_b\) bits per second, the aggregate ideal bandwidth is

\[ B_{\mathrm{peak}}=\frac{wr_b}{8}. \tag{18.2} \]

For a data rate expressed in gigabits per second per pin, equation (18.2) directly gives decimal GB/s after division by eight. One GB is \(10^9\) bytes; one GiB is \(2^{30}\) bytes. Consequently, 192 GB/s is \(192\times10^9/2^{30}\approx178.814\) GiB/s. A product rate and a benchmark rate must use the same byte unit before computing a percentage.

A clock-based derivation is possible when the clock convention is known. Let \(\nu_m\) be a particular memory clock in cycles/s, \(d\) symbol transfers per that clock cycle and \(b_s\) bits represented per symbol. Then \(r_b=\nu_m d b_s\). Ordinary two-level non-return-to-zero signaling, NRZ, carries one bit per symbol. Four-level pulse amplitude modulation, PAM4, can represent two bits per symbol. Double data rate describes transfers on both clock edges; it is not the same physical factor as bits per symbol.

The danger is that a published data rate can already include both factors. If a specification says 19 Gb/s per pin, that is already a bit rate. Multiplying it by two again because the memory uses PAM4 double-counts signaling. Likewise, a controller “memory clock,” a memory-device clock and an effective transfer clock can have different numerical values. The lecture's recipe listing data-rate, pumping and signaling factors is safe only after each factor's meaning has been established, rather than treating them as universally independent multipliers.

The GTX 1660 row is consistent with a 192-bit interface and an effective rate of approximately 8 Gb/s per pin, giving \(192(8)/8=192\) GB/s. This checks the lecture's arithmetic model. Its listed clock is 2001 MHz, approximately 2 GHz, not 2 MHz. Four effective bits per that listed cycle would yield 8.004 Gb/s and 192.096 GB/s; the displayed 192 GB/s is a rounded rate. The exact relationship between an internal clock and pin activity must come from the memory documentation, not from interpreting a label by eye.

The historical GA10x whitepaper, Table 2 on printed p. 14, supplies a cleaner comparison. Its RTX 2080 uses GDDR6, a 256-bit interface and 14 Gb/s, giving 448 GB/s. Its original 10 GB RTX 3080 uses GDDR6X, a 320-bit interface and 19 Gb/s, giving 760 GB/s. The RTX 2080 entry is not a PAM4 GDDR6X product. Other capacities and board variants must be identified separately.

For HBM2, the lecture supplies a 4096-bit V100 interface and a clock of 877.5 MHz with double-data-rate transfers. Equation (18.2) gives \(4096(877.5\times10^6)(2)/8=898.56\times10^9\) bytes/s, approximately 900 GB/s. For its A100 example, \(5120(1.215\times10^9)(2)/8=1555.2\times10^9\) bytes/s. The A100 40 GB whitepaper reports 1555 GB/s. A later A100 80 GB product is not assumed to have the same memory rate.

The following Python program checks operation and bandwidth arithmetic from the stated models and dated configurations. It has no hardware dependencies and prints exact deterministic results. Its sparse number is explicitly dense-equivalent, and its HBM rows use the slide clocks rather than silently replacing them with other rounded clocks.

"""Dated product/model arithmetic; these are not measured rates."""
def tf(sms, fmas_per_sm_cycle, ghz):
    return sms * fmas_per_sm_cycle * 2 * ghz / 1000

print("V100 4x4 A*B only: multiplies=64 adds=48 total=112")
print("V100 4x4 A*B+C: scalar_FMAs=64 conventional_flops=128")
print(f"V100 SXM2 FP16 Tensor model: {640*64*2*1.53/1000:.6f} TFLOP/s")
print(f"A100 FP64 Tensor dense model: {tf(108,64,1.41):.6f} TFLOP/s")
print(f"A100 TF32 Tensor dense model: {tf(108,512,1.41):.6f} TFLOP/s")
print(f"A100 TF32 structured-sparse equivalent: {2*tf(108,512,1.41):.6f} TFLOP/s")
for label, width, rate_gbps in [
    ("GTX1660", 192, 8), ("RTX2080", 256, 14),
    ("RTX3080", 320, 19), ("V100 slide clocks",4096,2*0.8775),
    ("A100 slide clocks",5120,2*1.215),

    gibps = gbps * 1e9 / 2**30

          f"bandwidth={gbps:.3f} GB/s = {gibps:.3f} GiB/s")
print("Six chips changing from 1 GB to 2 GB each: capacity doubles; width unchanged if organization unchanged.")

The calculations separate five different counts: matrix operations, physical execution units, enabled SMs, data-interface bits and capacity bytes. Their dimensions make several common errors visible. A result in operations per clock is not yet operations per second; a memory rate in bits is not bytes; and a sparse-equivalent matrix rate is not a dense scalar instruction rate.

Query the enabled device and measure a named data path

The lecture's bandwidth products are useful models, but a program runs on an enabled product with a particular software stack. The following query is an original extension that makes those assumptions inspectable. NVIDIA's GA10x whitepaper describes 128 FP32 execution pipelines per SM, including paths shared with integer arithmetic. Its Ampere tuning guide distinguishes compute capability 8.6 from the compute capability 8.0 A100. Thus the FP32 FMA throughput factor for this local 8.6 device is 128 FMA-equivalent results per SM per cycle under the applicable instruction mix; the factor is not inferred merely from the word Ampere. Integer instructions, dependencies and operand delivery can reduce an application's sustained FP32 rate. GA10x whitepaper, v2.1, SM architecture; Ampere tuning guide §1.4.1.6.

CUDA is NVIDIA's GPU programming platform. Here the host is the CPU program and the device is GPU 0. The macro named CUDA checks each runtime API result and exits on an error. Device properties describe the enabled configuration, while device attributes query particular capabilities. The installed CUDA 13.3 headers omit the old cudaDeviceProp clock members used in some older examples, so this program obtains clock attributes through cudaDeviceGetAttribute. The header descriptions identify these attributes as peak clock frequencies in kilohertz; they are not continuous measurements of the clock during a kernel. The arithmetic model is deliberately conditional on compute capability 8.6.

#include <cuda_runtime.h>
#include <cstdio>
#include <cstdlib>

#define CUDA(call) do { cudaError_t err = (call); if (err != cudaSuccess) { \
    std::fprintf(stderr, "%s: %s\n", #call, cudaGetErrorString(err)); \
    std::exit(1); } } while (0)

int main()
{
    int device = 0, runtime = 0, driver = 0;
    CUDA(cudaSetDevice(device));
    cudaDeviceProp prop;
    CUDA(cudaGetDeviceProperties(&prop, device));
    CUDA(cudaRuntimeGetVersion(&runtime));
    CUDA(cudaDriverGetVersion(&driver));
    int sm_khz, mem_khz, width, cache;
    CUDA(cudaDeviceGetAttribute(&sm_khz, cudaDevAttrClockRate, device));
    CUDA(cudaDeviceGetAttribute(&mem_khz, cudaDevAttrMemoryClockRate, device));
    CUDA(cudaDeviceGetAttribute(&width, cudaDevAttrGlobalMemoryBusWidth, device));
    CUDA(cudaDeviceGetAttribute(&cache, cudaDevAttrL2CacheSize, device));
    std::printf("device: %s\ncompute capability: %d.%d\n",
                prop.name, prop.major, prop.minor);
    std::printf("runtime=%d driver=%d SMs=%d warp=%d\n",
                runtime, driver, prop.multiProcessorCount, prop.warpSize);
    std::printf("global_memory_bytes=%zu L2_bytes=%d bus_bits=%d\n",
                prop.totalGlobalMem, cache, width);
    std::printf("reported_peak_SM_kHz=%d reported_peak_memory_kHz=%d\n",
                sm_khz, mem_khz);
    if (prop.major == 8 && prop.minor == 6) {
        double fp32 = prop.multiProcessorCount * 128.0 * 2 * sm_khz * 1000;
        std::printf("CC8.6 FP32 FMA model at reported clock: %.4f TFLOP/s\n", fp32/1e12);
    } else {
        std::printf("No architecture-specific FP32 rate assumed for this device.\n");
    }
    CUDA(cudaDeviceSynchronize());
    return 0;
}

The next program measures device-array copy and triad operations. Its CUDA kernel is a function marked __global__, called from the host with a grid of blocks and a number of threads per block. For these one-dimensional examples, blockIdx.x * blockDim.x + threadIdx.x gives a distinct array index. The guard prevents the final partially filled block from accessing beyond the array. This is enough syntax to follow the experiment; the mapping section below explains why these software threads are not a permanent list of physical arithmetic units.

Each array element is FP32. The two tested lengths are \(2^{20}\) and \(2^{24}\), giving 4 MiB and 64 MiB per array, where one MiB is \(2^{20}\) bytes. Three device arrays require at most 192 MiB. Copy requests one read and one write, hence \(8n\) logical bytes; triad requests two reads and one write, hence \(12n\). Adjacent threads request adjacent elements. This organization supports efficient combined memory transactions, although the program does not collect hardware transaction counters or prove their exact sizes.

After initialization and three untimed warmups, each trial places CUDA events around eight launches in the same default stream. Event synchronization waits for completion before reading elapsed milliseconds. Dividing by eight gives a batch mean per kernel; seven trials yield a minimum and median of those means. Event timing avoids treating an asynchronous host launch's return as kernel completion. It still includes the device timeline between launches, so very short kernels can include launch-related gaps. Allocation, host transfers and validation are outside this interval. NVIDIA's Best Practices Guide distinguishes this timing method and effective requested-byte bandwidth from actual memory traffic. Best Practices Guide §§9.1–9.2.

#include <cuda_runtime.h>
#include <algorithm>
#include <cstdio>
#include <cstdlib>
#include <vector>

#define CUDA(call) do { cudaError_t err = (call); if (err != cudaSuccess) { \
    std::fprintf(stderr, "%s: %s\n", #call, cudaGetErrorString(err)); \
    std::exit(1); } } while (0)

__global__ void init(float *a, float *b, int n)
{
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) { a[i] = (i % 1024) * 0.25f; b[i] = (i % 37) * 0.5f; }
}

__global__ void copy_values(const float *a, float *out, int n)
{
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) out[i] = a[i];
}

__global__ void triad(const float *a, const float *b, float *out, int n)
{
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) out[i] = fmaf(2.0f, b[i], a[i]);
}

int main()
{
    CUDA(cudaSetDevice(0));
    constexpr int trials = 7, repeats = 8, threads = 256;
    cudaEvent_t start, stop;
    CUDA(cudaEventCreate(&start)); CUDA(cudaEventCreate(&stop));
    for (int n : {1 << 20, 1 << 24}) {
        size_t bytes = (size_t)n * sizeof(float);
        float *a, *b, *out;
        CUDA(cudaMalloc(&a, bytes)); CUDA(cudaMalloc(&b, bytes));
        CUDA(cudaMalloc(&out, bytes));
        int blocks = (n + threads - 1) / threads;
        init<<<blocks, threads>>>(a, b, n);
        CUDA(cudaGetLastError()); CUDA(cudaDeviceSynchronize());
        for (int which = 0; which < 2; ++which) {
            auto launch = [&]() {
                if (which == 0) copy_values<<<blocks, threads>>>(a, out, n);
                else triad<<<blocks, threads>>>(a, b, out, n);
                CUDA(cudaGetLastError());
            };
            for (int warm = 0; warm < 3; ++warm) launch();
            CUDA(cudaDeviceSynchronize());
            float elapsed[trials];
            for (int t = 0; t < trials; ++t) {
                CUDA(cudaEventRecord(start));
                for (int r = 0; r < repeats; ++r) launch();
                CUDA(cudaEventRecord(stop)); CUDA(cudaEventSynchronize(stop));
                CUDA(cudaEventElapsedTime(&elapsed[t], start, stop));
                elapsed[t] /= repeats; /* milliseconds per kernel */
            }
            std::sort(elapsed, elapsed + trials);
            std::vector<float> result(n);
            CUDA(cudaMemcpy(result.data(), out, bytes, cudaMemcpyDeviceToHost));
            for (int i = 0; i < n; ++i) {
                float expected = (i % 1024) * 0.25f;
                if (which == 1) expected += (i % 37);
                if (result[i] != expected) {
                    std::fprintf(stderr, "payload mismatch at %d\n", i); return 2;
                }
            }
            double logical_bytes = (which == 0 ? 2.0 : 3.0) * bytes;
            double gbps = logical_bytes / (elapsed[0] * 1e6);
            double gflops = which == 0 ? 0 : 2.0*n / (elapsed[0] * 1e6);
            std::printf("n=%d %s min_us=%.3f median_us=%.3f effective_GBps=%.2f "
                        "GFLOPs=%.2f checked=%d\n", n, which == 0 ? "copy" : "triad",
                        elapsed[0]*1000, elapsed[trials/2]*1000, gbps, gflops, n);
        }
        CUDA(cudaFree(a)); CUDA(cudaFree(b)); CUDA(cudaFree(out));
    }
    CUDA(cudaEventDestroy(start)); CUDA(cudaEventDestroy(stop));
    return 0;
}

Pipeline latency and vector width answer different questions W7L1 1:24

W7L1 changes the question from chip-wide rates to how independent array operations pass through execution stages. Its teaching pipeline has three stages: load the input pair, execute an addition, and store the result. Assume each stage takes one cycle, different stages can work concurrently, there are no hazards or stalls, and the load stage can supply the required operands every cycle. These assumptions describe a model, not a measured modern CPU or GPU instruction pipeline. Actual global-memory latency is not one cycle.

Label cycles \(T_0,T_1,\ldots\). The first scalar input pair loads during \(T_0\), adds during \(T_1\), and stores during \(T_2\). Its result appears at the end of the third cycle. Meanwhile the second pair can load during \(T_1\), and the third during \(T_2\). Once full, the pipeline finishes one result per cycle. Thus first-result latency is three cycles, while the steady initiation interval, the time between starting successive pairs, is one cycle. Neither number can replace the other in a finite workload calculation.

A 64-bit element, such as an FP64 value, fills one 64-bit lane. A 128-bit packed vector can hold two such elements, and a 256-bit vector four. A lane is an element position that participates in the vector operation. Let \(v\) denote the number of lanes, \(g=\lceil n/v\rceil\) the number of element groups, and \(d_s\) the number of pipeline stages. If every stage processes a full group each cycle, the last group enters at cycle \(g-1\) and finishes at the end of cycle \(g+d_s-2\). Therefore elapsed cycles are

\[T_{\mathrm{cycles}}=g+d_s-1=\lceil n/v\rceil+d_s-1.\tag{18.3}\]

For twenty additions and three stages, equation (18.3) gives 22 cycles for scalar execution, 12 for two lanes and 7 for four lanes. The four-lane speedup over scalar is \(22/7\), approximately 3.143, rather than four, because pipeline filling and draining remain. The finite-run rates are twenty divided by those cycle counts. As the number of complete groups becomes large, the rate approaches \(v\) elements per cycle under the model assumptions. A partial final group can reduce lane utilization as well.

Width alone does not provide that rate. Four FP64 additions per cycle require an execution path capable of four additions and enough operand delivery. If each group needs two 256-bit input vectors and one 256-bit output vector, the ideal memory stages must sustain that traffic at their respective stages. Merely placing four elements in a wider register does not turn one scalar adder or one narrow load path into four. The lecture's diagrams make the architectural resource assumption visible by widening stages together.

The following simulation reconstructs the lecture's first four scalar sums and extends them to twenty deterministic entries. It groups operands by vector width, evaluates all sums, verifies equality across widths, and reports the ideal timing formula. It is a checked teaching model. Running it on a CPU does not measure CPU SIMD instructions, and its printed cycle labels do not claim the GPU's hardware pipeline depth.

Address size, architectural register width, instruction-set vector width, execution throughput and memory bandwidth are separate properties. Conversely, a machine can support a 256-bit vector instruction yet internally execute it over narrower resources. The practical lesson transfers directly to the triad. Enough arithmetic lanes do not guarantee enough bytes per cycle. SIMD and SIMT expose different software state W7L1 11:30

The recording next contrasts a packed vector with several scalar execution units, and then names SIMD and SIMT. Single instruction, multiple data, or SIMD, describes one operation applied across several data lanes. A vector addition expresses several element additions in one vector instruction. The programmer or compiler organizes values into vectors, handles bounds and deals with lanes that should be inactive. It does not follow that every SIMD architecture uses the same register width or predication rules.

Single instruction, multiple threads, or SIMT, exposes separate logical threads, each with its own registers and program state. CUDA lets each thread describe a scalar-looking operation on its index. Hardware groups threads into warps, which contain 32 threads on the queried device, and issues instructions for participating threads in those groups. The software state belongs to individual threads; issue and execution resources are shared. This is why a SIMT source program can be easier to express with scalar variables while its execution still requires reasoning about grouped instruction issue. PTX ISA §2, programming model.

The difference is not that SIMD has parallel data while SIMT has completely independent instruction streams every cycle. Threads in one warp can take different control paths, but executing those paths can reduce the number of lanes doing useful work at an instant. Nor does SIMT imply that every thread owns a physical CUDA core for its lifetime. The number of logical threads may exceed the number of arithmetic pipelines by orders of magnitude; schedulers select ready warp instructions as resources and dependencies permit.

Consider one hundred independent sums. A source loop can assign one sum to each of one hundred logical threads. Alternatively, fifty threads can each perform two sums through a loop. Both choices describe ownership of work, while vector width or warp issue width describes how instructions are executed. The second program does not automatically use half as many physical arithmetic lanes, and the first does not reserve one hundred processors. Register use, instruction count, memory access pattern and available ready work can change performance even when the mathematical sum set is identical.

Multiple threads also help tolerate latency. If one warp waits for an operand, a scheduler may issue another ready warp. This overlaps independent work rather than reducing the latency of the waiting memory operation itself. Similarly, several independent accumulators inside one thread can expose ready arithmetic while another accumulator awaits a dependency. These are two different sources of concurrency, both explored by the final experiment. More of either can increase register demand or other resource pressure, so “more threads” is not a proof of faster execution.

SIMD and SIMT are therefore useful descriptions at different layers, not mutually exclusive physical circuit categories. A GPU's warp instruction acts across many thread lanes, while its programming model preserves individual thread state. A CPU compiler can vectorize iterations that a programmer wrote as scalar loops. Performance reasoning becomes clearer by explicitly naming the layer: source work ownership, machine instruction, scheduler issue group, arithmetic pipeline, or memory transaction.

Blocks describe cooperation; SMs supply execution resources W7L1 19:08

A CUDA grid is the collection of blocks launched for one kernel invocation. A block is a group of threads that can cooperate through block-scoped synchronization and shared memory. Shared memory here means the GPU's explicitly managed on-chip memory available to a block, not the MPI shared-memory transport of earlier chapters. An SM is hardware; a block is a software scheduling and cooperation unit. A grid is not a hardware chip component, even though the recording usefully sketches grid-to-GPU, block-to-SM and thread-to-arithmetic-unit relationships.

Blocks are assigned to SMs for execution. An SM may host several resident blocks when thread, warp, register and shared-memory limits permit. It may also have fewer resident blocks than a simple thread-count quotient suggests because a different resource is exhausted. A block that cannot yet be admitted waits while others execute. Its logical indices do not encode the SM chosen for it. NVIDIA's GPU performance background explains this scheduling and the need for enough work to occupy resources. GPU performance background §3.

The lecture's example of 160 blocks on an 80-SM GPU gives an arithmetic average of two blocks per SM if all assignments are counted evenly. It does not establish that every SM holds two simultaneously, that the distribution is uniform at every instant, or that each block occupies a fixed fraction of an SM. Different block runtimes and resource requirements can produce different residency histories. The local device instead has sixteen enabled SMs; importing the lecture's eighty into a local launch would confuse an example product with the actual device.

The usual teaching picture places a block on one SM while its threads execute and share block resources. Avoid strengthening that picture into a persistent software identity rule about hardware location. PTX explicitly warns that the diagnostic SM identifier can change following preemption and rescheduling. An algorithm must use logical thread and block indices for ownership, not rely on a sampled physical SM number staying constant. The point is relevant even without using that special register in these examples. PTX ISA §10.8, special register %smid.

All measured kernels below use 256 threads per block, giving eight warps per full block. A launch of sixteen blocks contains 4096 threads, but that count alone does not prove one block lands on every SM, nor prove that all arithmetic pipelines are busy. A launch of 128 blocks supplies eight times as many threads and lets the scheduler draw from more work. This changes the opportunity for latency hiding, not the GPU's enabled SM count or advertised per-cycle arithmetic resources.

These distinctions prevent three common count errors. A Tensor core is not a CUDA block. A CUDA thread is not one physical scalar processor reserved forever. And a warp's thirty-two thread positions are not automatically thirty-two completed floating-point results per cycle for every instruction type. The supported operation, issue constraints and hardware pipelines determine the throughput of a warp instruction. The lecture's mapping is a starting vocabulary; numerical peak claims still require the operation-specific count developed earlier.

Independent arithmetic exposes a different throughput limit

The triad streams data with little work per element. To study scalar arithmetic separately, the final program keeps one or eight FP32 accumulators per thread in registers and performs 4096 FMA updates of each. The recurrence is \(x_{z+1}=1\cdot x_z+2^{-23}\), where \(z\) is the iteration index. Accumulator \(\gamma\), with \(\gamma=0,\ldots,k_c-1\) for \(k_c\) chains, starts at \(1+\gamma/8\). Different accumulators have no data dependencies on one another, while successive updates of one accumulator do. Thus eight chains expose instruction-level parallelism within one thread without claiming that one thread has eight permanently assigned physical arithmetic units.

The multiplication by one makes a deliberately exact validation case, but ordinary source optimization might remove that multiplication or simplify the loop. The listing therefore uses volatile inline PTX fma.rn.f32, specifying an FP32 FMA with round-to-nearest-even. The read/write operand supplies the previous accumulator and receives its new value. Volatile assembly preserves the stated arithmetic instructions. A native-machine-code inspection of the built executable confirmed scalar FFMA instructions. This is an experiment in ordinary FP32 arithmetic, not a Tensor matrix benchmark. PTX is introduced only for this narrow purpose; readers can use the operation count without writing PTX themselves.

All intermediate values remain in the interval from one to two. In that interval adjacent FP32 numbers differ by \(2^{-23}\), so every increment is exact. After 4096 updates the expected value is \(1+\gamma/8+2^{-11}\), below two even for the eighth chain. The host checks every stored accumulator against this expression, rejecting any mismatch. This special construction supplies a strong numerical check without using a tolerance that could conceal a missing loop or a missing chain.

Let \(b\) be the number of blocks, \(u\) the threads per block, \(k_c\) the chains per thread and \(r\) the update count. There are \(buk_c\) output values and \(2buk_cr\) counted FLOPs. Initialization, loop control and storing outputs take time but are excluded from that arithmetic count. The reported rate is therefore the rate of the selected FMA work over the full timed kernel, not a count of all instructions. The four cases cross one/eight chains with one/eight blocks per enabled SM as a grid-size construction. Actual placement remains the scheduler's decision.

#include <cuda_runtime.h>
#include <algorithm>
#include <cstdio>
#include <cstdlib>
#include <vector>

#define CUDA(call) do { cudaError_t err = (call); if (err != cudaSuccess) { \
    std::fprintf(stderr, "%s: %s\n", #call, cudaGetErrorString(err)); \
    std::exit(1); } } while (0)

template<int chains>
__global__ void fma_loop(float *out, int iterations, float scale, float increment)
{
    int tid = blockIdx.x * blockDim.x + threadIdx.x;
    float value[chains];
    #pragma unroll
    for (int c = 0; c < chains; ++c) value[c] = 1.0f + c * 0.125f;
    for (int i = 0; i < iterations; ++i) {
        #pragma unroll
        for (int c = 0; c < chains; ++c)
            asm volatile("fma.rn.f32 %0, %0, %1, %2;"
                         : "+f"(value[c]) : "f"(scale), "f"(increment));
    }
    #pragma unroll
    for (int c = 0; c < chains; ++c) out[tid * chains + c] = value[c];
}

template<int chains>
static void measure(int blocks)
{
    constexpr int threads = 256, iterations = 4096, repeats = 8, trials = 7;
    size_t count = (size_t)blocks * threads * chains;
    float *out;
    CUDA(cudaMalloc(&out, count * sizeof(float)));
    auto launch = [&]() {
        fma_loop<chains><<<blocks, threads>>>(out, iterations, 1.0f, 0x1p-23f);
        CUDA(cudaGetLastError());
    };
    for (int warm = 0; warm < 3; ++warm) launch();
    CUDA(cudaDeviceSynchronize());
    cudaEvent_t start, stop;
    CUDA(cudaEventCreate(&start)); CUDA(cudaEventCreate(&stop));
    float elapsed[trials];
    for (int t = 0; t < trials; ++t) {
        CUDA(cudaEventRecord(start));
        for (int r = 0; r < repeats; ++r) launch();
        CUDA(cudaEventRecord(stop)); CUDA(cudaEventSynchronize(stop));
        CUDA(cudaEventElapsedTime(&elapsed[t], start, stop));
        elapsed[t] /= repeats;
    }
    std::sort(elapsed, elapsed + trials);
    std::vector<float> result(count);
    CUDA(cudaMemcpy(result.data(), out, count * sizeof(float), cudaMemcpyDeviceToHost));
    for (size_t i = 0; i < count; ++i) {
        float expected = 1.0f + (i % chains) * 0.125f + iterations * 0x1p-23f;
        if (result[i] != expected) {
            std::fprintf(stderr, "FMA recurrence mismatch at %zu\n", i); std::exit(2);
        }
    }
    double operations = 2.0 * count * iterations;
    std::printf("blocks=%d chains=%d min_us=%.3f median_us=%.3f GFLOPs=%.2f checked=%zu\n",
                blocks, chains, elapsed[0]*1000, elapsed[trials/2]*1000,
                operations/(elapsed[0]*1e6), count);
    CUDA(cudaEventDestroy(start)); CUDA(cudaEventDestroy(stop)); CUDA(cudaFree(out));
}

int main()
{
    CUDA(cudaSetDevice(0));
    int sms;
    CUDA(cudaDeviceGetAttribute(&sms, cudaDevAttrMultiProcessorCount, 0));
    for (int multiple : {1, 8}) {
        measure<1>(sms * multiple);
        measure<8>(sms * multiple);
    }
    return 0;
}

A useful engineering model combines arithmetic and data delivery. If a compatible arithmetic limit is \(P_0\), the available bandwidth at a stated interface is \(B_0\), and a kernel has intensity \(I_0\) measured in operations per byte crossing that same interface, then an idealized bound is

\[P\le\min(P_0,I_0B_0),\qquad I_{\mathrm{ridge}}=P_0/B_0.\tag{18.4}\]

In equation (18.4), the crossover intensity \(I_{\mathrm{ridge}}\) is the amount of work per byte needed for arithmetic rather than bandwidth to become the smaller limit. NVIDIA's performance background develops this arithmetic-versus-memory reasoning. Dependencies, inadequate parallelism and instruction overhead can keep execution below both idealized limits. The inequality assumes that the work and byte definitions match the chosen limits; TF32 Tensor work and scalar FP64 work cannot share one interchangeable arithmetic ceiling. GPU performance background §4.

Using about 5.06 TFLOP/s as an empirical scalar-FMA reference and 180 GB/s as an empirical requested-byte streaming reference gives an illustrative crossover near 28 FLOP/byte. This combines two different microbenchmarks and is not a measured physical roofline with hardware-counter traffic. Nevertheless it explains scale: the triad's one sixth FLOP/byte is far below 28, and multiplying by 180 GB/s gives 30 GFLOP/s. Replacing ordinary arithmetic by a faster matrix unit alone cannot create the missing input reuse or make an arbitrary elementwise triad into a matrix multiplication.

The same reasoning sharpens a stencil optimization plan. A naive FP64 five-point Jacobi update reads four neighbours and writes one output: 40 requested bytes and three additions plus one multiplication, or four FLOPs, giving 0.1 FLOP/byte. Neighbour reuse can make DRAM traffic smaller than that source-level count. A tiled implementation should therefore distinguish its counted requests from bytes at DRAM before predicting a speedup. Merely quoting the GPU's FP32 Tensor peak would mix both precision and operation type with the stencil. The right question is how much useful work each byte supports and which measured path supplies that byte.

Exercises

Exercise 1 (derive and audit). For matrices \(A\in\mathbb R^{m\times k}\), \(B\in\mathbb R^{k\times n}\) and \(C\in\mathbb R^{m\times n}\), count work for \(AB\) and for \(AB+C\). Explain the 112-versus-128 distinction for 4-by-4 matrices. Then reproduce the V100 Tensor model using eighty enabled SMs, eight Tensor cores per SM, sixty-four FMA-equivalent results per core per cycle and 1.53 GHz. What would go wrong if eighty-four physical-design SMs were substituted?

Solution

There are \(mn\) output entries. A length-\(k\) dot product has \(k\) multiplications and \(k-1\) additions if started from its first product, so \(AB\) has \(mn(2k-1)\) scalar operations. Adding an existing \(C\) entry introduces one more addition, giving \(2mnk\). Equivalently, accumulate \(k\) products into each existing entry using \(mnk\) FMAs, conventionally two FLOPs each. For \(m=n=k=4\), the first count is \(16\times7=112\), the second \(16\times8=128\). Hardware may execute a matrix multiply by accumulating into zero, so its conventional advertised FMA count can still use 128; the mathematical expression and counting convention must be stated.

The dated enabled V100 model gives \(80\times8=640\) Tensor cores, \(640\times64=40960\) scalar FMA-equivalent results per cycle, and \(40960\times2\times1.53\times10^9=125.3376\times10^{12}\) FLOP/s. This rounds to 125 TFLOP/s. Substituting eighty-four multiplies the model by \(84/80=1.05\), producing 131.60448 TFLOP/s for resources the stated product does not enable. The error is a product-configuration error, not a subtle rounding discrepancy. The physical diagram and enabled-device specification answer different questions.

Exercise 2 (find the signaling error). An engineer reads “256-bit interface, effective 14 Gb/s per pin” and computes \(256\times14\times2/8=896\) GB/s because the memory is double-data-rate. Correct the result and express it in GiB/s. A second design has a 320-bit interface at effective 19 Gb/s and uses PAM4. Should another factor two be applied? Finally, explain why doubling the storage capacity of every package need not change either answer.

Solution

Effective bit rate already states transferred bits per second per pin. Therefore the first payload model is \(256\times14\times10^9/8=448\times10^9\) bytes/s, or \(448\times10^9/2^{30}\approx417.233\) GiB/s. The engineer counted the transfer-edge factor twice. If the input had instead been a clearly defined underlying clock, a signaling conversion would be needed, but it is not needed for an already effective bit rate.

The second model is \(320\times19\times10^9/8=760\times10^9\) bytes/s, approximately 707.805 GiB/s. PAM4 conveys two bits per symbol, but those bits are already represented in 19 Gb/s. Multiplying again would incorrectly produce 1520 GB/s. For comparison, a hypothetical 9.5-gigasymbol/s pin carrying two bits per symbol would first give 19 Gb/s; only then would width and division by eight be applied. Capacity depends on how many bits are stored, while the bandwidth model depends on how many data pins transfer how many bits per second. Denser packages can double capacity while preserving both interface width and signaling rate. No bandwidth increase follows from capacity alone.

Exercise 3 (precision counterexample). TF32 retains FP32's exponent range but reduces the input significand. Use an idealized round-to-nearest TF32 input conversion with ten stored fraction bits. Consider the two-term dot product \((1+2^{-12})\cdot1+(-1)\cdot1\). Compute its exact result, its result after the two nontrivial inputs are converted to TF32, and the relative error. Why can FP32 accumulation fail to restore the lost value? State the boundary of the example.

Solution

In exact arithmetic the terms cancel except for \(2^{-12}\), so the result is \(1/4096\). FP32 can represent all the stated inputs and this difference exactly. Near one, TF32 spacing with ten fraction bits is \(2^{-10}\). The perturbation \(2^{-12}\) is one quarter of that spacing, so nearest rounding maps \(1+2^{-12}\) to one; negative one and both multiplier ones are exactly representable. The converted dot product is consequently \(1-1=0\). Relative error against the nonzero exact answer is \(|0-2^{-12}|/2^{-12}=1\), or 100%.

A wider accumulator receives products of the already rounded operands. It cannot infer information removed before multiplication. This is a counterexample to treating exponent range or FP32 accumulation as proof of FP32-input accuracy. It is not a claim that every TF32 computation has this error, nor a specification of every library's conversion, fallback or correction mode. A real application must identify the chosen math mode and validate error on its conditioning and data. The higher Tensor throughput is useful only if that numerical contract is acceptable.

Exercise 4 (pipeline timing). In the three-stage model, nineteen additions are processed with four lanes. Give the number of groups, first-result and final-result cycle labels, total elapsed cycles, average useful elements per cycle and steady full-group throughput. Compare with scalar execution of the same nineteen additions. Explain why assuming a one-cycle first-result latency produces the wrong answer.

Solution

There are \(\lceil19/4\rceil=5\) groups, the last with three useful lanes. The first group starts in \(T_0\) and finishes at the end of \(T_2\), after three elapsed cycles. The fifth starts in \(T_4\) and finishes at the end of \(T_6\), giving seven elapsed cycles. Average useful throughput is \(19/7\approx2.714286\) elements/cycle. For a continuing stream of full groups, ideal throughput is four elements/cycle, a different quantity from the finite useful rate.

Scalar execution uses nineteen groups and \(19+3-1=21\) elapsed cycles, ending at \(T_{20}\). The finite speedup is \(21/7=3\), below four because of startup/drain costs and the unfilled lane. A one-cycle initiation interval means a new group can start each cycle; it does not mean the first group finishes after one cycle. Omitting the two fill/drain cycles would predict five cycles for the vector case. Even seven is conditional: enough load, arithmetic and store throughput must exist, with no hazards or stalls. The timing model alone does not establish those hardware resources.

Exercise 5 (choose a useful optimization). A device-resident FP32 triad reads two arrays and writes one, performing two FLOPs per element. Suppose an empirical streaming reference is 180 GB/s and a scalar arithmetic reference is 5.06 TFLOP/s. Predict the intensity-limited rate under the chapter's accounting. Evaluate three proposals: merely doubling arithmetic peak, halving the requested bytes without changing useful work, and doubling the host-link bandwidth. Which claims need extra evidence?

Solution

Requested traffic is twelve bytes per element, so intensity is \(2/12=1/6\) FLOP/byte. The illustrative memory-side rate is \(180/6=30\) GFLOP/s, far below 5060 GFLOP/s. Doubling the arithmetic reference to 10.12 TFLOP/s leaves the smaller limit at 30 GFLOP/s in this model. It cannot by itself speed an already bandwidth-limited triad. The crossover intensity based on the original references is \(5060/180\approx28.111\) FLOP/byte.

Halving requested bytes at equal useful work doubles intensity to one third FLOP/byte, producing a 60 GFLOP/s model rate if the applicable bandwidth remains 180 GB/s. That is a conditional opportunity, not a proof that bytes can be removed: inputs may be mathematically required, and fusion or reuse must preserve the intended result. Changed transaction patterns, caches and instructions can change the achieved bandwidth. Doubling a CPU-to-device link has no effect on the stated timed interval, because the arrays are already on the device. It could improve an end-to-end workflow that includes transfers, which requires a separately measured interval. Finally, the two references are microbenchmark rates with logical byte accounting, not independently established physical ceilings for every kernel.

Exercise 6 (implementation and measurement audit). Audit the largest FMA case: 128 blocks, 256 threads per block, eight chains per thread and 4096 updates per chain. Derive the output count and FLOP count, reconstruct its approximately 5062.77 GFLOP/s rate from 424.172 microseconds, and prove the exact expected output. Describe a bounded test plan that would detect missing work and distinguish correctness from timing claims.

Solution

The number of logical threads is \(128\times256=32768\). Each stores eight values, so output count is 262144, not 262144 threads. There are \(262144\times4096=1073741824\) FMAs, conventionally 2147483648 FLOPs. Dividing by \(424.172\times10^{-6}\) seconds and then \(10^9\) yields approximately 5062.77 GFLOP/s; the final digits reflect printed-time rounding. One must not multiply the count by eight launches again when the printed elapsed time has already been divided by eight.

Chain \(\gamma\) starts at \(1+\gamma/8\). Each FMA with multiplicand one adds exactly \(2^{-23}\), because every intermediate value is representable at the spacing in this interval. After 4096 updates the increment is \(2^{12}2^{-23}=2^{-11}\). The largest result is \(1+7/8+2^{-11}\), still below two, which closes the representability argument. Checking every output against \(1+\gamma/8+2^{-11}\) detects a missing chain, wrong initialization or missing updates; checking only finiteness or a single checksum would be weaker. The supplied implementation also checks all CUDA calls and launch errors, and synchronizes before reading results.

A bounded plan runs both chain counts with both grid sizes, performs the exact full-output check each time, verifies native FFMA instructions, and retains build flags, source hashes, commands, device query, stdout, stderr and timing endpoints. It then repeats timing serially with warmups and the same event protocol. The actual four configurations and four captures passed those payload checks. That establishes the stated cases; repeat ranges characterize short-run variability. It does not establish a stable peak, explain every stall, or make the 82.4% model ratio an architecture-independent utilization percentage.
