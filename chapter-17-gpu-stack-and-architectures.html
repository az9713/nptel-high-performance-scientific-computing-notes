GPU computing: the software stack, architectural units and the cost of offloading

Twenty updates of a million-element single-precision vector require about 40 million floating-point operations. A literal CPU-to-GPU port can also move the same two inputs and one output across the host link twenty times: about 240 MB. Keeping the arrays on the device reduces that host traffic to about 12 MB while preserving all twenty updates. A large advertised teraFLOP rate cannot decide which implementation wins. The decision needs an architectural unit model, a complete transfer-and-launch budget, and a checked result.

Grounded in W6L3, Introduction to GPU Computing, W6L4, A Dive into Software Stack and NVIDIA Architecture, and W6L5, Comparative Analysis of NVIDIA and Intel GPU Architectures, in NPTEL's High Performance Scientific Computing. These GPU-module lectures are presented by Vamshi Krishna, C-DAC Pune; the course's main instructor is Prof. Shivasubramanian Gopalakrishnan, IIT Bombay. Lecture material: CPU/GPU nodes, PCIe and NVLink, accelerator history and integrated/discrete devices; the software stack and host/device roles; NVIDIA GPC/TPC/SM organization and execution/storage units; Intel Xe-HPC stacks, slices, Xe-cores, vector and matrix engines; terminology and scalar peak arithmetic. Research extensions: NVIDIA's dated Volta and Ampere white papers, Intel's March 2023 oneAPI GPU guide, Intel's May 2022 PCIe datasheet, and CUDA API/programming/numerical documentation specify the architecture-dependent facts and software guarantees. Original teaching constructions: the offload cost model, explicit unit checks, full-versus-enabled comparisons, register-width counterexample, fused-rounding example, actual device query, complete checked programs, transfer-residency experiment and six worked exercises.

The objects of the chapter and the running case

A host is the CPU-side execution environment and its accessible memory. A device is an accelerator used by the host, here an NVIDIA GPU with separate device memory. A kernel is a function launched for parallel execution on that device. A programming model describes how a programmer names parallel work, storage and synchronization; a microarchitecture describes how a particular implementation executes it. Neither a software thread nor a hardware arithmetic lane is a complete CPU core.

A CUDA thread is one logical kernel invocation. A thread block is a group of those invocations that can cooperate using block-scoped synchronization and storage; a grid is the collection of blocks in a launch. These software groups are distinct from the physical execution resources that schedule them. The small programs introduce only the indexing needed for their checks; later chapters develop the full hierarchy.

The running case performs K passes of \(y_i\leftarrow2x_i+y_i\) for \(0\le i\lt n\). The input x is unchanged; y depends on its previous value at the same index but never on another index. We choose \(x_i=i\bmod17\) and initial \(y_i=1\), so after K passes the exact result is \(1+2Kx_i\). For K=20 every value is an integer between one and 641, exactly representable in binary32 arithmetic. This choice lets us check every output entry exactly without confusing a scheduling or transfer error with rounding variation.

A floating-point operation, abbreviated flop, is one arithmetic addition, multiplication or comparable scalar operation under a stated counting convention. The work of this recurrence is \(F=2nK\) flops: one multiplication and one addition per element per pass. A fused multiply-add may execute them as one instruction but still counts as two arithmetic operations. A rate in flop/s is work divided by elapsed time. “TFLOP/s” means \(10^{12}\) flop/s; it is a rate, whereas “TFLOP” alone is an operation count.

Distinguish two byte counts. Device-memory traffic supplies the kernel's loads and stores. Host-device traffic crosses the interconnect. With four-byte binary32 elements, a pass logically reads x and y and writes y, for twelve bytes per element before considering caches. Thus the kernel's logical arithmetic intensity is \(I=F/Q=2/12=1/6\) flop/byte. Caches and compiler transformations can change physical traffic; this accounting defines a lower-level question to measure rather than asserting that every access reaches external memory.

Let \(T_{\rm H2D}\) and \(T_{\rm D2H}\) be host-to-device and device-to-host transfer times, \(t_{\rm launch}\) the launch-related overhead per pass, and \(T_{\rm kernel}\) the execution time of one pass once data is available. An unoverlapped end-to-end time includes all four. Its denominator differs from a kernel-only timer. We use host wall-clock intervals that include the required copies and launches, while keeping allocation and initialization outside the timed interval for all compared implementations.

For architectural peak arithmetic, \(n_{\rm SM}\) is the number of enabled NVIDIA streaming multiprocessors, \(c_{32}\) the FP32 arithmetic-lane count per SM in the specified architecture, and \(\nu_{\rm clk}\) the selected clock rate in cycles per second. The nominal FMA peak model is \(P_{\rm peak}=2n_{\rm SM}c_{32}\nu_{\rm clk}\). Every factor needs a device, precision and clock convention. It is a capacity model, not a promise that a particular application can issue that work continuously.

A GPU node adds an accelerator and a communication path W6L3 5:03

A compute node is a whole computer: CPU sockets, memory, I/O connections, storage and networking, plus optional accelerators. Multiple CPU sockets and multiple cores per socket are different levels of organization. Two sixteen-core sockets and one thirty-two-core socket have the same simple core count but can differ in memory locality, memory channels, inter-socket traffic and clock behavior. Adding GPU cards does not remove those host-side constraints.

PCI Express connects endpoints such as GPUs and network or storage devices through serial lanes. A label x16 describes sixteen lanes; physical connector size and electrically active lane count need not coincide. The generation determines the signaling rate. For the PCIe 4.0 example, Intel's May 2022 desktop-processor datasheet, §2.2.3–2.2.4 and Table 2-10, specifies 16 GT/s and 128b/130b encoding. These are facts about that generation, not the negotiated link of the laptop used later.

At this non-return-to-zero signaling generation, one transfer carries one transmitted bit. Coding keeps 128 useful coding bits in every 130 transmitted bits. Dividing by eight bits per byte gives a coding-limited one-direction byte rate per lane; multiplying by 16 lanes gives

\[ B_{\rm lane}=16\times10^9\frac{128}{130}\frac18 =1.969230769\times10^9\ \mathrm{byte/s},\qquad B_{\rm x16}=16B_{\rm lane}=31.507692308\ \mathrm{GB/s}. \tag{17.1} \]

Here GB uses decimal billions of bytes. The lecture rounds the lane result to 2 GB/s and hence the link result to 32 GB/s. That is a rounded coding ceiling, not application payload throughput. Transaction headers, flow control, platform routing and transfer software reduce usable rates. Full duplex permits traffic in both directions; adding the two directions gives about 63.0 GB/s of aggregate coding capacity, not 63.0 GB/s for one unidirectional copy.

The accompanying connector illustration gives older-generation rates while the arithmetic uses PCIe 4.0. Those numbers must not be mixed. A general slot photograph cannot establish a generation, negotiated width or measured throughput. Nor does a newer slot guarantee that every attached endpoint or motherboard path operates at the same generation and width.

NVLink provides another interconnect family. NVIDIA's August 2017 V100 white paper describes six links and 300 GB/s aggregate GPU bandwidth. The 2020 A100 white paper, Third-Generation NVLink section, explicitly gives 25 GB/s in each direction per link and twelve links on A100. Six such full-duplex links yield 300 GB/s aggregate; twelve yield 600 GB/s. The W6L3 slide calls the V100 25 GB/s figure bidirectional, but that figure is per direction; otherwise its own six-link 300 GB/s total would not follow.

A bandwidth comparison must also fix topology. GPU-to-GPU traffic does not universally require a CPU-memory staging copy merely because the physical path is PCIe. CUDA 13.0, §6.2.9.4–6.2.9.5, describes peer access conditional on PCIe/NVLink topology and support queries; supported peer copies can avoid host staging. One local GPU cannot demonstrate a two-GPU peer path. We therefore distinguish a documented capability from a measured configuration and make no NVLink measurement on the laptop.

Throughput-oriented hardware still needs suitable independent work W6L3 17:42

A CPU core devotes substantial machinery to reducing the latency of a broad instruction stream: prediction, out-of-order execution, caches and a flexible control path. A GPU devotes more of its design to keeping many arithmetic and memory operations in flight. This is a design tendency, not a theorem that CPUs execute only serial code or that GPUs cannot execute branches. Earlier chapters already used CPU SIMD and OpenMP parallelism.

Latency is the time for one dependent result; throughput is completed work per unit time across many results. If a computation has one long chain of dependent pointer reads, additional arithmetic lanes do not manufacture independent addresses. If millions of independent cells need the same stencil expression, the machine can distribute them and use other ready work while some operations wait. The amount of independent work, memory access pattern and numerical precision matter more than comparing the words “core” in two product tables.

The lecture traces the transition from dedicated graphics functions to programmable graphics pipelines and then general-purpose GPU computing. The useful conceptual change is programmability: a data-parallel scientific kernel can use execution resources that also support graphics workloads. “GPGPU” names that general-purpose use. It does not mean that a different kind of arithmetic automatically appears when the same processor stops rendering pixels.

An integrated GPU commonly shares a package or die and host memory resources; a discrete accelerator commonly has its own memory and a separate interconnect. These are system-level distinctions, not complete descriptions of memory semantics. The programmer must still determine where an allocation resides, how data reaches the executing unit and what synchronization makes it usable. Packaging terminology alone cannot justify assuming zero transfer cost or coherent simultaneous access.

Similarly, low latency versus high throughput is more meaningful than the lecture table's universal “CPU higher clock/GPU lower clock” wording. Clock rates vary across products and operating conditions. A GPU clock can be lower while its aggregate lane throughput is higher. Its advantage can disappear for a tiny request because launch and communication overhead remain even when there are too few operations to amortize them.

The table's “no inter-warp context switching” should not be read as an inability to select another ready warp. Hardware schedules among resident warps whose state is already present; it need not perform an operating-system task-context save for each such selection. That is different from switching between processes or replacing nonresident execution state. A ready-work scheduler is precisely how the GPU keeps working when one warp waits. The detailed mapping is developed after the architectural overview.

API availability is also a software-stack property. A CPU has instruction-set, operating-system and library constraints; it is not literally free of API limitations. A GPU needs a supported compiler/runtime/driver path and a workload expressed in the model those tools support. This motivates inspecting the stack before calculating a peak from hardware counts.

The software stack turns an executable into checked device work W6L4 1:17

The lecture's layered picture places applications above a programming model, compilers/libraries, device drivers, the operating system and hardware. The boundaries are conceptual. A compiler is a build-time tool, while libraries and drivers participate at execution time. A library can itself launch device kernels; a programming model can have several language bindings. Drawing a vertical stack does not mean every call literally traverses one function in each layer.

For CUDA C++, the host program runs on the CPU and launches device functions compiled for a compatible NVIDIA target. The runtime API manages launches, memory and synchronization; the lower-level driver interface exposes related execution facilities. A toolkit version identifies the development software, a driver-supported API version identifies another compatibility dimension, and compute capability identifies a hardware feature level. They are three distinct numbers, not interchangeable measures of processing speed.

The local toolkit's actual version file identifies CUDA 13.3.1 and nvcc 13.3.73. The installed 13.3 header was read before writing the query: its cudaDeviceProp structure lacks older clockRate and memoryClockRate fields, while cudaDeviceGetAttribute still exposes the corresponding attribute names. The program therefore uses the available interface rather than assuming an old device-query example will compile unchanged. Public code contains no machine-specific header path.

All CUDA examples check API return values using the documented error-handling interface. A launch is asynchronous with respect to the host, so a host statement immediately after launch need not mean completion. Checking cudaGetLastError catches launch-related errors; a checked synchronization or subsequent correctly ordered blocking transfer is needed to surface completion errors and make results available. An executable that prints a number without checking its device operations has not demonstrated a successful computation.

The first CUDA program allocates 1024 bytes for 256 integers, launches one block with 256 threads, checks launch and completion, copies the result back and verifies every square. It then frees the allocation. The checksum is only a compact printed summary; the actual check is elementwise. This is a stack smoke test, not a throughput measurement.

In that launch, <<<1, 256>>> requests one block of 256 logical invocations, and threadIdx.x is each invocation's index from zero through 255 within the block. Each invocation writes a different element, so there is no write conflict. The checked host synchronization precedes every result read.

#include <cuda_runtime.h>
#include <cstdio>
#include <cstdlib>
#define CK(call) do {cudaError_t e=(call);if(e!=cudaSuccess){std::fprintf(stderr,"%s: %s\n",#call,cudaGetErrorString(e));std::exit(1);}} while(0)
__global__ void square(int *out){int i=threadIdx.x;if(i<256)out[i]=i*i;}
int main(){
    int *device=nullptr,host[256];CK(cudaMalloc(&device,sizeof host));
    square<<<1,256>>>(device);CK(cudaGetLastError());CK(cudaDeviceSynchronize());
    CK(cudaMemcpy(host,device,sizeof host,cudaMemcpyDeviceToHost));
    long sum=0;for(int i=0;i<256;++i){if(host[i]!=i*i)return 2;sum+=host[i];}
    CK(cudaFree(device));std::printf("checked launch: 256 squares; checksum=%ld\n",sum);return 0;
}

Compilation uses nvcc -arch=native on the verification machine; the nvcc architecture-option documentation defines this target selection. That choice targets the visible installed GPU and is not a portable deployment promise for every other machine. A production build intended for several architectures needs an explicit supported-target policy. Successfully compiling a host executable also does not prove that its device code can run on a particular driver/device combination; the checked launch supplies that evidence here.

NVIDIA's hierarchy groups arithmetic, scheduling and storage W6L4 9:10

The global diagram used in W6L4 is the full GV100 design from the 2017 Volta white paper. Six graphics processing clusters, abbreviated GPCs, contain seven texture processing clusters, TPCs, each; each TPC contains two streaming multiprocessors, SMs. Multiplying gives 84 SMs in the full-chip diagram. This is a hierarchy of a particular design, not a universal NVIDIA formula or a count of enabled units in every product sold from that design.

An SM combines arithmetic pipelines, scheduling and storage. In that Volta design it has 64 FP32 lanes, 32 FP64 lanes, 64 INT32 lanes and eight Tensor Cores, organized in four processing partitions. A partition's warp scheduler selects ready work; dispatch directs an instruction to the appropriate pipeline. Load/store units move operands between the memory hierarchy and execution state. Specialized arithmetic pipelines and matrix units are different resources with different operations and throughput.

The lecture calls a hardware partition a “process block.” A CUDA thread block is instead a software group, and several such groups may reside on an SM. These names do not establish a one-to-one mapping between a program block and a hardware partition.

A warp is a group of 32 CUDA threads in the architectures discussed here. It is not a claim that 32 independent CPU cores exist or that every 32-thread instruction completes in one cycle. Instruction issue, execution latency and sustained arithmetic throughput have different units. If one warp's next instruction depends on unfinished data, the scheduler can select another ready resident warp. More resident work can hide latency, provided independent work and execution resources remain available.

Registers hold per-thread execution values. The slide's 16384 registers per partition are 32 bits each. Four partitions therefore provide \(4\cdot16384\cdot32/8=262144\) bytes, or 256 KiB, per SM. A KiB means 1024 bytes. That capacity is separate from shared memory and from device-global memory. Registers allocated to one thread cannot simply be treated as a software-addressable scratch array shared among every thread.

Shared memory is a programmer-controlled storage space used by cooperating threads of a block; an L1 data cache is hardware-managed caching. Their physical capacity may share a combined subsystem, but their programming semantics differ. The SM-detail slide labels a 192 KB combined unit. NVIDIA's A100 paper specifies 192 KB on A100 versus 128 KB on V100; the capacity must be attached to the named architecture, rather than copied from one diagram into a different product's model.

For a teaching resource bound, suppose an SM has R register slots, each resident block contains b_t threads, and each thread uses r_t slots. Ignoring allocation granularity, registers alone allow at most \(\lfloor R/(b_tr_t)\rfloor\) blocks. A shared-memory budget S with s_b bytes per block permits at most \(\lfloor S/s_b\rfloor\), and a resident-thread limit t_max permits \(\lfloor t_{\max}/b_t\rfloor\). The feasible resident-block count cannot exceed the minimum of these limits and the architecture's block-count limit. A resource that is plentiful does not remove a tighter limit elsewhere.

A second bound explains what latency hiding asks of the machine. Let \(L\) be the average completion latency of a memory transaction in seconds, \(X\) the sustained completion rate in transactions per second, and \(\lambda\) the average number in flight. In a stable observation window, Little's law gives \(\lambda=LX\). If a transaction carries \(m_{\rm txn}\) bytes, a target bandwidth B requires \(X=B/m_{\rm txn}\), hence \(\lambda=LB/m_{\rm txn}\). The quantities must refer to the same transaction boundary; mixing a cache-hit latency with external-memory bandwidth would invalidate the accounting.

For explicitly hypothetical B=200 GB/s, L=400 ns and 32 bytes per transaction, the model requires 2500 transactions in flight on average. That is not 2500 threads or 2500 warps: one instruction can generate several transactions, and one warp can have different amounts of outstanding work. The calculation illustrates why a wide arithmetic datapath alone cannot ensure a high memory rate. Enough independent memory work, queue capacity and physical service bandwidth must coexist. It also explains why increasing thread count past another resource limit can stop helping. The example predicts a concurrency requirement under its assumptions, not the measured transaction count or latency of the laptop.

This is a capacity bound, not an occupancy measurement. Actual compiled register use, allocation granularity, dynamic shared memory and block constraints can lower residency. Occupancy is the fraction of a hardware residency limit occupied by active work, not a direct percentage of peak flop/s. A kernel with more resident warps can still be limited by memory bandwidth or a chain of dependent operations.

Special-function units do not make arbitrary high-level functions single hardware instructions. A supported approximate scalar transcendental instruction and a general matrix exponential are different computations. The latter normally requires an algorithm with many operations. Similarly, naming a Tensor Core does not specify its supported formats, matrix tile shape or work per clock; those are architecture-dependent facts developed in the next chapter.

Intel Xe-HPC illustrates why register width is not a throughput specification W6L5 1:49

The lecture distinguishes Xe-LP, Xe-HPG, Xe-HP and Xe-HPC as design families aimed at different workloads. These historical family labels are not a ranking of every future product with “Xe” in its name. The detailed example is Ponte Vecchio, associated with the Intel Data Center GPU Max family, using the March 31, 2023 oneAPI GPU Optimization Guide, Intel Xe GPU Architecture section.

The illustrated two-stack organization has four slices per stack and 16 Xe-cores per slice. Each Xe-core contains eight vector engines and eight Xe Matrix Extensions engines, abbreviated XMX. Multiplication gives \(2\cdot4\cdot16=128\) Xe-cores, and \(128\cdot8=1024\) vector engines plus 1024 matrix engines in the two-stack configuration. These are counts of different hierarchical objects, not 1024 CPU-equivalent cores.

The surrounding module/subsystem drawings distinguish packaging from programming. An OCP Accelerator Module, OAM, is a module form factor; the four-module X4 subsystem is one system arrangement shown in the recording. CPU sockets, inter-module links, memory fabric, dispatch and media-related blocks occupy different roles. A module photograph does not tell a kernel how its work-items will be scheduled, nor does it replace a supported-device capability query.

The 2023 guide describes a 512-bit vector engine and a 4096-bit matrix engine. The slide correctly counts sixteen 32-bit values or eight 64-bit values in 512 bits. Multiplying eight vector engines by sixteen values and two operations per FMA gives 256 FP32 operations per Xe-core per cycle under a one-register-vector-per-cycle assumption. But dividing register width by element width has only counted elements; it has not established the issue or execution rate of each precision.

This matters because the slide applies that same assumption to FP64 and obtains 128 operations per Xe-core per cycle. The cited Intel guide instead specifies 256 FP64 operations per Xe-core per cycle, equal to its 256 FP32 rate; its configuration table also lists equal single- and double-precision rates for this Xe-HPC configuration. We use the vendor's architecture-specific throughput. The register-width arithmetic remains a valid element-count calculation, but it is not a sufficient derivation of FP64 execution throughput.

A general dimensional model makes the missing factor explicit. If an engine handles a w-bit vector representation, b-bit elements, v engines per core, o arithmetic operations per element, and an effective rate q_b of such vector-sized operations per cycle, then the modeled core throughput is \(v(w/b)o q_b\) operations/cycle. Knowing w, b, v and the FMA convention o=2 does not determine q_b. The counterexample does not establish a particular hidden dual-issue mechanism; it establishes that width alone cannot supply the whole throughput model.

The lecture's 1024 matrix-engine count likewise does not imply 1024 FP64 vector engines or a matrix rate interchangeable with a scalar rate. Supported input format, accumulator precision, tile operation and operation-count convention must be specified. The table's 4096-bit descriptor is not permission to cast arbitrary 4096-bit program objects into one matrix instruction.

We have no Ponte Vecchio device in this verification environment and run no Intel GPU program. Those architecture facts are checked against the dated guide, while executable measurements use the queried NVIDIA laptop GPU. Keeping those evidence classes separate prevents a local CUDA result from being presented as verification of a different vendor's hardware.

Map programming concepts without equating hardware units W6L5 18:23

The terminology comparison is useful when translating a program's structure. A CUDA thread and a work-item both name an individual logical invocation in their respective models. A CUDA thread block and a work-group organize cooperating invocations. A CUDA warp and a subgroup describe smaller execution groupings, but subgroup size and supported operations depend on the device and model. A familiar word does not make two APIs semantically identical.

The table maps questions, not identical quantities. Counting one Xe-core against one SM without precision, clock, lane/engine throughput and memory limits loses the information needed for a comparison. Counting a CUDA core against one vector engine is worse: the first commonly denotes one arithmetic lane while the second can operate on a vector of values. Even within one vendor, the same marketing unit count can accompany different per-unit work across generations.

SIMT, single instruction multiple threads, is a programming/execution organization in which threads retain individual logical state while groups execute instructions across lanes. SIMD, single instruction multiple data, describes applying an instruction over multiple data elements. W6L5's contrast between “emulated” NVIDIA SIMT and “true” Intel SIMD should not be read as software simulation versus real hardware arithmetic. Both GPUs use physical parallel execution resources; the abstractions expose that execution differently.

A correct translation starts with invariants: which element an invocation owns, which values it reads, where cooperating invocations synchronize, and how group-local storage is scoped. Only then should group sizes and architecture-specific vector widths be selected. This is the same ownership-first reasoning used for OpenMP tasks and MPI partitions, with a different execution resource.

Derive scalar peak from enabled hardware and a declared operation count W6L5 21:41

The full-chip diagrams and the enabled products must be distinguished. The V100 peak table uses 80 enabled SMs, while the full GV100 diagram contains 84. The A100 peak table uses 108 enabled SMs, while the full GA100 diagram contains 128. The A100 white paper, hardware architecture section, explicitly labels that distinction. Multiplying full-chip units and product boost frequency would combine facts from different configurations.

At 80 SMs and 64 FP32 lanes per SM, V100 has 5120 enabled FP32 lanes. At 1.530 GHz, a nominal one-FMA-per-lane-per-cycle model gives \(5120\cdot2\cdot1.530\times10^9=15.6672\times10^{12}\) flop/s. Its 32 FP64 lanes per SM give 2560 lanes and 7.8336 TFLOP/s under the same clock assumption. These round to the lecture table's 15.7 and 7.8 TFLOP/s.

The analogous A100 scalar calculation is \(108\cdot64\cdot2\cdot1.410\times10^9=19.49184\times10^{12}\) flop/s for FP32 and 9.74592 TFLOP/s for FP64. The latter is the scalar FP64 path, excluding Tensor Core FP64 operations. Precision and execution path must accompany the rate. A matrix-unit rate with reduced-precision inputs or structured sparsity cannot silently replace this scalar peak in an application's accuracy budget.

An integer multiply-add can also be counted as two integer arithmetic operations, but those are not floating-point operations. The lecture slide labels its INT32 calculation as FLOPs; the correct unit for that arithmetic is integer operations per second under a stated instruction convention. Likewise, an addition-only workload should not divide its useful operations by an FMA denominator and call the result an architecture-independent utilization percentage.

FMA is also a numerical operation, not just a counting convention. It computes a product plus an addend with one final rounding rather than rounding the product first. NVIDIA's floating-point white paper, §2.3 and §4.3, explains why this can change the result. For exactly representable a=1+2⁻²³ and b=1−2⁻²³ in binary32, the exact product is 1−2⁻⁴⁶. Rounding the product first yields 1, so subtracting 1 gives zero; fused computation of ab−1 preserves−2⁻⁴⁶.

The C program checks both values with contraction disabled for the separate expression and an explicit fmaf call for the fused expression. Its input magnitudes are bounded and its expected values exactly representable. It demonstrates a rounding distinction; it is not a CPU-versus-GPU accuracy ranking.

#include <stdio.h>
#include <math.h>
int main(void){
    volatile float a=1.0f+0x1p-23f,b=1.0f-0x1p-23f;
    float separate=(float)(a*b)-1.0f;
    float fused=fmaf(a,b,-1.0f);
    if(separate!=0.0f||fused!=-0x1p-46f)return 1;
    puts("separate multiply/add: 0; fused multiply-add: -2^-46");
    puts("one FMA counts as two arithmetic operations and rounds once");return 0;
}

Finally query the actual GPU. The CUDA device-management API and device-property definitions identify the meanings of the fields. The local query reports 16 SMs and compute capability 8.6. The GA10x Ampere white paper, v 2.1, SM architecture section, supplies the 128 FP32-lane-per-SM model used only for this capability mapping. int main() {
    int count=0;CK(cudaGetDeviceCount(&count));if(count<1)return 2;

Keeping data resident changes the break-even point

The recurrence now connects the architectural model to a decision. Let c be the CPU time per pass, g the GPU kernel time per pass with its operands available, d the total transfer time for the initial x/y inputs and final y result, and t_launch the launch-related overhead per pass. Ignore overlap and assume these costs remain approximately constant over K passes. Then

\[ T_{\rm CPU}=Kc,\qquad T_{\rm naive}=K(d+t_{\rm launch}+g),\qquad T_{\rm resident}=d+K(t_{\rm launch}+g). \tag{17.2} \]

The naive form copies both x and y into the device and y back on every pass. Recopying unchanged x is deliberately retained as the literal-port baseline. The resident form copies x and initial y once, performs all passes on device, and copies final y back once. Both compute the same recurrence. If an application requires the host to consume or modify intermediate y after every pass, that application has a different communication requirement and cannot remove copies by silently changing its semantics.

The resident GPU wins over this CPU baseline only if its per-pass advantage is positive and large enough to amortize d:

\[ c-g-t_{\rm launch}\gt0,\qquad K\gt\frac{d}{c-g-t_{\rm launch}}. \tag{17.3} \]

If the denominator is zero or negative, increasing K cannot repay the one-time transfer cost under this model. For the Python example's hypothetical c=1 ms, g=0.1 ms, t_launch=0.01 ms, d=2 ms, the threshold is K greater than 2/0.89≈2.247, so three passes are the first winning integer count in that simplified model. A one-pass kernel can lose despite a tenfold kernel-only advantage.

The measured program uses n=1024, 1048576 and 4194304, with K=20. Each size has five trials of the serial CPU implementation, the naive port and the resident port, in that fixed order. Three complete independent captures are retained. CUDA buffers total two arrays, at most 32 MiB. Host initialization and allocation occur before timing. One warmup launch precedes the trials for each size.

Every timed interval uses the host steady clock. GPU intervals include the required input transfers, twenty launches, and final result copies. The CUDA 13.0 API synchronization specification makes the device-to-host copy a completion point for the copied result; all operations use the same default stream. Launch and API errors are checked. Thus the timer cannot stop merely because the host finished enqueueing unfinished work.

All implementations initialize y to one and verify every final entry against 1+40 x_i after timing. The integer-valued binary32 construction makes exact comparison appropriate for these inputs. CPU code is the serial host loop compiled in the same nvcc -O2 build, not a claim about the fastest vectorized or multithreaded CPU implementation. Timings can change with compiler options, thread placement, power management, temperature, display activity and other background work.

The vector kernel assigns global index \(i=b\cdot256+t\), where b is the block index and \(0\le t\lt256\) is the invocation's block-local index. Launching \(\lceil n/256\rceil\) blocks covers every integer index below n exactly once by quotient and remainder. The final block's excess invocations check \(i\lt n\) before accessing an array. Each invocation updates only y_i while all read the immutable x array; launches in the same stream order successive passes of the recurrence.

At 1048576 elements, CPU time ranged 8.897–33.441 ms, resident time 3.983–9.556 ms, and naive GPU time 59.460–111.963 ms. The CPU and resident ranges overlap across captures, so these summaries do not establish that every resident trial beat every CPU trial. They do establish that moving the arrays every pass was expensive in this experiment. A ratio of unrelated extreme timings should not be presented as a paired measured speedup.

At 4194304 elements, the ranges were 66.519–128.684 ms for CPU, 220.417–485.462 ms for the naive port, and 15.595–28.741 ms for the resident port. The reported resident range lies entirely below the CPU range, while the naive range lies above it. The result is a stronger statement than “the GPU is faster”: the same GPU loses or wins depending on the data-lifetime decision, even though its nominal scalar peak is unchanged.

For that largest size, twenty passes perform 167772160 flops. The logical host-device traffic falls from 1006632960 bytes in the naive version to 50331648 bytes in the resident version, a factor of twenty. Those are algorithmic transfer counts, not measured PCIe payload counters. The timing differences include launch/runtime behavior and host-memory staging; they do not isolate a physical-link bandwidth.

The arithmetic intensity also explains why peak arithmetic alone is an unsuitable predictor. At 1/6 flop per logical device-memory byte, sustaining 6.144 TFLOP/s would require 36.864 TB/s under that traffic model. The query does not measure memory bandwidth, so it cannot supply the missing bandwidth bound. More generally the roofline model \(P(I)\le\min(P_{\rm peak},I B_{\rm peak})\), with B_peak a stated memory-bandwidth ceiling, asks which resource could limit useful throughput before treating a large flop/s number as an attainable application rate.

The same residency decision applies to the book's Jacobi solver: keep u and unew on device through multiple sweeps, preserve the ordering between sweeps, and return only the information the host actually needs at each decision point. That is an implementation direction, not a claim that the recurrence program is already a CUDA Jacobi solver. Later chapters construct and verify the stencil kernel, memory organization and stopping logic.

What the architecture model and local checks establish

The five programs answer bounded questions: whether the installed stack can execute a checked kernel; which properties one actual device reports; whether fused rounding differs from separate arithmetic on a chosen input; whether the unit/count formulas reproduce their stated inputs; and whether residency changes end-to-end time for one affine recurrence. They do not independently measure all vendor peaks, determine an Intel device's throughput, or establish multi-GPU interconnect behavior.

Six worked exercises

1. Derive a PCIe ceiling without mixing directions

A PCIe 4.0 link has eight active lanes. Compute its coding-limited one-direction rate using 16 GT/s and 128b/130b encoding. How long would a 64 MiB payload require at that ceiling, excluding all transaction and software overhead? Why is summing both directions invalid for this one-way copy?

Solution

The per-lane byte rate is 16×10⁹×(128/130)/8=1.969230769×10⁹byte/s. Eight lanes give 15.753846154 GB/s. A 64 MiB payload has 64×1048576=67108864 bytes, so the ceiling-based time is 67108864/15753846154≈0.004260 seconds, or 4.260 ms. This is an optimistic coding-only time, not a measured transfer prediction. Full duplex permits a separate reverse-direction stream; it does not give this unidirectional payload access to twice the forward lanes. Headers, flow control, routing and memory/software effects increase real time.

2. Compute enabled scalar peaks and identify a misleading numerator

Compare a full GV100 diagram's 84 SMs with an 80-SM V100 product, using 64 FP32 lanes per SM and 1.530 GHz. Compute both FMA-model peaks and the relative overestimate from using the full diagram. Does an 8 Tensor-Core-per-SM count repair that mistake?

Solution

The enabled product has 80×64=5120 FP32 lanes, giving 5120×2×1.530 GHz=15.6672 TFLOP/s. Substituting 84 gives 5376 lanes and 16.45056 TFLOP/s. The relative overestimate is 84/80−1=0.05, or 5%. Tensor Core count is a different resource and cannot fix an incorrect scalar-lane count. A matrix-unit peak requires supported formats, tile operations and per-unit work rates; adding its count directly to FP32 lanes mixes units.

3. Diagnose the register-width throughput assumption

A proposed Xe-HPC model divides 512 bits by 64 bits, multiplies eight vector engines and two FMA operations, and predicts 128 FP64 operations per core per cycle. The dated vendor guide gives 256. Which factor is missing? What conclusion can and cannot be drawn from the discrepancy?

Solution

The arithmetic correctly counts eight 64-bit elements in 512 bits. Its throughput prediction additionally assumes one such vector-sized operation per engine per cycle. In the dimensional model v(w/b)o q_b, the prediction silently sets q_b=1. The vendor rate corresponds to an effective factor 256/(8×8×2)=2 relative to that representation-based accounting. This proves that representation width alone does not determine throughput. It does not by itself establish a specific physical dual-issue design or instruction schedule; those would require additional microarchitectural evidence.

4. Bound residency from three independent resources

An illustrative SM has 65536 register slots, 100 KiB of available shared memory and a 1536-thread resident limit. A block uses 256 threads, 32 registers per thread and 20 KiB shared memory. Ignore allocation granularity and the architecture's separate block-count limit. Find each bound and the resulting resident-thread fraction.

Solution

A block uses 256×32=8192 register slots, so registers permit floor(65536/8192)=8 blocks. Shared memory permits floor(100/20)=5 blocks. The thread limit permits floor(1536/256)=6 blocks. Their minimum is 5 blocks, containing 1280 threads, or 1280/1536=5/6≈83.33% of the thread limit. This is an upper bound under the assumptions, not a measured occupancy. Allocation granularity or a separate block limit can reduce it, and 83.33% residency is not 83.33% of peak arithmetic throughput.

5. Choose when data residency changes the decision

Use c=1 ms, g=0.1 ms, t_launch=0.01 ms, d=2 ms. Find the first integer K for which resident offload wins over the CPU model. Compare the naive and resident times at K=20. Give an application requirement that would invalidate removing the intermediate copies.

Solution

The per-pass advantage is 1−0.1−0.01=0.89 ms. Residency wins when K> 2/0.89≈2.247, so the first integer is 3. At K=20 the CPU model takes 20 ms, the naive GPU takes 20(2+0.01+0.1)=42.2 ms, and the resident GPU takes 2+20(0.01+0.1)=4.2 ms. These are hypothetical model times, not fitted measurements. If the host must inspect y and change x after every pass, keeping all intermediate values exclusively on device changes the application contract; a different coordination/data-flow design is needed.

6. Implement a complete offload timing contract

Extend the recurrence comparison to another bounded K and n. State how to preserve an exact result check, how to define comparable timed intervals, and what evidence would be needed before claiming a kernel-only or physical-link bandwidth improvement.

Solution

Choose K=8 and n=65536, retaining \(x_i=i\bmod17\) and initial \(y_i=1\). The exact result is \(y_i=1+16x_i\), bounded by 257, so every intermediate integer is exactly representable in binary32. There are 3855 complete cycles of residues zero through sixteen plus one final zero. Thus \(\sum_i x_i=3855\cdot136=524280\) and \(\sum_i y_i=65536+16\cdot524280=8454016\). This checksum is a supplementary diagnostic; verify every entry against the closed form.

The extension performs 1048576 flops. Its two device arrays occupy 524288 bytes, while logical host traffic is 6291456 bytes for eight naive rounds and 786432 bytes for one resident round. In the existing complete program set k=8, replace the size list by {size_t(65536)}, and change the printed literal passes=20 to passes=8. The existing verify(x,y,k) already uses the selected pass count, so its result formula follows that change. The launch/transfer/error-check structure remains applicable. Keep integer-valued binary32 inputs small enough that every intermediate result remains exactly representable. Preserve the same recurrence in CPU, naive and resident versions. Initialize and allocate outside every timed interval or include them consistently in all three; state the choice. Include all required transfers, launches and a checked completion point before stopping the GPU wall timer. Use warmups and several retained captures, and report actual ranges rather than ratios built from unrelated best cases.

For a kernel-only claim, use an appropriate stream-ordered device event interval or an explicitly synchronized interval that excludes copies, with enough work to exceed timer resolution. For a physical-link claim, record negotiated generation/width, direction, payload size, host-memory type and transfer protocol, and measure an isolated transfer rather than dividing all bytes by a whole offload interval. The current comparison changes data lifetime and counts host traffic; it does not isolate those other quantities.
