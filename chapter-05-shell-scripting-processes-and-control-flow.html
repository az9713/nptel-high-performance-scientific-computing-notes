Shell scripting: processes, input, and control flow

A parameter sweep runs the Jacobi solver of this book for four grid sizes, \(N=16,32,64,128\), with tolerance \(10^{-6}\) and an iteration limit of 5000. A script that ignores the exit status of the solver prints four lines with 515, 1657, 5000 and 5000 iterations; its own exit status is that of its last run only. Two of the four runs, \(N=64\) and \(N=128\), stopped at the limit with final changes of \(1.4\times10^{-6}\) and \(2.9\times10^{-5}\), which are 1.4 and 29 times the tolerance. Nothing in the output tells the reader which lines are results and which are failures. The disk-monitoring script of the second lecture has a second, unrelated cost: by the count derived in this chapter, its loop creates 7 processes for each line of the df table, and on this machine a 300-line table took between 0.7 and 1.7 s in that loop in four runs, while one awk process took 0.001 to 0.003 s, mostly its own start-up. This chapter defines the model in which a shell script runs, with processes, an environment, and an exit status for every command. It derives what each construct of the two lectures does inside that model, tests the lectures' statements with 12 verified listings, and builds the sweep script that records every outcome.

The objects of the chapter and the running case

The chapter studies programs written in the language of the shell, and it describes them with four kinds of object. All four are defined here and used unchanged in every later section.

Processes. A process is a running instance of a program. It has a process identifier (PID), a parent process, an address space, a working directory, a set of open files, a file-creation mask, and an environment: a finite list of name–value pairs of strings that the process received when its program started. Three system calls create, replace and collect processes. fork creates a copy of the calling process. exec replaces the program of the calling process with another program and gives the new program its argument list and its environment (execve(2), Linux man-pages 6.19 of 2026-02-08, "DESCRIPTION": the arrays argv and envp are "passed as the environment of the new program"). wait lets a parent obtain the termination status of a child. Chapter 2 treats these calls; this chapter needs only these three.

Shell execution environments. A shell is a program that reads text, splits it into words, performs expansions on the words, and runs the commands that result. A shell script is a file of such text. The POSIX standard lists what a shell execution environment contains (POSIX.1-2017, Shell Command Language, §2.12): open files, the working directory, the file-creation mask, traps, shell parameters and variables, functions, options, and aliases. This chapter tracks one part of it, the set \(V\) of shell variables, each a pair of a name and a string, together with the set \(X\) of names that carry the export attribute (the symbol \(X\) is local to this chapter). The set \(X\) matters because the standard states that the variables with the export attribute are the ones passed to a command that the shell starts (§2.12, "Variables with the export attribute, along with those explicitly exported for the duration of the command, shall be passed to the utility environment variables").

Commands and their three execution modes. A simple command is a list of words after expansion; the first word is the command name and the others are its arguments (§2.9.1). Bash resolves the name in this order (GNU Bash manual 5.3, §3.7.2): a shell function, then a shell builtin, then, for a name without a slash, the first executable file with that name in the directories listed in PATH. POSIX §2.9.1 puts the special built-ins (export, return, set, . and others) ahead of functions, and Bash follows that order in its POSIX mode (a function named export is accepted by Bash and rejected by bash --posix with "is a special builtin"). A function or a builtin runs inside the shell process and creates no process. An external program runs as a new process: the shell forks, the child execs the program with the exported variables as its environment, and the shell waits. A subshell environment is a duplicate of the shell's execution environment; Bash builds it as a forked copy of the shell process that does not exec (Bash manual §3.7.3), and this chapter calls such a process a subshell. The standard requires a subshell environment for command substitution, for commands grouped in parentheses, for background commands, and for every stage of a multi-stage pipeline, where the standard allows an implementation to run some or all stages in the current environment instead (§2.12). The standard states the key property of a subshell: "Changes made to the subshell environment shall not affect the shell environment."

Exit status. Every command ends with an exit status, a small non-negative integer. The convention has these fixed points: 0 means success; 127 means the command was not found; 126 means the file was found but cannot be executed; a command that a signal with number \(k\) terminated reports a value above 128, and Bash uses \(128+k\) (§2.8.2; Bash manual §3.7.5). Conditions in if and while test an exit status, not a Boolean expression. This is the most consequential fact of the chapter and Section "Exit status" derives its consequences.

Two relations summarise the model. A child process starts with the environment

\[ E_{\text{child}}=\{(n,v)\in V:\ n\in X,\ n\notin\operatorname{names}(A)\}\ \cup\ A,\tag{5.1} \]

where \(A\) is the set of assignments written in front of the command (NAME=value command); an assignment in \(A\) overrides an exported variable of the same name. Nothing the child does to its own copy changes \(V\) or \(X\) of the parent. Information reaches the parent from a child only through the exit status, through files, pipes and other output that the child writes, and through signals; the next sections check each consequence of (5.1) with a run. The second relation concerns cost. Let \(\kappa\) be the wall-clock time to create one process and wait for it to end. A construct that creates \(P\) processes costs about \(P\kappa\) on top of the work in those processes, and the construct does not appear to a reader of the script as a process creation at all. The section on the monitoring script derives \(P\) for the lecture's loop and measures \(\kappa\).

The running case is a parameter sweep. The solver is the Jacobi iteration of the book's heat problem (jacobi_step, u, unew, N, tol, max_iter; chapter 9 derives the method; this chapter treats the program as a black box). Its command line is ./jacobi N tol max_iter. It prints one line N iterations change, where change is the largest change of any interior value in the last sweep, and it exits with status 0 if change fell below tol, with status 2 if max_iter sweeps ran first, and with status 64 for bad arguments. The sweep script must run the solver for a list of grid sizes, record one row per run, and report honestly which runs failed. That specification needs every construct of the two lectures: scripts and their interpreter line, variables, quoting, read or arguments, if and case on exit statuses, for loops, functions, and pipelines with awk.

A script is a file of commands: the interpreter line, the execute bit and three ways to run it W2L1 1:45

The lecture defines a shell script as a file that contains a series of commands, executed by the shell, which it calls the command interpreter of Linux. It lists the uses that motivate scripts on HPC systems: automating repetitive tasks, monitoring a system, batch processing, manipulating data and taking backups. It names the shells that exist (Bash, sh, Zsh, Ksh, Csh, Tcsh, dash, fish) and the properties that distinguish them (ease of use, scripting power, customization, performance, portability), and it chooses Bash for the course. The workflow it demonstrates has four steps: create hello.sh in an editor, put #!/bin/bash on the first line followed by echo "Hello, World", make the file executable with chmod +x, and run ./hello.sh. The lecture says the extension .sh is a convention that marks a shell script, and that the first line states which shell the script uses.

The model of the previous section turns this workflow into three different mechanisms, and the lecture presents only the first.

Direct execution, ./hello.sh. The command name contains a slash, so the shell skips the search through PATH and asks the kernel to execute the file (POSIX §2.9.1, "Command Search and Execution"). The kernel's execve accepts a file that has execute permission and is either a binary executable or a text file whose first line has the form #!interpreter [optional-arg]. For such a file it runs interpreter [optional-arg] path arg..., so the interpreter receives the script's path as an argument and reads the script itself (execve(2), "Interpreter scripts"). The kernel, not the shell, reads the #! line, and the kernel does not look at the extension. The interpreter line is therefore a property of direct execution only. POSIX leaves its meaning open: "If the first line of a file of shell commands starts with the characters "#!", the results are unspecified" (§2.1). On Linux the entire text after the interpreter name is passed as one argument, and the text after #! is limited to 255 characters since Linux 5.1 and to 127 before (execve(2), Linux-specific notes on interpreter scripts).

Running through an interpreter, bash hello.sh. Here bash is the program that the kernel executes and hello.sh is only an argument. The kernel checks the execute bit of bash, not of hello.sh; Bash needs read permission on the script. The first line is then an ordinary comment, because # starts a comment in the shell language.

Sourcing, . ./hello.sh. The builtin . (also spelled source in Bash) reads the commands of the file and runs them in the current shell. No process is created, so the script can change the variables, the working directory and the function definitions of the caller. Every script run by the first two mechanisms is a child process and cannot.

The listing below runs one child script through all three mechanisms and reports whether the child's process identifier equals the caller's. The caller exports its own PID as CALLER, and the child compares $$, the PID of the shell that executes it, with that value. It then removes the execute bit to show that the second mechanism still works and the first fails with status 126, and it runs a script that has no interpreter line. The script needs a file system with real permission bits, so it works in a directory under /tmp. Every line of its output is deterministic.

#!/bin/bash
# exec_modes.sh: run one child script in four ways and report what each way does.
work=$(mktemp -d) && cd "$work" || exit 1       # a real Linux file system: chmod works here

cat > child.sh <<'END'
#!/bin/bash
if [ "$$" = "$CALLER" ]; then echo "same process as the caller"; else echo "new process"; fi
END
chmod +x child.sh
export CALLER=$$                                  # the caller's process id, exported to children

printf '%-22s' "./child.sh";       ./child.sh
printf '%-22s' "bash child.sh";    bash child.sh
printf '%-22s' ". ./child.sh";     . ./child.sh
chmod -x child.sh
printf '%-22s' "bash child.sh (-x)"; bash child.sh
./child.sh; echo "status of ./child.sh without the x bit: $?"

printf 'echo "no shebang line"\n' > plain.sh; chmod +x plain.sh
./plain.sh; echo "status of ./plain.sh: $?"
cd / && rm -rf "$work"

bash child.sh         new process
. ./child.sh          same process as the caller
bash child.sh (-x)    new process
status of ./child.sh without the x bit: 126
no shebang line
status of ./plain.sh: 0

The output matches the model. ./child.sh and bash child.sh run the child in a new process. The sourced script reports "same process as the caller". Without the execute bit, bash child.sh still runs, and ./child.sh fails with "Permission denied" and status 126, the code that §2.8.2 reserves for a file that is found but not executable. The script plain.sh has no interpreter line and ran with status 0, although a direct execve of such a file fails with ENOEXEC. The shell handles that failure itself: POSIX §2.9.1 and Bash manual §3.7.2 state that when the execution fails because the file is not in executable format, the shell assumes it is a shell script and runs it with a shell. The fallback hides a missing interpreter line, and the interpreter it picks depends on the caller. Bash runs the file with Bash. Programs that start commands through the C library's execvp or execlp (for example env and find -exec) also catch ENOEXEC, but they run the file with /bin/sh, which is dash on Ubuntu (execvp(3), DESCRIPTION: "these functions will execute the shell (/bin/sh) with the path of the file as its first argument"). A separate test on this machine used a file plain.sh that prints $BASH_VERSION and has no interpreter line. ./plain.sh printed 5.2.21(1)-release; env ./plain.sh and find . -name plain.sh -exec {} \; printed an empty value, so dash ran it, and all three ended with status 0. A program that calls execve directly gets the error: Python's subprocess.run(["./plain.sh"]) raised OSError: [Errno 8] Exec format error. A script written in Bash therefore needs its #!/bin/bash line.

The next listing checks the statements about the interpreter line directly. The first script has the interpreter /bin/cat and a file name that does not end in .sh; if the kernel reads the line and passes the script's path, executing it must print the file. The second script uses the common but non-portable form #!/usr/bin/env bash -e, which tests the Linux rule that everything after the interpreter name is one argument. The third uses #!/usr/bin/env bash, which finds bash through PATH. The listing sets LC_ALL=C so that the error text has a fixed wording and sends the error output to the same stream as the standard output so that the captured output contains it.

#!/bin/bash
# interp_line.sh: the kernel, not the shell, reads the "#!" line of an executed script.
export LC_ALL=C                                   # fixed wording of error messages
work=$(mktemp -d) && cd "$work" || exit 1

printf '#!/usr/bin/env bash\necho "bash found through PATH: $0"\n' > via_env.sh

Executing show.txt prints its own two lines: the kernel started /bin/cat with the script's path, as execve(2) describes, and the extension played no part. The second script fails with status 127, because env received the single argument bash -e and searched for a program of that name; the message of GNU env names the remedy, the -S option. The third script works, and it reports ./via_env.sh as $0. The cost of env is that the script now runs whichever bash comes first in the caller's PATH; the section on PATH shows how a user changes that. Scripts for a scheduler need extra care for this reason. The Slurm manual states that #SBATCH lines are read by Slurm and are comments to the shell: "#SBATCH directives are read directly by Slurm, so shell-specific syntax including variable names will be read as literal text. Once the first non-comment, non-whitespace line has been reached in the script, no more #SBATCH directives will be processed" (Slurm sbatch manual, "DESCRIPTION", page of version 26.05, retrieved 2026-10-26). A batch script is thus the kind of file this section describes, with a second reader of its comment lines. Chapter 30 treats schedulers.

Command substitution and arithmetic expansion W2L1 10:00

The lecture's second example prints Date is: $(date) and shows that the shell replaces $(date) with the current date, and its third example prints 5 + 2 = $((5 + 2)) and obtains 5 + 2 = 7. It says that a $ followed by brackets makes the interpreter run something, and that the dollar sign has several uses that appear later. The two forms are different expansions with different costs.

Command substitution, $(command), runs the command in a subshell and replaces the text $(command) with the standard output of the command, after removing all newlines at the end of the output (POSIX §2.6.3). Embedded newlines stay, and unless the substitution is in double quotes they are later treated as separators between words. The subshell is a forked process, which has two consequences that the next sections use. Whatever the command assigns to variables is lost when the subshell ends (the last line of the output of env_demo.sh in the next section shows it), and the substitution costs one process creation, which Section "The monitoring script" prices.

Arithmetic expansion, $((expression)), evaluates an integer expression inside the shell. POSIX requires only signed integer arithmetic of the C type long and allows extensions (§2.6.4). Bash evaluates "in the largest fixed-width integers available, with no check for overflow, though division by 0 is trapped" (Bash manual §6.5), with the operators and precedence of the C language, and it reads a constant with a leading 0 as octal. On this machine the integers have 64 bits. Let \(w=2^{64}\). Then the value of every addition, subtraction, multiplication, exponentiation and left shift is the true result reduced to the interval \([-w/2,\,w/2)\) by adding or subtracting multiples of \(w\):

\[ \operatorname{wrap}(z)=z-w\left\lfloor \frac{z+w/2}{w}\right\rfloor,\qquad w=2^{64}. \tag{5.2} \]

Division truncates toward zero, as in C, so that \(-7/2=-3\), and the remainder takes the sign of the dividend. Equation (5.2) predicts \(2^{62}=4\,611\,686\,018\,427\,387\,904\), which is below \(w/2=2^{63}\), \(\operatorname{wrap}(2^{63})=-2^{63}\), and \(\operatorname{wrap}(2^{64})=0\). A variable that holds text is evaluated as an expression when it is named inside $((…)), which the manual states ("The value of a variable is evaluated as an arithmetic expression when it is referenced"); a variable that is expanded with a dollar sign is replaced by its text first. If x holds 1+1, then $((x * 3)) is \((1+1)\cdot3=6\) and $(( $x * 3 )) is \(1+1\cdot3=4\). The listing checks each statement, and it feeds three invalid expressions to a fresh shell to show how the errors read. The output is deterministic, with the shell's own prefix of script name and line number removed by sed.

#!/bin/bash
# arith.sh: what $(...) and $((...)) compute, and where $((...)) surprises.
echo "5 + 2 = $((5 + 2))"
echo "7 / 2 = $((7 / 2)),  -7 / 2 = $((-7 / 2)),  7 % 3 = $((7 % 3))"
echo "2**62 = $((2 ** 62)),  2**63 = $((2 ** 63)),  2**64 = $((2 ** 64))"
x='1+1'
echo "x='1+1':  \$((x * 3)) = $((x * 3));   \$(( \$x * 3 )) = $(( $x * 3 ))"
echo "date of the epoch plus one day: $(date -u -d @86400 +%F)"
for expr in '08 + 1' '1.5 + 1' '1 / 0'; do
    printf '%-8s -> ' "$expr"
    bash -c "echo \$(( $expr ))" 2>&1 | sed 's/^bash: line [0-9]*: //'
done
# a number read from a user with a leading zero is octal
n=010
echo "n=010; \$((n + 1)) = $((n + 1)); \$((10#\$n + 1)) = $((10#$n + 1))"

Every prediction holds: \(2^{62}\) is exact, \(2^{63}\) becomes \(-9\,223\,372\,036\,854\,775\,808\), \(2^{64}\) becomes 0, and \(-7/2\) is \(-3\). The value of x='1+1' is 6 by name and 4 by text. The constant 08 is an error because a leading 0 selects octal and 8 is not an octal digit; the constant 010 is 8, so $((n + 1)) with n=010 is 9, and the prefix 10# forces base 10 and gives 11. A decimal fraction is a syntax error: the shell has no floating-point arithmetic, so a script that needs one calls awk or bc, as the monitoring script of the lecture calls awk.

The consequence for scripts that read numbers from users is concrete. The lecture's addition script reads num1 and num2 and prints $((num1 + num2)). A user who types 08 gets the error above, a user who types 1+1 gets the sum of 2 and the second number, and a user who types a number above \(2^{63}-1\) gets a wrapped result with no message. The boundary of the lecture's example is therefore the set of inputs that are decimal integers without a leading zero and below \(2^{63}\); the section on read shows how to enforce it.

Variables, the environment and child processes W2L1 13:52

The lecture defines a variable as an entity that stores a number or a string for later use in the script. Its first example assigns name="Pitter" and prints "Hello, $name!"; its second assigns the output of a command, current_time=$(date +%T), and prints it (the slide's terminal shows 07:58:11). The syntax has a rule that the lecture does not state and that decides whether the examples work: an assignment is one word, name=value, with no blank on either side of the equals sign. The shell recognises an assignment only in that form (POSIX §2.9.1). The session below runs the failures, and then the quoting rules of POSIX §2.2 and §2.6.5 to §2.6.6: the result of an unquoted expansion is split into words at blanks and then expanded as a filename pattern, and double quotes prevent both, while single quotes also prevent the expansion of $. Each command was run in a fresh shell; the shell's prefix with the line number was shortened to bash:.

With spaces around =, the shell runs a command called name with the arguments = and Pitter, and reports status 127. In greeting=hello world, the assignment is a prefix of the command world, which does not exist. The unquoted $f became the two words run and 16.dat, so [ received -f run 16.dat and failed with status 2, while "$f" stayed one word and the test succeeded. The rule that follows is mechanical: put every expansion of a variable in double quotes unless splitting is the intention. The lecture's scripts quote the variables in their echo lines and do not quote them in the tests of the second lecture ([ $num -gt 5 ]); the section on exit status shows what that costs.

The environment. The lecture shows env, which lists the variables of the terminal, and introduces export with two variables: NAME1=Rakesh without export and export NAME2=Mahesh. Its slide states that the first is set "in current shell session only, but not available in child processes" and the second is available. The demonstration has a script var4.sh that sets both variables and runs bash child.sh, and the child's output shows Name1 = empty and Name2 = Mahesh (slide at W2L1 24:15). The lecture calls the script that starts another script the parent and the started script the child. This is exactly rule (5.1) of the model: the child starts with the exported variables, and the other variables of the parent do not exist for it.

Rule (5.1) has more consequences than the lecture's example, and each one can be tested. (a) A child that changes an inherited variable changes only its own copy. (b) An assignment in front of a command, NAME3=once ./child.sh, puts NAME3 into the environment of that command only (POSIX §2.9.1; Bash manual §3.7.4). (c) env is an external program, so it prints its own environment, which is the exported subset \(X\); set is a builtin that prints all variables. (d) unset removes a variable from \(V\), and with it from \(X\). (e) A subshell is a copy, so assignments inside $( … ) are lost when it ends. The listing runs all five; the child script lives in a temporary directory, and declare -p prints the export attribute of each variable.

#!/bin/bash
# env_demo.sh: which variables a child process receives, and what it can change.
work=$(mktemp -d) && cd "$work" || exit 1
cat > child.sh <<'END'
#!/bin/bash
echo "  child sees: NAME1=[$NAME1] NAME2=[$NAME2] NAME3=[$NAME3]"
NAME2=changed_by_child                       # a change inside the child
END
chmod +x child.sh

NAME1=Rakesh                                  # shell variable, not exported
export NAME2=Mahesh                           # exported: part of the environment of children
echo "parent before:"; ./child.sh
echo "  parent after the child ran: NAME2=[$NAME2]"
echo "prefix assignment on one command:"; NAME3=once ./child.sh
echo "  parent afterwards: NAME3=[$NAME3]"

echo "env lists NAME1? $(env | grep -c '^NAME1=')    env lists NAME2? $(env | grep -c '^NAME2=')"
echo "set lists NAME1? $(set | grep -c '^NAME1=')    set lists NAME2? $(set | grep -c '^NAME2=')"
declare -p NAME1 NAME2

POSIX gives the exact semantics (§2.9.4). A for loop first expands the list of words after in into items and then runs the body once per item with the variable set to that item. A while loop runs its condition list, stops if the status is non-zero, runs the body, and repeats. The rule of choice follows: for iterates over a list that exists before the first iteration, and while re-evaluates a command before every iteration. The count of iterations of the lecture's while loop can be derived. Let the loop be while [ $c -le b ]; do …; c=$((c + d)); done with an integer step \(d\gt0\), a bound \(b\) and start value \(c_0\). Iteration \(k=0,1,2,\dots\) runs exactly when \(c_0+kd\le b\), that is \(k\le (b-c_0)/d\). The number of such \(k\) is

\[ n_{\text{iter}}=\max\!\left(0,\ \left\lfloor\frac{b-c_0}{d}\right\rfloor+1\right). \tag{5.4} \]

The quantity \(b-c\) is an integer that decreases by \(d\) in every iteration, so the loop ends. If the body forgets the update of c, that argument fails, and the loop runs forever. Equation (5.4) predicts 5 iterations for \(c_0=1\) with \(b=5\) and \(d=1\), 3 iterations for \(c_0=3\), and none for \(c_0=6\). A function runs in the current shell. Bash resolves a function name before a builtin and before a file (Bash manual §3.7.2; POSIX §2.9.1 keeps the special built-ins ahead of functions), replaces the positional parameters $1, $2 during the call, and runs the body without creating a process. Two properties follow from the model of the first section, and the lecture's examples contain both. Variables are global. The function add sets sum in the caller's environment, because the body runs in the caller's shell; local limits a variable to the function and its callees (Bash manual, local). Results travel by status or by output. return n sets the status of the call to \(n \bmod 256\) by (5.3), and the standard leaves a value above 255 unspecified (POSIX, return, "EXIT STATUS"). The lecture's claim that return returns the value of the sum holds only for sums from 0 to 255. A function that must return a larger number or a string writes it to standard output and the caller captures it with $(…), which costs a subshell.

The recursion of the factorial adds a cost and a range limit. Each call of factorial runs inside a command substitution, so each level of recursion is a new subshell: factorial 5 runs in 5 processes, one per call. The values have the range limit of (5.2). The product \(n!\) exceeds \(2^{63}-1\) at \(n=21\), where \(21!=51\,090\,942\,171\,709\,440\,000\) and \(\operatorname{wrap}(21!)=21!-3\cdot2^{64}=-4\,249\,290\,049\,419\,214\,848\). The result becomes 0 at a definite \(n\): by Legendre's formula, the exponent of 2 in \(n!\) is \(\sum_{i\ge1}\lfloor n/2^i\rfloor\), because \(\lfloor n/2^i\rfloor\) counts the multiples of \(2^i\) up to \(n\), each of which adds one factor 2. If \(n=\sum_j b_j2^j\) with bits \(b_j\), then \(\lfloor n/2^i\rfloor=\sum_{j\ge i}b_j2^{j-i}\), and the sum over \(i\ge1\) is \(\sum_j b_j(2^j-1)=n-s_2(n)\), where \(s_2(n)=\sum_j b_j\) is the number of 1 bits of \(n\). So the exponent is \(n-s_2(n)\), and \(n!\equiv0\pmod{2^{64}}\) as soon as that exponent is at least 64. For \(n=65=1000001_2\) the exponent is \(65-2=63\), so \(65!\equiv2^{63}\pmod{2^{64}}\) and the wrapped value is \(-2^{63}\); for \(n=66=1000010_2\) it is \(66-2=64\), so the result is 0. Three statements of this reading need correction or measurement. First, the loop does not monitor continuously. It runs once for each line of one df table and ends when the table ends. Each run of the script is a single check. Monitoring over time needs a second loop around it with a delay, or a scheduler that starts the script periodically. Second, the script assumes that the use column is a number followed by %. With df -a, pseudo filesystems such as /proc print - as their use (checked on this machine), and then [ $usage -ge $THRESHOLD ] is an error by the rules of the section on exit status. Third, the script is expensive for what it does. To count what the loop costs, count the processes. A command substitution runs in a subshell, which is one process; the pipeline inside it has one process per stage, and Bash runs each stage of a pipeline in its own forked process (Bash manual §3.2.3). The echo is a builtin but, as a pipeline stage, runs in a forked process. A command substitution with a pipeline of \(k\ge2\) stages therefore creates \(1+k\) processes, and a loop that runs it for \(R\) input lines (records) creates

\[ P=R\sum_{j}(1+k_j)\quad\text{processes, with } k_j \text{ the stages of the } j\text{-th substitution}. \tag{5.5} \]

For the lecture's loop the two substitutions have \(k=3\) (echo | awk | sed) and \(k=2\) (echo | awk), so \(P=R(4+3)=7R\); the [ test and the arithmetic of the loop add none. A single awk process that reads the table and compares the numbers needs one process in total. The listing counts the processes directly, from the PIDs of two probe processes that bracket the command: Linux assigns process identifiers in sequence, so the difference of the two probes, minus the identifiers that one probe consumes, is the number of processes created in between. The count is exact only if nothing else on the system starts a process or a thread in the meantime, which is why the timing and counting listing is checked by its return code. The listing also measures \(\kappa\), the cost of creating one process and waiting for it, as the time of 1000 runs of /bin/true, and it compares the lecture's loop with one awk on a table of 300 lines. The printed output is one sample run on this machine; four runs gave a loop time of 0.67 to 1.66 s, \(\kappa\) of 0.59 to 0.81 ms, and an awk time of 0.001 to 0.003 s.

The parameter sweep: every construct together

This section builds the running case with the constructs of the two lectures, and with two that the lectures do not treat, case and background processes with wait. The specification is the one in the first section: run ./jacobi N tol max_iter for a list of sizes, record one row per run with the iteration count, the final change and a label, and report failure through the exit status of the sweep.

Why the naive script is wrong. The first loop of the listing below runs the solver for each size and prints its output. It has the form of every sweep script that a beginner writes, and it fails silently for two of the four sizes. The reason is stated by the model: the output of a command is data and the exit status is a separate channel, and a loop that only prints the output discards the channel that carries the failure. The exit status of the solver is available in $? only until the next command runs, because each command overwrites it (POSIX §2.5.2: ? expands to the exit status of the most recent pipeline). The function run_case therefore reads $? as the very next command after the substitution. The variables are declared on a line of their own, local n=$1 out status label, and assigned on the next lines, because local out=$(…) would return the status of local (the result of the section on functions).

The function maps the status to a label with a case statement (0 to converged, 2 to iteration_limit, everything else to error), splits the output of the solver into positional parameters with set -- $out, and writes one row to its own file rows/N.csv. The files exist because of the process model. A second part of the script runs the same cases as background processes with & and collects their statuses with wait. A background command runs in a subshell, so a variable that run_case sets there is lost (rule (5.1), and the pipeline result of the section on loops), and only a file survives. The Bash manual states what wait returns: "the exit status of the last id", where each id is a process identifier. The script saves $!, the PID of the last background command, in a list, and it calls wait for each in turn. Finally, the script collects the rows in numeric order of \(N\) with sort -t, -k1,1n and compares the CSV files of the two modes with cmp. It ends with exit 1 if any row has the label iteration_limit, so that a caller, for example a batch script or make, sees the failure. The script contains its own copy of the solver source, jacobi_cli.c, and builds it with gcc -O2; the solver is the book's serial Jacobi kernel with the canonical IDX layout, the top edge held at 1 and the other edges at 0.

#!/bin/bash
# sweep.sh: run the Jacobi solver for several grid sizes and collect one CSV row per run.
# The solver contract: "./jacobi N tol max_iter" prints "N iterations change" and exits with
#   0 = converged, 2 = iteration limit reached, 64 = bad arguments.
work=$(mktemp -d) && cd "$work" || exit 1
TOL=1e-6; MAX_ITER=5000; SIZES="16 32 64 128"

build_solver() {
cat > jacobi.c <<'END'
#include <stdio.h>
#include <stdlib.h>
#include <math.h>

#define IDX(i, j) ((i) * (N + 2) + (j))

static double jacobi_step(int N, const double *u, double *unew)
{
    double change = 0.0;
    for (int i = 1; i <= N; i++)
        for (int j = 1; j <= N; j++) {
            unew[IDX(i, j)] = 0.25 * (u[IDX(i - 1, j)] + u[IDX(i + 1, j)]
                                    + u[IDX(i, j - 1)] + u[IDX(i, j + 1)]);
            double d = fabs(unew[IDX(i, j)] - u[IDX(i, j)]);
            if (d > change) change = d;
        }
    return change;
}

int main(int argc, char **argv)
{
    if (argc != 4) { fprintf(stderr, "usage: %s N tol max_iter\n", argv[0]); return 64; }
    int N = atoi(argv[1]), max_iter = atoi(argv[3]);
    double tol = atof(argv[2]);
    if (N < 1 || max_iter < 1 || !(tol > 0.0)) { fprintf(stderr, "bad argument\n"); return 64; }
    size_t cells = (size_t)(N + 2) * (N + 2);
    double *u = calloc(cells, sizeof *u), *unew = calloc(cells, sizeof *unew);
    for (int j = 0; j < N + 2; j++) u[IDX(0, j)] = unew[IDX(0, j)] = 1.0;   /* top edge u = 1 */
    int iter = 0;
    double change = 1.0;
    while (iter < max_iter && change >= tol) {
        change = jacobi_step(N, u, unew);
        double *t = u; u = unew; unew = t;
        iter++;
    }
    printf("%d %d %.3e\n", N, iter, change);
    free(u); free(unew);
    return change < tol ? 0 : 2;
}
END
    gcc -O2 -o jacobi jacobi.c -lm || exit 1
}

    for n in $SIZES; do ./jacobi $n $TOL $MAX_ITER; done
}

run_case() {                          # run_case N: write one CSV row to rows/N.csv, return the solver status
    local n=$1 out status label
    out=$(./jacobi "$n" "$TOL" "$MAX_ITER"); status=$?    # status of the solver, not of "local"
    case $status in
        0) label=converged ;;
        2) label=iteration_limit ;;
        *) label=error ;;
    esac
    set -- $out                       # split "N iterations change" into $1 $2 $3
    echo "$n,${2:-NA},${3:-NA},$label" > "rows/$n.csv"
    return $status
}

What the sweep establishes and what it does not. The construct establishes one property: every run of the solver contributes exactly one row, with a label derived from its exit status, so the CSV file cannot present a failed run as a result. The property rests on three facts of the model: the status is a separate channel, $? is read before any other command runs, and rows reach the parent through files. It does not establish that the solver is correct, that a converged run is accurate (the stopping rule bounds the last change, not the error), or that the runs are independent of one another. The background mode starts all cases at once. That is acceptable for 4 cases and unsuitable for 200: the machine has 12 logical processors of different speeds, a job scheduler allocates them to jobs and not to processes of one script, and the runs compete for memory bandwidth, so timings from concurrent runs are not timings of single runs. A sweep that measures performance runs its cases one after the other, and a sweep with many cases uses the scheduler's own mechanisms (chapter 30).

The model of execution environments establishes five things. A child process starts with the exported variables and the working directory of its parent, and changes in the child do not return (5.1). The status of a command is a separate channel of eight bits (5.3), and the conditions of if and while read it. Integer arithmetic in the shell wraps modulo \(2^{64}\) (5.2). A loop with start value \(c_0\), bound \(b\) and step \(d\) runs a computable number of times (5.4). The number of processes that a construct creates can be counted (5.5), and it dominates the cost of loops that process many records.

The model leaves out most of the language. It does not cover signals and traps, job control, the options set -e, set -u and pipefail, here-documents beyond their use in the listings, arrays, parameter-expansion operators, and the interactive features of Bash (history, completion, aliases). It describes Bash 5.2.21 and dash 0.5.12 on one Linux kernel (6.6.87.2, WSL 2), and it states POSIX behaviour only where §-numbers are cited; the behaviours of other shells (Zsh, Ksh, fish) were not tested. The Bash manual cited is for version 5.3, and the runs are on 5.2.21. The process counts of (5.5) come from a PID-difference probe that is exact only on an otherwise quiet system, and they were measured for Bash only; the value of \(\kappa\) is one machine under WSL 2, where process creation goes through a virtualised kernel, and it is not a property of Linux in general. The lecture's terminals show the prompt [root@localhost …]#, so its examples ran as user root; this chapter ran as an ordinary user, and nothing in the results depends on the difference except the execute-bit tests, which need a file system with permission bits.

A script that is correct in this chapter's sense is still not a correct experiment. The sweep records which runs converged, and it does not check that the solver is right, that the stopping rule bounds the error, or that timing runs were free of interference; those questions belong to chapters 9, 10 and 16.

Exercises

Exercise 1 (derive). From the rules of POSIX §2.12 derive the number of processes that x=$(a | b | c) creates when a, b and c are external programs, and explain why x=$(a) with one external program gives a different count. A loop reads \(R=10^{4}\) lines (records) and runs, per line, f=$(echo "$line" | cut -d, -f2) and g=$(echo "$line" | tr a-z A-Z | cut -c1-3). Use (5.5) and \(\kappa=0.59\) ms to estimate the time, and state the range that the check of the section on the monitoring script allows.

Solution

The substitution runs its command in a subshell (§2.6.3), which is one process. A pipeline of three stages runs each stage in a subshell environment (§2.12), so three more processes are created; the count is \(1+3=4\), and the measurement for echo | awk | sed in fork_cost.sh gave 4. The shell does not wait for the stages one by one, but the count does not depend on that. For one external program the measurement gave 1: a substitution whose command is a single simple command needs only the forked subshell to become that program, so no second process exists (the count of x=$(/bin/echo hi) was 1 in a separate probe, and of x=$(echo hi | cat) it was 3, in line with \(1+k\) for \(k=2\)). Rule (5.5) therefore holds for \(k\ge2\). For the loop: the first substitution has \(k=2\), 3 processes, and the second has \(k=3\), 4 processes, so \(P=R(3+4)=7\times10^{4}\) processes. At \(\kappa=0.59\) ms this is 41 s. The check of the section on the monitoring script found measured times between 0.54 and 1.34 of its 1.24 s prediction, which gives about 22 s to 55 s here. A single awk -F, '{print $2, toupper(substr($0,1,3))}' would run in one process.

Exercise 2 (compute). Give the output of each line and the reason. (a) echo $((2**63 - 1 + 1)). (b) f() { return 1000; }; f; echo $?. (c) c=3; while [ $c -le 100 ]; do c=$((c + 7)); done; echo $c, and the number of iterations. (d) The smallest \(n\) for which the recursive factorial of the lecture prints a negative number, and the smallest \(n\) for which it prints 0.

Solution

(a) Each operation wraps by (5.2): 2**63 is already \(-2^{63}\), subtracting 1 gives \(2^{63}-1\), and adding 1 gives \(-2^{63}\) again. The result equals \(\operatorname{wrap}(2^{63})\) because every step is exact modulo \(2^{64}\): the output is \(-9223372036854775808\). (b) By (5.3), \(1000 \bmod 256=232\), so 232 (POSIX leaves a value above 255 unspecified; Bash 5.2.21 gave 232). (c) By (5.4) with \(c_0=3\), \(b=100\), \(d=7\): \(\lfloor 97/7\rfloor+1=14\) iterations, and the final value is \(3+14\cdot7=101\); a run of these lines in a separate check printed 101 and 14. (d) The true value of \(n!\) first exceeds \(2^{63}-1\approx9.22\times10^{18}\) at \(n=21\), because \(20!=2.43\times10^{18}\) and \(21!=5.11\times10^{19}\). The wrapped value \(21!-3\cdot2^{64}=-4\,249\,290\,049\,419\,214\,848\) is negative, so \(n=21\). The value is 0 when \(2^{64}\) divides \(n!\). The exponent of 2 in \(n!\) is \(n-s_2(n)\) (Legendre), which is 63 for \(n=64\) (\(s_2=1\)) and for \(n=65\) (\(s_2=2\)), and 64 for \(n=66\). The exponent never decreases when \(n\) grows by 1, so 66 is the smallest \(n\) with result 0; \(65!\) is \(2^{63}\) times an odd number, which wraps to \(-2^{63}\). The listing functions_demo.sh printed these values for 21, 65 and 66.

Exercise 3 (counterexample). A student writes: "If a parent exports a variable, the child can use it to hand a result back to the parent." Show with a short script that the claim is false, and name the channels through which a result can reach the parent.

Solution

Take the pair of scripts of env_demo.sh: the parent runs export NAME2=Mahesh and starts child.sh, whose last line is NAME2=changed_by_child. After the child ends the parent prints NAME2=[Mahesh]. By (5.1), the child received a copy of the exported variable and changed the copy. The channels that do reach the parent are the following. (i) The exit status, which carries 8 bits by (5.3). (ii) The standard output of the child, captured with $(…) or a pipe; the cost is a subshell. (iii) A file that the child writes and the parent reads, as the sweep does with rows/N.csv. (iv) Sourcing: . ./child.sh runs the commands in the parent's own shell, so no child exists and the variable changes in place (exec_modes.sh shows the same process). Channel (iv) has the price that the script can also change the working directory and every other variable of the caller.

Exercise 4 (diagnose an assumption). The function below is meant to print the number of lines with ERROR in a file and to report an unreadable file. Its author says that it works. For the files log1.txt (two ERROR lines), log0.txt (none) and missing.txt (absent) predict the output, find the assumption that fails, and write a corrected version.

count_bad() {
    local n=$(grep -c ERROR "$1")
    if [ $? -ne 0 ]; then echo "grep failed"; fi
    echo "$n"
}
Solution

The assumption is that $? after local n=$(…) is the status of grep. It is the status of local, which is zero unless local is used outside a function, receives an invalid name, or names a read-only variable (Bash manual); the status of the substitution is discarded. The run on this machine printed 2 for log1.txt, 0 for log0.txt, and for missing.txt only the message of grep from its own error stream and an empty count: the text grep failed is never printed. A second defect hides behind the first. grep -c exits with 1 when it finds no match, so a corrected test of "status not zero" would report log0.txt, a valid file with zero errors, as a failure. A corrected version separates the declaration from the assignment, reads the status at once, and treats only 2 as an error:

count_good() {
    local n s
    n=$(grep -c ERROR "$1" 2>/dev/null); s=$?
    if [ "$s" -eq 2 ]; then echo "cannot read $1" >&2; return 2; fi
    echo "$n"
}

It printed 2 and status 0 for log1.txt, 0 and status 0 for log0.txt, and cannot read missing.txt with status 2 for the absent file.

Exercise 5 (design judgment). The sweep of the last section must now cover 40 grid sizes from \(N=16\) to \(N=1024\). In a separate run on this machine, \(N=64\) with 5272 iterations took 0.02 s and \(N=128\) with 16 148 iterations took 0.28 s. Choose a failure policy (stop at the first failed case, continue and report, or retry with a larger limit), choose between sequential and concurrent execution, and justify both with the numbers. Estimate the time of the \(N=1024\) case from the counts 515, 1657, 5272 and 16 148 iterations for \(N=16,32,64,128\), state what the estimate assumes, and then check it against the measurements in the solution.

Solution

The cost of a case is about \(t_u\,K(N)\,N^2\), with \(K(N)\) the iterations, \(N^2\) the cell updates per sweep and \(t_u\) the time per cell update. From the two measurements, \(K N^2\) grows from \(5272\cdot64^2=2.2\times10^{7}\) to \(16148\cdot128^2=2.6\times10^{8}\) updates, a factor 12.3, and the times grow by a factor 14 (0.02 s to 0.28 s; the 0.02 s value has one digit, so the factors agree within its resolution). The counts for \(N=16\) to 128 grow by 3.22, 3.18 and 3.06 per doubling. Estimate. If \(K\) keeps growing by about 3.1 per doubling, then \(K(1024)\approx16\,148\cdot3.1^{3}=4.8\times10^{5}\), the work is \(4.8\times10^{5}\cdot1024^2=5.0\times10^{11}\) updates, about 1900 times the work at \(N=128\), and at the same \(t_u\) the time is about \(0.28\times1900\approx530\) s. Check. The same solver, run without an iteration limit, gave 45 651 iterations at \(N=256\) in 3.63 s and 108 997 iterations at \(N=512\) in 51.4 s (one run each on this machine). The growth factors per doubling are then 2.83 and 2.39, not 3.1. A run at \(N=1024\) gave 193 751 iterations (a factor 1.78) and 677 s; it is one run on a loaded machine and was not repeated. So the estimate is 2.5 times too high in iterations (\(4.8\times10^{5}\) against \(1.94\times10^{5}\)), and it is close in time only because \(t_u\) rose as well: \(t_u\) is about 1.1 ns at \(N=128\), 1.2 ns at 256, 1.8 ns at 512 and 3.3 ns at 1024. Two errors of opposite sign cancel in the product. A reason for the falling growth factor, not tested here, is the one the sweep section states: the stopping test bounds the last change, not the error, and for a fixed error the last change shrinks with \(h^2\), so larger grids stop at a larger relative error. A reason for the rising \(t_u\), also not isolated, is the cache: the two arrays of \(N=128\) hold \(2\cdot130^2\cdot8\) B = 0.27 MB, which fits in one L2 cache of 1.25 MiB (7.5 MiB in 6 instances, as the guest reports), and the two arrays of \(N=1024\) hold \(2\cdot1026^2\cdot8\) B = 16.8 MB, more than the 12 MiB L3 cache that the guest reports. Failure policy: a failing case spends its whole limit before it fails, so a failure at the limit \(K_{\max}\) costs \(t_u\,K_{\max}\,N^2\), and the expensive cases are the ones most likely to fail if the limit is fixed. Stopping at the first failure would discard the cheap sizes that are already valid, so the policy is to continue, label every row by its status (as run_case does), and exit with a non-zero status at the end. Retrying with a larger limit is a decision for a person, because it multiplies the cost of the failed case. A limit set in advance from the growth model, \(K_{\max}(2N)\approx1.5\cdot3.1\,K(N)\), is safe, and the observed factors 2.83, 2.39 and 1.78 show how far it overestimates the need, so the cost of a failure at that limit exceeds the cost of a success by a factor that grows with \(N\); a limit taken from the measured count of the next smaller size is tighter. Concurrency: if the result is the iteration count and the final change, the cases are independent and may run concurrently, but 40 background processes on 12 logical processors of different speeds give no benefit beyond about 12 and make the largest case compete with the others for memory bandwidth; a bounded number of concurrent cases, for example with xargs -P or a scheduler array, is the design. If the result is a run time, the cases must run one after the other.

Exercise 6 (implementation and measurement). Write a script that measures the time per iteration of three loops: x=hi (\(10^{4}\) iterations), x=$(echo hi) (\(10^{4}\)) and x=$(/bin/echo hi) (\(10^{3}\)). Predict, before you run it, the process count of each loop body from (5.5), and whether each cost per iteration is below, near or above \(\kappa=0.59\) ms. Run it three times and compare.

Solution

A script needs only the time keyword of Bash with TIMEFORMAT=%R, as in fork_cost.sh:

TIMEFORMAT=%R
a=$( { time for ((i = 0; i < 10000; i++)); do x=hi; done; } 2>&1 )
b=$( { time for ((i = 0; i < 10000; i++)); do x=$(echo hi); done; } 2>&1 )
c=$( { time for ((i = 0; i < 1000; i++)); do x=$(/bin/echo hi); done; } 2>&1 )
echo "assignment: $a s; \$(echo hi): $b s; \$(/bin/echo hi): $c s"

Prediction: the assignment creates no process, so its cost is the cost of the interpreter, well below \(\kappa\), at most a few microseconds. $(echo hi) creates one process (a single simple command: only the forked subshell) that does not exec, so the cost should be below \(\kappa\), which includes an exec. $(/bin/echo hi) creates one process that also executes a program, so it should be near \(\kappa\) or above, because it also creates a pipe and reads the output. The count of 0, 1 and 1 processes was confirmed with the PID probe of fork_cost.sh (a separate run gave 0, 1, 1 in three repetitions). Three runs on this machine gave: assignment 0.012 to 0.015 s for \(10^4\) iterations, 1.2 to 1.5 µs each; $(echo hi) 4.4 to 5.8 s for \(10^4\), 0.44 to 0.58 ms each; $(/bin/echo hi) 0.95 to 1.9 s for \(10^3\), 0.95 to 1.9 ms each. The predictions agree in direction: 1.2 to 1.5 µs is below \(\kappa\) by a factor of about 400, the forked subshell without exec costs 0.75 to 0.98 of \(\kappa\), and the process that executes a program costs 1.6 to 3.2 times \(\kappa\). The first two agree with the model. The last is larger than the prediction of "near \(\kappa\) or above", and this chapter did not isolate how much of the excess is the pipe and the reading of the output and how much is the start of /bin/echo compared with /bin/true.
