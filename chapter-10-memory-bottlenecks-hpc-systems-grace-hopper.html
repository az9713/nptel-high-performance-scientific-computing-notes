Memory bottlenecks, the organization of large HPC systems and the Grace Hopper superchip

One Jacobi sweep on a grid of \(4096\times4096\) points performs \(8.4\times10^{7}\) floating-point operations and moves \(2.7\times10^{8}\) to \(4.0\times10^{8}\) bytes through the memory interface (16 to 24 bytes per point). The laptop used for this chapter performs 66.7 Gflop/s on one thread and 202 Gflop/s on twelve, in a loop that does nothing but arithmetic. Its one memory module has a pin rate of 25.6 GB/s; the STREAM scale kernel obtains 10.4 GB/s on one thread and 14.5 GB/s on four, counted as STREAM counts, which is 15.6 and 21.8 GB/s of DRAM traffic if every store first reads its line. The sweep ran at 3.3 Gflop/s on one thread and at 4.4 to 4.5 Gflop/s on four to eight threads: 2.2 % of the arithmetic peak, and 98 % of the rate that the scale kernel allows in the same count. Twelve threads ran it more slowly than eight in each of five runs. The Frontier node in the lectures has, for each GPU die, 26.5 Tflop/s and 1.6 TB/s, and the same sweep is bounded there (with 16 bytes per point) at 1.9 % of the die's peak. This chapter defines the quantities that make such statements checkable (arithmetic intensity, bandwidth, latency, the ridge point of the roofline), measures them on the machine, and applies them to the memory hierarchy, to the organization of a leadership-class system, and to the Grace Hopper superchip.

The objects of the chapter and the running case

The chapter asks one question about a program on a machine: which resource sets the run time? The answer needs two descriptions that can be compared. A program run is described by two counts. \(F\) is the number of floating-point operations (flop) the run performs; one addition, subtraction, multiplication or division of two doubles is one flop, a fused multiply-add is two, and a comparison or an absolute value is not counted. \(Q\) is the number of bytes that cross the interface between the processor chip and main memory (DRAM) during the run. Their ratio is the arithmetic intensity \[ I=\frac{F}{Q}\quad\text{(flop per byte).} \] A machine is described by two rates and by a list of memories. \(P_{\text{peak}}\) is the highest rate of flop the arithmetic units can sustain (flop/s). \(B_{\text{peak}}\) is the highest rate at which DRAM can deliver or accept bytes (byte/s). The list of memories is the hierarchy: registers, caches, DRAM, storage. Each level \(\ell\) has a capacity, a latency \(\tau_\ell\) (the time from the request for one item to its arrival) and a bandwidth \(B_\ell\) (the number of bytes per second the level can deliver when requests are plentiful). Latency and bandwidth are different quantities with different units, and the chapter keeps them apart.

Two statements about time follow without further assumption. The run cannot finish before the arithmetic units could have executed \(F\) flop, and it cannot finish before DRAM could have moved \(Q\) bytes. Therefore the run time \(T\) satisfies

\[ T\;\ge\;\max\!\Bigl(\frac{F}{P_{\text{peak}}},\ \frac{Q}{B_{\text{peak}}}\Bigr). \tag{10.1} \]

If the first term is the larger, the run is compute-bound; if the second is, it is memory-bound. Equation (10.1) is a lower bound. It is the starting point of the Roofline model in the section on the roofline, and the chapter uses it to read each measurement: a measured time far above the bound names a cost that the two rates do not describe, and a measured time below it names a counting error.

The running case is the book's Jacobi sweep from Chapter 9. On the grid of \((N+2)\times(N+2)\) doubles in row-major order, with the interior \(i,j=1,\dots,N\) and the index macro IDX(i,j) \(=i(N+2)+j\), one sweep computes

\[ u^{\text{new}}_{i,j}=\tfrac14\bigl(u_{i-1,j}+u_{i+1,j}+u_{i,j-1}+u_{i,j+1}\bigr) \]

for every interior point and returns the largest change \(\max|u^{\text{new}}_{i,j}-u_{i,j}|\). Each point costs three additions and one multiplication for the average and one subtraction for the change (the absolute value and the comparison are not counted, as in Chapter 9): \(F=5N^2\) per sweep. The question of the chapter is whether this sweep is limited by its \(F\) or by its \(Q\). A second question follows from the lectures: what does the organization of a large machine, from a laptop to the Frontier supercomputer, do to the answer?

The symbols of the book are used as in the notation table: \(p\) threads, \(T_1\) and \(T_p\) times on one and on \(p\) threads, \(S_p=T_1/T_p\), \(P(I)\) for the attainable rate, \(N\) the number of interior points per side. Three more symbols belong to this chapter. \(t_h\) is the hit time of a memory level, \(m_r\) its miss rate, and \(t_m\) its miss penalty, as defined in the section on average access time. \(\tau\) is a latency and \(b\) a number of bytes. Each is repeated at first use.

The memory hierarchy: speed, size and the width of the paths W3L3 3:21

The lecture starts from the von Neumann machine: a control unit and an arithmetic unit fetch an instruction, decode it, fetch its operands, execute it, and store the result, then move to the next instruction. Instructions and operands both live in memory, so every cycle of the loop needs memory. The lecture asks whether memory is uniform and answers with a pyramid: registers next to the logic circuits, then two or three levels of cache on the processor chip, then DRAM on the motherboard, then permanent storage (read-only memory, removable drives, network storage, disks). The speed falls and the capacity and the distance rise down the pyramid; the lecture ties the cost per byte to the distance from the arithmetic.

Chapter 7 treats the organization of the caches (lines, sets, tags), locality and coherence, and this chapter does not repeat it; the lecture's slides here are the coarse view that precedes it. A correction of the cycle count. The lecture describes a read from a storage device as costing a few thousand clock cycles and a read from main memory as costing about 100. The slide gives 10 000 000 ns for the disk and 100 ns for main memory. At a clock of 1 ns per cycle these are \(10^{7}\) and 100 cycles, so a disk figure of a few thousand cycles is too small by a factor of about \(10^{4}\). A measurement of the first three rows. The program defines the latency of a level as the time of one load whose address is not known until the previous load has returned. It builds one random cycle through all 64-byte lines of a working set of the given size, and then follows the cycle: each load depends on the one before. No hardware can overlap these loads, so the time per load is a latency of the smallest level that holds the working set. The second measurement reads the same amount of memory in address order, with several independent sums, so that loads overlap. It reports bytes per second and the time per 64-byte line. The program takes no input and prints one table; the check is only that it terminates normally, because the numbers depend on the load of the machine.

#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>
#include <time.h>

typedef double v4 __attribute__((vector_size(32)));
typedef struct node { struct node *next; char pad[56]; } node;   /* one 64-byte line */

static double now(void)
{
    struct timespec t;
    clock_gettime(CLOCK_MONOTONIC, &t);
    return (double)t.tv_sec + 1e-9 * (double)t.tv_nsec;
}

static uint64_t rng = 88172645463325252ULL;
static uint64_t rnd(void) { rng ^= rng << 13; rng ^= rng >> 7; rng ^= rng << 17; return rng; }

/* Latency: walk one random cycle through all lines; each load needs the previous one. */
static double chase_ns(size_t bytes)
{
    size_t n = bytes / sizeof(node), steps = 1L << 21;
    node *a = aligned_alloc(64, n * sizeof(node));
    size_t *order = malloc(n * sizeof(size_t));
    for (size_t i = 0; i < n; i++) order[i] = i;
    for (size_t i = n - 1; i > 0; i--) { size_t j = rnd() % (i + 1); size_t t = order[i]; order[i] = order[j]; order[j] = t; }
    for (size_t i = 0; i < n; i++) a[order[i]].next = &a[order[(i + 1) % n]];
    node *p = &a[order[0]];
    for (size_t k = 0; k < n; k++) p = p->next;                 /* warm-up pass */
    double best = 1e30;
    for (int rep = 0; rep < 3; rep++) {
        double t0 = now();
        for (size_t k = 0; k < steps; k++) p = p->next;
        double t = now() - t0;
        if (t < best) best = t;
    }
    if (p == NULL) puts("unreachable");                           /* keeps the walk alive */
    free(a); free(order);
    return best / (double)steps * 1e9;
}

/* Bandwidth: read all doubles in order, 4 independent 4-lane vector sums; independent loads overlap. */
static double read_gbs(size_t bytes)
{
    size_t n = bytes / sizeof(double);
    double *a = aligned_alloc(64, n * sizeof(double));
    for (size_t i = 0; i < n; i++) a[i] = 1.0;
    size_t passes = (size_t)(1e9 / (double)bytes) + 1;
    v4 s0 = {0}, s1 = {0}, s2 = {0}, s3 = {0}, *v = (v4 *)a;
    size_t nv = n / 4;
    double best = 1e30;
    for (int rep = 0; rep < 3; rep++) {
        double t0 = now();
        for (size_t k = 0; k < passes; k++)
            for (size_t i = 0; i + 4 <= nv; i += 4) { s0 += v[i]; s1 += v[i + 1]; s2 += v[i + 2]; s3 += v[i + 3]; }
        double t = now() - t0;
        if (t < best) best = t;
    }
    v4 s = s0 + s1 + s2 + s3;
    if (s[0] + s[1] + s[2] + s[3] < 0.0) puts("unreachable");
    free(a);
    return (double)passes * (double)bytes / best / 1e9;
}

int main(void)
{
    size_t kib[] = {16, 32, 128, 512, 1024, 2048, 4096, 8192, 16384, 65536, 262144};
    printf("%10s %12s %10s %12s %10s\n", "size", "chase ns/ld", "read GB/s", "read ns/line", "chase/read");
    for (int k = 0; k < 11; k++) {
        size_t bytes = kib[k] * 1024;
        double c = chase_ns(bytes), g = read_gbs(bytes), l = 64.0 / g;
        if (kib[k] >= 1024) printf("%7zu MiB", kib[k] / 1024); else printf("%7zu KiB", kib[k]);
        printf(" %12.2f %10.1f %12.2f %10.1f\n", c, g, l, c / l);
    }
    return 0;
}

Why the transfer unit grows with distance. The lecture shows the widths of the paths: 8 bytes between the registers and the cache, 32 bytes between the cache and memory, 4 KB between memory and disk. It asks why the width changes and answers with a supply chain: nobody sends one parcel at a time from the big warehouse to the shop in the city centre. A transfer model gives the quantitative form of the answer. Suppose a level has latency \(\tau\) and streaming bandwidth \(B\), and a transfer of \(b\) bytes takes

\[ t(b)=\tau+\frac{b}{B}. \tag{10.3} \]

The delivered rate is \(b/t(b)\). It reaches half of \(B\) when \(b/B=\tau\), that is at

\[ b_{1/2}=\tau B, \tag{10.4} \]

the half-performance length. Transfers much smaller than \(b_{1/2}\) run at a rate near \(b/\tau\), far below \(B\). The slide's numbers give \(b_{1/2}\) for the disk as \(10^{7}\ \text{ns}\times187\ \text{MB/s}=1.9\ \text{MB}\), while the page unit is 4 KB. A 4 KB transfer from that disk takes \(10\ \text{ms}+22\ \mu\text{s}\) and delivers 0.41 MB/s, 0.22 % of the streaming rate. The disk path is latency-dominated at the page size, and a system that moves pages in either direction has to treat a page fault as a very rare event. For main memory the product is \(\tau B\approx\) 100 ns \(\times\) 15 GB/s = 1.5 KB, which is 23 cache lines of 64 bytes. A 64-byte line therefore wastes most of the first request unless more requests are in flight. Equation (10.4) is the same relation as the bytes-in-flight rule below, applied to one transfer.

Bytes in flight. A level that has latency \(\tau\) and is to deliver bandwidth \(B\) must have requests for \(n=\tau B\) bytes outstanding at every moment (Little's law: the number of items in a system equals their arrival rate times the time each spends in it; Chapter 7 uses it in its section on the average access time). For the main memory of this machine, with the dependent-load latency of the sample and the bandwidth of the STREAM measurement below, \(n\) is about 2.9 kB, which is 46 lines of 64 bytes (\(\tau=134\) ns and \(B=21.8\) GB/s). The program above shows the effect directly: the last column, the ratio of the dependent-load time to the time per line of the independent reads, is the number of loads that the processor effectively keeps in flight. It is 26 to 63 for the working sets of 4 MiB and more. A program that follows pointers has one load in flight and runs at \(b/\tau\); a program that reads an array in order has many and runs near \(B\). This is why the chapter treats latency and bandwidth separately, and why the Jacobi sweep, which reads in address order, meets the bandwidth bound of (10.1) and not the latency.

The lecture also lists bandwidths by level from its slide (source: the same UMass course): processor to cache 24 GB/s, cache to main memory 0.5 to 6.4 GB/s, main memory to disk 187 MB/s ("serial ATA/1500"). The slide writes the unit as MBps; the difference between Mbps and MBps is a factor of 8, so the unit must be kept. The lecture states that the ratios between levels stay roughly fixed when technology improves, so that a faster disk brings a proportionally faster memory and cache. The next sections show that this is the part of the lecture that the research literature contradicts.

Virtual memory, paging and thrashing W3L3 16:00

The lecture poses a problem of portability. The same program may run on a machine with 1 GB of memory and 10 GB of disk, and on a machine with 1 TB of memory and petabytes of disk. A program cannot be written for one memory size, and it cannot name physical locations. The answer in the lecture is virtual memory: each process sees one address space, and the operating system maps pieces of it onto physical memory and, when memory is short, onto disk. The slide shows a column of virtual memory per process with arrows to blocks in RAM, to a block that holds "another process's memory", and to the disk.

The model has four parts. A page is a block of consecutive virtual addresses that is mapped as a unit; on this machine the page size is 4096 bytes (getconf PAGESIZE in the session above), the same 4 KB as the width of the path between memory and disk on the slide. A frame is a block of physical memory of the page size. A page table, kept by the operating system, records for each page of a process the frame that holds it, or that the page is on disk, or that it has not been created. A reference to a page that has no frame is a page fault: the processor traps to the operating system, which finds a frame, fills it (with zeros for a new page, with a copy from disk for a page that was written out), updates the table and restarts the instruction. If the system has no free frame, it first chooses a page to evict, usually one that was not used recently, and writes it to disk if it was modified. A fault that needs no disk transfer is a minor fault; one that reads the disk is a major fault. The working set of a program over a time window is the set of pages it references in that window. Thrashing is the state in which the working set does not fit in the frames available, so that most references fault and the system spends its time moving pages.

The cost of one fault, measured. The program below allocates 1 GiB, touches one byte in each page, and counts the minor faults with getrusage. It touches the same pages a second time. The first pass creates every page; the second finds them all present. No disk is involved, so the times are those of the minor fault alone, in a WSL 2 guest, where the guest's page fault may also cause a fault in the host. The program takes no input, and its numbers depend on the load of the machine, so the check is only that it ends normally.

#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <time.h>
#include <unistd.h>
#include <sys/resource.h>

static double now(void)
{
    struct timespec t;
    clock_gettime(CLOCK_MONOTONIC, &t);
    return (double)t.tv_sec + 1e-9 * (double)t.tv_nsec;
}

static long minor_faults(void)
{
    struct rusage u;
    getrusage(RUSAGE_SELF, &u);
    return u.ru_minflt;
}

int main(void)
{
    size_t bytes = 1UL << 30, page = (size_t)sysconf(_SC_PAGESIZE);
    char *a = malloc(bytes);                       /* reserved, not yet backed by physical pages */
    long f0 = minor_faults();
    double t0 = now();
    for (size_t i = 0; i < bytes; i += page) a[i] = 1;   /* first touch: one write per page */
    double t1 = now();
    long f1 = minor_faults();
    for (size_t i = 0; i < bytes; i += page) a[i] = 2;   /* second touch: pages are present */
    double t2 = now();
    long f2 = minor_faults();
    size_t pages = bytes / page;
    printf("page size %zu B, pages in 1 GiB %zu\n", page, pages);
    printf("first touch:  %.0f%% of the pages caused a minor fault, %.0f ns per page\n",
           100.0 * (double)(f1 - f0) / (double)pages, (t1 - t0) / (double)pages * 1e9);
    printf("second touch: %ld faults, %.0f ns per page\n", f2 - f1, (t2 - t1) / (double)pages * 1e9);
    free(a);
    return 0;
}

Cost of a major fault and the thrashing cliff. The lecture's account of thrashing is qualitative: if a program asks for data in no particular pattern, each request may pull in a whole page and push another out, and the effort of moving the page is the same even if one element of it is used. The model gives the numbers. Let \(t_{\text{mem}}\) be the access time when the page is present and \(t_f\) the time to service a fault. If a fraction \(m_f\) of the references fault, the average time per reference is

\[ T_{\text{avg}}=t_{\text{mem}}+m_f\,t_f. \tag{10.5} \]

With the slide's values \(t_{\text{mem}}=100\) ns and \(t_f=10\) ms, a slowdown of 10 % requires \(m_f t_f\le10\) ns, so \(m_f\le10^{-6}\): at most one fault per million references. Consider references to uniformly random locations in an array of \(V\) bytes of which only \(R\) bytes are resident. In steady state a reference finds its page resident with probability \(R/V\), so \(m_f=1-R/V\). An array 1 % larger than the resident memory (\(V/R=1.01\)) has \(m_f=0.0099\), and (10.5) gives 99 110 ns per reference, 991 times the fault-free time. The slowdown is a cliff, not a slope, because \(t_f/t_{\text{mem}}=10^{5}\). The program below prints this table for several sizes. The same program shows why the lecture advises contiguous access. A random fault pays the latency of the disk, 10 ms. A fault in a sequential scan, with the next pages read ahead, pays the transfer time of the page at the disk's streaming rate, \(4096\ \text{B}/187\ \text{MB/s}=22\ \mu\text{s}\), so the same page costs 457 times less. Read-ahead is an assumption of the model; it is what operating systems do for a sequential pattern, and the chapter did not test it.

Hit time, miss penalty, the average access time and the memory wall W3L3 22:40

The lecture ends with the vocabulary of the hierarchy. A request that finds its data in the upper level is a hit; the hit rate is the fraction of accesses that hit; a miss needs a block from the lower level, and the miss rate is \(m_r=1-\text{hit rate}\). The hit time \(t_h\) is the time to decide hit or miss plus the time to access the upper level. The miss penalty \(t_m\) is the time to replace a block in the upper level plus the time to deliver the block to the processor. The slide notes that hit time is much smaller than miss penalty, and the lecture closes with the advice that, for data sets that do not fit the caches, the only way to make the computation efficient is to reuse data that has come down to the faster levels.

Chapter 7 derives the average memory access time from these terms in its section on the average access time, extends it to three cache levels, and shows that it fails for independent accesses, for which it uses a bound from Little's law. This section recalls the result in the form that the slide's numbers need. Each access pays \(t_h\), and the fraction \(m_r\) of accesses pays \(t_m\) in addition, so

\[ \text{AMAT}=t_h+m_r\,t_m. \tag{10.6} \]

The slide gives numbers for exactly two cache levels. With \(m_1\) the miss rate of the first level, \(t_{h2}\) the hit time of the second level, and \(m_2\) its local miss rate (the fraction of the accesses that reach it and miss), the three-level form of Chapter 7 with two levels is

\[ \text{AMAT}=t_{h1}+m_1\bigl(t_{h2}+m_2\,t_{\text{mem}}\bigr). \tag{10.7} \]

With the slide's 2 ns, 6 ns and 100 ns, the first table of the listing above shows the structure. A first-level miss rate of 5 % and a local second-level miss rate of 20 % give 3.30 ns, 1.65 times the all-hit time of 2 ns: a program that hits 95 % of the time in the first level runs its memory accesses 65 % slower than the all-hit case. At \(m_1=0.2\) and \(m_2=0.8\) the time is 19.2 ns, 9.6 times the all-hit time. The numbers are small only because the miss rates of programs that reuse data are small. A streaming program does not reuse data.

Where the formula stops describing the machine. A loop that reads doubles in order from a large array has \(m_r=1/8\): one access in eight starts a new 64-byte line. If misses are served one at a time and each costs the measured dependent-load latency, (10.6) predicts \(1.3+134/8=18.1\) ns per double. The independent-read measurement of hierarchy.c reached 12.6 GB/s, 0.63 ns per double for the working sets in memory. The formula is wrong by a factor of 28 because its premise is false for this loop: the misses of a streaming loop are independent of each other, and the machine keeps many of them in flight. Chapter 7 finds the same failure for sums over a matrix (factors of 22 and 9.5 at \(N=4096\)). AMAT is the right model for pointer-chasing and for any loop whose next address depends on the last load. It does not describe a loop that is limited by how many bytes per second the memory can deliver, and for that case the chapter uses the bound (10.1) in the next sections.

The memory wall. Wulf and McKee (1995) name the situation, as Machanick's survey reports it, in which processor speed has improved so much faster than DRAM speed that, in time, memory access dominates the run time of every program. Machanick's 2002 survey, which the chapter could open, restates the argument with a processor that improves 50 % per year (a figure he calls conservative) and DRAM that improves 7 % per year. The speed gap then grows by a factor of \(1.5/1.07=1.40\) per year and doubles every 2.1 years. Put this into (10.6) with a miss rate that stays at 1 %. If the miss penalty is 100 times the hit time today, then \(\text{AMAT}=t_h(1+0.01\times100)=2t_h\). After ten years the ratio \(t_m/t_h\) has grown by \(1.40^{10}=29\), so \(\text{AMAT}=t_h(1+0.01\times2930)=30\,t_h\). The share of the access time spent on misses, \(1-t_h/\text{AMAT}\), rises from 50 % to 97 %. The lecture's remark that the ratios between levels stay fixed concerns transfer rates. For latency the argument above contradicts it. For bandwidth the chapter has one proxy, the ratio of the arithmetic rate to the DRAM bandwidth: the ridge points of Williams et al. for two processors of 2008 are 4.4 and 6.7 flop per DRAM byte, and those of Table 10.3 are 4.3 to 16.6, so this ratio has grown by at most a factor of 3.8 (16.6 against 4.4) in about 16 years, against a factor of \(1.40^{16}\approx220\) for the latency gap of the argument above.

The argument has a boundary. It rests on the assumption of a fixed miss rate. Ertl's critique of the paper (an undated web page) points out that the compulsory misses of a program are set by the amount of memory it touches and not by the number of instructions it executes, that longer cache lines (16 bytes on the 486, 64 bytes on the K7) reduce them, and that a memory system serves several misses at once, so that the time spent in compulsory misses is the memory touched divided by the memory bandwidth. The last point is the bytes-in-flight observation of this chapter, and it leads to the same place as the next section: the wall is a statement about a ratio, not about a latency. The ratio is \(P_{\text{peak}}/B_{\text{peak}}\), the number of flop that the arithmetic can perform in the time that memory delivers one byte. A program with fewer flop per byte than this ratio waits for memory, however many miss-rate improvements the caches deliver. One measurement of this chapter supports the lecture's side of the debate on latency: a dependent load from DRAM takes 126 to 171 ns for working sets of 16 and 64 MiB over five runs (126 to 134 ns in the printed sample) and 189 to 251 ns at 256 MiB on this machine, against 100 ns on the slide. The comparison is confounded by the virtualization layer and by 4 KiB page translation in the chain, which this chapter did not separate, so it shows that DRAM latency did not fall between the slide's era and now, and it shows no more.

STREAM: the bandwidth that the memory delivers

Equation (10.2) gives 25.6 GB/s for this machine. That number is a limit set by the pins of the memory module. A program never reaches it, because rows of the memory chips must be opened, refreshed and switched between reading and writing, and because the processor keeps only a limited number of requests in flight. The bound (10.1) needs the rate that a program can sustain. McCalpin's STREAM benchmark measures that rate for four simple loops over arrays much larger than the caches: copy \(a_i=b_i\), scale \(a_i=\kappa b_i\), add \(a_i=b_i+c_i\), and triad \(a_i=b_i+\kappa c_i\) (\(\kappa\) is the scalar of the benchmark). The STREAM reference page fixes three conventions that matter here (the arrays keep STREAM's names \(a\), \(b\), \(c\)).

The first is the size rule: each array must be at least 4 times the size of the sum of all the last-level caches used in the run, or one million elements, whichever is larger, so that no part of an array survives in a cache from one repetition to the next. The second is the repetition rule: the benchmark repeats the four kernels and reports the best of typically 10 trials. The third is the byte count, and it is the one that most often confuses a comparison. STREAM counts the bytes that the program asks to read and to write: 16 bytes per element for copy and scale, 24 for add and triad, and 0, 1, 1 and 2 flop per element. The page distinguishes this convention from two others, "bcopy" (which counts one transfer of the data) and "hardware" (what the memory system actually moves), and it states that most cached systems perform a write allocate when a store misses the data cache: they load the cache line before they overwrite it, so that the line has one valid copy. For triad, the program asks for 24 bytes per element, and a cache with write allocate moves 32: the line of \(a\) comes in, and later goes out.

The bound (10.1) is a statement about bytes that cross the DRAM interface. The bandwidth in it must therefore be counted in the same way as \(Q\). A STREAM result is in the "asked for" convention, which for triad is \(24/32=75\,\%\) of the hardware traffic on a machine with write allocate. The program below measures this. It runs the four kernels on arrays of 16 million doubles (128 MB each, 10.2 times the 12 MiB last-level cache), with the pages first touched by the threads that later use them, for 1, 2, 4, 8 and 12 threads. It adds a fifth kernel, triad-nt, which computes the same triad with 256-bit streaming stores (_mm256_stream_pd): these stores write a full line to memory without reading it first, so triad-nt asks for 24 bytes and moves 24. If write allocate is the only difference between triad and triad-nt, then at a bandwidth-bound size the rate of triad-nt, in the "asked for" count, should be up to 32/24 = 1.33 times the rate of triad. Each kernel is repeated 8 times and the first repetition is dropped; the printed rate is for the best of the remaining 7. The program checks the final array values against the same recurrence run on scalars, and it needs a processor with AVX2.

#include <stdio.h>
#include <stdlib.h>
#include <math.h>
#include <immintrin.h>
#include <omp.h>

#define N 16000000L          /* 128 MB per array: more than 4 x the 12 MiB last-level cache, as the STREAM rules require */
#define NTIMES 8
#define SCALAR 3.0

static double *a, *b, *c;

/* bytes the program asks to read and write per element, as STREAM counts them */
static const double bytes_per_elem[5] = {16.0, 16.0, 24.0, 24.0, 24.0};
static const char *name[5] = {"copy", "scale", "add", "triad", "triad-nt"};

static void kernel(int k)
{
    switch (k) {
    case 0: {
        #pragma omp parallel for schedule(static)
        for (long i = 0; i < N; i++) c[i] = a[i];
        break; }
    case 1: {
        #pragma omp parallel for schedule(static)
        for (long i = 0; i < N; i++) b[i] = SCALAR * c[i];
        break; }
    case 2: {
        #pragma omp parallel for schedule(static)
        for (long i = 0; i < N; i++) c[i] = a[i] + b[i];
        break; }
    case 3: {
        #pragma omp parallel for schedule(static)
        for (long i = 0; i < N; i++) a[i] = b[i] + SCALAR * c[i];
        break; }
    default: {      /* triad again, but the stores bypass the cache: no write-allocate read of a[] */
        __m256d vq = _mm256_set1_pd(SCALAR);
        #pragma omp parallel for schedule(static)
        for (long i = 0; i < N; i += 4)
            _mm256_stream_pd(a + i, _mm256_add_pd(_mm256_load_pd(b + i), _mm256_mul_pd(vq, _mm256_load_pd(c + i))));
        break; }
    }
}

int main(void)
{
    a = aligned_alloc(64, N * sizeof(double)); b = aligned_alloc(64, N * sizeof(double)); c = aligned_alloc(64, N * sizeof(double));
    int plist[] = {1, 2, 4, 8, 12}, ok = 1;
    printf("GB/s by the STREAM byte count (best of %d, first repetition dropped)\n", NTIMES - 1);
    printf("%8s", "threads");
    for (int k = 0; k < 5; k++) printf(" %9s", name[k]);
    printf("\n");
    for (int pi = 0; pi < 5; pi++) {
        omp_set_num_threads(plist[pi]);
        #pragma omp parallel for schedule(static)       /* first touch by the threads that will use the pages */
        for (long i = 0; i < N; i++) { a[i] = 1.0; b[i] = 2.0; c[i] = 0.0; }
        double best[5] = {1e30, 1e30, 1e30, 1e30, 1e30};
        for (int rep = 0; rep < NTIMES; rep++)
            for (int k = 0; k < 5; k++) {
                double t0 = omp_get_wtime();
                kernel(k);
                double t = omp_get_wtime() - t0;
                if (rep > 0 && t < best[k]) best[k] = t;
            }
        /* each repetition runs copy, scale, add, triad, triad-nt; the last two both leave a = b + SCALAR*c */
        double ea = 1.0, eb = 2.0, ec = 0.0;
        for (int rep = 0; rep < NTIMES; rep++) { ec = ea; eb = SCALAR * ec; ec = ea + eb; ea = eb + SCALAR * ec; ea = eb + SCALAR * ec; }
        if (fabs(a[N - 1] - ea) > 1e-9 * ea || fabs(b[7] - eb) > 1e-9 * eb || fabs(c[N / 2] - ec) > 1e-9 * ec) ok = 0;
        printf("%8d", plist[pi]);
        for (int k = 0; k < 5; k++) printf(" %9.1f", bytes_per_elem[k] * (double)N / best[k] / 1e9);
        printf("\n");
    }
    printf("results checked against the scalar recurrence: %s\n", ok ? "ok" : "MISMATCH");
    return ok ? 0 : 1;
}

The Roofline model: derivation, assumptions and the ceilings of this machine

Williams, Waterman and Patterson (2008 report; CACM 52(4), 2009) turn the bound (10.1) into a picture. Divide (10.1) into \(F\): the attainable rate \(P=F/T\) satisfies \(P\le P_{\text{peak}}\) and \(P\le F B_{\text{peak}}/Q=I\,B_{\text{peak}}\), so

\[ P(I)=\min\bigl(P_{\text{peak}},\ I\,B_{\text{peak}}\bigr). \tag{10.8} \]

This is the formula in §3 of the report: "Attainable GFlops/sec = Min(Peak Floating Point Performance, Peak Memory Bandwidth × Operational Intensity)". On a plot with \(\log I\) on the horizontal axis and \(\log P\) on the vertical axis the first argument is a horizontal line and the second is a line of slope one, which together form the "roofline". The two lines meet at the ridge point

\[ I^{*}=\frac{P_{\text{peak}}}{B_{\text{peak}}}, \tag{10.9} \]

the smallest intensity at which a program can reach the arithmetic peak. A program with \(I\lt I^{*}\) is memory-bound and a program with \(I\gt I^{*}\) can be compute-bound. A ridge point far to the right means that only programs with a very high intensity can use the arithmetic of the machine. The authors take the ridge point as a measure of how hard it is to reach the peak. The report quotes ridge points of 6.7 (Xeon) and 4.4 (Opteron X4) flop per DRAM byte for two multicores of 2008 (§6.3).

The report uses the name operational intensity for flop per byte of DRAM traffic after the caches have filtered the accesses, and it gives its reason for not using "arithmetic intensity": the older term counts the traffic between the processor and the cache, and the model needs the traffic between the caches and DRAM. The book's symbol \(I=F/Q\), with \(Q\) defined as the DRAM traffic in the section above, is the report's operational intensity.

What (10.8) assumes. (A1) Compute and data movement overlap completely, so that the time is the larger of the two terms and not their sum. (A2) \(Q\) counts the bytes at the DRAM interface after the caches have served every reuse they can; it is not the count of loads and stores that the program issues. The bound is correct with this \(Q\) whatever the cache size, and \(Q\) itself depends on the cache size (the three cases of the next section). (A3) \(P_{\text{peak}}\) and \(B_{\text{peak}}\) are rates that a program can approach, so they are measured and not read from a specification. The bound is an upper limit. A measured rate above it means that \(Q\) was overstated or that the caches served more than assumed. A measured rate far below it is the useful case: it points to a ceiling below the roof that the program has not broken through. The report names such ceilings: instruction-level parallelism and SIMD for the horizontal roof, unit-stride access and prefetching for the diagonal.

The arithmetic roof of this machine. The program below measures \(P_{\text{peak}}\). Each thread runs 10 independent chains of 4-lane (256-bit) fused multiply-adds; ten chains cover the latency of the FMA unit, and the start values differ so that the compiler cannot merge the chains. One round of the loop is 10 vector FMAs, 80 flop. Each thread does the same work, the program starts all threads together and takes the time of the slowest, as in the false-sharing section of Chapter 11, so the printed rate is \(p\) times the speed of the slowest thread. The program takes the best of 3 repetitions.

#include <stdio.h>
#include <omp.h>

typedef double v4 __attribute__((vector_size(32)));    /* 4 doubles = one 256-bit register */

#define CHAINS 10                                      /* independent accumulators hide the FMA latency */
#define ITERS 100000000L

/* one thread: ITERS rounds of CHAINS fused multiply-adds on 4 lanes = ITERS*CHAINS*4*2 flop */
static double burn(void)
{
    v4 m = {1.0000001, 1.0000001, 1.0000001, 1.0000001}, add = {1e-9, 1e-9, 1e-9, 1e-9};
    v4 a0 = {1, 2, 3, 4}, a1 = a0 + 1, a2 = a0 + 2, a3 = a0 + 3, a4 = a0 + 4,       /* distinct start values: */
       a5 = a0 + 5, a6 = a0 + 6, a7 = a0 + 7, a8 = a0 + 8, a9 = a0 + 9;               /* the chains cannot be merged */
    for (long i = 0; i < ITERS; i++) {                 /* each product-and-sum is contracted to one vfmadd */
        a0 = a0 * m + add; a1 = a1 * m + add; a2 = a2 * m + add; a3 = a3 * m + add; a4 = a4 * m + add;
        a5 = a5 * m + add; a6 = a6 * m + add; a7 = a7 * m + add; a8 = a8 * m + add; a9 = a9 * m + add;
    }
    v4 s = a0 + a1 + a2 + a3 + a4 + a5 + a6 + a7 + a8 + a9;
    return s[0] + s[1] + s[2] + s[3];
}

int main(void)
{
    double flop_per_thread = (double)ITERS * CHAINS * 4 * 2, sink = 0.0;
    printf("%8s %10s %10s\n", "threads", "Gflop/s", "per thread");
    int plist[] = {1, 2, 4, 8, 12};
    for (int pi = 0; pi < 5; pi++) {
        int p = plist[pi];
        double best = 1e30;
        for (int rep = 0; rep < 3; rep++) {
            double t0 = omp_get_wtime();
            #pragma omp parallel num_threads(p) reduction(+:sink)
            sink += burn();
            double t = omp_get_wtime() - t0;                  /* the slowest thread sets the time */
            if (t < best) best = t;
        }
        printf("%8d %10.1f %10.1f\n", p, p * flop_per_thread / best / 1e9, flop_per_thread / best / 1e9);
    }
    if (sink < 0.0) puts("unreachable");
    return 0;
}

Reading the two roofs together. The bandwidth that belongs in the roof of a kernel is the one measured with the same access pattern. The Jacobi sweep reads one stream (\(u\)) and writes one stream (\(u^{\text{new}}\)), as the copy and scale kernels of STREAM do. Both ask for 16 bytes per element and, with write allocate, move 24; so the DRAM traffic is 3/2 of the asked-for count. From the samples, one thread has \(P_{\text{peak}}=66.7\) Gflop/s and \(B_{\text{peak}}=15.6\) GB/s (the scale kernel on one thread, 10.4 GB/s asked for, times 3/2; the triad gives the same value, 11.7 times 4/3), so \(I^{*}=4.3\) flop/B. The Jacobi sweep under the roof

The intensity of the sweep has three values, according to what the caches do. Count the bytes of one sweep on a grid much larger than the caches, with 5 flop per point (Chapter 9 counts the same five: three additions and one multiplication for the average and one subtraction for the change).

  1. No reuse of loaded values. Every one of the five loads of the stencil comes from DRAM: 40 bytes. The store of \(u^{\text{new}}\) writes 8 bytes and, with write allocate, first reads the line: 16 bytes more. Total 56 bytes per point; \(I=5/56=0.089\).
  2. Rows reused from cache, ordinary stores. The point \((i,j)\) needs the rows \(i-1,i,i+1\) of \(u\). Moving from row \(i\) to row \(i+1\) needs the rows \(i,i+1,i+2\), of which two are already loaded. If the three rows stay in cache while the sweep runs along a row, each value of \(u\) comes from DRAM once: 8 bytes. The store costs 8 bytes of read and 8 bytes of write-back. Total 24 bytes; \(I=5/24=0.208\).
  3. Rows reused, streaming stores. As in case 2, but the stores bypass the cache and need no read: 16 bytes; \(I=5/16=0.3125\).

Every implementation of one sweep moves at least 16 bytes per point once the grid exceeds the cache: each interior value of \(u\) must be read at least once, and each value of \(u^{\text{new}}\) must be written once. Hence \(Q\ge16N^{2}\) and \(I\le0.3125\) for every way of coding a single sweep. Tuning the loop can move the sweep from case 1 to case 3 and no further. Williams et al. (§6.3.3) count the same structure for the explicit heat-equation stencil on a 3-D grid, 7 points: 8 flop for 24 bytes of compulsory traffic on write-allocate machines, an operational intensity of 0.33.

The layer condition. Case 2 holds when the three rows of \(u\) stay in cache. Three rows are \(3(N+2)\times8\) bytes. A cache replaces by use and not by plan, and the stream of \(u^{\text{new}}\) also passes through it, so a common rule of thumb asks that the rows fit in half of the cache of capacity \(C\):

\[ 24\,(N+2)\le \frac{C}{2}\quad\Longleftrightarrow\quad N\le\frac{C}{48}-2. \tag{10.10} \]

The rule is a heuristic and not a theorem. For the 48 KiB first-level cache it gives \(N\le1022\); for the 1.25 MiB second-level cache of a performance core, \(N\le27\,304\). The experiments below use \(N\le8192\). For \(N=4096\), three rows are 96 KiB: they do not fit in the first-level cache and they fit in the second, which is enough for DRAM traffic (the rows move from the second-level cache to the first-level cache several times, which does not reach DRAM). The condition holds for every out-of-cache size of the experiment, so the DRAM traffic is that of case 2 or case 3. For \(N\le512\) the whole working set, \(2(N+2)^2\times8\) bytes, is at most 4.2 MB and fits in the second-level or the third-level cache; DRAM is not involved, and the roof is a cache roof, which this chapter does not measure.

The bound. With \(I=5/24\) and the hardware bandwidth of the previous section, (10.8) gives \(P\le4.5\) Gflop/s for case 2 and \(P\le6.8\) Gflop/s for case 3 (5.1 Gflop/s with the 16.4 GB/s that the streaming stores reached). Against \(P_{\text{peak}}=202\) Gflop/s of the whole machine this is 2.2 % and 3.4 %. If an ordinary store costs a fraction \(w\) of a full extra read (the fill test above shows \(w\lt1\) at 4 threads), the sweep moves \(Q=16+8w\) bytes per point and the scale kernel, which has the same pattern, moves \(14.5(1+w/2)\) GB/s; the case-2 roof \(5B/Q=5\times14.5/16=4.53\) Gflop/s does not depend on \(w\). The roof of case 3, with streaming stores, is 5.1 Gflop/s at the 16.4 GB/s that the streaming-store triad reached. The sweep sits at \(I=0.208\) and the ridge is at \(I^{*}=9.3\): the sweep is to the left of the ridge by a factor of 45 in intensity (30 for case 3). The listing below measures it. It is the book's kernel, with the OpenMP directives of Chapters 11 and 12 added: parallel for splits the rows among the threads, reduction(max:…) combines the per-thread maxima, and omp simd allows the compiler to vectorize the inner loop with the maximum reduction. With one thread it is the serial kernel. The program first sweeps grids from \(N=64\) to 8192 on one thread, and then \(N=4096\) with 1 to 12 threads. It prints the time per point, the rate in Gflop/s at 5 flop per point, and a bandwidth computed from the modelled 24 bytes per point; that figure is a model value, not a measured byte count, because the guest shows no hardware counters. The build uses -O3 -march=native, whereas the serial timings of Chapter 9 use -O2; the interpretation below compares the two. The next program checks that the threaded sweep gives the same grid as the serial one.

#include <stdio.h>
#include <stdlib.h>
#include <math.h>
#include <omp.h>

#define IDX(i, j) ((i) * (N + 2) + (j))

/* One Jacobi sweep on the (N+2) x (N+2) grid u: 5-point average into the interior of unew,
   returns max |unew - u| over the interior. With one thread this is the serial kernel. */
static double jacobi_step(int N, const double *u, double *unew)
{
    double maxd = 0.0;
    #pragma omp parallel for reduction(max:maxd) schedule(static)
    for (int i = 1; i <= N; i++) {
        #pragma omp simd reduction(max:maxd)
        for (int j = 1; j <= N; j++) {
            double v = 0.25 * (u[IDX(i - 1, j)] + u[IDX(i + 1, j)] + u[IDX(i, j - 1)] + u[IDX(i, j + 1)]);
            double d = fabs(v - u[IDX(i, j)]);
            if (d > maxd) maxd = d;
            unew[IDX(i, j)] = v;
        }
    }
    return maxd;
}

static double *make_grid(int N)
{
    size_t n = (size_t)(N + 2) * (size_t)(N + 2);
    double *g = malloc(n * sizeof(double));
    #pragma omp parallel for schedule(static)           /* first touch with the same row split as the sweep */
    for (int i = 0; i < N + 2; i++)
        for (int j = 0; j < N + 2; j++) g[IDX(i, j)] = (i == 0) ? 1.0 : 0.0;   /* u = 1 on the top edge, 0 elsewhere */
    return g;
}

/* best time of three runs of 'sweeps' sweeps, in seconds per sweep */
static double time_sweeps(int N, int sweeps)
{
    double *u = make_grid(N), *unew = make_grid(N), best = 1e30, sink = 0.0;
    for (int rep = 0; rep < 3; rep++) {
        double t0 = omp_get_wtime();
        for (int s = 0; s < sweeps; s++) {
            sink += jacobi_step(N, u, unew);
            double *t = u; u = unew; unew = t;
        }
        double t = (omp_get_wtime() - t0) / sweeps;
        if (t < best) best = t;
    }
    if (sink < 0.0) puts("unreachable");
    free(u); free(unew);
    return best;
}

int main(void)
{
    const double flop_per_point = 5.0, bytes_per_point = 24.0;   /* the model of the text: 3 add + 1 mul for the average, 1 sub for the change; 8 B read + 8 B write + 8 B write-allocate */
    printf("serial sweep, 5 flop and 24 B per point (modelled, not measured)\n");
    printf("%6s %10s %9s %9s %9s\n", "N", "set (MiB)", "ns/point", "Gflop/s", "GB/s");
    omp_set_num_threads(1);
    for (int N = 64; N <= 8192; N *= 2) {
        double mib = 2.0 * (N + 2.0) * (N + 2.0) * 8.0 / 1048576.0;
        int sweeps = (int)(1e8 / ((double)N * N)) + 1;
        double t = time_sweeps(N, sweeps), pts = (double)N * N;

    }
    printf("\nN = 4096, threads\n%8s %9s %9s %9s %9s\n", "threads", "ns/point", "Gflop/s", "GB/s", "speedup");
    int plist[] = {1, 2, 4, 8, 12};

The grids agree bit for bit, because each point of \(u^{\text{new}}\) is computed from \(u\) alone and the maximum of positive numbers does not depend on the order of the comparisons. The values also show a property of Jacobi iteration that matters for the cost: after 200 sweeps on a grid with \(N=128\) the centre, 64 rows from the heated edge, holds \(1.1\times10^{-10}\), although the boundary value reached it at sweep 64; the point 8 rows from the edge is at 0.42. A Jacobi sweep moves information one grid point, but the value spreads like diffusion, over a distance of the order of the square root of the number of sweeps, which is why the number of sweeps to convergence grows as \(N^2\) (Chapter 9).

What the result changes in practice. Four consequences follow for the running case. First, adding threads beyond the number that saturates the memory buys nothing for this sweep on this machine, in contrast with the \(\pi\) loop of Chapter 11, which has no array traffic and scales to the arithmetic limit of the machine. Second, the one change that raises the roof is more bandwidth: a second memory module would double the pin rate of (10.2) from 25.6 to 51.2 GB/s; if the same 85 % of it were sustained, the bound of the sweep at four or more threads would double as well, and the \(\pi\) loop would not change. The chapter did not measure this, and one thread, which is limited by the requests it keeps in flight, would gain less. Third, changing the intensity needs a change of the data: a sweep in single precision has \(I=5/12=0.42\) in case 2, at the price of the precision of the answer, and a sweep that performs several iterations on one block of rows before it moves on (time blocking) raises \(I\) at the price of a different schedule. Neither is part of the book's kernel. Fourth, the result is the reason why accelerators matter for this problem: what they supply is bandwidth, as the next sections show.

Shared-memory and distributed-memory machines, and the node of a leadership system W3L4 0:06

The lecture divides parallel machines into two classes. In a shared-memory machine every processor can address the whole data space. The lecture's slide lists the advantages as ease of programming, suitability for automatic parallelization by compilers, and the ability to run large-memory serial programs; and the disadvantages as expense, difficulty of implementation in hardware, a processor count limited by contention and coherency ("currently around 512"), and the warning to "watch out for the NU part of NUMA", the non-uniform memory access time. In a distributed-memory machine each node has a locally addressable memory and the nodes are joined by a network (InfiniBand, Myrinet, Giganet on the slide). Its advantages are size, limited only by room size, cable length, power and cooling, and money; and lower cost to build and run. Its disadvantage is programming: the problem must be decomposed, the parts must be sent to the nodes explicitly, and data that sits on another node must be requested by a message. The lecture calls this the problem of data locality. A massively parallel processor (MPP) is distributed memory at the largest scale and often shared memory at the lower levels, as the slides' IBM BlueGene/L (131 072 processors at 700 MHz, 256 MB of RAM per processor) and Sandia's Red Storm (12 960 dual-core 2.4 GHz Opterons, 4 GB per processor) show. Large machines today are of this kind: the node is a shared-memory machine, and the system is the nodes plus a network.

A model for several links. Section "the Roofline model" applied (10.1) to one link, the DRAM interface. A system has more links: HBM to a GPU, DRAM to a CPU, the link between CPU and GPU, the network interface. Let \(Q_k\) be the bytes that the run sends across link \(k\) and \(B_k\) the bandwidth of that link. The argument that gave (10.1) applies to each link in turn: \(T\ge Q_k/B_k\) for every \(k\), and \(T\ge F/P_{\text{peak}}\). Dividing into \(F\), with \(I_k=F/Q_k\),

\[ P\;\le\;\min\Bigl(P_{\text{peak}},\ \min_k\, I_k B_k\Bigr). \tag{10.11} \]

The binding link is the one with the smallest \(I_kB_k\). The model assumes that all transfers overlap with each other and with the arithmetic, and that the links do not share a resource; both assumptions fail in places that the text points out. The same program has a different intensity at each link: the Jacobi sweep of one GPU has \(I_{\text{HBM}}=5/16\) at its high-bandwidth memory and \(I_{\text{net}}=5N^2/(32N)=5N/32\) at the network, because the halo that a subdomain of \(N\times N\) points exchanges per sweep is 4 sides of \(N\) values of 8 bytes. Chapter 16 develops the exchange itself.

The CPU and the GPU W3L4 7:21

The lecture shows a slide from Prof. Wen-mei Hwu (University of Illinois): a CPU drawn as a large control block, four ALUs and a large cache, next to a GPU drawn as many small ALU columns with little cache. It annotates the CPU as the von Neumann architecture, "single instruction, single data" (SISD), and the GPU as SIMD, "single instruction, multiple data". It adds an analogy: to deliver 10 000 pizzas, one could use one heavy truck or 1000 scooters of 10 pizzas each, and for a task that is repetitive and independent the scooters are faster although each is slower.

The analogy is correct and the labels need a correction. A modern CPU also executes SIMD instructions. The program peak_fma.c above reaches 66.7 Gflop/s on one thread of this laptop by executing 4-lane, 256-bit fused multiply-adds, and a scalar program on the same core would reach a quarter of that or less. The distinction that the slide draws is one of design: a CPU spends its area on control and cache to make one thread fast and to hide latency, and a GPU spends it on arithmetic lanes and on a memory system of high bandwidth to make many threads complete in a given time, hiding latency by switching between threads. The GPU programming model is called SIMT (single instruction, multiple threads) and differs from SIMD in that each thread has its own registers and may follow its own path through the code; Chapter 18 defines it. In the terms of this chapter, what the GPU adds is bandwidth. One GCD of the Frontier GPU has an HBM bandwidth of 1.6 TB/s, 62.5 times the 25.6 GB/s pin rate of the laptop's one memory module.

The lecture then states that the performance share of accelerators in the largest systems increases dramatically. The slide it shows (TOP500, 2006–2014) plots the number of systems with accelerators, which grows to about 70 of the 500 by 2014, not the performance share. The statement is supported for the count and not shown for the share.

The node as a ladder of bandwidths. The node of the slide has 1 CPU with 64 cores and 512 GB of DDR4, 4 MI250X packages that the operating system sees as 8 GPUs of 64 GB HBM each, 2 NVMe drives of 1.92 TB, and 4 network interfaces; each GCD is attached to one level-3 cache region of the CPU, and each network interface to one MI250X. The network: dragonfly groups W3L4 20:08

The lecture describes the Slingshot interconnect of Frontier as an Ethernet superset with HPC features and states that it uses a dragonfly topology: a group of endpoints connected to switches that are connected all-to-all, and a set of groups connected all-to-all, with at least one link between each pair of groups. Frontier has 74 compute groups with 128 nodes and 32 switches per group and 4 interfaces per node. Kim, Dally, Scott and Abts (ISCA 2008) define the topology by three parameters: \(\nu\) terminals per router, \(a\) routers per group, and \(\gamma\) global channels per router (Kim et al. write \(p\), \(a\), \(h\); this chapter keeps \(p\) for threads and \(h\) for the grid spacing). A router has radix \(r=\nu+a+\gamma-1\) (one port per terminal, \(a-1\) local channels, \(\gamma\) global channels). The routers of a group act together as one virtual router of radix \(a(\nu+\gamma)\), which is why a minimal route crosses at most one global channel (Kim et al., abstract). The largest network with these parameters has \(g=a\gamma+1\) groups and \(M=a\nu(a\gamma+1)\) terminals, with exactly one channel between each pair of groups; a smaller network has more global channels per group than there are other groups, and the excess is spread over the group pairs. For balanced load on traffic that is spread evenly, the authors recommend \(a=2\nu=2\gamma\), because a packet uses two local channels for each global channel it crosses.

Apply it to Frontier with the numbers of the HPE talk of 2023: each 64-port switch has up to 16 links to nodes, 31 local links to the other switches of its group, and up to 16 global links. The group has 128 nodes with 4 interfaces, which is 512 terminals on 32 switches, so \(\nu=512/32=16\), \(a=32\), \(\gamma=16\), and \(a=2\nu=2\gamma\) holds exactly: Frontier is built to the balance rule. Of the 64 ports, 63 are in use. A group has \(a\gamma=512\) global links, 7.0 for each of the 73 other compute groups if all were used for that. The same slide states "4 links between each of the 74 compute groups", which would use 292 of the 512 links; the two statements do not agree, and the chapter does not resolve them. The listing computes both consequences for the capacity across the middle of the machine. If 37 groups send to the other 37, the number of links that cross the cut is \(37\times37\times\) (links per pair); at 25 GB/s per link per direction (an assumption: the slides call it bidirectional) that is 137 TB/s for 4 links per pair and 240 TB/s for 7.0. The 4 736 nodes of one half (37 groups of 128) inject up to 474 TB/s. The network can therefore carry between 29 % and 51 % of the injection rate across the cut, so an exchange in which every node sends to the other half is limited by the global channels, and an exchange between neighbours inside a group is not. The dragonfly is cheaper than a full network because it has fewer long cables; Kim et al. report a cost 20 % below the flattened butterfly and 52 % below a folded Clos network for 16K nodes in their model. The chapter did not test the cost claim.

Two more facts of the lecture complete the picture and carry no number to check. The programming environments of Frontier include the Cray compiler (LLVM-based), the AMD ROCm compiler, GCC and oneAPI DPC++, with the models OpenMP, HIP, Kokkos, RAJA, SYCL, OpenACC, OpenCL and UPC++. The course limits itself to OpenMP, OpenACC, CUDA and MPI. The uses that the lecture shows are a NASA study of landing vehicles on Mars, which cannot be tested in flight in that atmosphere and is therefore computed, and a simulation of a mining-explosive transport accident in Utah to find safer ways of packing explosives. The lecture also shows the IIT Bombay machine Spacetime2, before the Frontier slides. From its slide, Spacetime2 has a peak of 1 PFLOP/s, a power of 0.2 MW, 43.75 TB of memory, 9 792 cores (Intel Skylake and Broadwell) and 64 P100 GPUs. The listing above gives two ratios between the machines: memory per unit of peak is 43.75 MB per GFLOP/s for Spacetime2 and 5.62 for Frontier, a factor of 7.8 less, and the peak per watt is 5.0 GFLOP/s per W against 75.3, a factor of 15. The superchip, NVLink-C2C and the cost of a link W3L5 13:43

The lecture describes the Grace Hopper superchip as a CPU and a GPU on one module, joined by a coherent interface of 900 GB/s. The relevance to the memory model of this chapter is the unit of transfer. A page migration moves 4096 bytes. If the GPU needs one 64-byte line of the page, the migration moves 64 times the bytes that were needed, and, in the section on paging, the cost of the fault is of the order of microseconds (1.2 to 3.3 μs for a minor fault on this laptop) while the bytes of a page cost 9 ns of link time at 450 GB/s. Co-scheduling and the one application result W3L5 23:30

The slide "Co-scheduling" shows the node divided among jobs: one job exclusive to the node, or job A on 64 Grace cores with its share of LPDDR5X, and job B on 8 cores plus a Hopper GPU or a slice of it (a multi-instance GPU partition, "MIG", in the slide; the datasheet describes MIG as partitioning the GPU into isolated instances). Each partition carries a label "MPAM", the Arm mechanism for partitioning and monitoring memory-system resources; the whitepaper states that administrators can partition the available LPDDR5X bandwidth and the CPU cache usage. The relation to this chapter's measurements is a reading of the chapter and not a statement of the slide: on this laptop the memory bandwidth saturates with two to four threads, so a job that takes four threads takes nearly all the bandwidth of the node, and a division of cores without a division of bandwidth does not isolate memory-bound jobs. A bandwidth partition is the control that a memory-bound job needs.

The slide that closes the lecture ("Grace + Hopper makes acceleration more accessible") shows normalized execution time for ABINIT, a materials-science code: 1 on x86, 1.16 times faster on x86 plus Hopper, and 4.25 times faster on Grace Hopper. The bars could be read as the speedups of different applications. The slide's caption and the whitepaper (Figure 19, p. 30) say otherwise. The caption reads "A performance simulation for ABINIT with NVBLAS featuring Titanium 255 Atoms using the LOBPCG algorithm". It is one application and one input, and it is a simulation of performance, not a measurement on every machine; the whitepaper adds that the code was ported by redirecting its BLAS calls to the GPU through NVBLAS, so that the GPU runs the dense linear algebra and the CPU runs the rest.

The bars carry more information than the two numbers. Reading the heights from the slide, with an uncertainty of about \(\pm0.03\): in the x86 bar the part that stays on the CPU is about 0.43 of the total time, and the part moved to the GPU is the remaining 0.57. If the GPU were infinitely fast and the transfers were free, the time would be 0.43 and the speedup 2.3. The simulated 1.16 for x86 plus Hopper is far below this because the segment of CPU–GPU transfers, about 0.40, takes back nearly all that the GPU gains from the 0.57. On the superchip the transfer segment is about 0.04 and the CPU segment is about 0.17, the CPU part running 2.5 times faster than on the x86 machine. The total of 0.235 is the sum of both effects, and the speedup of 4.25 is above the bound of 2.3 that the GPU alone could give, because Grace and the link both change the result. The accounting repeats the lesson of the roofline: the arithmetic that was offloaded was not the problem. The data movement between the two memories and the speed of the part that stayed behind were. The chapter reads the bars from a projected image, so the segment values are estimates; the speedups 1.16 and 4.25 are quoted from the slide.

The models of the chapter establish five things. First, the run time of a program has two lower bounds, one from the arithmetic and one from each memory link, and the larger one is a bound for the run (10.1, 10.11). Second, the loads of one dependent chain are limited by latency, and the loads of an independent stream by bandwidth, and the two rates differ by 26 to 63 times on this machine for the working sets that exceed the caches. Third, the sweep of the book's Jacobi kernel has an intensity of 0.208 flop/B in the realistic case and at most 0.3125 in any case, which is 30 to 59 times below the ridge point of this machine (9.3 to 12.3 flop/B) and 14 to 80 times below the ridge points of the machines of Table 10.3. Fourth, on this machine the measured sweep rate at \(N=4096\) lies between 3.3 and 4.5 Gflop/s on 1 to 8 threads, which is 2 % of the 12-thread arithmetic peak and, at 1, 2, 4 and 8 threads, 98 to 103 % of the memory roof of case 2 for the matching thread count. Fifth, the machines of the lectures differ from the laptop mainly in bandwidth, and the lecture's numbers for them are correct to the extent that the sources of Table 10.2 show.

The models leave out much. The roofline assumes full overlap of arithmetic and data movement, which (10.1) states as a bound and not as a prediction. It treats the memory system as one pipe of constant bandwidth, and the measurements show that the rate depends on the kernel and on the thread count: the kernels with stores reach 19.5 to 21.8 GB/s if every store reads its line, the read-only dot product of exercise 6 and the streaming-store triad reach 16.4 to 16.8 GB/s, and the write-only fill shows that ordinary stores do not always carry the full extra read. The chapter has no tested explanation, and the guest shows no hardware counters, so the traffic was not measured. The roofs for the Jacobi sweep therefore carry an uncertainty of up to a factor of 1.33 in \(B\) and in \(Q\) separately, which cancels in the placement because the sweep is compared with the scale kernel in the same count. The data show the spread. In the five runs of jacobi_bench.c the 4-thread rate at \(N=4096\) lay between 3.9 and 4.9 Gflop/s; the highest value (4.92) is 9 % above the roof of 4.53 Gflop/s. A rate above its bound means that \(B\) or \(Q\) was misestimated, as the section on the roofline says. At one thread the sample is 3 % above its roof.

The measurement conditions limit the numbers. The machine has one memory module, 25.6 GB/s of pin rate, a hybrid processor and a virtualization layer that this chapter did not control; other jobs were running, and the ranges over five runs are wide (the 12-thread FMA rate ranged from 196 to 210 Gflop/s in the five runs and was 233 to 290 Gflop/s in four earlier runs, which the chapter attributes, without a test, to the thermal or power state of the laptop). Every GPU number in the chapter is a bound computed from a datasheet or a slide, not a measurement; the RTX 3050 of this machine was not used. The energy numbers are the slide's. The original paper of Wulf and McKee could not be opened. The Frontier facts are dated 2026-10-26 and the machine is being upgraded.

Exercises

Exercise 1 (derive). For the transfer model (10.3), derive the transfer size \(b_\varphi\) at which the delivered rate \(b/t(b)\) is a fraction \(\varphi\) of \(B\). Compute \(b_{0.9}\) for the disk of the slide (\(\tau=10\) ms, \(B=187\) MB/s) and for a DRAM access with \(\tau=100\) ns and \(B=15\) GB/s. State what the second result says about a 64-byte cache line.

Solution

The delivered rate is \(b/(\tau+b/B)\). Set it equal to \(\varphi B\): \(b=\varphi B\tau+\varphi b\), so \(b(1-\varphi)=\varphi B\tau\) and \(b_\varphi=\dfrac{\varphi}{1-\varphi}\,\tau B=\dfrac{\varphi}{1-\varphi}\,b_{1/2}\). At \(\varphi=1/2\) this is \(b_{1/2}\), which checks (10.4). At \(\varphi=0.9\) the factor is 9. Disk: \(b_{1/2}=10^{-2}\ \text{s}\times187\times10^{6}\ \text{B/s}=1.87\) MB, so \(b_{0.9}=16.8\) MB, about 4100 pages of 4 KB. DRAM: \(b_{1/2}=100\times10^{-9}\times15\times10^{9}=1500\) B and \(b_{0.9}=13\,500\) B. A 64-byte line is 4 % of \(b_{1/2}\) and 0.5 % of \(b_{0.9}\): a single line transferred alone runs at \(64/(100\ \text{ns}+4.3\ \text{ns})=0.61\) GB/s, 4 % of \(B\). Ninety percent of the bandwidth needs about 200 lines in transit, \(13\,500/64=211\). The model counts the transfers of one request stream; the machine overlaps many (the last column of hierarchy.c), and (10.4) is then the number of bytes that must be in flight.

Exercise 2 (compute). A blocked matrix multiplication updates a tile \(Z_{ij}\) of \(n_b\times n_b\) doubles by \(Z_{ij}\mathrel{+}=X_{ik}Y_{kj}\), with the three tiles in the cache. Per tile update it loads \(X_{ik}\) and \(Y_{kj}\) from DRAM and keeps \(Z_{ij}\) in cache across the sum over \(k\). Give its intensity in flop per byte as a function of \(n_b\). Find the smallest \(n_b\) for which the intensity reaches the ridge point of 9.3 flop/B of this machine with 12 threads, and check that three tiles fit in the 1.25 MiB level-2 cache. Compare with the matrix–vector product \(y=Ax\) on an \(N\times N\) matrix.

Solution

A tile update performs \(2n_b^3\) flop and loads \(2n_b^2\) doubles, \(16n_b^2\) bytes, so \(I=2n_b^3/(16n_b^2)=n_b/8\). Setting \(n_b/8\ge9.3\) gives \(n_b\ge74.4\), so \(n_b=75\) (a multiple of 8 such as 80 is better for the vector units). Three tiles of 75 × 75 doubles are \(3\times8\times75^2=135\,000\) bytes, 132 KiB, about 10 % of the level-2 cache, so they fit with room for the layer-condition margin of (10.10). The matrix–vector product reads each of the \(N^2\) matrix entries once and does 2 flop per entry: \(I=2N^2/(8N^2)=0.25\) flop/B, plus \(O(N)\) for the vectors. Its intensity is 20 % above that of the Jacobi sweep in case 2 (0.208) and it cannot be improved by blocking, because each matrix entry is used once. Its bound on this machine is \(0.25\times21.8=5.4\) Gflop/s. Matrix–matrix multiplication can reach the arithmetic roof and the matrix–vector product cannot, and the reason is the reuse that each loaded entry of \(X\) and \(Y\) receives: \(n_b\) times.

Exercise 3 (counterexample). A student states: "The Jacobi sweep on this laptop cannot run faster than 4.5 Gflop/s, whatever the grid size." Use the measurements of the chapter to refute it, and say which assumption of the roofline the refutation breaks.

Solution

The first table of jacobi_bench.c gives, for a single thread, 12.5 Gflop/s at \(N=64\), 13.7 at 128 and 13.7 at 256, and 11.5 at 512, against the bound of 4.5 for 12 threads and 3.3 for one thread. These sweeps run from cache: the working set \(2(N+2)^2\times8\) bytes is 0.07, 0.26, 1.0 and 4.0 MiB, and the grids fit in the second-level or the third-level cache. The bound of 4.5 Gflop/s is \(I\,B_{\text{DRAM}}\), and it assumes (A2) that the bytes of the sweep cross the DRAM interface. For \(N\le512\) they do not, after the first sweep. The sweep then meets a higher bandwidth roof, that of the cache (the modelled 55 to 66 GB/s of the table, below the 120 to 250 GB/s that hierarchy.c measures for reads from the first and second level). The student's statement holds for grids that exceed the last-level cache, \(N\ge2048\) here, where the same program gives 3.2 to 3.4 Gflop/s on one thread; at \(N=1024\), a working set of 16 MiB just above the 12 MiB level-3 cache, the sample gives 4.6 Gflop/s, between the two regimes. The result also shows why the timing of a Jacobi code on a small grid says nothing about its behaviour at production size.

Exercise 4 (diagnose an assumption). A student reads from the STREAM table that triad reaches 15.0 GB/s with 4 threads, sets \(B_{\text{peak}}=15.0\) GB/s, computes the roofline bound of the Jacobi sweep as \((5/24)\times15.0=3.1\) Gflop/s, and then reports that the measured 4.45 Gflop/s of the 4-thread sweep "violates the roofline". Diagnose the errors and give the corrected bound.

Solution

There are two errors. First, the roofline needs the bandwidth in the same count as \(Q\). The sweep's \(Q=24\) bytes per point is the traffic at the DRAM interface, with write allocate. STREAM counts the bytes that the program asks for, 24 per element for triad, and a cache with write allocate moves 32. The 15.0 GB/s of the table is therefore \(15.0\times32/24=20.0\) GB/s of DRAM traffic, and the bound becomes \((5/24)\times20.0=4.17\) Gflop/s. The measured 4.45 Gflop/s is 7 % above it, so the first correction is not enough. Second, the triad has two read streams and one write stream, and the sweep has one read stream and one write stream; the kernels of STREAM with that pattern are copy and scale. Their counted rates at 4 threads are 14.4 and 14.5 GB/s, 21.6 and 21.8 GB/s of DRAM traffic (16 asked for, 24 moved), and the bound is \((5/24)\times21.8=4.53\) Gflop/s. The measured 4.45 Gflop/s is 98 % of it, so no violation. The single-thread values support the first correction: triad-nt, which avoids the write-allocate read, runs 1.32 times faster in the asked-for count than triad (15.5 against 11.7 GB/s), close to 32/24. The correction has its own uncertainty, stated in the section on limits: at 4 threads and more, triad-nt (16.4 GB/s of traffic) is below the 20 GB/s that the correction assigns to triad. \(Q\) and \(B\) are each uncertain by up to a factor of 1.33, and the uncertainty cancels in the comparison with the scale kernel. The lesson of the exercise is that a bandwidth measured in other bytes, or for another access pattern, is not a roof.

Exercise 5 (design judgment). The code of a research group is dominated by Jacobi sweeps on grids with \(N\ge4000\), run on this laptop with a tolerance of \(10^{-5}\) on the largest change. Compare three upgrades by their effect on the roofline bound and on the answer: (a) fill the second memory slot with a module of the same type; (b) replace the processor by one with twice as many cores at the same clock; (c) change the grid from double to single precision. Which would you choose first?

Solution

(a) The pin rate doubles from 25.6 to 51.2 GB/s (10.2), and if the same fraction of it is sustained (21.8 of 25.6, 85 %), the sustained bandwidth is 43.6 GB/s and the bound at \(I=5/24\) is 9.1 Gflop/s, twice the present 4.5. The answer does not change. The assumption is that two channels are populated in interleaved mode and that the processor can issue enough requests to fill them; the chapter measured neither. (b) The bound is \(I\,B_{\text{peak}}\) and does not contain the core count. Eight threads gave 4.43 Gflop/s and 12 gave 4.23, and the arithmetic peak is already 45 times above the sweep. The effect is nil, or a loss if the extra threads reduce the bandwidth, as the samples of 12 threads suggest. (c) Single precision halves the bytes per point (case 2: 12 bytes) and raises the intensity to \(5/12=0.42\), so the bound doubles to 9.1 Gflop/s at the same bandwidth. The cost is the answer: the rounding unit of single precision is \(6\times10^{-8}\), and the tolerance of \(10^{-5}\) on the largest change is 170 times larger, so the iteration will meet the tolerance. The rounding errors of single precision are not removed by the iteration, their size is at least the rounding unit, and the chapter did not measure how much they grow with the number of sweeps (of the order \(N^2\); Chapter 9). Choose (a) first: it doubles the bound and changes nothing else. Choose (c) only after checking the accuracy requirement, and then in addition to (a), for a factor of 4.

Exercise 6 (implementation and measurement). Write a read-only dot product \(s=\sum a_ib_i\) over two arrays of 16 million doubles, with an OpenMP reduction, and time it for 1, 2, 4, 8 and 12 threads as stream_mini.c does. State before running it which rate in the asked-for count the write-allocate model of the chapter predicts for 4 threads, given the copy and scale rates of 14.4 and 14.5 GB/s, and compare with the measurement.

Solution

The program is the loop #pragma omp parallel for schedule(static) reduction(+:s) over s += a[i] * b[i] with the same first-touch initialization and best of 7; it is built with gcc -O2 -march=native -fopenmp -ffast-math (the flag allows the compiler to vectorize the reduction). The dot product asks for 16 bytes per element and moves 16, because nothing is stored. The model of the chapter says that the DRAM interface delivered \(14.4\times24/16=21.6\) GB/s for copy, so a read-only kernel limited by the same interface should reach about 21.6 GB/s in the asked-for count, 2.7 Gflop/s at 2 flop per 16 bytes. Three runs on this machine gave, for 4 and 8 threads, 15.3 and 15.4, 16.2 and 16.5, and 15.4 and 16.8 GB/s, that is 1.9 to 2.1 Gflop/s, and 10.6 to 13.8 GB/s for one thread. The prediction failed by 22 to 29 %. The measurement agrees with the streaming-store triad (16.4 GB/s at 4 threads) and not with the kernels that store through the cache, so the interface did not deliver 21.6 GB/s to a stream without stores. The write-only fill of the section on STREAM decides part of the question: at 4 threads the ordinary fill asks for 14.6 GB/s, and a full write-allocate read would make it 29.2 GB/s, above the 25.6 GB/s pin rate, so at that thread count the write-allocate model overstates the traffic of the kernels with stores. How much it overstates them the chapter cannot say without counters. The exercise shows what a prediction from a model is for: the failed prediction located the limit of the byte-counting argument, which the successful predictions of the single-thread triad and of the Jacobi roof had hidden.
