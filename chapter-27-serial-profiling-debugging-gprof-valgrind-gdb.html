Profiling and debugging serial codes: gprof, Valgrind and GDB

A heat solver spends 4.12 sampled seconds updating a grid and 3.12 sampled seconds copying it. Accelerating only the update can never remove the copy: even an infinitely fast update would improve that recorded workload by only about 2.32 times. Meanwhile, a five-integer allocation can finish normally after writing a sixth integer and leaking all 20 allocated bytes. Performance and correctness therefore require different evidence. The running task is to decide which part of a serial solver to change, identify a memory defect that ordinary execution can conceal, and stop a wrong update at the instruction that creates it.

Grounded in the NPTEL High Performance Scientific Computing recordings W10L4: profiling serial codes using GNU gprof, W10L5: profiling and debugging using Valgrind, and W10L6: debugging using GDB. Lecture material: the sequential/parallel time model, Amdahl's bound, gprof compilation and reports, the Laplace compute/copy example, Memcheck, matrix and stencil locality with Cachegrind, instruction attribution with Callgrind, a threading-error example with Helgrind, and GDB breakpoints, stepping, variable inspection, watchpoints and backtraces. Research extensions: the original Graham–Kessler–McKusick gprof paper and GNU manuals explain measurement and attribution; Nethercote and Seward explain dynamic instrumentation and shadow state; the Valgrind and GDB manuals specify tool behavior and limits. Original teaching constructions: the numerical benefit budgets, sampling model, caller-cost counterexample, bounded self-contained programs, diagnostic contracts, first-sweep oracle and six solved exercises. Lecture measurements remain historical examples; the new captures use separate smaller workloads.

A program, an execution and a measurement are different objects

A source program is a description of possible computations. A binary is the machine code produced by a particular compiler, its options and its linked libraries. An execution is one run of that binary with particular inputs and an environment. A profile describes selected events in that execution: sampled instruction locations, counted calls, simulated cache accesses, or another stated quantity. These objects form a chain, and a claim about one member does not automatically apply to the next. Reading a source file does not determine how often a branch executes. Counting instructions does not determine how long the processor waits for memory.

The running numerical object is a square grid with \(N\) interior points in each direction. Two arrays, u and unew, each contain \((N+2)^2\) double-precision floating-point values, stored by rows with an explicit boundary. Here double precision means C's double as implemented on the checked machine; the examples use its ordinary arithmetic, not a guarantee of exact real arithmetic. The top edge is one, the other three edges are zero, and the initial interior is zero. Corners remain zero because the interior stencil never needs them. The spacing on the unit square is \(h_g=1/(N+1)\).

One Jacobi sweep replaces every interior value by the average of its four old neighbors. The superscript \(k\) denotes the iteration index, and \(r_k\) is the largest absolute change in the sweep:

\[ u^{k+1}_{i,j}=\frac14\left(u^k_{i-1,j}+u^k_{i+1,j}+u^k_{i,j-1}+u^k_{i,j+1}\right),\qquad r_k=\max_{1\le i,j\le N}|u^{k+1}_{i,j}-u^k_{i,j}|. \tag{27.1} \]

The function jacobi_step computes the new interior and returns this update norm. A driver can compare it with a tolerance tol, but the profiling driver deliberately performs a fixed max_iter sweeps. This holds work constant when comparing runs. The norm is not itself the temperature error or the differential-equation residual. For the old grid, the maximum magnitude of the discrete Laplacian is \(4r_k/h_g^2\). A small update needs interpretation through the grid and stopping rule.

The execution model also has memory objects with allocation lifetimes, a sequence of function calls, and a current machine state. Allocation creates a block; deallocation ends its lifetime. A pointer records an address, not permission to access every byte near it. A call stack records the active nested calls, rather than every call that has ever completed. These distinctions explain why a profiler, a memory checker and a debugger can observe different failures in the same source.

The examples run on the book's Intel Core i5-12450H machine under Windows Subsystem for Linux (WSL), Ubuntu 24.04. GNU gprof 2.42, Valgrind 3.22.0 and GNU Debugger (GDB) 15.1 were checked as installed tools on 2026-10-28. Every listing creates its own files in its isolated execution directory. Core dumps are disabled; GDB runs in batch mode with initialization and history saving disabled. There is no debugger-attachment, system-configuration or package-installation experiment.

A time budget identifies valuable changes W10L4 0:38

Let \(p\) be the number of processing elements. Let \(T_1\) and \(T_p\) be wall-clock execution times for a fixed problem on one and \(p\) elements; speedup is \(S_p=T_1/T_p\), and parallel efficiency is \(E_p=S_p/p\). In the lecture's decomposition, \(\sigma(N)\) is the time that must remain sequential, \(\varphi(N)\) is work time that might be divided among elements, and \(\kappa(N,p)\) is additional parallel overhead, all measured in seconds. The model assumes the parallel part can be divided evenly and retains the same amount of useful work:

\[ T_1=\sigma+\varphi,\qquad T_p\geq\sigma+\frac{\varphi}{p}+\kappa,\qquad S_p\leq\frac{1}{f+(1-f)/p+\kappa/T_1},\quad f=\frac{\sigma}{T_1}. \tag{27.2} \]

The last expression follows by dividing both times by \(T_1\). Here \(f\) is the sequential fraction, so \(1-f\) is the parallelizable fraction. Setting \(\kappa=0\) gives the familiar Amdahl bound. For \(f=0.1\), the limit as \(p\) grows is ten, while at eight elements the bound is \(1/(0.1+0.9/8)=4.706\). Ninety percent parallelizable means ten percent sequential. The end cases require care: \(f=1\) permits no useful parallel speedup in this model; \(f=0\) gives the ideal bound \(p\), with no finite saturation limit when overhead is neglected.

These are assumptions about a decomposition, not labels a tool can infer from a function name. A function that took 40 percent of a serial execution is not thereby inherently sequential. A copy may be parallelizable but already limited by memory bandwidth; distributing it may fail to divide its time by \(p\). Conversely, changing an algorithm can eliminate work and leave the fixed-work model. A measured speedup beyond a simple model can indicate changed cache behavior or a changed baseline. It calls for checking the model before declaring the measurement impossible.

The historical flat profile at W10L4 18:52 shows 4.12 seconds in compute, 3.12 in copy, and 0.01 in initialization, totaling 7.25 sampled seconds. The report prints 56.83, 43.03 and 0.14 percent respectively; the rounded seconds and percentages need not divide into exactly identical last digits. Both major functions have 1000 counted calls. Their call counts agree with a driver that performs 1000 sweeps; the profile alone does not establish that those sweeps converge.

For choosing a serial optimization, let \(a\) be the fraction of baseline time affected by a change and \(q\) its local speedup. These differ from the inherently sequential fraction \(f\) and processor count \(p\). If all other costs stay fixed, the new time and overall gain are

\[ T_{\mathrm{new}}=T_{\mathrm{old}}\left[(1-a)+a/q\right],\qquad G=\frac{T_{\mathrm{old}}}{T_{\mathrm{new}}}=\frac1{(1-a)+a/q}. \tag{27.3} \]

With the lecture's update fraction \(a=0.5683\), a fourfold faster update gives \(G=1/(0.4317+0.142075)=1.743\). An infinitely fast update gives only \(1/0.4317=2.316\). This is why a small, elegant optimization to initialization has little value for that particular fixed-sweep run. Eliminating every initialization cost would improve it by about 0.14 percent. A different workload with very few sweeps could have a different budget.

The copy suggests a stronger design question: can it be removed instead of accelerated? If two full grids keep identical boundary values, the driver can exchange their pointers after a sweep. The new current grid then contains the new interior without copying it. This changes data movement rather than merely assigning the same copy to more processors. The historical profile motivates the question; it does not measure the gain of that redesign. Boundary initialization, output ownership and which buffer contains the final result must all be checked when implementing it.

The decision order is therefore explicit. First establish the required numerical behavior. Then measure where the chosen execution spends time. Estimate the largest possible benefit of a proposed change. Finally implement it, recheck correctness and measure an uninstrumented executable. A profile supports prioritization; it cannot replace the final comparison.

gprof combines counted calls with sampled execution locations W10L4 8:45

Instrumentation means adding operations that collect observations. Sampling means observing execution at selected instants instead of recording every event. gprof combines these methods. Its call information comes from compiler-added entry accounting, while its time distribution comes from samples of the program counter, the address of the currently executing instruction. The GNU implementation description, §9.1, identifies the entry hook commonly called mcount. The compilation instructions, §2.1, require -pg during the relevant compilation and linking steps. Adding it only to a final link cannot retroactively instrument separately compiled functions.

The basic experiment has three stages. Build an instrumented executable, run it on a representative input, then analyze its generated profile data together with that same executable. A successful ordinary termination normally writes gmon.out in the working directory. That file belongs to a run and a binary; pairing it with another build can misattribute addresses. A failed or abruptly killed process may not produce a usable final profile. Keep runs in separate directories or use explicit output management, so a stale file cannot masquerade as new evidence.

The flat-profile description, §5.1, distinguishes self time, cumulative time, calls and per-call values. Self time charges a sample to the function containing the sampled instruction. Cumulative seconds are a running sum down the displayed rows; they are not a function's elapsed lifetime. The count of calls is separate evidence. Dividing self seconds by calls estimates average self time per invocation for that observed input, with the time estimate's sampling limitations intact.

The following complete program uses \(N=256\) and 1200 fixed sweeps. Its two grids occupy \(2(258)^2(8)=1{,}065{,}024\) bytes on the checked machine. It verifies the first-sweep values and requires every final interior value to be finite and between zero and one. The bound is an invariant of averaging neighbors in that interval; it is a useful defect detector, not a solution-accuracy certificate. The build uses no optimization and prevents inlining so that named functions remain visible. This is a teaching profile of that build, not a claim about an optimized production solver.

The run command generates both flat and call-graph files, requires 1200 calls of each major routine, and displays the beginning of the flat profile. No earlier listing or scratch file is needed. The printed profile is one sample capture, checked by successful return rather than identical time percentages. A subsequent run may have different samples while retaining the same counted calls.

#include <stdio.h>
#include <stdlib.h>
#include <math.h>
#define IDX(i,j) ((size_t)(i)*(N+2)+(j))
double jacobi_step(int N, const double *u, double *unew) {
    double change=0;
    for (int i=1;i<=N;i++) for (int j=1;j<=N;j++) {
        size_t k=IDX(i,j);
        unew[k]=0.25*(u[k-1]+u[k+1]+u[k-(N+2)]+u[k+(N+2)]);
        double d=fabs(unew[k]-u[k]);
        if(d>change) change=d;
    }
    return change;
}
void copy_grid(int N, const double *unew, double *u) {
    for(int i=1;i<=N;i++) for(int j=1;j<=N;j++) u[IDX(i,j)]=unew[IDX(i,j)];
}
int main(void) {
    int N=256, max_iter=1200;
    size_t count=(size_t)(N+2)*(N+2);
    double *u=calloc(count,sizeof *u), *unew=calloc(count,sizeof *unew);
    if(!u || !unew) {free(u);free(unew);return 2;}
    for(int j=1;j<=N;j++) u[IDX(0,j)]=unew[IDX(0,j)]=1;
    double change=0;
    for(int iter=0;iter<max_iter;iter++) {
        change=jacobi_step(N,u,unew);
        if(iter==0 && (unew[IDX(1,1)]!=0.25 || unew[IDX(2,1)]!=0)) return 3;
        copy_grid(N,unew,u);
    }
    double sum=0;
    for(int i=1;i<=N;i++) for(int j=1;j<=N;j++) {
        double v=u[IDX(i,j)];
        if(!isfinite(v) || v<0 || v>1) return 4;
        sum+=v;
    }
    if(!(sum>0 && change>0)) return 5;
    puts("first-sweep and range checks passed; iterations=1200");
    free(u);free(unew);return 0;
}

The report's function percentages describe this input, compiler configuration and instrumentation. A solver with expensive input parsing, frequent output or a library preconditioner can move the hotspot elsewhere. The whole-program wall time also includes scheduling delays and other intervals that this profile need not charge as sampled user execution. For example, waiting for a file or sleeping can lengthen elapsed time without producing proportionate samples inside the waiting routine. Always name the measured quantity before using its fractions in a benefit calculation.

A zero time entry can mean insufficient samples W10L4 18:52

Suppose the report assigns a duration \(\Delta\) seconds to each sample and a function receives \(m\) samples. Its estimated self time is \(\widehat t=m\Delta\). Under an idealized Poisson model, where independent sample arrivals have a constant average rate, the variance of the count equals its mean. Replacing the unknown mean by the observed count gives a one-standard-deviation scale

\[ \operatorname{sd}(m)\approx\sqrt m,\qquad \operatorname{sd}(\widehat t)\approx\Delta\sqrt m,\qquad \frac{\operatorname{sd}(\widehat t)}{\widehat t}\approx\frac1{\sqrt m}. \tag{27.4} \]

The square root belongs to the number of samples, not directly to time in seconds. If \(\Delta=0.01\) seconds and the function receives 100 samples, the estimate is one second and the fluctuation scale is about 0.1 seconds, or ten percent. At 10,000 samples it is 100 seconds with about one second uncertainty, or one percent. The GNU sampling-error discussion, §6.1, gives this square-root rule and distinguishes sampled timing from counted calls. Equation (27.4) supplies a model for reasoning about the rule, rather than an assertion that every actual sample stream is Poisson.

The historical compute entry corresponds to roughly 412 samples and the copy entry to 312 at the printed 0.01-second period. Their individual fluctuation scales from this model are about 0.203 and 0.177 seconds. This does not license reporting the fractions as exact to two decimal places. Those digits are report formatting. For a fixed total of \(M_s\) independent samples and a true time fraction \(\theta\), a binomial model instead gives variance \(M_s\theta(1-\theta)\) for the function's count. The estimated fraction has standard deviation approximately \(\sqrt{\widehat\theta(1-\widehat\theta)/M_s}\). Both models warn against overinterpreting small counts.

Consider a function whose mean count would be one. The Poisson probability of seeing no samples is \(e^{-1}\approx0.368\). Thus it can execute and still have zero sampled time in more than a third of such idealized experiments. Conversely, if zero samples are observed, an approximate one-sided 95 percent upper count mean solves \(e^{-\mu}=0.05\), yielding \(\mu\approx2.996\). At a 0.01-second period that is about 0.030 seconds under the model. It is a model-dependent bound on an unseen average sampled duration, not proof that the function costs less than that in every execution.

Real runs can violate independence. A periodic workload can synchronize with periodic sampling; processor scheduling can change which intervals are observed; instrumentation changes the program being measured. Enlarging the input can also change the execution mix or cache regime. The practical response is to repeat representative runs, retain the sample counts and sampling period, and check whether the qualitative conclusion survives. Repetition reduces random uncertainty only when it brings new information; repeating the same systematic bias does not remove it.

There are two separate observer costs. Entry accounting adds work to each call, which can disproportionately affect programs made of many tiny functions. Sampling and writing the final profile also consume resources. A simple model writes instrumented time as the original time plus approximately \(c_e C_e\), where \(C_e\) is the number of instrumented entries and \(c_e\) is added cost per entry, plus other collection costs. The approximation need not be additive in practice because changed code layout affects caches. No universal fixed overhead percentage follows from this model.

Do not subtract the displayed mcount row and assume the remaining profile exactly recovers the original executable. Its changed layout and sample mix remain. Use a separate uninstrumented build with the intended optimization flags for the before/after elapsed-time comparison. A profile can reveal a likely target even when its timing is unsuitable as the final benchmark. That distinction is particularly important when comparing an instruction-counting run with a native execution.

Inclusive cost explains structure, but attribution has assumptions W10L4 21:39

A call graph is a directed graph whose vertices are functions and whose edges record calls from one function to another. A dynamic call graph includes edges traversed in the observed execution. An edge count tells how many calls followed that relationship. It does not provide their full chronological order. A complete event trace would record that order and can be much larger. The original Graham, Kessler and McKusick paper, pp. 120–122, §§2–3, develops the distinction and the combination of execution counts, samples and graph structure.

Self cost belongs to instructions in a function itself. Inclusive cost includes work charged through its callees. A main routine can have nearly zero self cost and nearly all the inclusive cost, because almost every instruction belongs to something it calls. Adding inclusive costs down a chain double-counts the same work. If main calls solve and solve calls jacobi_step, the time in that last function can appear in all three inclusive totals. Only a suitable disjoint decomposition sums to the whole.

The GNU call-graph description, §5.2, explains the self/children presentation. For the lecture's simple driver, every compute and copy call comes directly from main and neither major routine invokes another profiled application function. This makes its interpretation unusually transparent. The 7.25-second inclusive total for main does not contradict its zero self-time entry. It summarizes the descendants' work.

The difficult case is a shared callee. Suppose small_case calls a worker 99 times with cheap inputs, while large_case calls it once with an expensive input. Let the cheap calls cost one microsecond each and the expensive call cost one second. The worker's total is about 1.000099 seconds. Allocating that total in proportion to call counts charges roughly 0.990098 seconds to the cheap caller and 0.010001 seconds to the expensive caller. The actual costs are 0.000099 and one second. Accurate total time and accurate edge counts can therefore coexist with a badly misleading split between callers.

This is exactly the assumption identified by GNU's §6.2, estimating children times: average callee time is assumed independent of its caller when propagating cost using counts. The counterexample makes the missing information visible. Counts alone do not tell which caller supplied expensive arguments. A useful repair is to collect a context-sensitive profile, instrument separate input classes, or add explicit region timing around the two phases. Renaming functions without changing what is measured does not recover that information.

Recursion introduces cycles, so inclusive propagation requires cycle handling rather than a simple one-pass sum along a tree. Inlining, tail-call transformations and uninstrumented libraries further change the relationship between source routines and recorded nodes. Treat missing nodes as a coverage question. A function can disappear because the compiler folded it into its caller, because its binary lacked entry instrumentation, or because the run did not visit it. The profile does not choose among these explanations automatically.

The counted-call guarantee also has a threading boundary. In a multithreaded program, or one using multithreaded libraries, reliable entry counts require a thread-safe counting routine. GNU’s manual, §6.1, warns that mcount in the GNU C Library (glibc) is not thread-safe. The serial checks here therefore do not validate gprof call counts for an OpenMP or pthreads execution; use a profiler whose threading support has been established for the intended runtime.

The actionable interpretation is structural: identify a subsystem whose total work matters, inspect its expensive descendants, and then verify the assumed accounting. An expensive worker can motivate changing the algorithm that requests it as much as changing the worker itself. In a solver, avoiding redundant sweeps or unnecessary copies can be more valuable than reducing a few arithmetic instructions inside an unchanged call schedule.

Memcheck tests executed memory operations W10L5 0:40

Valgrind is a framework with several tools, rather than a synonym for its default Memcheck tool. Dynamic binary instrumentation translates and augments executed machine code while the program runs. It can observe operations in code that was not rebuilt with a special profiling flag. Nethercote and Seward, §§1–3, explain the framework and shadow values: additional state describing ordinary register and memory values. The extra execution and state explain why these checks can be expensive. Their cost is the price of collecting different information, not a native execution-time estimate.

A useful teaching abstraction gives each byte an addressability flag and each data bit a definedness flag. Allocating a heap block makes its bytes addressable; ordinary malloc does not establish initialized application values. Writing a defined value establishes definedness. Freeing a block ends its valid allocation lifetime. A read or write can be invalid even when the processor happens to map the surrounding page, because page accessibility and membership in the allocated object are different boundaries. The Memcheck manual, §§4.2 and 4.5, specifies the actual valid-address and valid-value machinery.

Now allocate five four-byte integers. The block occupies byte offsets zero through nineteen. Element index four starts at offset sixteen; index five starts at offset twenty, exactly one past the block. C permits forming a one-past pointer for some operations such as loop comparisons, but not dereferencing it to store an integer (C11 committee draft N1570, §6.5.6 paragraph 8). A memory checker can report an invalid four-byte write even if ordinary execution prints nothing unusual. No crash is required for a memory defect.

A leak is a separate question about ownership and reachability. If the program loses its only usable reference to allocated storage without releasing it, later work cannot reclaim that block through the ordinary deallocation interface. The leak checker classifies the pointer graph at its observation point. In brief, definitely lost means no pointer to the block is found; indirectly lost means it is reachable only through lost blocks; possibly lost involves an interior-pointer chain; still reachable retains a start-pointer chain. These categories are diagnostic descriptions, not substitutes for the application's ownership specification.

The following source deliberately reproduces the lecture's two-error shape in one bounded function: one out-of-bounds store and one 20-byte leak. Its second mode initializes five legal elements and frees the allocation. The bad mode must run only as a diagnostic example. Undefined behavior means its ordinary numerical or termination behavior is not a portable specification. Compiling without optimization helps retain this particular intended operation; the test contract is the tool report for the executed binary.

The command disables core dumps, captures each report in a local file, and explicitly selects an error exit status of 97. It sets --vgdb=no because this Windows-mounted workspace does not support the FIFOs needed by Valgrind's debugger bridge. The memory checker itself remains enabled; no debugger bridge or attach operation is claimed. It requires the invalid-write message and the definite-leak message, then requires zero reported errors for the fixed mode. The executable's own bad-mode return is zero, but the tool's error status is 97. The wrapper succeeds only when these expected diagnostic conditions hold, then prints a deterministic summary. This makes an intentionally erroneous program usable in a regression check without declaring its error a successful clean run.

#include <stdlib.h>
#include <string.h>
_Static_assert(sizeof(int)==4,"this diagnostic demonstration expects 4-byte int");
__attribute__((noinline)) void bad(void) {
    volatile int *p=malloc(5*sizeof(int));
    if(!p) exit(2);
    p[5]=10; /* Intentional out-of-bounds write; allocation is also leaked. */
}
int main(int argc,char **argv) {
    if(argc!=2) return 2;
    if(strcmp(argv[1],"bad")==0) {bad();return 0;}
    if(strcmp(argv[1],"fixed")!=0) return 2;
    int *p=malloc(5*sizeof *p);
    if(!p) return 2;
    for(int k=0;k<5;k++) p[k]=k;
    int ok=(p[4]==4);
    free(p);
    return ok?0:3;
}

bad: invalid write and 20-byte definite leak; tool exit=97
fixed: zero reported errors; tool exit=0

The static assertion states the integer-size assumption behind the 20-byte diagnostic. A different C implementation may reject that assumption at compilation; silently treating every integer as four bytes would be weaker teaching. The fixed mode checks its last initialized element before freeing. Its clean report establishes that this finite execution produced no reported errors under these options. It does not prove all inputs, branches, allocation-failure paths or executions are safe.

Uninitialized data require another distinction. Copying an uninitialized byte is not always the point at which a checker reports an error. A consequential use, such as a branch condition or a system-call argument derived from undefined data, may trigger the diagnostic later. The first report is therefore a place to begin following the value's origin, rather than proof that the allocation site itself performed the final harmful action. The Valgrind Quick Start, §§2–4, recommends debug information and fixing errors in report order, because one defect can cause later symptoms.

For a Jacobi code, lifetime checks and numerical checks complement each other. A wrongly sized allocation can produce an invalid access; the correct allocation with a factor of one-half instead of one-quarter can remain entirely addressable while computing the wrong mathematics. A leak-free program can still fail to converge, and a numerically plausible output can still have corrupted memory. Maintain both kinds of evidence rather than choosing a single tool as a universal validator.

Cachegrind asks a memory-locality question W10L5 10:53

A cache stores recently used memory blocks close to execution. A cache line is the block size transferred by the cache model; a hit finds a requested block there, while a miss needs a lower level. A first-level data cache and a last-level cache answer different questions. Cachegrind's labels D1 and LLd refer to simulated first-level data misses and last-level data misses. They are not interchangeable, and neither is automatically a measured number of off-chip transactions on the physical laptop.

The Cachegrind manual, §§5.2.11 and 5.8, describes the optional cache simulation and its limitations. The listing explicitly enables it with --cache-sim=yes. A simulated result is conditional on its cache geometry and model. Real prefetching, overlap, memory controllers and other microarchitectural details can make elapsed-time changes differ from miss-count changes. Use the model to test a locality explanation, then time the actual intended build separately.

The historical matrix example has 512 rows and columns, stored in C's row-major order. For a matrix entry \(B_{k,j}\), the element offset is \(kM+j\), where \(M\) is the matrix dimension. Advancing \(k\) with \(j\) fixed advances by \(M\) elements. For four-byte entries at \(M=512\), that stride is 2048 bytes. By contrast, advancing the last subscript advances four bytes. If a model line has 64 bytes, it can hold sixteen such adjacent entries. A row walk can exploit them consecutively, while a column walk can request a new line at every step.

This address calculation predicts an access-pattern issue, not a universal sixteenfold speedup. A line may be reused by later loops, the full matrix may fit at another cache level, and associativity controls collisions among active lines. The surrounding loop order matters as much as one address expression. Counting the maximum available spatial reuse is a first hypothesis, not a complete cache analysis.

The mathematical product is \(C_{i,j}=\sum_{k=0}^{M-1}A_{i,k}B_{k,j}\). Replacing \(B_{k,j}\) by \(B_{j,k}\) without changing stored data computes a different product. Instead define a stored transpose \(BT_{j,k}=B_{k,j}\), then use \(A_{i,k}BT_{j,k}\). Both inputs now advance by adjacent entries as \(k\) increases. The transpose costs \(M^2\) reads and writes before the \(M^3\) multiply-accumulate loop. Whether that extra preparation pays off depends on size, reuse and the intended implementation.

W10L5 also shows blocking, which partitions the index ranges into small tiles so data can be reused before eviction. Transposition and blocking are distinct transformations. Either can help some implementations; combining them still requires correct tile-edge handling and accumulation. The bounded example below isolates transposition alone. It uses \(M=96\) and small integers so accumulation is exact and cannot approach the checked machine's integer range: every product has magnitude at most six, and a 96-term sum at most 576.

The uninstrumented check mode computes both formulations and compares every one of the 9216 output entries. The two profiling modes perform only their selected formulation, so the reference calculation does not dominate the simulated profile. Each includes initialization and the final checksum; transposed mode includes its preparation cost. This declared scope prevents silently comparing an entire baseline with only an optimized inner loop. The command retains both cache reports and then collects one Callgrind profile for the transposed mode.

#include <stdio.h>
#include <string.h>
#define M 96
static int A[M][M], B[M][M], BT[M][M], C[M][M], reference[M][M];
void multiply_strided(void) {
    for(int i=0;i<M;i++) for(int j=0;j<M;j++) {
        int sum=0;
        for(int k=0;k<M;k++) sum+=A[i][k]*B[k][j];
        C[i][j]=sum;
    }
}
void transpose_matrix(void) {
    for(int i=0;i<M;i++) for(int j=0;j<M;j++) BT[j][i]=B[i][j];
}
void multiply_transposed(void) {
    for(int i=0;i<M;i++) for(int j=0;j<M;j++) {
        int sum=0;
        for(int k=0;k<M;k++) sum+=A[i][k]*BT[j][k];
        C[i][j]=sum;
    }
}

    if(argc!=2) return 2;

Callgrind counts work; Helgrind diagnoses ordering W10L5 21:45

An instruction reference is an executed machine instruction counted by the tool. It is not a floating-point operation: a single instruction might compute several arithmetic results, move data, compare indices or control a branch. It is also not a processor cycle. Two instructions can have different latencies, overlap in execution, or wait for dependencies. Consequently an instruction fraction cannot be substituted for an elapsed-time fraction in Equation (27.3) without an additional performance model.

The Callgrind manual, §§6.1 and 6.6, describes instruction counts, calling relationships and source annotation, plus optional cache and branch simulation. Its annotation can show self or inclusive costs. The listing requests inclusive annotation explicitly. Read that option together with the event name: inclusive instruction references include descendant work, whereas self instruction references exclude it. Neither setting turns instruction counts into seconds.

The lecture's annotation displays 739,829,324 total instruction references. Compute accounts for 520,070,130, about 70.30 percent; copy accounts for 190,450,270, about 25.74 percent. Those values need not match the earlier gprof timing shares of 56.83 and 43.03 percent. Instruction count and sampled execution time are different observables, and the recordings also change profiling workloads. Even for an identical run, copy's relatively simple operations may spend time moving data rather than executing many arithmetic instructions. Comparing the two reports can suggest this hypothesis, but does not by itself measure bandwidth or stall cycles.

A line annotation localizes counted work to source locations using debug information. A loop header can accumulate many counts for index arithmetic and branching, while the assignment line accumulates data operations. Changing optimization changes that mapping. A source line with zero cost may have been folded into another location rather than avoided logically. Use annotations to investigate the generated computation, not to assign an intrinsic cost to the text of a line.

Thread errors require a separate question: are conflicting accesses ordered by synchronization? A data race involves conflicting accesses by different threads to the same location, at least one a write, without the synchronization required to order them. A mutex is a mutual-exclusion object: successful locking gives one thread access to a protected region until it unlocks. Correctly using the same mutex for every conflicting access establishes the intended exclusion. A shared counter increment is a read-modify-write operation; volatile does not make it atomic or provide that synchronization. C11 defines conflicting actions in different threads, at least one non-atomic and with neither happening before the other, as a data race with undefined behavior (N1570, §5.1.2.4 paragraph 25). Here happens-before is the ordering relation established by the language and synchronization operations, not simply which instruction happened to run first on a clock.

The Helgrind manual, §§7.1–7.4, describes checking of POSIX thread synchronization, lock ordering and races. POSIX is the Portable Operating System Interface; the example uses its pthreads library directly to keep the relevant synchronization visible. A runtime such as OpenMP can implement synchronization through mechanisms a particular checker understands incompletely. A report in a runtime library therefore needs investigation of its stacks and synchronization model, rather than immediate suppression or an assumption that every warning proves an application defect.

This bounded example creates two threads, each performing 1000 increments. Its bad mode deliberately omits the mutex. A successful ordinary execution, or even the expected final counter value, would not repair its data race. The wrapper requires a Helgrind race diagnostic and error status 97. The fixed mode protects every increment, joins both threads before checking the counter and requires exactly 2000. Its clean tool report is evidence about this execution and instrumented threading path.

#include <pthread.h>
#include <string.h>
#include <stdlib.h>
static volatile int counter=0;
static int protected_mode=0;
static pthread_mutex_t lock=PTHREAD_MUTEX_INITIALIZER;
static void *worker(void *unused) {
    (void)unused;
    for(int k=0;k<1000;k++) {
        if(protected_mode && pthread_mutex_lock(&lock)) abort();
        counter++;
        if(protected_mode && pthread_mutex_unlock(&lock)) abort();
    }
    return NULL;
}
int main(int argc,char **argv) {
    if(argc!=2) return 2;
    if(strcmp(argv[1],"fixed")==0) protected_mode=1;
    else if(strcmp(argv[1],"bad")!=0) return 2;
    pthread_t a,b;
    if(pthread_create(&a,NULL,worker,NULL)) return 3;
    if(pthread_create(&b,NULL,worker,NULL)) return 3;
    if(pthread_join(a,NULL) || pthread_join(b,NULL)) return 3;
    if(protected_mode && counter!=2000) return 4;
    return pthread_mutex_destroy(&lock)?5:0;
}

unsynchronized accesses diagnosed; tool exit=97
mutex version counter=2000; zero reported errors

The expected summary concerns diagnosis, not a specific bad counter value. C provides no portable result for the racy mode, so printing a particular observed count as a guaranteed loss would teach the wrong rule. In the fixed mode, a join waits for a worker to finish before the main thread inspects the result. The final read therefore occurs after both workers, and all worker increments use the same mutex. These ordering facts explain the count, rather than merely relying on a quiet report.

Valgrind's core manual, §§2.7.2–2.7.3, documents control options including log files and error-exit behavior. Retaining separate logs matters because a wrapper's final zero exit means its expected checks succeeded; it does not mean every inner executable was error-free. A diagnostic test should preserve both the original tool status and the rule that interprets it. Otherwise a deliberately failed run can be mistaken for a clean test or an accidentally empty log can be mistaken for no errors.

GDB stops at the state that can distinguish two explanations W10L6 1:14

A debugger controls an execution and inspects its current state. The program it controls is called the inferior. Debug information connects machine addresses with source locations, variable names and types. Compiling with -g adds this mapping; it does not itself add a correctness check. Optimization can still reorder, combine or eliminate source operations. The GDB discussion of optimized code, §11, explains why source-level stepping and variable availability can become surprising. The demonstration uses -O0 -g to simplify the relationship.

A breakpoint requests a stop at a location, such as a function entry or source line. A conditional breakpoint adds a predicate, useful when only a particular iteration matters. The breakpoint manual, §5.1.1, gives the location forms. Stopping before an assignment executes is different from stopping after it. At a loop header, the loop variable might not yet have received its new value. Reading a stale or uninitialized local there does not establish that the first executed iteration used that value.

Stopping a greeting program before its print statement permits inspection of the string and its underlying bytes. A typed expression such as print str uses type information. A memory command such as x/5bx str requests five units, with b selecting bytes and x hexadecimal display. The memory-examination manual, §10.6, defines the count, format and unit fields. A valid address still needs a valid interpretation; displaying arbitrary bytes as a string can continue beyond the intended object if no terminator is present.

Breakpoints at compute and copy in the Laplace program isolate the transition between calculating a new grid and making it current. That choice tests the boundary between phases: has the new grid been calculated, and has it become the current grid? For the chapter's boundary condition, the first computed value at interior cell \((1,1)\) must be 0.25. This supplies an oracle, a separately justified expected result. It is stronger than watching a sequence of numbers and deciding that they look plausible.

GDB's next advances to the next source line in the current frame, normally stepping over function calls; step can enter a called function; finish resumes until the current function returns; continue resumes until another stop or termination. These are execution controls, not commands for reversing arbitrary program effects. Their behavior is specified under continuing and stepping, §5.2. Repeatedly stepping every loop iteration is often a poor search strategy. Stop near the first point where a stated invariant can fail.

A watchpoint stops when a watched expression changes. A read watchpoint requests a stop on reading, while an access watchpoint requests a stop on reading or writing. Hardware support and available debug registers constrain what can be watched. The watchpoint manual, §5.1.2, distinguishes watch, rwatch and awatch, and explains hardware versus software implementations. A hardware watchpoint reports a machine-level access; the next displayed source location may follow the instruction that performed the store.

The complete program below deliberately defaults its neighbor-sum coefficient, WEIGHT, to one-half. A second build overrides that coefficient with one-quarter. It stays inside every allocation, so a memory checker need not diagnose it. The correct first sweep on the two-by-two interior has upper interior values 0.25 and lower interior values zero. The erroneous first value is 0.50. This is a logic defect with an exact local oracle; no long convergence experiment is needed.

The GDB command first breaks at jacobi_step, where its argument unew is in scope. It then watches the location unew[5], which is cell \((1,1)\) in the four-wide allocated grid. On the first value change it records a backtrace and prints observed and expected values. It disables the watchpoint before continuing, avoiding unnecessary later stops. The inferior exits with code two because its independent first-sweep check fails. GDB's successful batch-command exit is a different status; the wrapper explicitly checks the inferior-exit text as well as the watchpoint observation.

#include <stdio.h>
#ifndef WEIGHT
#define WEIGHT 0.5
#endif
#define IDX(i,j) ((i)*(N+2)+(j))
double jacobi_step(int N,const double *u,double *unew) {
    double change=0;
    for(int i=1;i<=N;i++) for(int j=1;j<=N;j++) {
        int k=IDX(i,j);
        unew[k]=WEIGHT*(u[k-1]+u[k+1]+u[k-(N+2)]+u[k+(N+2)]); /* Intentional factor bug. */
        double d=unew[k]-u[k];
        if(d<0) d=-d;
        if(d>change) change=d;
    }
    return change;
}
int main(void) {
    int N=2;
    double u[16]={0},unew[16]={0};
    u[IDX(0,1)]=u[IDX(0,2)]=1;
    unew[IDX(0,1)]=unew[IDX(0,2)]=1;
    double change=jacobi_step(N,u,unew);
    if(unew[IDX(1,1)]!=0.25 || change!=0.25) return 2;

The same correct formula also appears in the independently run profiling listing. Its first-sweep and range checks connect the inspected defect to the intended solver behavior.

The batch invocation uses -nx to skip initialization files, disables auto-loading (§22.8) before inferior processing and disables history saving. For larger failures, record the input, executable, compiler options and exact stop condition. A core file can preserve selected process state after a crash, as the lecture notes, but it is a snapshot rather than a complete history and can contain application data. No core file is generated or analyzed here. Likewise, successful launch-and-debug under this environment establishes neither unrestricted attach permissions nor support for every target operating system and debugger feature.

What the combined evidence establishes

The tools answer complementary questions. gprof identifies sampled self-time and counted call relationships for an instrumented execution. Cachegrind and Callgrind measure selected execution events and model-dependent cache behavior. Memcheck diagnoses supported memory defects along exercised paths. Helgrind examines the ordering visible through supported synchronization. GDB supplies state and active call context at chosen stops. None of these observations alone is a proof that a numerical method solves the intended physical problem.

The examples intentionally separate test success from clean application behavior. A bad memory run passes its regression contract only when the requested errors appear. The racy run has no specified numerical result. The debugger example passes only when the wrong value and inferior failure are observed. Their fixed or mathematically correct counterparts have separate checks. Removing a diagnostic message, suppressing a report or forcing an exit status would weaken those contracts rather than repair the underlying program.

The locality experiment compares exact small integer products, and the solver checks an exact first sweep plus finite-value and range invariants. Those are finite checks at specific inputs. They leave discretization accuracy, convergence to a specified tolerance, untested paths, different builds and different machines open. Sampling uncertainty and instrumentation effects also remain. A practical release needs both numerical acceptance criteria and an uninstrumented performance comparison using the intended workload.

Six exercises with reasoned solutions

1. Derive a benefit bound before choosing a target

A serial execution takes ten seconds: six in updating the grid, three in copying and one elsewhere. You can make update four times faster or eliminate copying with a correct pointer exchange. Compute each overall gain and the gain if both changes succeed. State what must stay fixed for this calculation.

Solution

The fourfold update changes six seconds to 1.5, leaving \(1.5+3+1=5.5\) seconds, for gain \(10/5.5=1.818\). Removing copying leaves seven seconds and gain \(10/7=1.429\). Combining them leaves \(1.5+0+1=2.5\) seconds, for gain four. The gains do not add: both changes act on one common baseline denominator. The calculation assumes the same numerical work, unchanged other costs and no new overhead. Pointer exchange also requires equal boundary conditions in both buffers and correct ownership of the final grid. If eliminating the copy changes cache behavior, the arithmetic is a planning estimate and a new measurement must determine the actual gain.

2. Compute the information content of a short profile

A report uses a 0.01-second sampling period. One function receives four samples and another 400. Estimate their self times and relative fluctuation scales under Equation (27.4). How much longer would the first observation need to become to reach approximately ten percent relative uncertainty with the same execution mix?

Solution

The first estimate is \(4(0.01)=0.04\) seconds. Its count fluctuation scale is two, time fluctuation scale 0.02 seconds and relative scale 50 percent. The second estimate is four seconds, with count fluctuation scale twenty, time fluctuation scale 0.2 seconds and relative scale five percent. Ten percent requires roughly \(m=100\) samples because \(1/\sqrt{100}=0.1\). The first function therefore needs about 25 times its current sampled duration, or one sampled second in total. The whole execution must usually grow correspondingly if its mix stays fixed. This is a model calculation, not a guaranteed confidence interval; correlated samples and changing cache regimes can invalidate the assumed scaling.

3. Construct a counterexample to caller-proportional charging

Two callers each invoke worker ten times. Calls from the first always cost one microsecond, calls from the second one millisecond. What total worker time is observed? What does equal call-count charging assign to each caller, and why is the resulting inclusive attribution misleading?

Solution

The cheap caller costs ten microseconds; the expensive caller costs ten milliseconds, or 10,000 microseconds. Total worker time is 10,010 microseconds. Equal counts assign half, 5005 microseconds, to each caller. The cheap caller is overcharged by a factor of 500.5, and the expensive caller receives about half its actual descendant cost. The total and call counts can both be right. The missing fact is the correlation between caller and per-call cost. A context-sensitive measurement or explicit timing of the two input classes supplies information that total time plus counts cannot reconstruct. An averaged per-call figure is therefore insufficient for deciding which caller to redesign.

4. Diagnose two different memory failures

A function allocates five four-byte integers, stores through index five and returns without retaining or freeing the pointer. Ordinary execution exits zero. Explain the two separate defects, the expected tool/target status distinction, and what a clean fixed run would establish.

Solution

The allocated byte range is offsets zero through nineteen. The store starts at offset twenty and writes four bytes outside it; an absence of a hardware fault does not make that store legal. Losing the final pointer leaves the allocation unreleased, separately producing a definite leak in the demonstrated execution. Memcheck can diagnose both. With --error-exitcode=97, the target can return zero while the Valgrind process returns 97 because errors were found. A wrapper should require that status and the expected messages for the bad test, then require a clean status for the repaired one. Replacing index five by a legal initialized element and freeing the block removes these demonstrated defects. A clean finite run establishes no reported supported defect on that path, not a universal memory-safety proof.

5. Judge a proposed cache optimization

A row-major matrix product accesses B[k][j] in its innermost loop. A colleague proposes changing only the subscripts to B[j][k], reports fewer D1 misses and calls the program correct and faster. Identify the missing mathematical and performance evidence. Give a valid transformation.

Solution

The original element is \(\sum_k A_{i,k}B_{k,j}\). The replacement computes \(\sum_k A_{i,k}B_{j,k}\), generally the product with the transpose of B. A smaller miss count cannot establish equality of those expressions. Store \(BT_{j,k}=B_{k,j}\) first, then use \(A_{i,k}BT_{j,k}\), preserving the product while changing locality. Compare every output against a reference on bounded inputs, including non-symmetric matrices so a transposition error cannot hide. Include the transpose cost in the intended measurement scope. D1 misses belong to one simulated cache level; they are neither last-level misses nor elapsed seconds. Time the intended uninstrumented build with the same inputs and correctness tolerance before claiming a speedup.

6. Design the smallest useful debugger experiment

A two-by-two Jacobi interior starts at zero, with top boundary one and all other boundaries zero. A memory checker is quiet, but the first upper interior value is 0.50. Design a stop condition and an independent check that distinguish a wrong averaging factor from a copy-phase defect. Explain how to preserve a bounded diagnostic contract.

Solution

Before any copy, cell \((1,1)\) has neighbors one, zero, zero and zero, so its correct new value is 0.25; both lower interior values stay zero. Break at entry to jacobi_step and watch the storage for unew[5] in the four-wide allocation. When its first store changes the value, inspect the formula and active stack. An immediate value of 0.50 before copying implicates the update computation; a value of 0.25 there followed by a wrong current grid after copying directs attention to the phase transition. Add a program check of the first sweep with a nonzero inferior exit on failure. Run only this tiny case, disable core dumps, skip startup files and history, retain the full local log and verify both observed value and inferior status. After repairing the formula, rerun the same numerical oracle and the intended longer regression. Changing a value manually during debugging tests a hypothesis but does not modify the faulty source.
