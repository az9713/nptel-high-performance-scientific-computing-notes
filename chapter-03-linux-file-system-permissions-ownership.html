The Linux file system: names, inodes, permission bits and ownership

Three people share one results directory. Alice owns it and runs the jobs. Bob is in her group and must read and write her files, and she must read and write his. Carol is on the same cluster, outside the group, and must read nothing. A file has nine permission bits, so there are \(2^{9}=512\) possible modes. Exactly 4 of them give the owner and the group read and write access and give everyone else no access: 660, 670, 760 and 770. The default configuration of the lecture's machine produces mode 664 for a new file and puts the file in the creator's personal group, so a file that Bob creates is read-only for Alice. One more bit, set once on the directory, makes Alice and Bob read and write every new file and keeps Carol out: mode 2770 for the directory with a creation mask of 002 in every member's shell. This chapter defines the file-system objects that these numbers describe, derives the rule that decides each access, and checks the rule against the kernel of the verification machine for 1536 requests on files that the test user owns, for files in all three classes, and for three numeric identities in a scratch directory.

Grounded in two recordings of the NPTEL course High Performance Scientific Computing (Prof. Shivasubramanian Gopalakrishnan, IIT Bombay): W1L3, Mastering Linux Directory and File Management, and W1L4, Understanding File Permissions and Ownership in Linux. The objects of the chapter and the running case

The chapter describes the part of a Linux system that stores named data and decides who may use it. The description has three parts: the objects that are stored, the processes that act on them, and the operations that connect the two.

Stored objects. An inode is a record that describes one file. It holds a type (regular file, directory, symbolic link, device, FIFO, socket), a mode \(m\), an owner user ID \(u_f\), a group ID \(g_f\), a link count \(n\), a size, timestamps, and a reference to the content (inode(7)). The mode is a number from 0 to 4095, so it has 12 bits. The low 9 bits are the permission bits. The 3 high bits are the special bits: set-user-ID (octal 4000), set-group-ID (2000) and sticky (1000). A regular file has as content a sequence of bytes. A directory has as content a table that maps names to inodes; each pair of a name and an inode is a directory entry. A symbolic link has as content a path. A name is not an attribute of an inode: the same inode can have several names, in the same directory or in different ones. Ritchie and Thompson (1974, p. 366) state it as a design rule, "a file does not exist within a particular directory; the directory entry for a file consists merely of its name and a pointer to the information actually describing the file", and POSIX.1-2024 (XBD 4.8) calls the whole structure a directed graph because several entries may refer to one file. A path is a string of names separated by /; resolving a path is following the entries from a starting directory to an inode.

Processes. A process \(q\) carries credentials: an effective user ID \(u_q\), an effective group ID \(g_q\), and a set \(\Sigma_q\) of supplementary group IDs. Write \(G_q=\{g_q\}\cup \Sigma_q\). The kernel compares these numbers, not names, with the numbers in the inode (credentials(7), path_resolution(7)). A process also has a working directory and a creation mask \(\mu\) (the umask), a 9-bit number defined in the section on defaults. A privileged process is one that the system exempts from the permission bits (except that execution needs at least one execute bit; see the section on permissions); on Linux this is a process with the appropriate capability, normally one that runs as user 0 (root). All other processes are unprivileged, and this chapter's rules describe them.

Operations. The operations are the system calls behind the commands of the lectures: mkdir, rmdir, open with creation, link, symlink, unlink, rename, chmod, chown, and path resolution. Each is a function of the inode table, the credentials of the caller and the arguments. The chapter derives, for the operations that the lectures show, the permission that each needs and the change that each makes to the table.

Notation. The three classes of the lecture are the owner (u), the group (g) and the other class (o; the lecture's "others"). The octal digit of class \(c\) in a mode is \(m_c=\lfloor m/8^{e_c}\rfloor \bmod 8\) with \(e_{\mathrm u}=2\), \(e_{\mathrm g}=1\), \(e_{\mathrm o}=0\); the three digits are the three groups of three permission bits. The weights of the access rights are read \(=4\), write \(=2\), execute \(=1\). The symbols \(\wedge\), \(\vee\) and \(\lnot\) denote bitwise AND, OR and complement on 9-bit numbers, so \(\lnot\mu=511-\mu\). Modes are written in octal, with or without a leading zero (0644 and 644 are the same mode); a single octal digit is the digit of one class.

The directory tree, paths and the working directory W1L3 10:53

The lecture defines a file as a collection of data stored on a disk or in memory and a directory as a special file that contains references to other files and directories; the slide adds "It's like a folder that organizes files into a hierarchy" (W1L3 11:15). The model of this chapter makes the second definition exact: a directory is an inode whose content is a table of names. The next section develops it. This section treats the tree that the tables form and the commands that move through it: pwd, ls, cd.

Where things are. The Filesystem Hierarchy Standard (FHS 3.0, 19 March 2015) fixes the top of the tree by two distinctions. A file is shareable if one host can store it and others can use it, and static if it changes only by administrator action (FHS §2). Files that differ in either respect belong in different directories, so that they can sit on different file systems. This yields /usr for static shareable programs, /etc for static host-specific configuration, and /var for variable data (FHS §2 and §3). User files live under /home, which the standard calls "clearly a site-specific filesystem": "no program should assume any specific location for a home directory, rather it should query for it" (FHS §3.8.1). The lecture's home directory is /home/master. Temporary files go to /tmp, whose contents a program "must not assume" survive between runs (FHS §3.18.1), or to /var/tmp, whose contents "must not be deleted when the system is booted" (FHS §5.15.1). This chapter's listings use /tmp for that reason.

Resolution. A path that begins with / is absolute and starts at the root directory. Any other path is relative and starts at the working directory of the process (path_resolution(7)). The kernel takes the path one name at a time. For each name it needs search permission on the current directory, otherwise it fails with EACCES ("Permission denied"); the name must exist, otherwise ENOENT; and every name except the last must be a directory, otherwise ENOTDIR. Two names are special: . is the current directory and .. its parent. At the root, .. is the root itself; the listing below confirms it. The working directory belongs to the process and is looked up at each resolution. It follows that a separate program cannot change the working directory of the shell that started it, which is why cd is built into the shell.

The lecture shows four uses of cd: with a name, with no argument (the user goes to the home directory), with - (to the previous directory) and with .. (to the parent). A directory is a table of names: link counts, hard links and symbolic links W1L3 15:53

The lecture reads the second column of ls -l as the number of links associated with the file or directory and does not develop it. The column is the link count \(n\) of the model, and it answers a question that the lecture's commands raise: what exactly does rm remove, and what does mv change? Ritchie and Thompson describe the original structure (1974, pp. 366 to 369). A directory entry holds a name and an i-number, an index into a table of i-nodes. The i-node holds the owner, the protection bits, the addresses of the contents, the size, the time of last modification, the number of links ("the number of times it appears in a directory") and the type. Making a link "involves creating a directory entry with the new name, copying the i-number from the original file entry, and incrementing the link-count field of the i-node". Deleting a file "is done by decrementing the link-count of the i-node specified by its directory entry and erasing the directory entry. If the link-count drops to 0, any disk blocks in the file are freed and the i-node is deallocated". The Linux system calls keep this design: link(2) creates a new name for an existing file, and the two names have "the same permissions and ownership" and are indistinguishable ("it is impossible to tell which name was the original"); unlink(2) deletes one name, and the file itself is deleted only when that name was the last link and "no processes have the file open" (the file then remains until the last descriptor is closed).

The link count of a directory. Which names refer to a directory \(\delta\) that has \(s(\delta)\) subdirectories? The entry for \(\delta\) in its parent; the entry . inside \(\delta\); and the entry .. inside each of the \(s(\delta)\) subdirectories. Each such name adds one to the link count, so on a file system that follows the original convention \[ n(\delta) = 2 + s(\delta). \tag{3.1} \] The 1974 paper states the first part (p. 366): "each directory always has at least two entries". The lecture's screen gives three checks. The home directory (. in the first line of the ls -la screen) has link count 22, so it has 20 subdirectories, hidden ones included; the parent /home has count 4, so 2 subdirectories; and anaconda3 has count 28, so 26 subdirectories. The ls -la screen at W1L4 4:45 adds a fourth: the entry . there is Desktop, with link count 4 and exactly two subdirectories, simpleproject and TestDir2. The first four lines confirm (3.1): proj has three subdirectories and link count 5, proj/data one subdirectory and count 3, and the two empty directories count 2. The hard link b.txt and the original a.txt have the same inode, and the count is 2. After unlink of a.txt the file is still readable through b.txt and the count is 1: only a name was removed. The symbolic link is its own file. Its mode is 0777, which symlink(7) states is always so on Linux because the permissions of a symbolic link "are not used in any operations"; its content is the text b.txt; and when the target name is unlinked the link stays and fails to resolve, so opening it returns ENOENT. The next five lines show the three limits of links. A hard link to a directory fails with EPERM (link(2)); the 1974 paper gives the reason, that with arbitrary links to directories "it would be quite difficult to detect when the last connection from the root to a directory was severed". rmdir of a non-empty directory fails with ENOTEMPTY (rmdir(2)), and Linux reports unlink of a directory as EISDIR (unlink(2), which notes that POSIX prescribes EPERM). The program found /tmp and /dev/shm on different file systems, and both rename and link across them fail with EXDEV, "not on the same mounted filesystem" (rename(2), link(2)). Ritchie and Thompson (p. 367) give the same rule for the first UNIX file system: "no link may exist between one file system hierarchy and another". Inside one file system, rename keeps the inode, so the last line prints True.

These results give the exact meaning of two commands of the lecture. mv inside one file system changes directory entries and no data. When the destination is on another file system, rename cannot work, and GNU mv "falls back on copying as if by cp -a, then (assuming the copy succeeded) it removes the original" (Coreutils manual, §11.4); the cost then grows with the size of the data. A script that moves a result file from a fast scratch file system to a home file system therefore moves bytes, and its time grows with the size of the file. If the copy fails, mv removes the partial copy in the destination. If several directories are moved and the copy of a later one fails, the ones already copied stay at the destination and the rest stay at the source (Coreutils manual, §11.4), so one command can leave the data split across two file systems. And rm does not erase a file. It removes a name, and the file disappears when the last name and the last open descriptor are gone.

Owner, group and other: the access rule and the ten characters W1L4 25:50

The lecture states that Linux is a multi-user system, so a file needs an owner and rules for others, and divides users into three categories: the owner (slide: "The person who owns the file"), the group ("A group of users who share access to the file") and others ("Everyone else"). It divides the access into read, write and execute, and says that for a directory, execute permission lets a user navigate or traverse it (slide: "traverse a directory"). These statements are correct. They leave one question open: when a user fits more than one category, which rights apply?

The access rule. The question for a process \(q\) and a file \(f\) is whether the kernel grants the access \(a\), where \(a\) is 4 for read, 2 for write or 1 for execute (search, for a directory). Linux selects one class and looks at that class only (path_resolution(7), section "Permissions"): the owner class when the effective user ID of \(q\) equals the owner of \(f\); otherwise the group class when the group of \(f\) is the effective group or one of the supplementary groups of \(q\); otherwise the other class. In symbols, with \(u_q\) and \(G_q\) from the model, \[ c(q,f)=\begin{cases}\mathrm{u} & u_q=u_f,\\ \mathrm{g} & u_q\ne u_f \text{ and } g_f\in G_q,\\ \mathrm{o} & \text{otherwise,}\end{cases}\tag{3.2} \] and an unprivileged process is granted the access \(a\) exactly when \[ m_{c(q,f)}\wedge a\neq 0 .\tag{3.3} \] Linux compares the file-system user ID, which equals the effective user ID unless a program changes it with setfsuid (path_resolution(7)). POSIX.1-2024 (XBD 4.7) states the same: access is granted "if the requested access permission bit is set for the class (file owner class, file group class, or file other class) to which the process belongs"; a privileged process is granted read, write and search always, and execute if at least one execute bit is set. The same section lets an implementation add mechanisms: an additional mechanism "shall only further restrict" access, and an alternate mechanism must be "enabled only by explicit user action, on a per-file basis". For a file reached by a path, the kernel applies (3.3) to the file and also requires search permission, (3.3) with \(a=1\), on every directory of the path before the last name.

The consequence of the word "otherwise" in (3.2) is that the classes are not cumulative. A user who owns a file is judged by the owner digit alone, even if the group digit is larger. Table 3.2 gives the meaning of the three rights. In the directory column, read and execute are independent rights, and creation and removal need write and execute together.

def mode_string(mode):
    """The ten characters of ls -l for st_mode, from the bit layout of stat(2)."""
    kind = {0o140000: 's', 0o120000: 'l', 0o100000: '-', 0o060000: 'b',
            0o040000: 'd', 0o020000: 'c', 0o010000: 'p'}[mode & 0o170000]
    out = [kind]
    for shift, special, low, high in ((6, 0o4000, 's', 'S'), (3, 0o2000, 's', 'S'), (0, 0o1000, 't', 'T')):
        bits = (mode >> shift) & 7
        out.append('r' if bits & 4 else '-')
        out.append('w' if bits & 2 else '-')
        if mode & special:
            out.append(low if bits & 1 else high)
        else:
            out.append('x' if bits & 1 else '-')
    return ''.join(out)

Changing the mode: symbolic and octal notation W1L4 33:07

Only the owner of a file, or a privileged process, may change its mode (POSIX chmod, DESCRIPTION; chmod(2)). The lecture presents the two notations of chmod. This section gives each a precise meaning and tests the symbolic one against the program on the machine.

Octal notation. The lecture assigns the weights 4, 2 and 1 to read, write and execute and adds the weights of the rights to be granted: 7 is 4+2+1, 5 is 4+1, 6 is 4+2. The assignment is a bijection between the eight subsets of \(\{r,w,x\}\) and the numbers 0 to 7: \[ d = 4\,[r] + 2\,[w] + 1\,[x] , \tag{3.4} \] where \([r]\) is 1 if read is granted and 0 otherwise, and likewise for \([w]\) and \([x]\). Equation (3.4) is a binary numeral whose leading bit is \([r]\). Every integer from 0 to 7 has exactly one such numeral, so each digit names exactly one subset. Three classes give \(8^3=512=2^9\) permission modes, and a fourth digit for the special bits gives the 4096 values of the decoder. The lecture's examples follow: 755 is owner 7 (rwx), group 5 (r-x), other 5 (r-x); 644 is rw-, r--, r--; 777 is rwx for everyone.

Symbolic notation. A symbolic mode is a list of clauses separated by commas. Each clause is a who (any of u, g, o, or a for all three, or nothing), an operator (+, - or =), and a permission (any of r, w, x, or one of u, g, o to copy the current rights of that class); a clause may repeat the operator and permission part (POSIX chmod, EXTENDED DESCRIPTION; the letters X, s and t are left out of this chapter's model). Let \(K\) be the set of classes of the who, with all three when the who is a or empty, and let \(b\) be the 3-bit value of the permission. Let \(\sigma_K(b)\) be \(b\) placed in each class of \(K\): \(\sigma_K(b)=\sum_{c\in K}b\cdot 8^{e_c}\). Let \(A\) be the mask of bits that the clause may change: \(A=\lnot\mu\) when the who is empty and \(A=511\) otherwise, where \(\mu\) is the creation mask of the process that runs chmod. Then the clause changes the current mode \(m\) as \[ m'=\begin{cases} m\vee(\sigma_K(b)\wedge A) & \text{for } +,\\ m\wedge\lnot(\sigma_K(b)\wedge A) & \text{for } -,\\ \bigl(m\wedge\lnot\sigma_K(7)\bigr)\vee(\sigma_K(b)\wedge A) & \text{for } =. \end{cases}\tag{3.5} \] For the permission copied from a class, \(b\) is the digit of that class in \(m\) before the operation. The mask \(A\) is the point that the lecture does not make. POSIX.1-2024 states: when the who is not specified, the bits are set or cleared "except for those with corresponding bits in the file mode creation mask of the invoking process". The Coreutils manual (§27.2.6) gives the example that with a mask of 2 the mode +w gives write permission to the owner and the group "but not to other users", while a+w "ignores umask".

import os, re, subprocess, tempfile

R, W, X = 4, 2, 1
SHIFT = {'u': 6, 'g': 3, 'o': 0}

def apply_symbolic(mode, spec, umask):
    """POSIX symbolic mode on the nine permission bits (no s, t, X)."""
    for clause in spec.split(','):
        who = re.match(r'[ugoa]*', clause).group()
        classes = 'ugo' if who in ('', 'a') or 'a' in who else who
        masked = who == ''
        for op, perm in re.findall(r'([-+=])([ugo]|[rwx]*)', clause[len(who):]):
            if perm in ('u', 'g', 'o'):
                bits = (mode >> SHIFT[perm]) & 7
            else:
                bits = sum({'r': R, 'w': W, 'x': X}[c] for c in perm)
            field = 0
            for c in classes:
                field |= bits << SHIFT[c]
            allowed = 0o777 & ~umask if masked else 0o777
            span = sum(7 << SHIFT[c] for c in classes)
            if op == '+':
                mode |= field & allowed
            elif op == '-':
                mode &= ~(field & allowed)
            else:
                mode = (mode & ~span) | (field & allowed)
    return mode

The creation mask. A program that creates a file passes the mode that it requests to the system call, and the kernel removes the bits that the process's creation mask \(\mu\) names. For open with O_CREAT, "in the absence of a default ACL, the mode of the created file is (mode & ~umask)" (open(2)); for mkdir it is "(mode & ~umask & 0777)" (mkdir(2)). In the notation of the model, \[ m_{\text{new}} = m_{\text{req}}\wedge\lnot\mu . \tag{3.6} \] The mask belongs to the process and is set by the shell command umask (POSIX umask), so the same command can create files with different modes in two sessions. The tools of the lectures behave as if they request 0666 for a file (touch, the editors, redirection) and 0777 for a directory (mkdir): no execute bit is requested for a file, and a directory needs the execute bit to be usable. (The requests of the lecture's tools were not observed; the statement is the assumption that the next program makes.) The lecture's machine produced 664 and 775. The set-user-ID bit. The first UNIX file system had seven protection bits: six gave read, write and execute permission independently to the owner and to all other users, and the seventh worked as follows; "if the seventh bit is on, the system will temporarily change the user identification of the current user to that of the creator of the file whenever the file is executed as a program" (Ritchie and Thompson 1974, p. 367). That bit is set-user-ID (octal 4000, S_ISUID; inode(7)). A process started from such a file has the file's owner as effective user, and (3.2) then judges it as that user. The decoder's example, /usr/bin/passwd with mode -rwsr-xr-x and owner root on this machine, is an instance: a user who runs it gets a process whose effective user is root, the owner of the file. The first system had no group class at all, and the nine-bit mode with a group digit of this chapter is a later extension; the 1974 paper does not describe it. This chapter does not run a set-user-ID program, so it does not test the effect, and the description above rests on the paper and on inode(7).

The set-group-ID bit on a directory. On a regular file, set-group-ID (2000) is the group counterpart of the bit above. On a directory it has a different, documented meaning: "newly created subfiles inherit the same group as the directory, and newly created subdirectories inherit the set-group-ID bit of the parent directory" (Coreutils §27.5; open(2) and mkdir(2) say the same). Without the bit, a new file takes the creator's effective group, as the section on ownership showed. The bit solves the problem of the running case, because it makes the group of every new file the group of the project directory with no action by the creator. BIT = {'r': 4, 'w': 2, 'x': 1}

def may(mode, owner, group, user, want):
    """Access predicate for an unprivileged process. user = (uid, set of group ids)."""
    uid, gids = user
    shift = 6 if uid == owner else 3 if group in gids else 0   # first matching class only
    return bool((mode >> shift) & BIT[want])

# Numeric identities of the running case; group 2100 is hpsc.
USERS = {'alice': (2001, {2001, 2100}), 'bob': (2002, {2002, 2100}), 'carol': (2003, {2003})}
EGID = {'alice': 2001, 'bob': 2002, 'carol': 2003}
HPSC = 2100

def create(directory, who, umask):
    """New file: owner = creator, mode = 0666 & ~umask, group = directory's if setgid else creator's."""
    dmode, dgroup = directory
    group = dgroup if dmode & 0o2000 else EGID[who]
    return (0o666 & ~umask, USERS[who][0], group)

def rights(directory, fileinfo, who):

    return ''.join(c if reach and may(fmode, fowner, fgroup, USERS[who], c) else '-' for c in 'rw')

The three result lines of the kernel, alice r- bob rw carol --, alice r- bob rw carol -- and alice rw bob rw carol --, are the three lines of the model, so all 18 yes-or-no answers (three configurations, three users, two rights) agree, and the modes and groups of the files agree with the model's (-rw-r--r-- with group 2002, -rw-rw-r-- with group 2002, -rw-rw-r-- with group 2100). Carol's attempt to list the directory ends with Permission denied, and the test of search permission exits with status 1. The line alice rm exit status 0 shows a consequence that the requirement did not exclude. Alice removed Bob's file, although its mode was 000 and she was not its owner, because removal needs write and search permission on proj, which her group digit gives her. Every member can therefore remove any other member's files. The sticky bit (mode 3770 for the directory) would allow only the owner of a file and Alice, as owner of the directory, to remove it. The exercises return to this choice.

The result is established for the model of nine permission bits, three classes selected first-match, and the setgid and mask rules, on one local file system, for three numeric identities. It is not established for a cluster. On a cluster the account and group tables come from a directory service, the home and project directories may sit on a network or parallel file system whose server also checks identities, and an ACL or a security label may allow or deny access beyond the mode bits. The chapter did not test any of these.

The model establishes six things. The files of a system are inodes, and a directory is a table of names, so removal, renaming and linking are edits of tables, and the link count of a directory is two plus its subdirectories (3.1). Access is decided by one class, selected first-match, and not by the union of the classes (3.2, 3.3); the kernel agreed on every request tested: exhaustively for the owner class, and on a sample of system files without an ACL. The order between the group class and the other class (for example, a group member refused under mode 0604) was not tested against the kernel. The mode string and the octal digits are two codings of the same 12 bits (3.4). The symbolic chmod is a set of bit operations whose mask depends on the creation mask (3.5). The creation law (3.6) explains the default modes of new files, and, under the conditions stated in the section on defaults, the lecture's shell used the mask 002. The running case needs a directory of mode 2770 and the mask 002.

The model leaves out most of what a production system adds. It has no access control lists, and the journal files of this machine show that the nine bits are not the whole rule there. It has no security labels (the dot after the mode string), no file attributes such as the immutable flag (named in unlink(2)), and no capabilities beyond the single notion of a privileged process. It has no network or parallel file system, where a server decides and identities must agree between machines. It has no time dimension: a program that tests test -w file and then writes can find the answer changed between the two steps. It gives no performance information, although the cost of mv across file systems, which scales with the data, matters for large results. Three limits of the evidence are listed again for the reader who wants to repeat the chapter. The transcripts with three numeric identities need root. The checks against the system files depend on the files of the machine that ran them. The lecture's screens come from a virtual machine that is not available, so statements about its umask, its security module and its free are inferences from the screens.

Exercises

Exercise 1 (derive). (a) Prove that (3.4) maps the 8 subsets of \(\{r,w,x\}\) one-to-one onto \(\{0,\dots,7\}\). (b) Count the nine-bit modes in which the owner class and the group class both hold read and write and the other class holds nothing, and write them in octal. (c) Count the nine-bit modes in which at least one class holds write permission without read permission.

Solution

(a) Suppose two different subsets have the same sum. Remove the elements they share. The remaining sets are disjoint and not both empty, with the same sum. Let \(w_{\max}\) be the largest of all the remaining weights; it lies in one of the sets. The other set holds only weights smaller than \(w_{\max}\), and the sum of all weights smaller than \(w_{\max}\) is less than \(w_{\max}\) (4 is greater than 2+1, and 2 is greater than 1). The sums differ, which contradicts the assumption, so the map is injective. It maps 8 subsets into the 8 values 0 to 7, so it is also onto. (b) The owner digit must be 6 or 7 (read and write granted, execute free), the group digit likewise, and the other digit must be 0, so there are \(2\times2\times1=4\) modes: 0660, 0670, 0760 and 0770. (c) A class has write without read when its digit is 2 or 3, which is 2 of the 8 digits. Each class has 6 digits that are not of that kind, so \(6^3=216\) modes have no such class, and \(512-216=296\) have at least one.

Exercise 2 (compute). (a) Write the four-digit octal mode of each string: -rwsr-xr-x, drwxrws---, -rw-r-Sr--, drwxrwxrwt. (b) A user has the mask 037. Compute the mode of a new file that a tool creates with the request 0666 and of a new directory created with the request 0777. (c) On the lecture's ls -la screen, the entry . has link count 22, the entry .. (the directory /home) has 4, and anaconda3 has 28. How many subdirectories does each of these directories have?

Solution

(a) -rwsr-xr-x: the set-user-ID bit is set and the owner execute bit is set (lowercase s), so the special digit is 4; the digits are 7 (rwx), 5 (r-x), 5 (r-x): 4755. drwxrws---: set-group-ID with group execute, special digit 2; owner 7, group 7, other 0: 2770. -rw-r-Sr--: the capital S in the group position means set-group-ID without group execute; special digit 2; owner rw- is 6, group r-S is 4 (read only), other r-- is 4: 2644. drwxrwxrwt: sticky with other execute, special digit 1; 777: 1777. (b) \(\lnot037=511-31=480=0740\) in octal. The file: \(0666\wedge0740=0640\). The directory: \(0777\wedge0740=0740\). (c) By (3.1), \(s=n-2\): the home directory has 20 subdirectories, /home has 2, and anaconda3 has 26. The first count includes hidden directories such as .cache and .config, which the screen shows.

Exercise 3 (counterexample). A student claims: "(i) A user who is a member of a file's group can always use the group's rights on it. (ii) To remove a file, a user needs write permission on the file." Give one counterexample to each claim, using the results of this chapter.

Solution

(i) Let the user own a file of mode 070, and let the file's group be the user's primary group. The user is a member of the group, and the group digit is 7. By (3.2), the owner class is selected first, because \(u_q=u_f\); the owner digit is 0, so (3.3) refuses every access. The listing owner_class.sh shows cat failing with Permission denied for the modes 070 and 007. The claim holds only for a user who is not the owner. (ii) Removal changes the directory's table, not the file. The listing files_session.sh removed a file of mode 000 with rm and refused to remove a file of mode 666 in a directory without write permission. With the sticky bit on the directory, even write permission on the directory is not enough: the transcript shows Operation not permitted for Bob in a 1777 directory.

Exercise 4 (diagnose an assumption). A student wants the members of her group to edit the result files in a directory. The files have mode 444. Her shell has the mask 022. She runs chmod +w *.dat, and the group still cannot write. (a) Predict the mode of the files after the command. (b) State the assumption that fails. (c) Give a command that gives write permission to the group and to nobody else, and compute the mode it produces; then say why chmod a+w is a wrong repair.

Solution

(a) The clause +w has no who, so \(A=\lnot022=0755\) and \(\sigma_{\{u,g,o\}}(2)=0222\). The bits that change are \(0222\wedge0755=0200\), the owner's write bit only. The mode is \(0444\vee0200=0644\); the model listing prints this case: 444 +w umask 022 -> 644. (b) The assumption that fails is that a clause without who acts on all classes. By the POSIX rule, bits of the creation mask are excluded, and the mask 022 contains the write bits of the group and the other class. (c) chmod g+w *.dat has a who, so \(A=511\) and the change is \(0020\): \(0444\vee0020=0464\). The command chmod ug+w would also let the owner write and give 0664. The repair chmod a+w gives \(0444\vee0222=0666\) (the model listing prints 444 a+w umask 022 -> 666): the other class also gets write permission, so every user who can search the directory can change the results; this is more than the requirement asks.

Exercise 5 (design judgment). A principal investigator (PI) owns a directory for the results of a project. The students of the project, in the group lab, must create and edit files. External collaborators, in a group ext, must read the files and must not change them. Nobody else may read them. (a) Show that no assignment of owner, group and nine mode bits to one file meets all four requirements. (b) Propose a design that meets them for the students and the PI with mode bits only, and say what is given up. (c) Say what the sticky bit would add to the design and what it would cost.

Solution

(a) The rights over one file are given by three digits that apply to three sets of users: the owner, the members of one group (the file's group), and everybody else. The requirement gives three different rights to three sets that each contain users other than the owner: the students (read and write), the collaborators (read only) and the rest (none). Apart from the single owner, a file distinguishes only two sets: the members of its one group, and everyone else. So at most two of these three sets can receive different rights. If the file's group is lab, the collaborators fall into the other class, which must then be 0 to keep out the rest, so they get nothing. If the file's group is ext, the students fall into the other class. The owner class can hold the PI only, because it applies to one user ID. Hence the four requirements cannot all hold with mode bits alone. (b) Make the PI the owner of the directory, the group lab, mode 2770 (or 3770), make the PI a member of lab (otherwise the PI falls into the other class for files that students create, and the other digit is 0), and have every member work with the mask 002; then the PI and the students meet R1 to R3 of the running case, as the case section showed, and the collaborators have no access. What is given up is the collaborators' read access. Two ways to restore it lie outside the model of this chapter and were not tested here: an access control list entry for the group ext, which POSIX XBD 4.7 allows as an alternate mechanism and which the journal files of this machine suggest the kernel honours (the listing did not decode the ACL), or a second directory, owned by the PI, with the group ext and mode 2750, filled with copies that the PI makes. The copies are new inodes (the listing files_session.sh), so they fall out of date, and the ACL is not visible in the mode string except as a +. (c) With the bit (mode 3770), only the owner of a file, the PI (as owner of the directory) and a privileged process can remove or rename a file, so one student cannot remove another's files; the case-section transcript showed the opposite without the bit. The cost is that a student cannot remove or replace a file that a colleague created, even one that the student needs to rebuild, and the PI becomes the only unprivileged user who can remove files that other people created.

Exercise 6 (implementation and measurement). Write a C function mode_string(mode_t m, char out[11]) that returns the ten characters of ls -l for a st_mode value, including the special bits. Write a test that creates seven files, sets the modes 0644, 0755, 04755, 02770, 01777, 03000 and 0070 with chmod, and compares the function's result with stat -c %A. Run it. Explain the output for 03000.

Solution

The function reads the three class digits with a shift and replaces the execute character by s, S, t or T when the matching special bit is set, as the Coreutils manual specifies. The program calls stat -c %A on each file through popen and compares the two strings.

#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/stat.h>
#include <unistd.h>

/* The ten characters of ls -l for a st_mode value. */
static void mode_string(mode_t m, char out[11])
{
    const char *kind = "?";
    switch (m & S_IFMT) {
    case S_IFREG: kind = "-"; break;
    case S_IFDIR: kind = "d"; break;
    case S_IFLNK: kind = "l"; break;
    case S_IFIFO: kind = "p"; break;
    case S_IFCHR: kind = "c"; break;
    case S_IFBLK: kind = "b"; break;
    case S_IFSOCK: kind = "s"; break;
    }
    out[0] = kind[0];
    static const mode_t special[3] = { S_ISUID, S_ISGID, S_ISVTX };
    static const char on[3] = { 's', 's', 't' }, off[3] = { 'S', 'S', 'T' };
    for (int c = 0; c < 3; c++) {
        int bits = (m >> (6 - 3 * c)) & 7;
        out[1 + 3 * c] = bits & 4 ? 'r' : '-';
        out[2 + 3 * c] = bits & 2 ? 'w' : '-';
        out[3 + 3 * c] = (m & special[c]) ? (bits & 1 ? on[c] : off[c]) : (bits & 1 ? 'x' : '-');
    }
    out[10] = '\0';
}

int main(void)
{
    char dir[] = "/tmp/hpsc-modestr-XXXXXX";
    if (!mkdtemp(dir)) return 1;
    if (chdir(dir)) return 1;
    const mode_t modes[] = { 0644, 0755, 04755, 02770, 01777, 03000, 0070 };
    int bad = 0;
    for (size_t i = 0; i < sizeof modes / sizeof modes[0]; i++) {
        char name[16], text[11], cmd[64], line[64];
        snprintf(name, sizeof name, "f%04o", (unsigned)modes[i]);
        close(creat(name, 0600));
        chmod(name, modes[i]);
        struct stat st;
        stat(name, &st);
        mode_string(st.st_mode, text);
        snprintf(cmd, sizeof cmd, "stat -c %%A %s", name);
        FILE *p = popen(cmd, "r");
        if (!p || !fgets(line, sizeof line, p)) return 1;
        pclose(p);
        line[strcspn(line, "\n")] = '\0';
        bad += strcmp(text, line) != 0;
        printf("%04o %s %s\n", (unsigned)(st.st_mode & 07777), text, strcmp(text, line) ? "DIFFERS" : "same as stat -c %A");
    }
    printf("disagreements: %d\n", bad);
    char cmd[64];
    snprintf(cmd, sizeof cmd, "rm -rf %s", dir);
    return system(cmd) != 0 || bad;
}
